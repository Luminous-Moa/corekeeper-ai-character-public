# 대상·행위·조건·결과 그래프 반영 사전 조사

## 결론

사용자가 지정한 대상은 여태 수집한 게임 자체의 대상·행위·조건·결과 그래프다. 조사한 현행 진입점에는 이 연구 그래프의 생성기나 정본이 아직 없다. 검수된 추출 정본들을 입력으로 읽는 파생 그래프를 만들고, 기존 개발 지식그래프의 안내에서 찾아갈 수 있게 연결하는 것이 의미와 범위를 보존하는 최소 변경이다. 이는 게임 지식의 경쟁 정본을 하나 더 만드는 것이 아니라 같은 게임 원본을 source·조건·소비 단계까지 자세히 조회하는 파생 관점이다. 현재 AI 조회 경로에 이 지식을 제공하는 어댑터와 공개 규칙 적용은 이번 연구 반영 뒤 별도로 이어질 소비 연결 작업이다.

## 권장 파생 구조와 주 조회 흐름

정본 후보는 세션 `work/게임행동-그래프/`다. 현재 작업 브랜치명 `게임-상호작용-수집`과 겹치지 않는다. 그 아래 생성기·조회기·설명과 생성 graph/coverage/manifest를 둔다. 작업 검수·실행근거는 이번 날짜 폴더에 둔다. 최종 경로와 스키마는 HEAD 판단 대상이다.

- source 노드는 전체 sourceKey를 신원으로 두고 ObjectID·variation은 탐색 속성으로 둔다. 이름/ID만으로 여러 prefab을 합치지 않는다.
- 행위 이름과 source별 주장/시도 노드를 분리한다. 자동 전파·선행 충전·소비 단계·UI 입구·비적용 판정을 전부 사용자의 의도적 행동으로 세지 않는다.
- 조건·결과·실패·근거 수준·원문 pointer/hash는 누락 없이 따라갈 수 있어야 한다. 주장의 원문 payload는 보존하고 그래프는 탐색 관계를 추가한다.
- 기존1432행과 보강949행의 보강/선행/소비 연결을 사용한다. 문자열이 같은 경우에도 무조건 병합하지 않는다. 신규행 수나 graph node 수를 고유 게임 행동 수로 부르지 않는다.
- 원본 미결과 후속 판정을 관계로 연결한다. 알려진 미결·현재 판정·runtime 미관측·모집단 밖을 별개로 표시한다.

대표 실제 소비 흐름은 다음이면 충분하다: `대상 검색 → 정확한 source/variation 선택 → 행위·조건·결과/실패 → 보강 단계 → 원본/코드 근거`. 예시로 상자 사용(기존 추출 보존), 수리(기존→B 선택 보강), 압력판(기존→C 필터→A 전력), 요리 순서쌍,6506/4600 미결을 조회한다. 생성→조회→근거 열람까지 대표 흐름을 실행하고 독립 검수한다. 게임 실행은 필요하지 않다.

## 구현 명세: 입력 해석과 변경 책임

HEAD가 승인한 정본 위치는 `work/게임행동-그래프/`다. 다음은 생산 코드가 아니라 책임 명세다.

### 입력 어댑터

- 원래 final의 `records[]`는 sourceKey/objectId/variation/names와 `interactions[]`, `unresolved[]`, `otherEvents`, `authoring`을 갖는다. interactions의 verb/label/conditions/result/assetEvidence/codeEvidence/evidenceLevel을 그래프 주장으로 투영한다. 상호작용 없는592 source도 대상 노드를 만들고 `미발견/미추출`로 표시하며 불가능으로 바꾸지 않는다.
- 후속 패키지의 실제 구조는 `groups[].payload["extraction.json"]`이고 coverage/verification도 파일명 키다. 그룹의 basePath와 referenceContext를 근거 경로 해석에 사용한다. `recordIndex`·baselineRecordIndex를 입력 pointer 연결의 출발점으로 재사용한다.
- `rule` 또는 `ruleRef`를 같은 그룹 rules에 연결한다. baseline A/D에는 extraction rules가 없으므로 그룹의 근거 파일/원문에 있는 명시된 참조를 보존한다. 보강 B의 rules는 payload에 없고 기본 B와 relationToPrior를 통해 연결된다. rule 이름만 남기고 조건·결과가 빈 것으로 내보내면 안 된다.
- 특히 보강 D의172 records는 대부분 source/행위/assetEvidence/rule만 있고, 실제 conditions/result/failureBranches/inputProcessingConsumer/unknown은 `rules`19개에 있다. 따라서 query는 행과 rule을 함께 해석해야 한다. 보강 A의26 rules도 조건·결과·실패·flow를 가진다.
- 공통 필드 대응은 conditions/condition, result/results, failure/failureBranches/failurePaths, unresolved/unknown이다. 단순 문자열 치환이나 병합 대신 필드별 원문 pointer와 적용 주체(행 자체/공통 규칙/이전 보강)를 유지한다. 둘 다 존재하면 둘 다 표시하고 한쪽을 덮지 않는다.
- 보강 관계는 priorRelations/relationToPrior/relationToPrevious/supplementsRecordId/previousRelation, 선행은 prerequisiteForRecordId 및 package.stageLinks, 소비 연결은 crossGroupRelations/localConsumerRecords/relatedDRecords의 실제 참조를 사용한다. 근거 없이 같은 action 문자열만으로 동일 행동·완결 흐름을 추론하지 않는다.
- cooking-pairs의 pairs6561개는 inputObjectIds/inputSourceKeys/condition/outputObjectId/outputVariation/primaryObjectId/secondaryObjectId를 가진다. 두 재료 순서를 보존한 결과 관계로 읽고, 확률·특수 결과 조건을 성공 확정으로 바꾸지 않는다.
- gap-index.originalGapStatus16개와 previousUnknownLedger1671개를 원문 pointer와 함께 관계화한다. 초기 미결5090문구는 별도 역사적 주장이다. 같은 source에 보강행이 생겼다는 이유만으로 공통 Baker 미결 전체를 닫지 않는다. 특정 해소 근거와 연결되는 것만 현재판정으로 표시한다.

### 파생 그래프·조회 책임

생성기는 읽기 전용 입력→source·행위/단계 주장·규칙·조건·결과·실패·미결·근거의 관계를 결정적으로 만든다. 원문 payload 보존만으로 끝내지 않고, query가 연결을 따라 **적용 조건과 결과를 내용으로 반환**해야 한다. 조건/결과를 다시 해석해 새로운 게임 규칙을 만드는 것은 범위 밖이다.

권장 사용 표면은 대상 이름/ID/source 검색, source별 행동 목록, 주장 상세, 조건/결과/실패 조회, 근거 조회, 미결·범위 조회다. ID만 같고 variation/source가 여럿이면 후보를 보여 주고 명시 source로 좁힐 수 있게 한다. 행위/선행 단계/자동 소비/기존 보강/비적용이 구분되어야 한다. '아직 조사 안 됨'과 '이 규칙은 비적용'은 다른 상태다.

생성 graph·coverage·manifest와 사람이 읽는 README/요약은 생성기가 소유한다. 읽기 조회는 파일을 변경하지 않는다. `check`는 참조·해시·원문 pointer·전체 source 보존·주장과 요리쌍 보존·규칙 연결·판정 연결·결정적 재생성을 검사한다. 기존 게임원본/전체추출/미결보강 폴더는 수정하지 않는다. 외부 그래프 생성이나 AI 브리지 로딩은 변경하지 않는다.
