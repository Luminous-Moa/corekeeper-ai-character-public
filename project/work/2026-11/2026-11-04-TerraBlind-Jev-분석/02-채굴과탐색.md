# TerraBlind 채굴과 탐색의 관측 및 Jev 선택지 분석

기준 소스는 Reisenbug/TerraBlind의 `0859ca29aedea7bb48324c68eaece35b629c6d37`이다. 로컬 소스는 `C:\Dev\_scratch\terrablind-review-20261104`에 있다. 아래 설명은 이 커밋의 생산 코드 호출을 정적으로 추적한 결과이며 게임 실행이나 실제 Jev 요청으로 얻은 성능 측정은 아니다. 링크는 같은 커밋에 고정했다.

핵심은 세 경로를 구분하는 것이다. **벌목에는 실제 Jev 후보 선택이 연결되어 있지만, 광맥 채굴은 코드가 후보를 고르는 루프이며, 길찾기 막힘용 Jev 질문은 아직 API에 연결되지 않은 상태다.** 따라서 `Jev`라는 폴더명이나 주석만 보고 모든 채굴·길찾기를 모델이 판단한다고 해석하면 안 된다.

읽기 순서는 실제 Jev 입력을 보려면 2~4절, 광맥 채굴과의 차이를 보려면 5~7절, 코어키퍼 설계에 참고할 부분은 8절이다.

## 1 현재 동작하는 경로의 구분

| 기능 | 상위 호출 | 현장 후보를 고르는 주체 | Jev에 전달되는가 |
|---|---|---|---|
| 보통 나무에서 Wood 모으기 | `chop_wood(count, constraints)` | Jev가 나무 ID 또는 `stop` 선택 | 연결되어 있음 |
| 특정 광석 여러 타일 채굴 | `mine_vein(name, count)` | 가까운 미시도 타일을 코드가 선택 | 이 선택 루프에는 없음 |
| 한 방향 통로 굴착 | `mine(dir, target_x, target_y)` | 상위 도구 인자와 코드 실행기 | 실행기에 Jev 호출 없음 |
| 특정 타일에 도구 사용 | `use_item(x, y, slot, ...)` | 상위 도구 인자와 코드 실행기 | 실행기에 Jev 호출 없음 |
| 여러 종류 재료 모으기 | `gather` | 거리와 종류별 보정 점수로 코드가 선택 | 이 선택 루프에는 없음 |
| 목표 위치로 이동 | `nav_to` → `RecedingNav` | 물리 후보·비용장·A*·막힘 처리 코드 | 막힘 관측 로그만 존재 |
| 한 방향 계속 탐색 | `ExploreCoordinator` | 전방 지형에서 목적지 점수 계산 | Jev 호출 없음 |

여기서 “Jev 호출 없음”은 해당 후보 선택 경로에 관한 설명이다. 동일 게임에서 보스 전투 제어가 별도로 켜져 있거나 상위 LLM이 도구를 선택하는 것까지 없다는 뜻은 아니다. 상위 LLM, Jev, 코드 실행기는 서로 다른 의사결정 경계다. 생산 분기는 [AgentTools.cs:494](https://github.com/Reisenbug/TerraBlind/blob/0859ca29aedea7bb48324c68eaece35b629c6d37/Agent/AgentTools.cs#L494)와 [WoodHarvest.cs:24](https://github.com/Reisenbug/TerraBlind/blob/0859ca29aedea7bb48324c68eaece35b629c6d37/Agent/WoodHarvest.cs#L24), [Gather.cs:37](https://github.com/Reisenbug/TerraBlind/blob/0859ca29aedea7bb48324c68eaece35b629c6d37/Agent/Gather.cs#L37)에 있다.

## 2 실제 Jev 경로인 벌목의 입력 수집

### 2.1 상위 LLM이 넘기는 목표

`chop_wood`는 다음 인자를 받는다.

- `count`: 이번 호출에서 추가로 얻을 일반 Wood 수량. 기존 보유량을 포함한 총수량이 아니다. 1~9999만 허용한다.
- `constraints`: 장소·나무 보호 등에 관한 사용자 제한의 원문. 없으면 빈 문자열이다.

실행 전 `Config.I.TypeSafeKey`가 있는지 검사한다. 이 경로는 `JevCombat.Key()`의 환경변수 등 다른 키 탐색을 호출하지 않는다. 키가 없으면 오류를 반환한다. 실행 중 `StateSpacePlanner.PreserveTerrain = true`로 접근 경로의 지형 변경을 제한하고, `finally`에서 `false`로 되돌린다. 이 상태 설정과 자연어 `constraints` 해석은 별개의 장치다. [도구 스키마](https://github.com/Reisenbug/TerraBlind/blob/0859ca29aedea7bb48324c68eaece35b629c6d37/Agent/Tools.json#L240), [실행 분기](https://github.com/Reisenbug/TerraBlind/blob/0859ca29aedea7bb48324c68eaece35b629c6d37/Agent/AgentTools.cs#L497)

### 2.2 원시 게임 데이터

`GameWoodHarvest.Observe()`는 `NativeAgent.OnMain()`으로 게임 메인 스레드에서 다음 데이터를 읽는다.

| 데이터 | 읽는 위치 또는 방법 | 모델이 받는 형태 |
|---|---|---|
| 플레이어 좌표 | `ActExecutor.OriginCx/OriginCy(player)` | `player_cell: [cx, cy]` |
| 현재 체력 | `player.statLife` | `hp` 정수. 최대 체력 필드는 없음 |
| 일반 목재 보유량 | `player.inventory`에서 `ItemID.Wood` 스택 합 | `wood` 정수 |
| 일반 나무 타일 | `Main.tile[x,y]`, `HasTile`, `TileID.Trees` | 뿌리 좌표로 정규화한 `trees` |
| 주변 가구 타일 | 문·작업대·의자·탁자 타입 검사 | 각 나무의 `nearby_furniture` |
| 사망·비활성 | `player.dead`, `player.active` | `error: player_dead` |
| 도끼 유무 | 인벤토리 0~49 중 `axe > 0` | 없으면 `error: no_axe` |

`Observe`의 `error`는 호출 루프가 Jev 요청 전에 검사하므로 사망·도끼 없음 상태를 모델에게 보내 해결 방향을 고르게 하지 않는다. [GameWoodHarvest.cs:19](https://github.com/Reisenbug/TerraBlind/blob/0859ca29aedea7bb48324c68eaece35b629c6d37/Agent/GameWoodHarvest.cs#L19)

### 2.3 나무 후보 수집과 축소

후보 생성 순서는 다음과 같다.

1. 플레이어 기준 가로 `cx-120`~`cx+120`, 세로 `cy-48`~`cy+48` 타일 범위를 검사한다. 맵 테두리에서 잘린다.
2. `HasTile && TileType == TileID.Trees`인 타일을 찾는다.
3. `ItemUseCoordinator.TrySnapTree()`로 좌표를 수간 밑동에 맞춘다.
4. 보정 결과도 일반 `TileID.Trees`인지 다시 검사한다.
5. 같은 밑동 `(tx,ty)`은 사전으로 중복 제거한다. 각 x 열에서는 후보를 찾거나 이미 찾은 밑동에 걸리면 y 탐색을 끝내는 `break`가 있다. 모든 트리 타일을 단순 전수 나열하는 방식은 아니다.
6. 거리 `abs(cx-tx) + abs(cy-ty)`를 계산한다. 직선거리가 아닌 맨해튼 거리다.
7. 거리순으로 정렬해 최대 12개를 남긴다.

나무 ID는 `tree_<x>_<y>` 형식이다. 후보 개체가 전송된 이후 Jev는 이 ID를 선택한다. 모델이 새 좌표를 생성하지 않는다.

밑동 보정은 단순히 아래로만 걷는 처리가 아니다. 입력 주변 ±12 타일에서 `TileID.Sets.IsATreeTrunk`에 해당하는 가장 가까운 타일을 찾고, 그 주변 ±3 열에서 같은 타입의 세로 연속 길이가 가장 긴 열을 수간으로 고른 뒤, 같은 타입이 이어지는 가장 아래 타일까지 내려간다. 이는 가지·뿌리 장식 대신 나무 전체를 쓰러뜨릴 수간 밑동을 겨냥하기 위한 코드다. [후보 수집](https://github.com/Reisenbug/TerraBlind/blob/0859ca29aedea7bb48324c68eaece35b629c6d37/Agent/GameWoodHarvest.cs#L24), [수간 보정](https://github.com/Reisenbug/TerraBlind/blob/0859ca29aedea7bb48324c68eaece35b629c6d37/Actions/ItemUseCoordinator.cs#L339)

### 2.4 주변 가구 정보의 의미

각 밑동을 기준으로 가로 ±12, 세로 위 12~아래 4 타일을 읽는다. 문, 열린 문, 작업대, 의자, 탁자 타일을 최대 16개 기록한다.

```json
{
  "id": "tree_120_65",
  "x": 120,
  "y": 65,
  "distance": 24,
  "nearby_furniture": [
    { "x": 112, "y": 63, "type": 18 }
  ]
}
```

위 숫자는 형식을 설명하기 위한 재구성 예시이며 실게임 관측이 아니다. `type`은 실제 타일의 숫자 타입이며 이 예시에서 특정 가구의 뜻을 추가로 추정하지 않는다.

중요한 한계는 다음과 같다.

- 가구 개체가 아니라 **가구를 이루는 타일 좌표**를 기록하므로 여러 타일짜리 가구가 중복 항목으로 들어갈 수 있다.
- 집의 소유자, 보호구역 경계, 나무의 소유권을 수집하지 않는다.
- 그래서 프롬프트에도 “주변 가구는 좌표의 사실이지 주택 소유권 증명이 아니다”라고 명시한다.
- 미리 경로를 계산한 `reachable`, 예상 접근 시간, 위험도, 경로의 장애물 목록은 후보에 없다. 모델에 “가깝고 접근하기 쉬운 나무 우선”이라고 요구하지만 이 선택 단계에서 제공되는 직접 근거는 거리·가구·직전 실패 정도다. 실제 접근 가능성은 선택 후 네비게이터가 시도해 확인한다.
- 스캔은 `Main.tile`을 직접 읽으며 이 함수에는 시야·조명·탐사 여부 조건이 없다. 사람에게 이미 보였던 나무만 아는 시스템과는 관측 범위가 다르다.

## 3 벌목에서 Jev에게 제공하는 요청

### 3.1 호출별 상태 조립

`WoodHarvest.Run()`은 처음 관측한 `wood`를 기준 보유량 `baseline`으로 잡는다. 매 회차 새 현장을 관측하고 `gained = max(0, currentWood - baseline)`를 계산한다. 목표를 달성했으면 모델을 부르지 않는다.

각 나무 ID별 시도 횟수를 로컬 사전에 보관하며 2회 이상 시도한 후보를 제외한다. 후보가 없으면 `no_available_trees`로 끝낸다. 이 사전은 해당 `Run` 호출의 임시 상태이며 장기기억이 아니다.

다음 필드를 관측값에 추가한다.

| 추가 필드 | 값과 목적 |
|---|---|
| `wanted_additional_wood` | 이번 호출에서 추가로 얻을 목표량 |
| `gained` | 시작 대비 현재 일반 Wood 증가량, 최솟값 0 |
| `constraints` | 상위 LLM이 넘긴 사용자 제한 문장 |
| `last_failure` | 직전 실패 또는 줍기 실패 결과. 성공 후에는 null로 지울 수 있음 |

실패 이력 전체를 모델에게 보내지는 않는다. 횟수 제한은 코드에 남고, 모델에는 직전 실패 한 건과 현재 남은 후보가 전달된다. [WoodHarvest.cs:24](https://github.com/Reisenbug/TerraBlind/blob/0859ca29aedea7bb48324c68eaece35b629c6d37/Agent/WoodHarvest.cs#L24)

### 3.2 선택지 구조

`criteria`에는 항상 `stop`을 먼저 넣고, 나무 후보 ID를 키로 추가한다. 각 후보의 값은 설명 문자열이 아니라 **해당 나무 JSON 개체의 복사본**이다.

따라서 한 나무의 좌표·거리·가구 정보는 `state.trees`에도 있고 `questions.tree.criteria.<id>`에도 중복된다. 보스 회피처럼 가공된 이동 효과를 길게 설명하는 방식과 다르다.

```json
{
  "model": "jev-latest",
  "state": {
    "wood": 7,
    "trees": [
      {
        "id": "tree_120_65",
        "x": 120,
        "y": 65,
        "distance": 24,
        "nearby_furniture": []
      }
    ],
    "player_cell": [100, 61],
    "hp": 100,
    "wanted_additional_wood": 30,
    "gained": 0,
    "constraints": "집 주변 나무는 남겨 둬",
    "last_failure": null
  },
  "questions": {
    "tree": {
      "type": "choice",
      "instructions": "실제 코드의 벌목 선택 지침 문자열",
      "criteria": {
        "stop": "제한에 맞는 후보가 없거나 안전하게 계속할 정보가 부족하면 상위 Agent에 반환",
        "tree_120_65": {
          "id": "tree_120_65",
          "x": 120,
          "y": 65,
          "distance": 24,
          "nearby_furniture": []
        }
      }
    }
  }
}
```

이 예시는 실제 전송 캡처가 아니다. 코드의 구조를 따라 숫자·사용자 제한·설명 문구를 한국어로 재구성했다. 실제 요청에서는 `state`가 **JSON object**다. 보스 `Dodge` 경로의 문자열화된 `state`와 혼동하면 안 된다.

실제 `instructions`가 모델에게 맡기는 내용은 다음과 같다.

1. 사용자 제한과 후보 현장을 보고 다음 나무를 선택한다.
2. 가깝고 접근하기 쉬운 나무를 우선한다.
3. 장소·보호 제한을 지킨다.
4. 가구 좌표로 소유권을 단정하지 않는다.
5. 직전 실패를 보고 같은 나무를 다시 시도할 가치가 있는지, 다른 나무로 바꿀지 판단한다.
6. 제한에 맞는 후보가 없으면 `stop`을 고른다.
7. 좌표·이동 명령을 생성할 필요는 없다. 이동·도끼·수량 계산은 코드 책임이다.

근거: [WoodHarvestDecision.Choose](https://github.com/Reisenbug/TerraBlind/blob/0859ca29aedea7bb48324c68eaece35b629c6d37/Agent/WoodHarvest.cs#L85)

### 3.3 전송과 응답 검증

- HTTP: `POST https://api.typesafe.ai/v1/systemone`
- 헤더: Bearer 인증, `application/json`
- 모델 이름: `jev-latest`
- 클라이언트 제한: `AgentTools.HarvestHttp`의 HTTP timeout 8초
- 기대 응답 위치: `answers.tree.choice`
- 검증: choice가 존재하며, 이번 요청에 만든 `criteria`의 키 중 하나여야 한다.
- HTTP 비성공·없는 선택지·응답 불량은 예외다. 유효한 나무를 자동으로 대신 선택하는 fallback은 이 경로에 없다.
- 응답의 confidence·probabilities를 읽거나 낮은 confidence를 기각하지 않는다.
- 사용자 취소가 아닌 HTTP 취소는 벌목 요청 timeout 오류로 바꾼다.

모델 오류는 상위 `AgentTools.Execute`에서 `tool_exception` 형태로 정리될 수 있다. 이동 중 사망 등 게임 상태 변화는 실행기와 대기 함수가 처리한다. 이 경로는 요청을 순차적으로 `await`하므로 동시에 여러 나무 선택 요청을 날리지 않는다. 다만 보스 회피처럼 요청 번호·상태 세대·응답 TTL을 대조하는 별도 장치는 없다. 선택 후 실행에서 실제 타일 상태를 다시 검사한다. [HTTP와 응답 처리](https://github.com/Reisenbug/TerraBlind/blob/0859ca29aedea7bb48324c68eaece35b629c6d37/Agent/WoodHarvest.cs#L100), [HTTP 클라이언트](https://github.com/Reisenbug/TerraBlind/blob/0859ca29aedea7bb48324c68eaece35b629c6d37/Agent/AgentTools.cs#L24), [상위 예외 처리](https://github.com/Reisenbug/TerraBlind/blob/0859ca29aedea7bb48324c68eaece35b629c6d37/Agent/AgentTools.cs#L241)

## 4 선택된 나무를 실행하고 다시 판단하는 과정

### 4.1 이동과 도구 사용

`stop`을 받으면 `needs_agent_decision`으로 반환한다. 나무를 받으면 해당 ID의 시도 횟수를 늘린 뒤 아래 순서로 실행한다.

| 단계 | 코드 실행 | 현장 재확인과 제한 |
|---|---|---|
| 접근 | `Reach.CanMine` 검사 후 필요하면 `Navigate(... reach:true)` | 최대 20초 대기. 끝나면 `Reach.CanMine` 재검사 |
| 도끼 선택 | 인벤토리 0~49를 도끼 위력 내림차순으로 검색 | 사용 가능한 도끼 없음이면 오류 |
| 대상 검증 | 선택한 좌표가 아직 `TileID.Trees`인지 확인 | 아니면 `target_changed` |
| 벌목 | `ItemUseCoordinator.Start(Strict=true, DurationTicks=0)` | 다른 나무로 자동 스냅하지 않고 지정 밑동을 사용 |
| 벌목 결과 대기 | `/item_use_status` 폴링 | 최대 8초, 실제 `removed` 여부 확인 |
| 줍기 | 300ms 대기 → 밑동 좌표로 `Navigate` → 300ms 대기 | 네비게이션 최대 20초. 완료 못 하면 `cannot_approach_drops` |
| 수량 확인 | 다음 `Observe()`와 종료 시 최종 `Observe()` | 나무가 쓰러진 수가 아니라 실제 일반 Wood 인벤토리 증가량 |

접근 실패는 `cannot_reach_tree`에 네비게이션 결과를 붙여 반환한다. `removed`일 때만 `trees_felled`를 늘리고 해당 나무를 재선택하지 않도록 시도 횟수를 2로 만든다. 벌목 실패 중 `reason`이 `tool_weak`, `blocked`, `no_axe`이면 해당 후보를 즉시 소진 처리한다. 그 외에는 최대 두 번 선택될 수 있다. [접근·벌목·줍기](https://github.com/Reisenbug/TerraBlind/blob/0859ca29aedea7bb48324c68eaece35b629c6d37/Agent/GameWoodHarvest.cs#L56), [회차 갱신](https://github.com/Reisenbug/TerraBlind/blob/0859ca29aedea7bb48324c68eaece35b629c6d37/Agent/WoodHarvest.cs#L49)

`ItemUseCoordinator`는 타일이 실제로 사라졌는지 확인한다. 45틱의 유예 뒤에도 해당 플레이어의 `hitTile` 누적 피해가 0이면 원인을 분류한다. `WorldGen.CanKillTile`이 허용하면 `tool_weak`, 허용하지 않으면 `blocked`다. 도구 사거리, 용암 위험, 전투 제약도 실행 단계에서 확인한다. 이는 모델이 실패 원인을 상상하는 방식이 아니라 실제 게임 상태에서 실패 이유를 구성해 돌려주는 방식이다. [진행·실패 판정](https://github.com/Reisenbug/TerraBlind/blob/0859ca29aedea7bb48324c68eaece35b629c6d37/Actions/ItemUseCoordinator.cs#L92)

### 4.2 재판단 주기와 종료 조건

벌목 Jev는 일정한 300ms 주기로 호출되지 않는다. **나무 선택 → 접근 → 벌목 → 줍기 → 새 관측**이 끝나야 다음 요청이 나간다. 전투의 짧은 반응 판단과 작업 단위가 다르다.

최대 16회차이며, 루프 시작 시 경과시간이 180초 미만인지 검사한다. 이것은 180초 시점에 진행 중인 모든 작업을 즉시 끊는 전역 deadline은 아니다. 마지막 회차의 네트워크·접근·벌목·줍기 대기는 180초를 넘겨 끝날 수 있다. 반면 `Gather.Run`에는 별도의 취소 토큰 시간 제한이 있다.

반환값은 `outcome`, `wanted`, `gained`, `trees_felled`, `jev_calls`, `elapsed_ms`, `last_failure`다. 상위 도구 래퍼는 인벤토리의 전후 차이인 `got`·`lost`와 최신 위치·체력도 붙인다. 결과를 평가하는 기준을 모델의 “완료했다”는 응답이 아니라 실제 아이템 증가로 두었다는 점이 참고할 만하다. [루프 한도·최종 관측](https://github.com/Reisenbug/TerraBlind/blob/0859ca29aedea7bb48324c68eaece35b629c6d37/Agent/WoodHarvest.cs#L34), [공통 결과 래퍼](https://github.com/Reisenbug/TerraBlind/blob/0859ca29aedea7bb48324c68eaece35b629c6d37/Agent/AgentTools.cs#L131)

### 4.3 벌목의 실제 책임 경계

| 모델에 남긴 판단 | 프로그램이 결정하는 것 |
|---|---|
| 사용자 자연어 제한 해석 | 일반 나무만 수집 |
| 후보 중 다음 나무 선택 | 주변 검색 범위와 12개 상한 |
| 직전 실패를 보고 재시도 또는 변경 | 각 나무 최대 두 번 시도 |
| 정보가 부족하거나 제한에 맞지 않으면 중지 | 지형 보존 설정, 경로 실행, 도끼 선택 |
| 후보 정보의 의미를 종합 | 타일 소멸, 누적 채굴 피해, 사거리 검사 |
|  | 실제 인벤토리 증가량과 목표 완료 판정 |

따라서 이 구현을 참고할 때 “모델이 모든 채집 동작을 지능적으로 수행한다”보다 “모델은 의미 있는 대상 선택을 하고, 실행과 확인은 정해진 절차가 담당한다”가 맞다.

## 5 광맥 채굴은 어떤 정보를 읽고 누가 선택하는가

### 5.1 대표 광맥 채굴 경로

`mine_vein("Lead", count)`를 호출했다고 가정한다. 이는 설명을 위한 입력 예시이며 실측 실행 기록이 아니다.

1. `AgentTools.MineVein`이 `count`를 1~1000으로 제한한다.
2. `/find_tiles {name, n:30, max_dist:2000}`를 호출한다.
3. 반환된 타일 중 이 호출에서 아직 시도하지 않은 첫 좌표를 고른다. 선택 직전에 이 좌표를 `skipped`에 넣는다.
4. `Navigate({x,y,exact:true})`로 그 타일을 목표로 이동한다. 실제 고체 광석이라면 `RecedingNav.Mode.Mine`이 되어 필요시 통로를 파는 네비게이션으로 이어진다.
5. `/mine_reach`로 현재 채굴 가능한 범위의 경계값을 얻는다.
6. 핫바 0~9에서 `pick` 값이 가장 높은 곡괭이를 선택한다. 없으면 `no_pickaxe`로 끝낸다.
7. `/find_tiles {name,n:40,max_dist:60}`으로 주변 동종 타일을 다시 찾는다.
8. 현재 사거리 경계 안의 타일마다 `/item_use`를 `strict:true`, `duration_ticks:0`으로 호출하고 최대 60초 결과를 기다린다.
9. `outcome == removed`이면 `removed`를 하나 늘린다. `reason == tool_weak`이면 종료한다.
10. 부족하면 처음으로 돌아간다. 반복 횟수는 `wanted + 8` 미만, 제거량이 wanted 미만인 동안이다.

여기에는 `questions`, `criteria`, Jev HTTP 요청이 없다. 가까운 타일 선택·반복·실패 처리 모두 코드다. 또한 이름은 `mine_vein`이지만 이 함수가 연결 성분으로 광맥을 분리해 크기·가치·위험을 모델에게 제시하는 것은 아니다. **가까운 동종 타일을 찾아 접근하고 범위 안 타일을 제거하는 루프**다. [AgentTools.MineVein](https://github.com/Reisenbug/TerraBlind/blob/0859ca29aedea7bb48324c68eaece35b629c6d37/Agent/AgentTools.cs#L746)

### 5.2 타일 탐색의 원시 데이터와 정렬

`/find_tiles`의 실제 읽기 경로는 다음과 같다.

- `TileID.Search.TryGetId`로 문자열을 타일 타입에 대응시킨다.
- 플레이어 **중심 좌표**를 16픽셀로 나눠 타일 좌표로 바꾼다.
- 반경 0부터 `max_dist`까지 정사각형 테두리를 넓혀 가며 `Main.tile`을 읽는다.
- `HasTile && TileType == wantType`인 타일을 수집한다.
- 맨해튼 거리순, 같은 거리면 y, 다음 x 순으로 정렬한다.
- `n`개를 넘으면 잘라 내며, 현재 반경 밖에서 더 가까운 결과가 나올 수 없는 조건이 되면 탐색을 끝낸다.
- 각 결과에 `x`, `y`, `dist`, `near_hive_wall`을 붙인다. 상자에는 종류도 붙이며 잠긴 상자 등 별도 필터가 있다.
- 아무것도 없으면 `searched_radius`와 맵 크기를 반환해 “검색 범위에 없다”와 “전체 맵에 없다”를 구분한다.

이 함수에도 조명·시야·탐사한 지역 검사 없이 `Main.tile`을 직접 읽는 경로가 있다. 광맥을 발견한 기억을 검색하는 기능과는 성격이 다르다. [HttpServerSystem.cs:2414](https://github.com/Reisenbug/TerraBlind/blob/0859ca29aedea7bb48324c68eaece35b629c6d37/Infra/HttpServerSystem.cs#L2414)

상위 `find_tiles` 도구에는 이름 모호성을 다루는 `AgentTools.FindTiles` 래퍼도 있지만, `MineVein` 내부에서는 `/find_tiles`를 직접 호출한다. 따라서 이 내부 경로가 그 래퍼의 모호성 처리까지 거친다고 설명해서는 안 된다. [이름 해석 래퍼](https://github.com/Reisenbug/TerraBlind/blob/0859ca29aedea7bb48324c68eaece35b629c6d37/Agent/AgentTools.cs#L630)

### 5.3 사거리와 진행 확인

`/mine_reach`는 현재 플레이어와 손에 든 아이템의 추가 사거리 등을 반영해 근처 셀에 `Reach.CanMine`을 적용하고, 참인 셀의 경계 `lx,ly,hx,hy`를 반환한다. `MineVein`은 그 경계 안의 후보를 남긴다. 하지만 이 조회는 최고 위력 곡괭이 슬롯을 고르기 **전**에 수행된다. 슬롯 선택 또는 이동으로 상태가 바뀌었을 때 사거리의 최종 사실은 도구 실행기가 다시 판단한다. [사거리 조회](https://github.com/Reisenbug/TerraBlind/blob/0859ca29aedea7bb48324c68eaece35b629c6d37/Infra/HttpServerSystem.cs#L380)

또한 `MineVein`의 중단 기준 `removed >= wanted`는 **아이템 입수량이 아닌 직접 제거한 타일 수**다. 이동하면서 네비게이터가 파낸 타일, 아직 줍지 못한 드롭, 인벤토리 포화 등과 수량이 어긋날 수 있다. 함수는 이를 `note`로 알리고, 공통 결과 래퍼가 실제 인벤토리 `got`를 따로 제공한다. 벌목의 `gained` 기반 완료 판정과 동일하게 취급하면 안 된다.

`Navigate` 결과를 이 함수가 즉시 성공 여부로 분기하지 않고, 이어서 현재 사거리와 주변 타일을 조회하는 점도 중요하다. 네비게이션 실패가 곧 전체 광맥 채굴 종료가 되는 구조는 아니다. 각 `Navigate`는 기본 180초 대기, 개별 타일 작업은 최대 60초 대기이므로 함수 전체가 180초로 제한되는 것도 아니다. [MineVein](https://github.com/Reisenbug/TerraBlind/blob/0859ca29aedea7bb48324c68eaece35b629c6d37/Agent/AgentTools.cs#L746), [Navigate](https://github.com/Reisenbug/TerraBlind/blob/0859ca29aedea7bb48324c68eaece35b629c6d37/Agent/AgentTools.cs#L697)

### 5.4 통로를 파는 MineCoordinator

`MineCoordinator`는 선택모델이 아니라 매 게임 업데이트에서 몸의 위치와 실제 타일을 읽어 입력을 만드는 실행기다. `MineRequest`에는 방향, 출발·목표 셀, 계획상 제거할 타일 목록, 그 목록만 제거할지 여부가 들어간다.

플레이어의 실시간 충돌상자에서 좌우 열·머리 행·발 행을 다시 계산한다. 가로 굴착은 몸 앞 열에서 필요한 타일을 고르고 목표 열에 도달했으며 남은 장애물이 없으면 완료한다. 아래 굴착은 발 위치와 그 아래 행을 파고 목표 높이에 내려왔는지 확인한다. 위 굴착은 머리 위 두 행의 공간을 비운 뒤 기둥 쌓기 실행에 넘긴다. 계획된 타일 목록은 실시간 창에서 벗어난 장애물을 찾는 보조 근거로 사용한다. [MineCoordinator.cs:89](https://github.com/Reisenbug/TerraBlind/blob/0859ca29aedea7bb48324c68eaece35b629c6d37/Actions/MineCoordinator.cs#L89)

실행기의 보호·실패 조건은 구체적이다.

| 조건 | 처리 |
|---|---|
| 핫바 앞 10칸에 곡괭이 없음 | `no_pickaxe` |
| 시작~목표 사각형에 ±2타일 여유를 준 범위에서 이탈 | `out_of_box`, 상위가 새 위치로 재계획 |
| 제거할 타일이 있는데 600프레임 동안 남은 수가 줄지 않음 | `stalled` |
| 제거할 타일을 90프레임 넘게 찾지 못함 | `no_tiles` |
| 용암 방출 위험 | `lava_risk` |
| `WorldGen.CanKillTile` 거부 | `unbreakable` |
| `Reach.CanMine` 거부 | `out_of_reach` |
| 정상 대상 | 커서 조준, 슬롯 선택, `controlUseItem = true` |

용암 검사는 해당 타일이 Hellstone이거나 주변 3×3 중 용암이 있으면 채굴을 막는 코드다. 이는 모델에 “용암을 어떻게 할지” 묻는 선택지가 아니다. [굴착 실패 조건](https://github.com/Reisenbug/TerraBlind/blob/0859ca29aedea7bb48324c68eaece35b629c6d37/Actions/MineCoordinator.cs#L187), [LavaSafety.cs](https://github.com/Reisenbug/TerraBlind/blob/0859ca29aedea7bb48324c68eaece35b629c6d37/Core/LavaSafety.cs#L16)

`MineCoordinator`의 곡괭이 선택은 앞 10칸에서 첫 번째 유효 곡괭이다. `MineVein`의 개별 타일 도구 선택은 앞 10칸 중 가장 높은 pick 값이다. 비슷한 이름의 경로라도 세부 선택 정책이 다르다. 또한 `MineCoordinator`에는 사거리 부족 시 임시 팔 연장이라는 옛 주석·코드가 남아 있으나, 현재 흐름은 그보다 앞에서 `!Reach.CanMine`이면 종료한다. 이 부분을 실제 정상 fallback으로 소개하면 부정확하다. [사거리 gate와 뒤의 코드](https://github.com/Reisenbug/TerraBlind/blob/0859ca29aedea7bb48324c68eaece35b629c6d37/Actions/MineCoordinator.cs#L244)

## 6 막힘 현장용 Jev 설계는 있으나 연결되지 않았다

### 6.1 준비된 상태 형식

`StuckScene`은 길찾기가 막힌 순간을 다음 JSON으로 표현할 수 있게 되어 있다.

| 필드 | 의미 |
|---|---|
| `player_cell` | 플레이어 발밑 기준 셀 |
| `goal_cell` | 해당 네비게이션 구간의 목적지 |
| `potential_here` | 현재 셀에서 목표까지의 추정 비용 H |
| `unmineable_under_foot` | 발밑을 막는 타일 타입·좌표·현재 곡괭이로 못 판다는 설명, 없으면 null |
| `astar_already_searching` | 우회 A*가 이미 백그라운드 검색 중인지 |
| `commitment_already_active` | 중간에 비용이 늘더라도 특정 방향으로 계속 가는 commitment가 이미 있는지 |
| `any_physics_edge_available` | 생성된 물리 이동 후보가 하나라도 있는지 |
| `terrain_9x9` | 중심 주변 9×9 타일을 한 문자열로 표현 |
| `terrain_legend` | `#` 고체, `=` 플랫폼, `~` 용암, `.` 공기, `/` 줄바꿈 |

9×9 스캔은 맵 밖을 `?`로 쓰지만 legend에는 `?` 설명이 없다. 용암→플랫폼→고체→공기 순서로 판별한다. 이름 설명을 넣으려는 주석이 있으나 실제 `unmineable_under_foot`에는 숫자 `tile_id`와 “현재 곡괭이로 채굴 불가”라는 문장만 있다. [StuckScene.cs](https://github.com/Reisenbug/TerraBlind/blob/0859ca29aedea7bb48324c68eaece35b629c6d37/Jev/Nav/StuckScene.cs#L8)

### 6.2 준비된 선택지

`JevTriage.QuestionJson()`에는 `type: choice`와 다음 criteria가 정의되어 있다.

| 키 | 코드에 적힌 의미 |
|---|---|
| `AstarEscape` | 잠시 비용이 늘거나 우회해야 나갈 수 있는 곳에서 짧은 A* 탈출 경로 검색 |
| `DigFootBlock` | 현재 곡괭이로 못 파는 발밑 열을 피해 옆으로 한 칸 이동 |
| `Commit` | 근처의 더 낮은 비용 셀로 방향을 정하고 중간 비용 상승에도 되돌아오지 않기 |
| `WalledIn` | 사방이 파괴 불가능한 장애물로 막혔다고 판단 |
| `Unknown` | 어느 선택지에도 맞지 않음 |

`MinConfidence = 0.6`과 `QuestionId = "stuck_rung"`도 선언되어 있다. 그러나 **실제 `Pick()`은 이 질문을 전송하지 않고 `_fallback.Pick(in s)`만 호출한다.** 따라서 0.6 confidence 기준이 현재 Jev 응답에 적용된다고 설명할 수 없다. 실제 HTTP 클라이언트·응답 파서도 이 클래스에 없다. [JevTriage.cs](https://github.com/Reisenbug/TerraBlind/blob/0859ca29aedea7bb48324c68eaece35b629c6d37/Jev/Nav/JevTriage.cs#L5)

### 6.3 로그상의 선택과 실제 동작도 구분해야 한다

`Triage.Observe()`는 `JevTriage`를 호출해 나온 baseline 결과를 로그와 `JevLog`에 기록한다. `State = s.ToJson()`가 로그에 있으므로 화면에 정교한 state와 pick이 보일 수 있지만, API 요청 증거는 아니다.

더 중요한 점은 `RecedingNav`가 그 반환값을 받아 switch로 실행하지 않는다는 것이다. `Observe()`는 void이며 이후 원래의 제어 흐름이 계속된다.

1. 지형 보존 중이면 `no_progress_preserving_terrain`으로 중단한다.
2. 막힘 현장을 `Triage.Observe`로 기록한다.
3. 기존 A* 탈출을 시도한다.
4. 발밑 채굴 불가 열이 있고 commitment·A*가 활성 상태가 아니면 `Unstick.Handle`로 우회한다.
5. A*도 진행 중이지 않고 commitment가 없으면 commitment를 시작한다.
6. 물리 후보 자체가 없으면 `walled_in`으로 중단한다.

BaselineTriage는 이 처리 의도를 흉내 내는 별도 판단 규칙이므로, 로그의 pick과 실제 실행 사이의 동일성을 전제하면 안 된다. 실제 동작은 `RecedingNav`의 후속 코드가 결정한다. [Triage.Observe](https://github.com/Reisenbug/TerraBlind/blob/0859ca29aedea7bb48324c68eaece35b629c6d37/Jev/Nav/Triage.cs#L12), [BaselineTriage](https://github.com/Reisenbug/TerraBlind/blob/0859ca29aedea7bb48324c68eaece35b629c6d37/Jev/Nav/BaselineTriage.cs#L7), [RecedingNav.cs:550](https://github.com/Reisenbug/TerraBlind/blob/0859ca29aedea7bb48324c68eaece35b629c6d37/Nav/RecedingNav.cs#L550)

### 6.4 낙하 위험 설명도 API 연결 여부를 구분해야 한다

`FallCost.Json()`에는 낙하 높이, 안전 높이 초과량, 예상 피해, 현재·최대 체력, 낙하 뒤 체력, 치명 여부, 거미줄 개수, 계산 규칙을 JSON으로 만드는 코드가 있다. 계산은 `max(0, fallCells - 25) * 10`이다. 그러나 조사한 생산 소스에서 이 JSON을 Jev 요청으로 보내는 호출 경로는 확인되지 않았다.

실제로 쓰이는 것은 선택적 `RiskLayer`다. 활성화하면 기존 후보 비용에 코드가 위험 비용을 더한다.

- 낙하 예상 피해가 현재 HP 이상이면 100000.
- 나머지는 낙하 예상 피해 × 3.
- 후보 종착점에서 맨해튼 거리 8 이내의 적은 일반 적 `40/(d+1)`, 중력 없는 적 `25/(d+1)`를 더함.

이것은 모델의 판단 결과가 아니라 프로그램의 비용 함수다. `StateSpacePlanner`에서 `candidate.total + RiskLayer.Penalty(...)`가 최소인 후보를 고른다. 기본 false이며 설정 `AvoidDanger`와 연결된다. 낙하 계산은 이 코드에 적힌 단순 모델이므로 모든 장비·버프·게임 상황에 대한 완전한 피해 예측이라고 부르면 안 된다. [FallCost](https://github.com/Reisenbug/TerraBlind/blob/0859ca29aedea7bb48324c68eaece35b629c6d37/Jev/Nav/FallCost.cs#L7), [RiskLayer](https://github.com/Reisenbug/TerraBlind/blob/0859ca29aedea7bb48324c68eaece35b629c6d37/Jev/Nav/RiskLayer.cs#L6), [후보 비용 적용](https://github.com/Reisenbug/TerraBlind/blob/0859ca29aedea7bb48324c68eaece35b629c6d37/Nav/StateSpacePlanner.cs#L2721)

## 7 일반 채집과 방향 탐색

### 7.1 여러 재료를 모으는 gather

`Gather.Run`은 1~8개의 서로 다른 아이템 목표를 받는다. 각 목표에는 아이템 타입, 목표 **총보유량**, 공급 타일 이름들, 드롭을 얻을 적 타입들이 들어간다. 현장 후보는 다음과 같이 만든다.

- 목표 아이템의 실제 인벤토리 수량.
- 플레이어에서 1600픽셀 미만인 해당 아이템 드롭. 약 100타일 범위다.
- 1280픽셀 미만인 지정된 비우호·비주민 NPC. 약 80타일 범위다.
- 부족한 목표에 대해 타일 이름별 `/find_tiles` 래퍼 호출. 최대 12개, 검색 반경 2000.

후보 필드는 `item_type`, `kind`, `id`, `x`, `y`, `distance`이고, 드롭·NPC는 엔티티 번호 `who`, NPC에는 `npc_type`을 더한다. 드롭·NPC 거리는 유클리드 타일 거리, 타일 검색의 `dist`는 맨해튼 거리다. 점수에 쓰이는 거리의 정의가 후보 종류별로 완전히 같지 않다.

선택은 다음 코드 점수의 오름차순이다.

```text
score = distance + kind_bias
kind_bias(drop) = -1000
kind_bias(npc)  = -20
kind_bias(tile) = 0
```

이미 목표 수량이 찼거나 후보별 시도 횟수가 2 이상이면 제외한다. 따라서 드롭을 강하게 우선하고 적을 일정 정도 우선하는 정책을 코드가 정한다. 이 점수나 후보들은 Jev 요청에 실리지 않는다. 최대 32회 행동이며 1~180초로 제한된 취소 토큰을 사용한다. 종료 시 다시 인벤토리를 관측해 모든 목표를 검증한다. [Gather.cs](https://github.com/Reisenbug/TerraBlind/blob/0859ca29aedea7bb48324c68eaece35b629c6d37/Agent/Gather.cs#L22), [GameGather.Observe](https://github.com/Reisenbug/TerraBlind/blob/0859ca29aedea7bb48324c68eaece35b629c6d37/Agent/GameGather.cs#L15)

실행도 종류별 코드다. 타일은 `CollectTarget`이 곡괭이·도끼·망치를 실제 타일 속성에 맞춰 선택하고, 드롭은 움직임이 가라앉는지 확인한 다음 접근한다. NPC는 타입과 엔티티의 현재 유효성을 다시 검사하고 필요시 접근한 뒤 `FightCoordinator`를 실행한다. 이 채집 후보 선택이 Jev가 아니란 것과, 전투 하위 시스템의 동작은 따로 구분해야 한다. [GameGather.ActCore](https://github.com/Reisenbug/TerraBlind/blob/0859ca29aedea7bb48324c68eaece35b629c6d37/Agent/GameGather.cs#L74)

### 7.2 방향 탐색

`ExploreCoordinator`는 방향 부호를 받아 그 방향으로 구간별 목적지를 정한다.

- 전방 5~60타일, 위·아래 50타일을 훑는다.
- 각 열에서 위에서 아래로 내려오며 첫 번째 `StandablePublic` 셀을 찾는다.
- `score = forward + max(0, rise) * 2`로 점수를 계산한다.
- 가장 높은 점수의 목적지를 고르고 `StateSpacePlanner.Execute`로 보낸다.
- 현재 구간의 예상 도착 위치에서 다음 구간을 백그라운드 계획한다.
- 실제 도착과 예상 도착이 x·y 각각 2타일 이내면 캐시한 다음 계획을 사용한다. 아니면 버리고 새로 계획한다.
- 연속 실패 8회면 `explore_stuck`으로 중단한다.

후보 선택·예측 캐시·실행 검증 모두 코드이며 Jev에 지형 후보를 보내는 단계가 없다. 또한 점수로 선택된 장소가 실제 도달 가능하다는 보장은 없고 실행 계획기가 확인한다. [ExploreCoordinator의 상수와 실행](https://github.com/Reisenbug/TerraBlind/blob/0859ca29aedea7bb48324c68eaece35b629c6d37/Flow/ExploreCoordinator.cs#L31), [선행 계획](https://github.com/Reisenbug/TerraBlind/blob/0859ca29aedea7bb48324c68eaece35b629c6d37/Flow/ExploreCoordinator.cs#L121), [목적지 점수](https://github.com/Reisenbug/TerraBlind/blob/0859ca29aedea7bb48324c68eaece35b629c6d37/Flow/ExploreCoordinator.cs#L212)

## 8 코어키퍼 전투 개선에 가져올 수 있는 설계 판단

다음은 TerraBlind의 사실을 바탕으로 한 적용 해석이며, 코어키퍼의 확정 설계나 구현 변경이 아니다.

**첫째, 관측·후보·실행 결과를 같은 대상 식별자로 연결하는 방식이 유용하다.** 벌목은 `tree_x_y`를 선택하고 실행 직전에 같은 좌표의 실제 타일을 확인한다. 전투에서는 적 엔티티와 요청 당시 행동 정의를 연결하고, 답변 도착 시 대상·행동의 유효성을 확인하는 데 대응한다. 위치만 같은 새 적을 이전 적으로 취급하지 않도록 엔티티 수명까지 고려해야 한다.

**둘째, 실행기가 이미 알 수 있는 실패 사실을 모델에게 돌려주는 것이 중요하다.** 사거리 부족, 도구 부족, 구조적으로 파괴 불가, 접근 실패를 구분하면 “실패했다” 한 단어보다 다음 판단이 구체적이다. 전투라면 사거리 밖, 공격 중 이동 불가, 시야 차단, 목표 소멸, 탄약 없음 등이 해당한다. 다만 실패 이유가 실제 측정인지 추정인지 구분해야 한다. TerraBlind의 `tool_weak` 분류도 모든 게임 상황을 완벽히 설명한다고 보장되지는 않는다.

**셋째, 목표 선택과 순간 제어의 시간 단위를 섞지 않아야 한다.** 벌목의 대상 선택은 나무 한 그루 작업이 끝난 뒤 재판단해도 되지만, 적 공격을 피하는 선택은 그보다 짧은 행동·관측 주기가 필요하다. `chop_wood`의 루프를 전투에 그대로 옮기는 것은 적합하지 않다.

**넷째, 선택지에 없는 사실은 모델이 보완해 줄 것이라고 기대하기 어렵다.** 벌목에서 “접근하기 쉬운 나무”를 요구하지만 실제 후보에는 사전 경로 비용이 없다. 전투에서도 “안전한 방향을 고르라”는 문장만으로는 부족하다. 방향별 예상 충돌, 이동 가능 거리, 공격 예고와 범위를 관측·계산해 제공해야 그 지침이 근거를 갖는다.

**다섯째, 범용 위험 정보 제공과 프로그램의 전술 강제는 구분해야 한다.** `RiskLayer`는 위험을 알려 주는 기능이 아니라 위험 점수로 후보 선택을 바꾸는 기능이다. 사용자님 원칙에 맞추려면 계산한 위험을 선택지 설명에 붙이는 것과 코드가 최종 행동을 고르는 것을 분리해서 결정해야 한다.

**여섯째, 관측 권한 차이가 비교 난이도를 크게 바꾼다.** 이 구현의 나무·타일 스캔은 게임 메모리의 넓은 범위를 직접 읽는다. 코어키퍼에서 사람에게 보이는 정보와 탐사 기억만 쓰려면 “현재 관측”, “과거에 보았음”, “추정”을 구분해 전달해야 한다. TerraBlind의 검색 범위 숫자를 그대로 가져오는 것은 같은 조건의 설계가 아니다.

**일곱째, 후보가 정해져 있어도 불확실함을 돌려줄 출구가 필요하다.** 벌목에는 `stop`이 실제로 연결되어 있어 사용자 제한을 만족하는 후보가 없을 때 상위 Agent로 반환할 수 있다. 막힘용 `Unknown`은 정의만 있고 Jev 연결은 없다. 전투에서는 정지 자체가 위험할 수 있으므로 어떤 유효한 행동·상위 요청으로 이어질지 별도 판단이 필요하다.

**여덟째, 완료·성공은 실행 후 사실로 판단해야 한다.** 벌목은 실제 아이템 증가량으로 완료하지만 광맥 루프는 타일 제거량을 먼저 센다. 전투도 “회피를 선택했다”, “방향키를 눌렀다”, “실제로 공격 범위를 벗어났다”, “피해를 받지 않았다”를 서로 다른 결과로 기록하는 것이 적절하다. 이 구분이 있어야 다음 모델 판단과 개선 평가가 잘못된 성공 신호에 의존하지 않는다.

## 9 확인 범위와 남은 한계

- 문서는 고정 커밋의 생산 호출을 따라 조사했다. 로그 포맷·질문 정의만 있는 코드를 실제 API 동작으로 취급하지 않았다.
- 벌목 요청 형식과 광맥 채굴 경로는 함수 연결로 추적했다. 실제 게임에서 네비게이션 성공률, 벌목 성능, 요청 latency, 응답 confidence 분포는 측정하지 않았다.
- `StuckScene`, `QuestionJson`, `FallCost.Json`의 준비된 형식은 참고 설계로 활용할 수 있으나 현재 연결되어 검증된 모델 기능의 증거는 아니다.
- 코드 내 API URL과 모델명은 해당 커밋의 구현 사실이다. 서비스의 현재 외부 API 계약이나 제공 상태를 검증한 문서는 아니다.
- 코어키퍼의 전투 구현·설정·기억 데이터는 변경하지 않았다.
