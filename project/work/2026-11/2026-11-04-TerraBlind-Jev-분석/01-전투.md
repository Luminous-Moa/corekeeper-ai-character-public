# TerraBlind 전투 관측과 Jev 선택지 구성

코어키퍼의 짧은 전투 행동과 판단 입력을 설계할 때 참고하기 위한 소스 분석이다. 기준은 TerraBlind `0859ca29aedea7bb48324c68eaece35b629c6d37`이다. 아래의 동작은 이 커밋의 실제 호출 경로를 정적으로 추적한 결과다. 게임에서 관측한 승률·지연·생존 성능을 뜻하지 않는다. 예시 숫자는 별도로 표시한 설명용 재구성이다.

가장 중요한 구분은 **보스, 일반 몬스터, PvP가 같은 판단기를 쓰지 않는다는 점**이다. 보스는 Jev가 이동을 고르고 코드가 사격·회복한다. 일반 몬스터 전투의 현행 두 경로는 주로 코드로 움직인다. PvP는 이동·무기·조준 가설·발사 여부를 묶어 Jev가 고른다. README의 옛 축별 질문이나 남아 있는 `JevCombat` 클래스를 현재 전체 전투 구조로 읽으면 틀린 결론이 된다.

## 1. 실제 실행 경로

| 경로 | 시작과 매 프레임 실행 | Jev의 결정 | 코드가 맡는 부분 |
|---|---|---|---|
| 보스 | `set_combat({boss_control:true})` 또는 모드 설정 → `StateSnapshotPlayer`의 `Dodge.Tick()`·`Combat.Tick()` | 완성된 이동 행동 하나 | 관측·위험 가공·행동 가능성, 조준·발사·회복, 이동 실행 |
| 일반 몬스터 자동 반격 | `Combat.Tick()`의 보스가 없는 갈래 | 현재 호출 없음 | 타깃 점수, Fight 고정, 무기 선택·연속 공격 |
| 일반 몬스터 `fight` 도구 | `AgentTools` → `FightCoordinator.Start()` → `FightCoordinator.Tick()` | 현재 호출 없음 | 24프레임 이동 위험 근사, 회피 후보 최솟값, 사선 확인·공격 |
| PvP | `combat_start`/`duel_player` → `PvpDuel.Start()` → `NativeAgent`의 `Update()`와 입력 훅의 `ApplyInputs()` | 이동×구체 무기×조준 가설×발사 여부의 결합안 | 후보·탄도 계산, 입력 실행, 사선·권한·무기 참조 재검사 |
| 원위치 PvP | `fight_player` → `PlayerCombat` | 없음 | 현재 위치에서 상대 중심을 조준하고 공격 |
| 옛 일반 전투 판단기 | `JevCombat : ICombatBrain`·`CombatBaseline` | 클래스에는 Fight/Ignore/Flee/WallOff/Heal 질문이 있음 | **현행 `Combat.Tick`에서 호출하지 않음** |

보스 모드의 활성화와 공격/회피 허가는 서로 다른 값이다. `boss_control`은 `Combat.Enabled`와 `Dodge.Enabled`를 켜지만 `AgentPermissions.Attack/Dodge`가 별도로 허용되어야 한다. PvP가 활성화되면 입력 훅은 PvP 쪽을 우선하고 일반 보스·자동 반격 경로를 건너뛴다. 매 프레임 실행은 게임 업데이트 기준이며 실제 벽시계에서 항상 60 Hz를 보장한다는 뜻은 아니다.

근거: [AgentTools 도구 연결][S1], [입력 훅 533행 이후][S2], [NativeAgent의 PvP Update][S3], [Combat.Tick][S4], [FightCoordinator][S5].

## 2. 보스 관측의 원자료와 수집 범위

### 2.1 화면을 읽는 것이 아니라 게임 객체를 읽는다

`GameSensor`는 `Main.npc`, `Main.projectile`, `Player`, `Main.tile`을 직접 조회한다. 이미지 인식이나 사용자의 화면 캡처를 거치지 않는다. 월드의 활성 NPC/투사체 배열에서 수집한 뒤 전송 단계에서 거리를 제한한다. 따라서 **화면 안에서 보이는 정보만 쓴다는 계약은 없다**. 어둠이나 벽에 가려졌는지로 보스 관측을 걸러 내지도 않는다.

좌표는 기본적으로 월드 픽셀, 속도는 픽셀/게임 프레임이다. 한 타일은 16픽셀이다. 모델용 JSON에서는 많은 수치를 타일과 타일/초로 바꾼다. X는 오른쪽 양수, 게임 Y는 아래쪽 양수지만 전송 필드 `speed_upward`, `cells_above_me`는 위쪽을 양수로 뒤집는다. `int` 변환으로 소수부를 버리는 값이 많다.

근거: [GameSensor 전체][S6], [DecisionFacts 직렬화][S7].

### 2.2 보스가 있는지와 공격 대상은 두 단계로 고른다

1. `Dodge.Boss()`는 보스 본체 또는 하드코딩된 보스 부위/Probe 중 플레이어에게 가장 가까운 것을 찾는다. 타일 좌표의 맨해튼 거리 `|dx|+|dy|`가 200 이하인 것이 대상이다. 이것은 회피 활성 여부와 우선 공략 문구에 쓰인다.
2. `GameSensor.Capture()`는 별도로 `npc.boss == true`인 활성 NPC를 모은다. 기본적으로 제곱 유클리드 거리가 가장 가까운 보스를 고르지만 **Spazmatism이 있으면 우선**한다. 이 스냅샷의 `Boss`는 실제 자동 사격 타깃이다.
3. `npc.realLife`가 보스 ID를 가리키거나 `BossPart(type)`에 등록된 NPC를 `Parts`에 추가한다. 몸통·꼬리·손·촉수·Prime 무기·Probe 등의 목록은 게임 데이터를 무조건 자동 발견하는 것이 아니라 일부 타입을 코드에 열거한 것이다.

따라서 가장 가까운 위협, 공략을 먼저 붙이는 보스, 사격 타깃은 같은 개체라는 보장이 없다. 보스 본체가 없으면 `Capture()`는 null을 반환한다. `BossBook`에 “손/작은 적부터 공격”이라는 문장이 있다고 해서 현행 `ProjectileAim`이 자동으로 그 타깃을 고르는 것은 아니다.

근거: [Dodge.Boss 88~109행][S8], [GameSensor.Capture 31~82행][S6].

### 2.3 수집 필드

| 원자료 | 실제 읽는 값 | 사용 목적 |
|---|---|---|
| 플레이어 | `Center`, `velocity`, `width/height`, `statLife/statLifeMax2`, `lifeRegen` | 상대 위치·속도, 충돌 크기, 체력, 지속 피해 여부 |
| 보스·부위 | `whoAmI`, `Name`, `Center`, `velocity`, `width/height`, `damage`, `life/lifeMax`, `realLife` | 위협·충돌 근사, 체력으로 단계 추정, 접촉 위험 |
| 최근 보스 속도 | 매 `Observe()`에서 최근 60 tick 이내 `(tick,speed)` 큐 | 현재 속도와 최근 1초 최고 속도 비교 |
| 투사체 | 활성/적대 여부, `damage`, `Center`, `velocity`, `width/height`, `extraUpdates` | 탄막 위험·충돌 예상 시간 |
| 이동 능력 | `AnyExtraJumpUsable()`, `wingTime>0`, 갈고리 장착/인벤토리, `miscEquips[3]` | 점프·비행·갈고리·수직 탈것 사용 가능 정보 |
| 사격 | `HeldItem.shootSpeed/shoot/useAmmo`, `PickAmmo`, 투사체 기본 정의 | 실제 탄약 반영 탄속과 자동 조준 |
| 지형 | 플레이어 Hitbox 주위 타일, 월드 크기 | 좌·우·위·아래 빈 공간, 이동 후보 제한 |

보스 속력은 유클리드 길이가 아니라 `(abs(vx)+abs(vy))*60/16`이다. 대각선 이동에서 일반적인 속력보다 크게 나온다. 투사체 속도는 `velocity*(extraUpdates+1)`로 보정한다. 한 게임 프레임 안에 여러 번 갱신되는 탄막을 과소평가하지 않기 위한 처리다.

`damage/currentHP`는 방어력·피해 감소·무적 시간까지 적용한 실피해 예측이 아니라 원시 피해값을 현재 체력에 대한 비율로 표현한 것이다.

### 2.4 지형 스캔

`ScanSolids(Player.Hitbox)`는 몸 너비/높이를 갖는 네 방향 띠를 최대 100타일까지 스캔한다. 처음 만나는 완전한 실체 타일과 Hitbox 사이 거리를 픽셀로 구한다. 다음은 벽으로 세지 않는다.

- 작동 해제된 타일(`IsActuated`).
- 플랫폼(`tileSolidTop`).
- 경사 타일(`Slope != 0`).
- 반 블록(`IsHalfBlock`).

못 찾은 방향은 1600픽셀이다. 모델용 `room`은 `clamp(min(실체 거리, 월드 가장자리 거리 - 40*16)/16, 0, 60)`의 정수다. **관측 최대 100타일과 모델에 보고하는 최대 60타일이 다르다.** 플랫폼까지 아래 거리는 별도로 수집하지만 현재 보스 `State()`에는 전송하지 않는다. 네 방향 띠 스캔이므로 대각선 경로 전체나 착지면을 보장하지 않는다.

근거: [GameSensor.ScanSolids 162행 이후][S9], [DecisionFacts.Room 170행][S10].

## 3. 보스 모델 입력의 정확한 구성

`GameSensor`의 스냅샷 전체를 그대로 보내지 않는다. `DecisionFacts.State()`가 다음 정보만 골라 JSON 문자열로 만든다.

| 전송 필드 | 의미·계산 |
|---|---|
| `hp_percent` | `Health*100/max(1,MaxHealth)` |
| `i_am_losing_health_over_time` | `lifeRegen<0` |
| `my_speed_to_the_right`, `my_speed_upward` | X 속도 및 부호를 뒤집은 Y 속도, 타일/초 정수 |
| `movement.can_double_jump`, `.can_fly` | 추가 점프·날개 잔량 여부 |
| `movement.has_hook` | 사용 가능한 갈고리 아이템 발견 여부 |
| `movement.vertical_mount` | `none`, `Slimy Saddle`, `Gelatinous Pillion` |
| `threats[]` | 보스·부위별 상대 위치·속도·체력·충돌 시간 |
| `incoming_projectiles[]` | 필터링한 최대 12개 탄막의 상대 위치·속도·충돌 시간·피해 비율 |
| `room.left/right/above/below` | 0~60타일 공간 |
| `boss_notes` | 현장 보스별 공략을 JSON처럼 구성한 **문자열** |

### 3.1 보스·부위 축약

`Bosses.Concat(Parts)`를 **Name별로 묶고 플레이어에게 가장 가까운 개체 하나만 남긴다.** 이후 맨해튼 거리 200타일 이하만 보낸다. 각 항목의 필드는 다음과 같다.

`id`와 `name`은 둘 다 이름 문자열이다. 실제 `whoAmI` ID는 이 배열에서 노출하지 않는다. 그 밖에 `health_percent`, `contact_damage_percent_of_my_hp`, `cells_to_my_right`, `cells_above_me`, `speed_to_the_right`, `speed_upward`, `speed_cells_per_second`, `top_speed_in_the_last_second`, `frames_until_it_hits_me`를 보낸다.

장점은 같은 이름의 많은 몸통 때문에 입력이 커지는 것을 줄이는 것이다. 대가는 **가장 가까운 몸통과 가장 빨리 충돌할 몸통이 다를 수 있는데도 하나만 남긴다**는 점이다. 이 손실은 구조상 가능하며, 실제 패배 원인인지는 별도 검증이 필요하다.

### 3.2 투사체 필터

수집한 모든 활성 적대·양수 피해 투사체에 대해 다음 순서로 필터링한다.

1. 충돌 시간 계산값이 0 이상이거나, 현재 거리 30타일 이내여야 한다.
2. 이미 겹쳐 있거나, 거리 96픽셀(6타일) 이내이거나, X/Y 중 한 축에서 플레이어 쪽으로 움직여야 한다.
3. 충돌 시간이 작은 순으로 정렬한다. 충돌하지 않는다고 계산된 항목은 뒤로 보낸다.
4. 앞의 12개만 남긴다.

개별 탄막은 이름, 현재 HP 대비 피해 비율, 상대 타일 좌표, 타일/초 속도, 충돌 예상 프레임을 보낸다. 가까운 탄막을 배열 인덱스 순으로 자르는 것보다 위험 우선순위를 반영하지만, 13번째 이후 위협과 필터 밖의 탄막은 모델이 직접 읽지 못한다. 후보 설명의 탄막 밀집도 계산은 별도로 **스냅샷 전체 투사체**를 사용한다.

### 3.3 충돌 예상 시간 계산

보스와 투사체 모두 `FramesUntilContact(entity,player)`를 사용한다.

```text
dx = enemy.x - self.x
dy = enemy.y - self.y
gapX = abs(dx) - (enemy.width + self.width)/2
gapY = abs(dy) - (enemy.height + self.height)/2
relativeVelocity = enemy.velocity - self.velocity
closeX/closeY = 각 축에서 간격을 줄이는 상대속도

두 축의 gap이 모두 <=0: 0
각 축:
  gap<=0: 축 도달시간=0
  close>0.1: 축 도달시간=gap/close
  그 외: 충돌하지 않는다고 판단
결과 = max(축 도달시간 X, Y)
600프레임 초과 또는 한 축이 불가능: "not heading at me"
그 외: 정수 프레임
```

**정밀 swept AABB 충돌 판정은 아니다.** 한 축에 진입할 때 다른 축에서 이미 빠져나갔는지(이탈 시간)를 비교하지 않는다. 이미 겹쳐 있는 축을 0으로 놓고 이후의 이탈도 고려하지 않으므로 실제로 스쳐 지나갈 경로에 충돌 시간을 붙일 가능성이 있다. 가속·궤도 변화·보스의 다음 돌진·유도탄·지형 충돌 역시 모델링하지 않는다. 요청 프롬프트도 현재 속도 유지라는 가정을 명시한다.

근거: [DecisionFacts.State][S7], [FramesUntilContact 206행 이후][S11].

### 3.4 수집하지만 보스 모델에 보내지 않는 것

`CombatSnapshot`에는 `Sequence`, `Tick`, `PreviousIntent`, `PreviousDurationMs`, `WeaponName`, `ShotSpeed`, `ShotProjectileType`, `CanDash`, `PlatformDistanceBelow`도 있다. 그러나 현행 `DecisionFacts.State()`는 이 항목들을 직렬화하지 않는다. 일부는 실행·후보 생성·조준에서 쓰고, 일부는 현재 경로에서 사용되지 않는다.

특히 보스용 질문에는 **이전 행동의 실제 결과·지속 시간, 관측 시각, 선택한 무기, 예상 도착 시각을 포함하는 명시적 행동 이력**이 없다. DPS·피격·디버프·전투 요약을 로그로 기록하는 코드가 존재하지만 그 로그가 자동으로 보스 Jev 입력에 들어가는 것도 아니다. 코어키퍼에 이 구조를 참고할 때 ‘이미 모든 실시간 피드백을 전달한다’고 가정하면 안 된다.

근거: [스냅샷 계약][S12], [전송 필드][S7], [Dodge의 DPS·피격 로그][S13].

## 4. 보스 선택지 생성과 설명

### 4.1 방향과 수단을 결합한 후보

`GameMovement.AvailableActions()`는 수평 5종 × 수직 6종의 조합에서 출발한다. 정지까지 이론상 30개이고, 조건에 따라 더 줄어든다.

| 축 | 기본 후보 | 뜻 |
|---|---|---|
| 수평 | 없음 / Left Small / Left Medium / Right Small / Right Medium | Small은 보통 이동, Medium은 갈고리 이동 |
| 수직 | 없음 / Up Small / Up Medium / Up Large / Down Small / Down Large | Up Small은 점프·추가 점프, Up Medium은 갈고리, Large는 수직 탈것, Down Small은 하강·플랫폼 통과 |

예: `LeftSmallUpLarge`, `RightMedium`, `DownLarge`, `Stay`. 현재 질문은 예전의 ‘Away/Hold/Near’, ‘Rise/Level/Drop’를 따로 고르는 형식이 아니라 **완성된 행동을 하나 선택하는 `action` 질문**이다. 타입에 `Dash`가 남아 있어도 현재 후보 생성은 모두 `false`이고 보스 질문에 대시 선택지가 없다.

### 4.2 이동 후보를 제거하는 규칙

1. `Blocked()`가 해당 방향에 공간이 부족하다고 판단하면 제거한다.
2. `Up/Down Large`는 지원 수직 탈것이 있어야 한다. 지원 대상은 Slimy Saddle와 Gelatinous Pillion이다.
3. 내려가는 탈것과 수평 갈고리는 같이 허용하지 않는다.
4. 갈고리 행동은 방향에 걸 수 있는 타일이 있어야 한다. Up Large는 갈고리 없이도 남을 수 있으나, 수평 Medium이 있으면 실제 갈고리 지점이 필요하다.
5. `Stay`는 처음부터 항상 포함한다.

추가 점프·날개가 없는 상태라는 이유만으로 Up Small을 모두 제거하지는 않는다. 후보에는 목적과 수단이 섞여 있고, 실제 수행 가능성과 이동량은 실행 때 다시 달라질 수 있다.

### 4.3 안전 여유를 포함하는 경계 필터

보스용 `reserveScale=1`일 때 픽셀 단위 여유 거리 계산은 다음과 같다.

```text
horizontalReserve = max(35*16, abs(vx)*60*1.2)
                    + max(0, 요청수평방향*vx)*18
upperReserve      = max(18*16, max(0,-vy)*60*0.6)
                    + 5*16 + max(0,-vy)*18
lowerReserve      = 4*16
```

수평/상단 여유에 `reserveScale`을 곱하고, 아래쪽 실체 타일 거리와 비교하는 `4*16`에도 배율을 곱한다. 지형 또는 월드 경계가 해당 한계 안에 있으면 이동을 막는다. **월드 가장자리의 40타일 여유는 배율을 적용하지 않는다.** 특히 아래 월드 경계 조건은 `(4+40)*16` 그대로이며 전체 44타일에 배율을 적용하지 않는다. 즉 이것은 ‘충돌하기 직전에 멈춤’만이 아니라 **벽에 몰리지 않도록 35타일 수준의 공간을 사전에 확보하는 정책**이다. 좁은 공간에서는 행동 목록을 크게 줄일 수 있다. PvP는 같은 실행기에 `.075`를 주어 배율 적용 대상인 여유만 줄인다.

코어키퍼에서 ‘모델이 전술을 정하고 코드는 물리적 가능성만 보장한다’는 원칙을 유지한다면 이 부분은 그대로 옮길 구현이 아니라 정책 선택 사항이다.

### 4.4 갈고리 지점 수집

장착 슬롯과 인벤토리에서 갈고리 투사체 타입을 찾고 타입별 사거리를 얻는다. 일반 타입은 사거리 표, 모드 투사체는 `GrappleRange()`를 사용한다. 수평 갈고리는 수평 및 기울기 -0.35/+0.35의 세 광선을, 수직/대각 갈고리는 해당 방향 광선을 4픽셀 간격으로 탐색한다. 활성 실체 타일 또는 광산 수레 레일을 만나고 거리 6타일 초과면 후보 지점으로 삼는다. 탐색 순서상 먼저 발견한 점을 쓴다.

이것은 갈고리가 실제 도달할 때까지의 충돌·타일 변화를 완전히 보장하는 시뮬레이션이 아니다. 실행 시 저장 지점의 방향·거리·타일 유효성을 다시 확인하고 필요하면 새 지점을 찾는다. `HookRange`의 알려지지 않은 기본 타입 fallback은 2500픽셀이므로 모든 타입의 정확한 사거리라는 뜻도 아니다.

근거: [후보·경계 규칙 17~86행][S14], [갈고리 탐색 378행 이후][S15].

### 4.5 후보마다 붙이는 미래 설명

`DecisionFacts.Describe()`는 동작 이름만 보내지 않고 다음을 문장으로 설명한다.

- 방향과 약 0.6초 동안의 예상 변위.
- 주변 각 보스·부위와의 거리 변화 경향.
- 그 경로의 탄막 밀집도.
- 안전 여유를 제외한 남은 수평·수직 공간.
- 갈고리 타깃 거리와 걸린 뒤 점프로 해제한다는 실행 의미.
- 수직 탈것의 상승·하강과 조향 성질.

예상 변위는 실제 플레이어 물리를 매번 적분한 값이 아니다. 수평 Small은 ±12타일, Medium은 ±20타일로 고정한다. 수직 기본값은 위 10/아래 18타일, Large는 위 18/아래 22타일이며 수직 여유 공간으로 제한한다. 수평 변위는 이 함수에서 남은 공간으로 직접 clamp하지 않는다. 후보를 앞 단계에서 거르기는 하지만 실제 이동 가능 거리와 설명 숫자는 여전히 근사다.

거리 경향은 70타일 안 보스·부위 각각에 대해 다음을 계산한다.

```text
selfAfter = selfPosition + 예상변위
enemyAfter = enemyPosition + enemyVelocity*36
afterDistance - currentDistance > 5타일  → opens space
afterDistance - currentDistance < -5타일 → closes space
그 외                                    → little separation change
```

여기는 이름별 축약 전 `Bosses.Concat(Parts)` 전체를 대상으로 하므로 위협 배열과 정보 집합이 다르다.

탄막 경로 설명은 다음 근사다.

```text
r = projectilePosition - selfPosition
v = projectileVelocity - 예상변위/36
t = |v|²<0.01 이면 36, 아니면 clamp(-dot(r,v)/|v|², 4, 36)
|r+v*t| < 10타일이면 exposed 개수 +1
0개 → clear / 1~2개 → exposed / 3개 이상 → crowded
```

탄막과 몸의 실제 Hitbox 충돌이 아니라 **10타일 반경의 근접 개수**다. 공격력 가중치도 없고 궤도 변화도 반영하지 않는다. 가장 가까운 접근 시간이 4프레임 미만이어도 4로 밀리므로 매우 임박한 위험의 설명은 별도 `frames_until_it_hits_me`와 함께 읽어야 한다.

근거: [DecisionFacts.RouteDescription 91~136행][S16].

## 5. 보스 공략 지식을 제공하는 방식

`BossBook`은 NPC 타입을 키로 한 개발자 작성 텍스트다. 부위 타입을 본체의 공략으로 매핑하고, 현장 보스마다 하나씩 중복을 제거해 모은다. 가장 가까운 보스/부위의 공략을 먼저 넣는다. 설정에서 이름으로 보스 공략을 바꾸거나 끌 수 있고 `UseKnowledge`로 공략 주입 대조 실험도 가능하다.

문장에는 단순 소개뿐 아니라 행동 지침이 있다. 쌍둥이는 Spazmatism 우선, 위험 거리, 50% 체력 단계, 돌진 시작 위치를 향한다는 설명, 두 눈의 위치를 모두 고려하라는 지침이 들어간다. 플랜테라는 단계별 선회/이격 지침이 있다. Wall of Flesh 설명에는 평평하게 준비한 영상용 경기장을 전제하는 문장도 있다.

따라서 이 시스템의 일반화는 ‘아무 보스나 이름만 주면 대응’이 아니라 **범용 관측·행동 + 사람이 정리한 보스 지식**에 가깝다. 공략이 없는 보스도 일반 위협 정보는 받을 수 있지만 같은 수준의 대응을 보장하지 않는다. 공략 문구 자체를 게임의 확정 규칙으로 검증한 문서는 아니며, 여기서는 주입하는 입력으로 분석한다.

근거: [BossBook 기본 지식][S17], [공략 설정·현장 수집 189행 이후][S18].

## 6. 보스 요청과 응답 처리

### 6.1 전송 형태

`POST https://api.typesafe.ai/v1/systemone`, 모델 문자열은 `jev-latest`, HTTP timeout은 5초다. 인증키 값은 본 문서에 포함하지 않는다. 요청은 대략 다음 모양이며 **보스 요청의 `state`는 JSON 객체가 아니라 JSON을 담은 문자열**이다.

```json
{
  "model": "jev-latest",
  "state": "{\"hp_percent\":70,\"movement\":{...},\"threats\":[...],...}",
  "questions": {
    "action": {
      "type": "choice",
      "instructions": "한 반응 구간에 실행할 완성된 회피 행동을 고른다. ...",
      "criteria": {
        "Stay": "...",
        "LeftSmall": "...",
        "LeftSmallUpLarge": "..."
      }
    }
  }
}
```

위 JSON은 설명용 축약이며 실제 캡처가 아니다. 프롬프트의 요지는 모든 부위·탄막의 진행 방향과 도달 시간을 고려하고, 현재 속도 유지 가정을 이해하고, 체력으로 단계와 공략을 해석하며, 벽·다른 위협을 피할 퇴로를 남기라는 것이다. 행동은 다음 응답까지 계속된다고 명시한다.

### 6.2 요청 주기와 프레임 제어

- `Task.Run` 안에서 HTTP를 호출하고 게임 주 스레드는 기다리지 않는다.
- `_busy`로 하나만 진행하며 응답은 `_pending`으로 전달한다.
- 응답 처리 뒤 실행 가능한 상태이면 즉시 다음 요청을 시작한다. 현행 코드에 ‘항상 300ms마다 호출’이라는 고정 간격은 없다. 300ms 상수는 무작위 대조군에 있다.
- 요청 때 `Sequence`, 전송 시각, 후보 이름→행동 사전, 상태 문자열을 캡처한다.
- 기다리는 동안 마지막 적용 행동을 매 tick 실행한다. 모델은 매 프레임 버튼을 직접 보내지 않는다.

### 6.3 응답 검사

다음 응답은 버린다.

1. 시퀀스가 이미 적용된 것 이하.
2. 요청 시각이 최근 `Release()` 시각 이하.
3. 요청 후 1500ms를 초과해 도착.
4. `action.choice`를 읽지 못했거나 요청 당시 후보 사전에 없는 이름.

받아들인 응답은 행동과 시퀀스를 바꾸고 적용 시각을 갱신한다. `confidence`와 `probabilities`는 로그·HUD·채팅에 사용하지만 **현행 보스 경로에는 confidence 하한으로 거부하는 조건이 없다**. 옛 `JevCombat`의 0.6 하한을 여기에 적용했다고 설명하면 잘못이다.

보스 응답은 `Seg/Field`라는 손 파서로 읽는다. 중괄호 깊이와 문자열 찾기에 의존하며 JSON 문자열 내부의 중괄호·escape를 완전하게 파싱하는 일반 JSON 파서는 아니다. 현재 기대하는 제한된 형식에는 맞지만 코어키퍼의 새 프로토콜에 그대로 복제할 이유는 없다.

HTTP 오류나 파싱 실패 후 이전 행동이 최근이면 계속 쓰고, 마지막 적용 시각에서 1500ms가 지나면 이동을 해제한다. 이것은 자동으로 더 안전한 방향을 새로 고르는 fallback이 아니다. 사격은 별도 코드이므로 이동 해제와 같은 시점에 모든 공격이 중지되는 구조도 아니다.

근거: [요청 Body·Fire 445행 이후][S19], [Parse 514행 이후][S20], [Tick·Drive][S8].

## 7. 보스 행동 실행과 자동 공격

### 7.1 매 tick 달라지는 실행

`GameMovement.Apply()`는 요청 때의 행동을 버튼으로 번역하되 지금 지형과 장비를 재검사한다.

- 현재 네 방향 벽 거리를 다시 측정하고 막힌 수평/수직 성분은 0으로 만든다.
- 탈것이 사라졌으면 강도를 낮춘다. 탈것 중 수평 갈고리 조합도 낮춘다.
- 갈고리는 요청 sequence당 한 번 발사한다. 45tick 동안 걸리지 않으면 해제한다.
- 걸린 뒤 다음 tick 이후 점프로 끊어 이동을 이어가고, 해제 뒤 2tick cooldown을 둔다.
- 수동 갈고리가 이미 걸려 있으면 자동 행동을 보류한다.
- 상승 탈것은 위쪽 속도가 -4px/frame 이하일 때 탑승하고 정점에서 내린다. 하강 탈것은 하강이 끝나면 내린다.
- 점프 누르기/떼기, 추가 점프의 재입력도 코드가 처리한다.
- `ActionResult`에 요청 행동, 실제 적용 행동, 조정 이유를 담아 로그로 남긴다.

즉 Jev는 ‘왼쪽 위로 큰 이동’ 같은 완성된 수단을 선택하지만, 갈고리 latch·점프 cancel·탈것 탑승 타이밍은 코드의 운동 제어다. 코어키퍼에서도 이 두 수준을 분리하면 모델의 1회 선택이 실제로 무엇을 보장하는지 명확해진다.

**스냅샷 결합 주의:** 보스 `Drive()`는 응답에 딸린 고정 스냅샷이 아니라 전역 `_snapshot`에 `_appliedSequence`만 덮어 실행한다. `Tick()`은 응답을 받은 직후 다음 요청의 `_snapshot`을 먼저 만들 수 있다. 따라서 후보 이름→행동 검증은 원래 요청 사전으로 하더라도, 실행 시 갈고리 지점·능력은 더 최신 스냅샷 후보에서 다시 찾을 수 있다. 이는 코드상 데이터 흐름이고 실제 오동작 여부는 검증되지 않았다. PvP는 별도 `requestSnapshot/appliedSnapshot`으로 구분한다.

근거: [GameMovement.Apply 108행 이후][S21], [Dodge.Drive 209행][S22].

### 7.2 자동 무기 선택과 사격

보스가 있을 때 `Combat.Tick()`은 일반 타깃/무기 점수 경로로 내려가지 않고 `Dodge.TryAttackBoss()`를 부른다.

- 체력이 최대 HP의 50% 미만이거나 용암에 잠겼으면 `QuickHeal()`을 시도한다. 포션 가용성과 게임 cooldown 때문에 매 호출마다 회복이 성공한다는 뜻은 아니다.
- `ProjectileAim.SelectFirstWeapon()`은 처음에 핫바 0~9에서 양수 피해, 사용 가능 스타일, 곡괭이/도끼/망치가 아닌 첫 무기를 선택한다. 보스전 종료 시에도 자동 선택한 슬롯을 계속 들고 있고 원래 슬롯 기록이 유효할 때 이전 슬롯을 복원한다. 중간에 사용자가 다른 슬롯으로 바꾸면 자동 슬롯 기록을 해제하므로 복원을 생략한다.
- 매 공격 tick에 새 스냅샷을 얻어 목표의 현재 위치·속도와 현재 탄속으로 조준한다.
- 사격 투사체가 없거나 탄속이 0 이하이면 `TryAttack()`은 false다. 따라서 현행 이 보스 사격기는 모든 근접 무기를 지원한다고 볼 수 없다.
- 일반 탄은 선형 요격식으로 미래 조준점을 구한다. Dart Pistol은 발사 원점의 작은 오프셋을 보정한다.
- 갈고리를 발사하는 상태에서는 공격을 잠시 하지 않는다. 발사 가능하면 마우스 좌표와 `controlUseItem=true`를 설정한다.

요격식은 `|d+v*t|=shotSpeed*t`이다. `a=dot(v,v)-s²`, `b=2dot(d,v)`, `c=dot(d,d)`의 이차방정식에서 양수인 가장 작은 근을 고른다. 해가 없거나 시간이 유효하지 않으면 발사하지 않는다. 현행 `Port.Intercept`에는 옛 일반 `Combat.Lead`의 **45프레임 상한이 없다**. 중력·유도·반사·장애물 사선도 이 보스 조준 함수는 검사하지 않는다.

근거: [Dodge.TryAttackBoss][S23], [ProjectileAim][S24], [Intercept][S25].

## 8. 보스 한 번의 판단이 실행되는 예

다음은 실제 로그가 아닌 정적 경로 설명이다. 플레이어 오른쪽에서 보스가 접근하고, 왼쪽에는 갈고리를 걸 표면이 있으며, 투사체가 지나간다고 가정한다.

1. 입력 훅이 `Dodge.Tick()`을 호출한다. 허가·생존·수동 입력을 확인하고 200타일 안 보스/부위를 찾는다.
2. `GameSensor.Capture()`가 플레이어와 모든 활성 보스·부위·탄막을 읽고, 플레이어 주위 벽 거리 및 갈고리·탈것 능력을 수집한다.
3. `State()`가 이름별 가까운 위협과 위험 우선 12개 탄막을 골라 상대 위치·속도·충돌 프레임으로 바꾼다.
4. `AvailableActions()`가 지형 여유와 실제 갈고리 타깃을 검사해 `LeftSmall`, `LeftMedium`, `LeftSmallUpLarge` 등의 후보를 만든다.
5. 각 후보에 .6초 변위, 보스와의 이격 경향, 탄막 경로 분류를 붙여 하나의 choice 요청을 보낸다.
6. 응답이 `LeftMedium`이라면 원래 후보 사전에 있는지와 요청 나이를 검증한다. confidence는 기록한다.
7. 매 tick 실행기는 왼쪽이 여전히 열렸는지 확인하고 갈고리를 발사하고, 걸리면 점프로 해제한다. 변경이 필요하면 이유를 기록한다.
8. 사격 경로는 별도로 새 위치를 읽어 자동 조준·발사한다. 다음 Jev 요청은 이전 HTTP가 끝난 뒤 다시 진행한다.

이 예에서 ‘왼쪽이 상대적으로 낫다’는 최종 선택은 Jev가 하지만, ‘왼쪽 후보가 있는가’, ‘갈고리 지점은 어디인가’, ‘얼마나 거리가 벌어질 것 같은가’, ‘실제 버튼은 언제 누르는가’는 코드가 정한다.

## 9. 일반 몬스터 경로와 옛 JevCombat 구분

### 9.1 자동 반격 Combat

현행 `Combat.Tick()`에는 “목표가 있으면 공격하고 Jev에게 묻지 않는다”는 코드와 주석이 있다. 보스가 없으면 가까운 적을 고르고 `CombatAct.Fight`, confidence 1로 만든다. 배치 작업 중에는 공격을 보류하고, 그 외 입력 소유권은 회수해 공격할 수 있다.

일반 적 범위는 기본 30타일 맨해튼 거리다. 타깃 점수는 다음과 같다.

```text
score = (npc.damage/max(1,currentHP))*100/(distance+1)
        + (abs(npc.vx)+abs(npc.vy))*2
        + SkeletronHand이면100
```

공격은 순수 무기 핫바를 고르고, 탄속으로 선형 요격을 계산하되 45프레임으로 외삽을 제한하며, 아이템 애니메이션이 끝날 때 공격 입력을 누른다. 이 경로에 남아 있는 보스 분류·타깃 선택 코드의 일부는 앞의 `BossOnField()` 조기 반환 때문에 현행 보스전 주 경로가 아니다.

`ThreatScan.Json`은 이름·피해·현재 HP 대비 피해·속력·거리·비행 여부·벽 가림·보스 여부를 만든다. 그러나 이 함수가 있다는 사실은 현행 일반 전투에서 Jev에 보낸다는 근거가 아니다. `Combat`에서는 로그 상태에도 사용된다.

### 9.2 fight 도구의 코드 기반 회피

`FightCoordinator`는 `fight`나 재료 수집 중 적 처치에서 사용한다. 가장 가까운 허용 NPC 타입을 대상으로 핫바 무기를 선택한다. `AgentPermissions.Dodge`가 켜져 있으면 다음 여섯 후보를 코드가 평가한다.

`(-1,0,+1 수평 방향) × (점프 안 함/점프)`이며 공중에서는 새 점프 후보를 제외한다.

각 후보는 24프레임 동안 플레이어 수평 가속·최대 속도·점프 유지·중력을 근사하고 `Collision.SolidCollision`로 지형 충돌을 검사한다. 적/탄막은 현재 속도 유지로 전진시킨다. 탄막에는 `extraUpdates+1`을 반영한다.

- 최초 이동 비용 .01, 점프 비용 .02.
- 시작 시 사선이 막혔다면, 예측 프레임에서도 사선이 막힌 동안 매 프레임 +1.
- 몸/탄막이 겹칠 것으로 계산되면 `(25-frame)*100` 추가. 빠른 충돌을 더 크게 벌한다.
- 탄막 충돌 여유는 6픽셀, NPC 접촉 여유는 4픽셀이다.
- NPC는 600픽셀 안의 적대·양수 피해 개체, 탄막은 활성 적대·양수 피해 전부를 수집한다.
- 가장 낮은 위험 후보를 골라 점프를 12tick 유지하고 이동 입력을 적용한다.

이 회피는 Jev 선택지가 아니다. 코어키퍼에서 이를 참고한다면 ‘모델에 후보 위험을 설명하는 계산’과 ‘코드가 위험 최솟값을 직접 선택하는 정책’을 구분해야 한다. 보스 `DecisionFacts`의 고정 .6초 변위보다 플레이어 물리를 더 구체적으로 근사하지만, 모든 게임 물리/특수 장비/플랫폼을 완전히 재현하는 시뮬레이터는 아니다.

### 9.3 남아 있는 옛 JevCombat

`JevCombat` 클래스 자체는 `jev-latest`, `state` 문자열, `act` choice(Fight/Ignore/Flee/WallOff/Heal), `interrupt_placement` noul 질문을 만든다. 무기가 Star Wrath라고 고정된 상태 설명도 있다. confidence가 0보다 크고 .6 미만이면 baseline으로 돌아가고, `interrupt_placement>0.7`이면 배치를 중단할 수 있게 한다.

그러나 소스 전체의 현행 호출 검색에서 `new JevCombat()`나 `JevCombat.Decide()`를 사용하는 전투 루프는 확인되지 않았다. `Dodge`가 `JevCombat.Key()`를 쓰는 것은 키 로더 재사용이다. 옛 질문과 신뢰도 규칙을 현행 보스/PvP에 섞어 설명하지 않아야 한다.

근거: [Combat.Tick 193행 이후][S4], [ThreatScan][S26], [FightCoordinator.Evade 27행 이후][S5], [옛 JevCombat][S27].

## 10. PvP는 더 풍부한 결합 선택지 구조다

### 10.1 관측과 짧은 이력

`PvpDuel.Update()`는 활성 세션에서 매 tick 플레이어·상대·투사체를 관찰한다. 기본 단위는 픽셀과 픽셀/프레임이며 `perception.units`에 적힌다. 장착 무기, 양쪽 위치·속도·크기·HP, PvP/팀 여부, 아이템 사용 애니메이션/시간, 자신의 마나를 제공한다. 상대 마나는 null이다.

최근 180tick(60tick/s 기준 약 3초)의 `PvpHistory`는 다음을 저장한다.

- 양쪽 위치, 상대 속도, 양쪽 HP.
- 발사 입력이 켜진 프레임, 사선이 열렸다고 판단한 프레임.
- 자기 소유의 새 투사체 개수.
- 0.5픽셀 미만으로만 움직인 연속 프레임.
- 수평 방향 반전 횟수.

전송 이력은 6프레임마다 표본을 남기되 방향 반전 전후·수직 속도 부호 변화 전후·마지막 표본은 추가 보존한다. HP 증감과 투사체 생성은 보고하지만 **`confirmed_hits=null`**로 둔다. HP 감소를 자신의 명중 횟수로 속이지 않는 구분이다.

지형은 엔진 사선 검사, 첫 막힘 주변 타일 타입·경사·반 블록, 근처 발판 후보를 제공한다. 발판 후보는 X 오프셋 -12/-6/0/6/12타일 × Y -8/-4/0/4/8타일에서 아래 8타일까지 받침을 찾는다. 몸이 들어가고 상대에게 사선이 열리는지는 검사하지만 `reachability=unknown_not_a_computed_path`라고 명시한다. **서 있을 수 있다는 것과 거기까지 갈 수 있다는 것을 분리한다.**

상세 조회는 자신의 주변 65×41타일, 상대 주변 33×25타일 창을 run-length 형식으로 제공하지만 일반 Jev 요청의 `Perception(...,false,...)`에는 이 전체 타일 창이 없다.

근거: [PvpHistory][S28], [PvpSession.Perception][S29], [PvpTerrain][S30].

### 10.2 PvP 이동·무기·조준 후보

이동은 보스의 `GameMovement.AvailableActions()`를 재사용한다. 수평/상단 이동 여유와 아래쪽 실체 타일 여유에 `.075` 배율을 적용하지만, 월드 가장자리의 40타일 여유 및 아래 월드 경계의 44타일 한계는 그대로 둔다. 상대 플레이어를 보스 접촉 피해처럼 취급하지 않기 위해 기본 movement state의 `threats/boss_notes`를 제거한다. 설명도 ‘접촉 피해 회피’ 대신 사선·공격 거리·위치 확보를 고려하게 한다.

무기는 핫바 0~9만 실행 후보로 쓴다. 선호 슬롯부터 돌면서 빈 아이템, 양수 피해가 아닌 것, 사용 스타일 없는 것, 탄약 자체, 채굴 도구, 탄약 부족, 마나 부족, 플레이어/Agent 금지 규칙에 걸린 것은 제외한다. `noMelee=false`면 melee 후보, `shoot>0`면 ranged 후보가 될 수 있어 같은 아이템이 양쪽에 들어갈 수 있다. 동종 후보가 여러 개면 슬롯·타입·prefix로 구분한다.

모델에는 후보 무기별 `slot/name/damage/type/prefix`, `shoot_speed/projectile_type`, `can_attack_now`, `contact_reach_pixels`, `aims`를 보낸다. `damage`는 `GetWeaponDamage()`이며 상대 방어를 적용한 피해가 아니다. 인벤토리 0~49의 무기 목록도 맥락으로 제공하나 실제 선택 가능한 무기와는 다르다.

| 조준 가설 | 생기는 조건·계산 | 알려 주는 한계 |
|---|---|---|
| `body` | 현재 위치에 머문다고 가정 | 움직이면 빗나갈 수 있음 |
| `velocity` | 현재 속도를 계속 유지 | 갑작스러운 대시·반전 미예측 |
| `brake` | 최근 수평 반전이 있으면 추가, 6프레임까지만 진행 후 정지 가정 | 실제 미래 반전을 알아낸 것이 아님 |
| `landing` | 최근 4개 하강 표본으로 안정적인 가속도를 얻고 30프레임 내 받침 예측 가능 | 미래 점프·대시·모드 물리 미상 |
| `exit` | 현재 수평 진행 방향 12타일 내 실제 발판 끝 발견 | 상대가 그 끝을 넘을지는 모름 |

각 가설에 `clear`, `flight_frames`, `assumption`, `trajectory_source`를 붙인다. 단순 “조준 성공 확률 80%”처럼 검증되지 않은 확률을 만들어 주지는 않는다.

근거: [PvpDuel.Weapons·SolveShot][S31], [PvpDuel 후보 입력 구성 302행 이후][S32].

### 10.3 탄도와 사선 계산

탄약 기본 속도는 `PickAmmo()`와 `extraUpdates`로 보정한다. 발사된 자신의 화살은 개체 슬롯뿐 아니라 identity를 확인해 추적하고, 속도 변화로 중력과 중력 시작 지연을 추정한다. 관측된 화살 모델이 없으면 무기/탄약 기본 속도와 중력 0을 쓴다. 모든 무기의 특수 탄도를 재현하는 것은 아니다.

`PvpTactics.Solve()`는 비행 시간 2~90프레임을 0.5 간격으로 탐색한다.

```text
destination = 선택한 조준 가설에 따른 목표점
fallingTime = max(0, time-gravityDelay)
launchVelocity = (destination-origin - (0,gravity*fallingTime²/2))/time
abs(|launchVelocity|-shotSpeed) <= shotSpeed*0.025 이어야 함
```

각 1프레임 궤도 구간을 `Collision.CanHitLine` 4×4 probe로 검사해 막히면 제외한다. 먼저 발견된 유효한 해를 쓰고, 반환 조준점은 발사 방향 400픽셀 앞이다. 실제 공격 시 현재 상태로 해를 다시 계산한다.

근접 거리는 `max(32,max(item.width,item.height)*scale+self.width/2)+target.width/2`의 근사이며 현재 거리와 사선이 모두 맞아야 공격 가능으로 본다. 모든 무기 애니메이션의 실제 피해 Hitbox는 아니다.

근거: [PvpTactics.Solve][S33], [화살 관측과 Attack][S34].

### 10.4 후보 수를 64개로 제한하는 방식

`PvpTactics.Choose()`는 이동 × 무기 × 사선이 열린 조준 가설을 조합한다. 지금 닿지 않는 근접 후보는 제외한다. 이동마다 발사하지 않는 후보도 추가한다.

전체 조합이 많으면 다음 대표성을 먼저 확보하고 최대 64개로 줄인다.

1. 이동별 첫 후보 하나.
2. 무기별 첫 후보 하나.
3. 조준 가설별 첫 후보 하나.
4. 비발사 후보 하나.
5. `candidate_rotation`에 따라 나머지 조합의 시작점을 바꾸며 채움.

따라서 후보 축소는 위험 점수 상위64개 방식이 아니다. 다양성을 먼저 확보하고 순환시키는 방식이다. 열거 순서의 영향을 완전히 없애지는 못한다.

후보 ID는 `p0`, `p1`…이며 state의 `plans`가 `{move,weapon,aim,fire}`를 담는다. `questions.plan.criteria`는 각각 이동·무기·조준의 세부 facts를 state에서 보라고 안내한다. 보스 요청과 달리 **PvP의 state는 JSON 객체**이다.

### 10.5 PvP 요청 필드와 처리

state의 주요 최상위 필드는 `strategy`, `movement_options`, `weapon_modes`, `current_mode`, `directive`, `session`, `candidate_rotation`, `perception`, `captured_tick`, `movement_state`, `dx/dy`, `target_vx/vy`, `self_hp/target_hp`, `hp_change/target_hp_change`, `previous_move`, `movement_result`, `moved_pixels`, `aim_clear`, `trajectory_observed`이다. `Choose()`에서 `plans`, `plans_before_budget`를 추가한다.

directive에는 플레이어 목표, general/movement/weapon/aim/terrain/inventory 지침과 플레이어/Agent 제한을 넣는다. 플레이어 제한이 우선이며 무기 제한은 후보 생성/실행 양쪽에서 강제한다. 일부 제한은 프롬프트만이 아니라 코드의 실행 규칙이다.

요청은 같은 `systemone` endpoint와 `jev-latest`, 질문 `plan`, 형식 `choice`다. `answers.plan.choice`가 실제 plans에 있어야 한다. 일반 JSON 파서 `JsonNode`를 사용한다. **confidence는 로그에만 쓰며 임계값으로 행동을 거절하지 않는다.** HTTP timeout은 3초다.

응답 적용 때 directive revision이 요청 당시와 같은지 검사한다. 무기는 요청 당시 슬롯·타입·prefix와 현재 후보가 모두 맞을 때만 발사 의도를 적용한다. 오래된 무기 참조가 새 아이템을 쏘게 하지 않도록 막는다. 인벤토리나 지침 변경·죽음·외부 도구 작업은 진행 요청을 취소하고 필요 시 다시 샘플링한다.

보스의 1500ms 응답 TTL과 같은 나이 제한은 PvP 적용 경로에 없다. `choiceAge`를 계산하지만 동일한 TTL 거부 조건으로 쓰지 않는다. 대기 중 이전 의도를 유지하며, 요청 실패는 `jev_request_failed`로 대전을 종료한다. 조용히 원위치 사격 fallback으로 바꾸지 않는다. 상대/자신이 죽으면 복귀를 기다렸다가 이어가며, 거리/권한/접속 조건이 깨지면 중지한다.

실행은 고정 `appliedSnapshot`을 쓰되 추가 점프와 날개 가능 여부는 매번 갱신한다. 사격 조준은 현재 위치로 다시 풀고, 무기가 실제 장착되고 타입/prefix가 맞으며 사선이 열리고 갈고리 사용 중이 아닐 때 발사한다. 아이템 사용 중에는 무기 전환이 지연될 수 있다.

근거: [PvpTactics.Choose 47행 이후][S35], [PvpDuel.Update·ApplyInputs][S36], [PvpSession 취소·revision·도구 점유][S37], [PvpDirective][S38].

## 11. 코어키퍼 전투 개선에서 가져올 핵심

다음은 이 소스에서 도출한 설계 참고점이며 현재 코어키퍼의 확정 변경안은 아니다.

1. **관측과 해석을 구분해 보낸다.** 위치·속도·공격 상태·크기·관측 시각은 사실, 예상 충돌 시간과 경로 위험은 가정이 붙은 계산값이다. 어느 쪽이 틀렸는지 로그로 나눠 볼 수 있어야 한다.
2. **행동 후보의 실행 의미를 구체화한다.** ‘거리 벌리기’ 한 개보다 방향·짧은 지속 시간·실제로 실행할 수단과 예상 이동량을 알 수 있는 후보가 진단하기 쉽다. 실제 적용 결과와 조정 이유도 다음 판단에 돌려준다.
3. **위험도는 도착점뿐 아니라 이동 구간을 본다.** 다만 TerraBlind 보스의 .6초 고정 변위·10타일 반경 휴리스틱을 정답으로 복제하지 않는다. 코어키퍼의 실제 속도·공격 범위·전조·탄막으로 검증할 필요가 있다.
4. **이전 행동을 다음 요청에 연결한다.** 이 점은 보스보다 PvP 경로가 더 좋은 참고다. `previous_move`, 이동량, 사선, HP 증감, 짧은 속도 이력, 요청 시각/시퀀스를 함께 쓰면 ‘선택했지만 못 움직임’과 ‘움직였지만 판단이 틀림’을 나눌 수 있다.
5. **선택지 축소가 정보를 지우는 방식도 기록한다.** 이름별 가까운1개와 최대12탄막처럼 입력 예산을 관리하되, 근접순이 임박위험순과 같은지 검증한다. 생략 개수·최대 위험·선택 이유를 남기는 보완도 검토할 수 있다.
6. **공격과 이동의 결합을 별도 검토한다.** PvP처럼 이동하면서 원거리 공격할 수 있는 조합은 ‘공격 또는 회피’의 강제 양자택일을 줄인다. 코어키퍼의 모션·장비·입력 제약 안에서 실제 동시 실행 가능성을 먼저 확인해야 한다.
7. **안전 필터와 전술 결정의 경계를 사용자 원칙에 맞춘다.** 벽 여유 35타일, 자동 50% 회복, 코드 최저위험 선택은 모두 제품 정책이다. 후보의 물리적 가능성 검사와 같다고 설명하지 않는다.
8. **응답 신선도와 후보 참조를 묶는다.** 관측 sequence·요청 시각·후보 ID·실행 ID를 고정하고 응답이 어느 장면의 것인지 추적한다. 재검사로 행동이 바뀌면 requested/applied를 구분한다. 보스의 전역 snapshot 재사용과 PvP의 고정 snapshot 구분은 비교할 지점이다.

이 코드의 가치는 ‘Jev가 테라리아를 잘하므로 같은 입력을 주면 해결된다’가 아니라, **모델이 고르기 전에 어떤 관측·가공·행동 인터페이스를 준비해야 하는지 구체적으로 보여 준다**는 데 있다. 실제 성능은 다른 문서의 실사용 후기·제작자 시연 근거와 구분해서 판단해야 한다.
