# 연결 준비 상태 확인 — 통합 활동

기존 A 활동 `ACT-A-01`을 채택한다. 새 활동 ID나 화면요소를 만들지 않는다. 원본은 A/A4/inferences.md의 ACT-A-01이며 실제 요소는 A/A2/screens.md의 BRG-02와 BRG-03이다. 이 문서는 C-3 후 얻는 것과 한계를 보완한다.

운영자는 서비스를 사용할 준비가 되었는지 알기 위해 `/v1/health`에 GET한다. HTTP 상태 `BRG-02#1`은 경로가 응답했는지를, `ok`·`members`·`busy`(`BRG-02#2`, `#3`, `#4`)는 브리지가 보관한 현재 상태를 보여 준다. 응답 성공만으로 게임 동료의 접속·행동·캐릭터 저장이 준비되었다고 판정하지 않는다.

상태를 읽은 뒤 준비 완료의 근거가 있는지 판단한다. 이번 격리 환경은 전체 및 멤버별 `ok:false`였다. 이는 preflight를 하지 않은 빈 격리 환경의 응답이며 운영 계정의 설치·인증 실패를 뜻하지 않는다. A-3는 안내가 없어 스스로 `/`를 찾아갔지만 `BRG-03#1`의 404와 `BRG-03#2`, `#3`의 `ok:false`, `not found`만 얻었다. 루트 탐색은 실제 사용자의 시도이지 화면에서 안내한 이동이나 홈 화면이 아니다.

C-3 새 컨텍스트는 이 흐름 중 health GET을 다시 수행했다. `2026-11-05T10:12:15+09:00`의 HTTP 200·본문 원문은 C/C3/에 있다. 연결 도달과 보고값 읽기는 가능했고, 준비 완료는 확인되지 않았다. 다음 조치·필드 정의·원인 우선순위가 없어 복구 행동은 결정하지 못했다. 최종 활동의 얻는 것은 **응답 도달과 현재 보고값**까지다. 설치·로그인·사용량·설정 중 무엇을 고칠지는 이 화면만으로 얻지 못한다.

코드에서 읽는 의미는 별도 근거다. B 기준판의 preflight.mjs:59~72에서 `memberHealth`가 기존 `state`를 읽고 멤버 ok를 구성하며, `health`가 멤버 중 하나라도 ok인지와 `busy` 목록을 반환한다. 이 구현 해석을 사용자가 출력만 보고 알아들었다고 쓰지 않는다. 해당 설명을 제품 출력에 추가할지는 C/C4-반영.md의 미결이며 이번에는 변경하지 않았다.

다음 활동은 확정하지 않는다. 환경이 바뀐 뒤 재조회할 수 있다는 예상만 있다. 정상 사용으로 이동한 관측은 없고, 게임 화면 확인은 사용자 지시로 유예했다.
