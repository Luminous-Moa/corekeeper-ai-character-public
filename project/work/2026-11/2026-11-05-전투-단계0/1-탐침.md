### 1.2 ObjectPropertiesCD 해시

해시는 `CRC32("ChargeAttack/<이름>")`(부호 있는 int)다. 이번에 node로 다시 계산해 참고본 상수와 맞췄다.

- 참고본의 `ChargeAttackStateSystem`·`ChargeAttackStateRequest` 등이 `Get`/`Has`로 읽는 서로 다른 해시는 **38개**다.
  - 정적 조사 표의 35개에 더해 `hitDistanceInfront`(1313543880), `hitBoxHalfLength`(-859250850), `hitBoxHalfWidth`(-295879974)가 있다(`ChargeAttackStateSystem.cs:925-928`, 끝 공격 상자).
  - 정적 조사 본문의 "39개"와 하나 차이다. 어느 것을 세었는지는 확인하지 못했다.
- 종류별로 찍는다. float 24, int 2(`damage`, `tileDamage`), 회전 방식 enum 2, 있음 표시(Has) 10.
- 참고본이 읽지 않는 작성기 이름 4개도 있음 여부와 값을 찍는다(`extra`): `damageMultiplier`, `tileDamageMultiplier`, `steerTowardsTargetMaxAngleDeg`, `level`. 굽기 때 사라졌다면 `-`로 나온다.
- 값 줄에는 `Has`가 거짓이면 `(absent)`를 붙인다. 값 속성에 `Has`가 어떻게 답하는지는 실게임에서 처음 본다.

### 1.3 잴 것과 로그의 대응

| 잴 것 | 로그 | 계산 방법 |

## 2. 로그 형식

### 2.1 공통

- 파일 줄: `wall=<벽시계 ms> t=<Unity realtime 초, 소수 3자리> stk=<서버 틱> st=<서버 시간 초> [@<AI 이름>] <머리말> <내용>`
  - `t`는 Player.log(`t=…F1`)·결정 로그(`t=…F2`)와 같은 시계다. 그래서 `DECISION #… APPLY`, `SWITCH`와 바로 맞춰 볼 수 있다.
  - 숫자는 InvariantCulture(소수점 `.`).
- Player.log 거울 줄: 기존 `AIPlayerSpikeMod.Log` 형식 그대로다. `[AIPlayerSpike] t=… [@이름 ]BRUTE-PROBE <머리말> <내용> [wall=… t=… stk=… st=…]`.
  - 거울로 보내는 것: `ON`, `OFF`, `NEW`, `COMPS`, `PROPS`, `EVT`, `HIT`, `TILES-AFTER`, `GONE`, `PERF`, `MOVE-APPLY`, `MOVE-START`.
  - 보내지 않는 것: `TICK`, `MOVE-TICK`(틱마다 나오는 줄). Player.log는 줄마다 스택을 찍는 `Debug.Log`라 비싸다.
- 머리말: 야수 쪽은 `BRUTE-PROBE <종류>`, AI 쪽은 `MOVE-APPLY`·`MOVE-TICK`·`MOVE-START`.
- logshape의 감시 머리말(`WATCH`)에 이 머리말들은 없다. 켜 두어도 리팩토링식 모양 비교에 새 모양으로 잡히지 않는다.

### 2.2 모양 예시

아래 값은 형식을 보이려고 지어낸 것이다. 실측이 아니다.

```

… BRUTE-PROBE TILES-AFTER e=5123:1 charge state left (Chase); tiles here…
… @Claude MOVE-APPLY skill=거리 벌리기(keepaway:…) swingLeft=0.120 mid='swing' boundary=0 pos=(…) speed=0.00 serverInput=(0.00,0.00)
… @Claude MOVE-TICK +1 pos=(…) moved=0.000 along=0.000 speed=0.00 serverInput=(0.00,0.00)@16121 swingLeft=0.070
… @Claude MOVE-START skill=거리 벌리기(keepaway:…) applied t=812.004 stk=16120; server input changed +2tk/101ms to (-1.00,0.00); first move any +3tk/150ms; first move along input +3tk/150ms
… BRUTE-PROBE PERF 30s: probe 0.041ms avg/0.90ms max per frame over 3050 frames; server ticks sampled 600; brutes tracked 1; move traces open 0; lines 812
```

- `EVT`의 `|` 앞은 바뀐 것(`state a->b`, `phase a->b`, `connected 0->1`, `maxDamagePerHit a->b`, `cooldown …`)이다. 뒤는 그 틱의 전체 값이다. 처음 본 틱은 `-`에서 시작하는 EVT 한 줄이다.
- `TICK`은 `state=Charge`(모든 phase)인 동안 매 서버 틱이다. 틱이 건너뛰어졌으면(프레임이 두 틱 이상) `dTick=N`을 붙인다.
- `dDeg`는 앞 틱 `targetDirection`과의 각도 차(도)다.
- `MOVE-START`의 셋:
  - `server input changed`: 서버 플레이어의 `ClientInput.movementDirection`이 적용 전 값과 처음 달라진 틱이다. 멈춤(0)으로 바뀐 것도 센다.
  - `first move any`: 위치가 0.02칸 넘게 바뀐 첫 틱(방향 무관)이다.
  - `first move along input`: 새 입력 방향 성분으로 0.02칸을 넘은 첫 틱이다.
  - 끝 사유: 성공, `superseded by a new apply`, `the new input is no movement`(공격·먹기 등, 10틱 뒤), `no move along the new input within 2 s`.
- `PERF`: 탐침 자체의 프레임당 ms(평균·최대)다. 같은 30초 창의 기존 `PERF` 줄(fps, 프레임 p95/p99)과 함께 본다.

## 3. 스위치

- 기존 `AITestSwitches` 방식을 따른다. `AIPlayers\` 아래 파일이 있어야 켜진다. **`testcmds.on`이 있을 때만** 본다. 1초마다 확인한다(`Refresh` :102).

- 끄기: 둘 중 하나를 지운다. `BRUTE-PROBE OFF lines N` 뒤 파일을 닫는다.
- 탐침 안에서 예외가 나면 `ERROR bruteprobe: … turning off`를 남기고 스스로 꺼진다. 게임과 AI는 계속 돈다.
- `movetrace.on`(Claude만, testcmds 무관)과는 별개다. 함께 켜도 된다.

## 4. 스위치 꺼짐일 때 영향이 없다는 근거

1. **호출이 스위치 확인 뒤에만 일어난다(코드).**
   - `AIPlayerSpikeMod.cs:254` `AIBruteProbe.Frame(server)`: 첫 줄이 `Refresh(now)`(1초에 한 번 `File.Exists`)다. 다음 줄 `if (!On || _w == null) return;`(:182)에서 끝난다.

### 6.3 게임에서 (월드·순서)

**월드:** 리팩토링 실기와 같은 rftest(시드 917121490949, 새로 만들기)를 쓴다. 장면 C·D에서 블록을 놓으므로 기존 월드(ai2)는 쓰지 않는다. 끝나면 게임 안에서 rftest를 지운다(9-L2 5절).

**0. 시작 확인:**
- Player.log에 `Successfully compiled AIPlayerSpike`와 `BRUTE-PROBE ON -> …bruteprobe-….log`가 있다.
- 30초 안에 `BRUTE-PROBE PERF`가 나온다.

**A. 기준(탐침 켬, 야수 없음, 2분):**
- `/ai on`(Claude만)으로 둔다. 30초 PERF 4개를 받는다. 탐침 PERF의 `probe … ms avg`와 기존 PERF fps를 기록한다.
- 이어서 `bruteprobe.on`을 지우고 다시 PERF 2개를 받는다(켬/끔 비교). 그 뒤 다시 켠다.

**B. 컴포넌트·속성(1분):**
- `/ai claude arena go <x> <z>`로 Claude를 열린 굴 자리로 보낸다. 자리는 rftest에서 호스트가 고른 넓은 바닥이고, 좌표는 호스트 위치에서 읽는다. 이어서 `/ai arena spawn 1 MushroomBrute`.
- 1초 안에 `NEW`, `COMPS` 2줄, `PROPS` 2줄이 나와야 한다. 여기서 바로 확인한다:
  - `ChargeAttackStateCD=yes`인가.
  - `PROPS`의 `anticipationDuration`·`lockOrientationAtMultiplier`·`vulnerabilityDuration`이 0이 아닌가.
  - `hitTiles`가 있나.
- 이 줄들이 없으면 멈추고 원인(`ERROR bruteprobe`)을 본다.

**C. 자연 벽 앞 돌진 유도(3분 × 2):**
- `/ai off`로 Claude를 내보낸다. 야수의 대상을 호스트 하나로 만들기 위해서다.
- 호스트가 자연 벽(흙·돌 벽)을 등지고 선다. 야수와 5~7칸 떨어진 곳이다.
- 야수가 준비 자세를 취하면 벽을 따라 옆으로 2~3칸 비킨다(사람이 하는 것이 가장 확실하다).
- 자동화로 해야 하면 대체 방법을 쓴다: 호스트가 `ui\gkey.ps1`로 벽을 따라 A/D를 0.6초씩 번갈아 누르기를 3분 되풀이한다. 노린 방향이 고정된 뒤 호스트가 비켜 있으면 벽에 박힌다. 성공률은 낮다.
- 목표: `HIT … hitEntity=tile:wall…` 3번 이상. 정면(`dot<-0.34`)과 비스듬한 경우를 각각 1번 이상.
- 같은 장면에서 **헛돌진**(열린 쪽으로 비켜 아무것도 안 맞음)도 1번 이상 받는다. `phase Charging->End`이고 `connected`가 0인 경우다.

**D. 놓은 블록 앞 돌진 유도(3분 × 2):**
- **블록 놓기:**
  1. 호스트가 곡괭이로 주변 흙벽을 몇 칸 캔다. 흙벽 블록(`WallDirtBlock`)이 가방에 들어온다. 이미 있으면 생략한다.
  2. 단축칸에서 그 블록을 고른다.
  3. 열린 바닥에 서서 놓을 칸을 겨누고 오른쪽 클릭(사용)으로 놓는다. 일자로 3~5칸을 놓아 벽 하나를 만든다. 뒤가 다시 열려 있게 해서 자연 벽과 구분되게 한다.
  - 자동화: `ui\ui.ps1 gclick`으로 칸을 겨눠 오른쪽 클릭한다. 좌표는 `ui.ps1 shot` 화면에서 정한다.
  - 놓은 칸 좌표는 Player.log `HIT`의 `tiles ahead1/ahead2`로 확인한다. 놓은 블록의 tileset은 주변 자연 흙벽과 같을 수 있어 층 목록만으로는 구분이 안 된다. 그래서 놓은 좌표를 노트에 적어 둔다.
- 그 블록 벽을 등지고 C와 같이 유도한다.
- 볼 것:
  - `HIT`가 나오는가.
  - `hitEntity`의 종류.
  - `TILES-AFTER`에서 놓은 칸이 그대로인가(`hitTiles`가 켜져 있으면 깨질 수 있음).

**E. 전조 중 때리기(2분):**
- 호스트가 야수 바로 옆에서, 준비 자세가 보이는 동안 휘두른다.
- `EVT state Charge->TookDamage`가 나오는지, 아니면 `hp`만 줄고 phase가 이어지는지 본다. 2번 이상.

**F. AI와 함께(5분, 판단 → 이동 지연):**

### 6.4 화면 전조 시각 기록

- **방법:** C·D·E 동안 화면 캡처 고리를 돌린다. 가장 단순한 것은 PowerShell 한 프로세스가 게임 창 영역을 `CopyFromScreen`으로 초당 약 20장 저장하는 것이다(`ui\win.ps1`처럼 창 사각형을 구함).
  - 파일 이름은 캡처 직전 `DateTime.Now`의 `HHmmss_fff`.
  - 해상도는 1/2, JPEG로 저장한다.
  - 이 스크립트는 실행 차례에 만든다(지금은 없음). 녹화(OBS 등)를 쓰면 화면에 벽시계를 함께 띄워야 대조할 수 있다.
- **대조:**
  - 각 돌진의 `EVT phase …->StartCharging` 줄 `wall=`에서 그 전후 프레임을 본다.
  - 준비 자세가 처음 보인 프레임의 시각을 화면 전조 시각으로 적는다.
  - 차이 = 화면 − 서버다. 같은 방식으로 `->Charging`(달리기·먼지 시작)과 `connected 0->1`(부딪힘·화면 흔들림)도 잰다.
- **오차:**
  - 캡처 주기 약 50ms.
  - 게임 프레임(60fps면 17ms).
  - 표시 지연.
  - 캡처 자체의 부하(PERF로 같이 본다).

## 7. 확인 못 한 것

- **실게임 동작 전체.** 게임에서 컴파일되는지(Unity·게임 컴파일러), 값이 실제로 읽히는지는 아직 모른다. compile-check만 통과했다.
- `ObjectPropertiesCD.Has(해시)`가 값 속성(float/int)에도 참을 주는지 모른다. 거짓이면 `(absent)`로 나오지만, 값 자체는 `Get`으로 찍힌다. 게임 시스템도 같은 해시를 조건 없이 `Get`한다.
- `server.Time.ElapsedTime`을 시스템 밖(MonoBehaviour Update)에서 읽는다. 마지막 틱의 시간이라 남은/지난 시간이 한 틱(0.05초) 안쪽으로 어긋날 수 있다. 틱 사이 비교에는 `stk`·`wall`도 쓴다.
- 프레임이 두 틱 이상 걸치면 중간 틱은 못 본다(`dTick`으로 표시). 서버 20틱/초, 화면 30~120fps라 드물 것이다.
- 서버 플레이어의 `ClientInput`이 그 틱에 적용된 입력이라는 것은 movetrace와 같은 가정이다.
- 타일 체력(블록이 얼마나 깎였는지)은 읽지 않는다. 깨졌는지는 타일 층 목록으로만 본다. 놓은 블록과 자연 블록이 같은 tileset이면 층 목록으로 구분되지 않는다(좌표 노트로 구분).
- 플레이어 명중(판정 a)과 물리 충돌(판정 c)은 게임이 따로 표시하지 않는다. `hitEntity` 종류, 법선 내적, 대상 거리·체력 변화로 추정한다.
- 플레이어 공격 타이밍(`PlayerAttackCD.hitDelay/hitDuration`, 정적 조사 6절)은 이번 탐침에 넣지 않았다. 휘두르기는 모드의 `AIMotion.SwingLeft`로만 본다.
- 정적 조사의 "해시 39개"와 이번 38개(+작성기 이름 4)의 차이.
- Unity 컴파일 관문(5절 이유).
