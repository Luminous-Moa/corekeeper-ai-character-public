## 0. 요약

- **[사실] 토큰.** 같은 내용을 영어로 옮기면 입력 토큰이 실제 API `usage.input_tokens` 기준으로 **0.77~0.80배**가 된다. 표본 4개를 합치면 0.785배로, 약 21% 줄어든다.
- **[해석] 비용.** 이번 달 사용량($22.02)에 이 비율을 대면 약 $17.3이 되어 $4.7가 준다. 같은 속도로 30일을 쓴다고 하면 약 $132가 약 $104가 되어 월 $28쯤 준다.
- **[사실] 지연.** 토큰 1,000개당 지연이 약 5.7ms 늘어난다. 영어로 줄어드는 토큰은 호출당 약 490개이므로 지연은 약 3ms 준다. 중앙값 260ms에 비하면 1% 수준이라 무시할 만하다.
- **[해석] 선택 품질은 모름.** 영어/한국어 표본 4개에서 1순위 선택은 모두 같았다. 확률 분포는 달라졌다. 전투 표본 S3에서는 1순위 확률이 0.21에서 0.43으로 뚜렷해졌고, 비전투 표본 S1에서는 0.68에서 0.52로 퍼졌다. 이것만으로 어느 쪽이 낫다고 할 수 없다.
- **[사실] 깨지는 곳.** 모델에 가는 문장과 같은 문자열을 내용으로 판정하는 코드가 있다. 기술 끝 이유(Reason)에서 "길 없음", "막힘", "시간 초과", "도구 부족" 같은 말을 찾는 곳, `blocks.StartsWith("보이는 목표 품목 벽")` 등이다. 이 밖에 deaths.log 정규식, AIExpCore의 why 분류, 시험·로그 도구가 걸린다(3절). 같은 문자열을 게임 채팅·로그·위쪽 LLM 보고에도 쓰므로, 그대로 옮기면 사용자가 보는 문장도 영어가 된다.
- **[사실] 코드로 번역할 수 없는 한국어.** 남는 것이 많지 않다.
  - 호스트가 친 목표 품목 이름(`Goal.itemName`). 예: "나무", "흙벽 블록".
  - 디스크의 memory.json에 저장된 `baseBy` "호스트".
  - 브리지가 보내는 오류 detail(자유 시간 이유).
  - 한국어로 지은 플레이어 이름(있을 경우).
  - 호스트 채팅 원문과 위쪽 LLM의 이유 문장은 **Decisions 요청에 들어가지 않는다.**

### 1.6 코드로 번역할 수 없는 한국어

| 값 | Decisions에 들어가는가 | 경로와 비고 |
|---|---|---|
| 목표 품목 이름 `Goal.itemName` | **들어간다**(목표 줄) | `AIGoals.TryItem`(209~220행). 흙, 구리, 주석, 나무 네 가지는 코드에 적힌 한국어 이름("흙벽 블록" 등)이다. 나머지는 호스트가 `/ai goal`에 친 말이나 위쪽 LLM이 보낸 `goal.item` 토큰을 그대로 쓴다. 한국어 이름표나 게임 현지화는 없다. ObjectID 이름이 함께 붙는다 |
| 플레이어 이름 | **들어간다** | 게임 커스터마이즈 이름이다. 지금 호스트는 "Luminous"(영어). 한국어 이름이면 한국어가 남는다 |

| 브리지 오류 detail | **들어간다**(자유 시간 이유) | AIPlanner 526, recall-loop.mjs의 한국어 detail("모드가 연결을 끊음" 등) |

| 호스트 채팅 원문 | **들어가지 않는다** | AIPlanner와 브리지로만 간다 |
| 위쪽 LLM의 why/say/plan 문장 | **들어가지 않는다** | 종류, 품목, 개수만 `SetGoal`로 간다. 단 멈춤 이유 "위쪽 LLM이 멈춤"(코드 문구)은 `_recent`에 들어간다 |

## 4. 토큰 측정

### 4.1 방법
- **[사실]** `decisions-*.log` 12개에서 DECISION INPUT과 RESULT를 짝지어 20,601건을 뽑았다. 각 요청을 o200k_base(js-tiktoken)로 셌다.
- **[사실]** o200k로 센 input + instructions + 설명 + 선택지 값의 합과, 로그에 남은 실제 `tokens`의 차이는 거의 일정했다. 차이 = 약 93 + 2.5 × 선택지 수(평균 110, p90 121). 비율로는 평균 1.062배, p90 1.081배다. **o200k_base는 gpt-6-luna의 토큰 수를 사실상 그대로 맞힌다.** 표본 4개의 o200k 추정과 API 실측의 차이는 0~8토큰이었다.
- **[사실]** 표본은 4개다.
  - S1: 비전투, 나무 모으기, 선택지 11개(decisions-221936.log #117)
  - S2: 버섯 야수 근접전, 선택지 6개(decisions-182701.log #294)
  - S3: 버섯 야수 근접전, 선택지 22개(같은 로그 #678)
  - S4: 버섯(MushroomEnemy) 전투와 목표 진행, 선택지 14개(decisions-221936.log #125)
- **[사실] 번역 방법.** S1과 S2는 손으로 옮겼다. S3과 S4는 같은 문구를 표로 만들어 바꾼 뒤 한국어가 남지 않았는지 확인했다. 직역 쪽으로 옮겨서 영어 문장이 조금 길다. 다듬으면 영어 쪽이 더 줄 수 있다.

### 4.3 비용 어림
- **[사실]** decisions-usage.json(2026-11, 11-05 23:11까지): 96,679회, 220,221,038토큰, $22.02. 호출당 평균 2,278토큰. 캐릭터별로는 Claude $15.35, Gemini $2.83, ChatGPT $1.89, Grok $1.78. 월 상한 설정은 $200이다.
- **[해석]** 0.785배를 대면 다음과 같다.
  - 이번 달 지금까지: $22.02 → **$17.29**(−$4.73)
  - 11-01~05와 같은 속도로 30일을 쓴다고 하면(시험 기간이라 실제와 다를 수 있음): 약 $132 → 약 **$104**(−$28/월)
  - 호출 1회: 약 −490토큰, 약 −$0.000049
- **[해석]** base-s3에서 설명이 길어지는 만큼 영어화로 아끼는 금액도 그에 비례해 커진다. 비율은 비슷하게 유지될 것으로 본다.
- **[사실]** 캐시: 게임 로그에서 cached>0인 요청은 20,601건 중 15건뿐이다. 시험 호출에서는 같은 요청을 다시 보내면 1,220토큰이 캐시되었다(S2 한국어). 게임에서는 input 앞부분(위치, 체력)이 매번 바뀌어 캐시가 거의 안 걸린다. 이 점은 영어화와 상관없다. 앱의 비용 계산은 cached를 할인하지 않는다.

### 4.4 지연 어림
- **[사실]** 로그 20,601건에서 지연을 토큰 수에 대해 회귀하면 토큰 1,000개당 **+5.7ms**다. 구간별 p50은 1,500토큰 미만 0.25s, 1,500~2,500토큰 0.26s, 2,500~4,000토큰 0.27s, 4,000토큰 이상 0.30s다.
- **[사실]** 시험 호출 24회의 평균은 한국어 255ms, 영어 248ms였다. 잡음 범위 안이다.
- **[사실]** 전투가 10초 넘게 이어진 구간 29개에서 판단은 캐릭터 하나당 **초당 2.67회**였다(`combatContinuous`, 한 번에 하나만 보냄). 전투 요청은 평균 2,054토큰, 비전투는 1,253토큰이다.
- **[해석]** 영어로 바꾸면 전투 요청 한 번에 약 440토큰이 줄어 약 2.5ms가 빨라진다. 전투 루프 주기(약 375ms)의 1% 안쪽이다. 지연에서 얻는 이득은 사실상 없다. 답이 조금 빨리 오는 만큼 전투 중 호출 수가 아주 조금 늘 수 있다(1% 이하). C#에서 문자열을 만드는 비용은 글자가 1.8배로 늘어 조금 커지지만, 지금 준비 시간(prep 약 100ms, 주로 후보 계산)에 비하면 무시할 만하다.

### 4.5 고른 선택지와 확률 분포 엿보기 (참고 표본, 결론으로 쓰지 않음)
- **[사실]** 같은 요청은 3번 보내도 답이 완전히 같았다(선택, 확률, confidence). 24회 모두 그랬다. 이 모델은 같은 입력에 같은 답을 낸다. 따라서 비교할 때 같은 상태를 여러 번 보낼 필요가 없고, 상태 수를 늘려야 한다.

### 5.1 선택 품질을 판단할 실험 방법 제안
- **[해석] A/B 재전송.** decisions 로그에 요청 전체가 남아 있고, 같은 입력에는 같은 답이 나온다(4.5). 이를 이용한다.
  1. 로그에서 상황 종류별(비전투, 근접전, 다수 적, 제작, 기지, 밭, 요리)로 200~500건을 고른다.
  2. 같은 요청의 한국어판과 영어판을 각각 한 번씩 보낸다.
  3. 1순위가 일치하는 비율과 분포 차이(KL, top-1 확률)를 잰다.
  4. 1순위가 다른 경우만 사람이 보고 어느 쪽이 맞는지 판정한다.
  - 비용: 1,000회에 약 2,000,000토큰, 약 $0.20.
- **[해석] 번역 만드는 법.** 손 번역은 비싸다. 문구 표(이번에 만든 `tr.js` 방식)로 하거나, 영어 생성기를 하나 만들어 같은 상태에서 두 가지를 다 내게 하는 편이 좋다. 후자는 5.2의 B안과 같은 결과물이 된다.
- **[해석] 실제 경기 결과 비교.** 버섯 야수 전투 승률과 피해, 목표 완료 시간을 시험장(testcmds)에서 같은 빌드에 스위치로 비교한다. 지금 `AITestSwitches`처럼 `english.on` 같은 스위치를 두는 방식이다. 결정을 내리는 근거는 이쪽이 더 강하다.
- **[사실]** 기존 리플레이 도구(AssemblerReplayTests, asmcheck.mjs)는 후보를 조립하는 단계만 재현한다. 요청을 다시 보내는 도구는 없다(3.3). 이번 scratchpad의 `parse.js`와 `call.js`를 다듬어 `Tools/`에 두면 재전송 A/B 도구가 된다. `ai-bridge/replay.mjs`의 pick/run/table/judge 구조를 본뜰 수 있다.
- **[해석]** OutcomeTests와 StallTests는 만드는 쪽 문장의 복사본으로 판정을 확인한다. 그래서 만드는 쪽만 영어로 바꾸면 시험은 통과하면서 실제 동작이 깨진다. 어느 방식으로 가든 먼저 이 시험들이 실제로 문장을 만드는 함수를 부르게 바꾸거나, 판정을 문자열이 아닌 코드로 바꿔야 한다.

## 6. 전환 방식 후보

1. **A. 직접 치환.** 모델에 가는 문구를 영어로 바꾸고, 같은 문자열을 쓰는 채팅·로그도 영어가 되는 것을 받아들인다. 내용 판정 코드는 같이 고치고, deaths.log와 경험 파일은 옛 한국어도 읽게 둔다.
   - 장점: 작업이 가장 작다.
   - 단점: 사용자가 읽는 로그와 채팅까지 영어가 된다. base-s3와 정면으로 충돌한다.
2. **B. 모델용과 화면용 분리.** Reason, desc, PromptLine을 만드는 곳에서 결과를 구조화한다(종류 코드 + 값). 영어 문장(모델용)과 한국어 문장(화면·로그용)을 각각 만든다. 내용 판정은 문자열 대신 코드로 한다.
   - 장점: 사용자는 계속 한국어로 읽는다. 내용 판정 의존이 없어진다. A/B 스위치로 두 언어를 비교할 수 있다.
   - 단점: 작업이 가장 크다. 생성 지점 약 600곳 이상을 손댄다. 두 문장이 서로 어긋날 위험이 있다.
3. **C. 단계적 전환.** 토큰 비중이 큰 곳부터 바꾼다. 선택지 설명이 53%이고, 그중 버섯 야수 근접전과 돌진 계산 문구(Candidates 686~960, AIChargeMath)가 가장 길다. 고정된 input 문장과 instructions가 다음이다. 각 단계는 시험 스위치로 A/B 비교한 다음 넘어간다. base-s3가 끝난 파일만 손댄다.
   - 장점: 효과와 위험을 단계마다 잴 수 있다. 충돌이 적다.
   - 단점: 오랫동안 한국어와 영어가 섞여 있다.

## 7. 열린 질문
- 영어 분포 변화(전투에서 뚜렷해지고 비전투에서 퍼짐)가 실제 결과에 좋은지 나쁜지. 5.1의 실험이 필요하다.
- 사용자가 디버깅할 때 모델 원문(영어)을 직접 읽어야 하는지, 화면용 한국어 대응문으로 충분한지.
- base-s3를 마친 뒤에 할지, 그 전에 분리 구조(B)만 먼저 둘지.
- 월 $28 안팎(시험 기간 기준)을 아끼는 것이 작업 규모에 맞는지. 4인 동시 플레이로 정상 운영하면 사용량이 얼마가 될지는 아직 모른다.

## 8. 쓴 API 호출과 비용
- Decisions API 26회: 표본 4개 × 한국어·영어 × 3회 = 24회, 섞인 경우 2회.
- 입력 토큰은 모두 75,250개, 비용은 약 **$0.0075**다(입력 100만 토큰당 $0.10).
- 키는 `OPENAI_API_KEY` 환경 변수에서 읽었다. 출력하거나 기록하지 않았다.
