- 날짜: 2026-11-06. 처음 판을 [6-설계검수.md](6-설계검수.md), [7-대조판정](7-대조판정/판정.md), 사용자 결정(P2)에 맞춰 고쳐 썼다. 바뀐 점은 끝의 **9절 검수 반영**에 모았다.
- 상태: 설계. 코드는 고치지 않는다. 구현은 base-s3가 ai-character에 합쳐진 뒤에 한다.

  - 판단 모델에 들어가는 input, instructions, choices description은 영어로 한다.
  - 근거:
    - 비용 약 −17%(2차 실측 토큰 0.828배)
    - 앞으로 Jev 계열 등 다른 판단 모델로도 시험해야 하는 것
  - 다음은 보고를 받은 뒤 내린 결정이다.
    - 품질 이득이 없다
    - 다듬어 온 효과를 잃을 수 있다

  - 확인 시점의 base-s3: a52384f

## 0. 요약

1. **문장 두 종류**
   - 같이 쓰는 문장(화면이나 위쪽 LLM에도 나오는 것)
     - 지금 string 필드를 그대로 둔다.
     - 영어는 곁 필드(`descEn`, `NameEn`, `ReasonEn` 등)로 더한다(P1).
   - 모델에만 가는 문장
     - 검증 기간에는 Ko를 얼려 둔다. Ko는 S0 문장 그대로다.
     - 합격하면 영어 한 벌만 남긴다(P2).
   - 여러 조각을 합쳐 만드는 곳(blocks, `_recent`, trigger, PromptLine 부품, BuildInput)에만 `AIText`(Ko/En 한 쌍)를 쓴다.
2. **사실 값은 한 번만 계산한다.** 같은 함수 안에서 같은 변수로 두 틀을 쓴다. 다음 검사를 둔다.
   - Ko→En 사실 토큰 포함 검사(한 방향, 한글 수사 대응)
   - En에 한글이나 빠진 틀이 있는지 셈
   - 신호 문구 짝 검사
   - Ko 틀 해시 잠금(P6)
   - 틀별 거친 횟수(P7)
3. **문구 판정을 코드 값으로**
   - 합친 코드에서 기계로 목록을 다시 만든다. b2fa4cc의 9곳에 base-s3에서 새로 생긴 7종을 더한다.
   - gates.sh에 "한글 상수로 판정 금지" 검사를 넣는다.
   - 의도한 동작 차이는 목록으로 적는다. 문 실패는 따로 `SkillEnd.DoorFail`로 둔다.
4. **경계**
   - 지금은 `DecisionRequest`/`DecisionResult`와 OpenAI 인코딩·읽기 하나만 만든다.
   - 다른 모델을 붙일 자리와 그때 필요한 것만 적어 둔다(P3).
   - 다른 모델 시험은 재송신 도구의 백엔드로 한다.
5. **합격 경로**
   - 1차 판정에서 출발 틀(819개) 그대로의 영어는 이미 떨어진다. 비전투는 한국어 승 11 대 영어 승 1이다.
   - 바꿔 쓰기 대조 판정에서 비전투 손실은 대부분 바꿔 쓰기 자체의 손실로 나왔다(11 : 3).
   - 그래서 S5에 **신호 보존** 작업을 넣는다. 원문 한국어 어느 문구가 판단을 이끌었는지 문구 바꿔 넣기 시험으로 찾아, 영어에 같은 무게로 옮긴다.
   - 다듬기용 표본과 합격용 보류 표본을 나눈다.
   - V4는 판정자 한 명, 고정 기준표, 기준 사례(앵커)로 하고, 허용 폭을 숫자로 둔다.
6. **순서**
   - 검증이 끝나야 기본 언어를 en으로 바꾼다.
   - 그 전까지 영어는 시험 스위치 `decisionlang.en`으로만 보낸다.
   - 합격 뒤 정리 단계(S9)에서 모델 전용 Ko와 스위치를 지운다.

## 1. 문장의 분리

### 1.1 문장 두 종류와 처리
- **[결정] 같이 쓰는 문장.** 화면, 위쪽 LLM, 기록에도 쓰이는 문장이다. 두 언어로 오래 유지한다.

| 객체 | 지금 필드(그대로 둠) | 더하는 곁 필드 / 처리 | Ko를 쓰는 곳(바뀌지 않음) | En을 쓰는 곳 |
|---|---|---|---|---|
| `AICandidate` | `desc` | `descEn` | 채팅 "AI 판단:", RESULT 줄, deaths.log 마지막 선택, ASM `desc` | choices, `Who()`, `_held` |
| `AISkill` | `Name`, `Reason` | `NameEn`, `ReasonEn`. `Finish(s, reason, end, reasonEn = null)`. `Progress()` 옆에 `ProgressEn()`(기본 null) | 채팅, SKILL/SWITCH 로그, 경험 기록, 위쪽 LLM | `_recent`, 계속하기, 실패 메모, `_skippedNote` |
| `AIGoal` | `Text` | `TextEn`(ObjectID만, 3.1) | 채팅, StatusText, 보고, planner 이벤트, deaths.log | 목표 줄 |
| blocks | `List<string>` | `List<Block{AIText text; BlockKind kind}>` | 막힘 why, BRAIN 로그 | 갈 수 없는 대상 |
| `_prepNote`, `_skippedNote`, trigger, `_sdWhy`, `FreeWhy` | string | `AIText` | 채팅, 보고 craft_needed, StallNote, planner 이벤트 | input |
| PromptLine 부품(`BaseText`, `ChestText`, `Rule`, `SnapText`, `Pair.Text`), `AIMemory.Summary`, `AIFood.Meaning`/`Rule`, `AITeammates.Summary` | string | 부품 함수가 `AIText`를 돌려준다. `ReportFields`, `StallNote`, `/ai base`, `/ai mem`은 `.Ko` | 보고, 채팅 | input, desc |
| `AIChargeMath` 문구, 조립기의 앞뒤 문구, `_edgeMoreNote` | string | `AIText`(desc의 부품이라 같이 쓰는 문장) | ASM `desc`, 채팅 | desc, input |

- **[결정] 모델에만 가는 문장.** 검증 기간에는 Ko를 얼려 두고, 합격 뒤 En만 남긴다.
  - BuildInput의 틀 줄: 첫 줄, 이름표, 내 상태, 보이는 범위, 지금 동작, 전투 상황, 자기 방어, 자유 시간, 다시 판단하는 이유의 머리
  - instructions
  - `_held` 줄, `SwitchHistoryText`, `AIMotion.Mid`, `SwarmNote`
  - `_bruteObs`(적 관측, 나, 주변, 진행 중 이동, 시간 값, 알려진 사실)
  - 시험 스위치 전용 줄(KillIntent)
  - 목록은 S0 직후 기계로 뽑는다. 판별 기준은 "그 문자열이 BuildInput/BuildJson 밖에서 읽히는가"다.
- **[결정] 위쪽 LLM 쪽은 모두 지금 string 필드나 `.Ko`에서 만든다.** 같은 객체를 써도 보고와 프롬프트는 지금과 같다.

### 1.2 `AIText`
- **[결정]** `Core/AIText.cs`에 둔다(Unity를 쓰지 않음).

```csharp
public readonly struct AIText {
    public readonly string Ko, En;                 // En == null: 영어 틀 없음
    public static AIText Of(string ko, string en,
        [CallerFilePath] string f = "", [CallerLineNumber] int l = 0);   // 틀 위치를 셈(P7)
    public static AIText Same(string s);           // ObjectID, 키, 좌표, 이름
    public static implicit operator AIText(string ko);   // = Of(ko, null)
    public override string ToString() => Ko;       // F6: 보간과 ToString은 지금 문자열과 같게
    public static AIText operator +(AIText a, AIText b);  // 한쪽 En이 null이면 결과 En도 null
    public static AIText Join(AIText sep, IEnumerable<AIText> parts);   // 하나라도 null이면 null
    public string For(Lang l);                     // En이 null이면 Ko를 내고 EN-UNTRANSLATED를 셈
    public AIText Trim(int koLen, int enLen);      // 3.2
}
```

- **[결정] 모델 쪽 조립은 보간을 쓰지 않는다**(F6). BuildInput, BuildJson, `Who()`, `_held`에서는 `For(lang)`와 `descEn ?? desc`(셈 올림)만 쓴다.
  - 보간으로 Ko가 섞여 들어가면 EN-HANGUL 셈에 잡힌다.
  - 화면과 보고 쪽은 `ToString() => Ko`라 지금과 같다.

### 1.3 어긋남을 막는 장치

| 장치 | 내용 | 어디서 |
|---|---|---|
| 같은 함수, 같은 변수 | 사실 값은 지역 변수로 한 번 계산해서 두 틀에 넣는다. 자주 쓰는 꼬리(계속하기, 바꾸는 비용, 돌진 예상, 남은 시간 등)는 `Core/Text/` 공용 함수로 둔다 | 코드 |
| 사실 토큰 포함(F9) | Ko에서 숫자, 좌표, ASCII ID를 뽑는다. 그것이 En에 같은 횟수로 있어야 한다(한 방향). 한글 수사 대응표(한/두/세 ↔ 1/2/3, once/twice)와 방향어 대응(동↔east, (남)↔(S))을 둔다. En에만 있는 숫자는 허용 목록이 있어야 한다 | core-tests(Core 함수), 실행 중 testcmds.on일 때 `TEXT-PARITY` |
| En에 한글·빠진 틀 | SEND 줄에 `enHangul=`, `enUntranslated=`. 플레이어 이름은 예외로 표시해서 뺀다 | 실행 중 |
| 신호 문구 짝 | 판단을 이끄는 문구(4.2)는 Ko 문구 ↔ En 문구를 등록한다. Ko에 있으면 En에도 있어야 한다 | core-tests, 실행 중 |
| Ko 틀 해시 잠금(P6) | 소스에서 `AIText.Of`와 `desc =`/`descEn =` 짝을 뽑아 Ko 틀의 해시를 `text-lock.json`에 둔다. Ko만 바뀌고 잠금이 그대로면 gates.sh가 실패한다. **검증 기간에는 모델 전용 Ko도 잠근다**(S0 그대로를 지키기 위해). **합격 뒤에는 두 언어로 남는 문장만 잠근다**(P2) | `Tools/core-tests/textlock.mjs`, gates.sh |
| 틀별 거친 횟수(P7) | decisionlog.on일 때 `AIText.Of`의 파일·줄마다 거친 수와 Parity 결과를 모은다. V2 끝에 한 번도 안 거친 틀 목록을 낸다 | 실행 중, 도구 |

### 1.4 판단 모델 경계 (P3)
- **[결정] 지금 만드는 것**
  - `DecisionRequest {Lang; State; Instructions; Choices[(value, description)]; Meta}`
  - `DecisionResult {Choice; Probs?; Confidence?; InputTokens; CachedTokens; Usd; Fail; Error}`
  - `OpenAIDecisions.Encode(DecisionRequest) → json`, `OpenAIDecisions.Read(UnityWebRequest) → DecisionResult`(지금 AIDecisionsApi를 옮김)
  - brain은 `AIPrompt.Build(…) → DecisionRequest`를 만들고 보낸다.
  - 인터페이스와 Caps는 지금 두지 않는다.
- **[결정] 두 번째 백엔드를 게임에 붙일 때 할 일**(지금은 하지 않음)
  - `OpenAIDecisions` 자리에 `IDecisionBackend {Encode, Read, Caps}`를 세운다. 설정 `backend`로 고른다.
  - 그때 필요한 것

| 차이 | 내용 | 그때 할 일 |
|---|---|---|
| 요청 형식 | Jev와 호환 계열은 `POST /v1/systemone`(state와 questions, choice·score·noul) | Encode/Read를 따로 쓴다 |
| 확률 | 없거나 보정 의미가 다르다(ECE 0.66~13%) | `Probs`/`Confidence` 없음을 brain 로그와 도구가 다룬다. 게임 동작은 1순위만 쓰므로 그대로다 |
| 한도 | 64k/요청, 선택지 26개 같은 한도 | Caps에 둔다. 우리 요청은 최대 24개, 약 8k라 지금은 닿지 않는다 |
| 과금 | 단가, 질문별 재과금, 공급자마다 다른 토큰 셈 | 비용 계산을 백엔드로. 월 상한 검사는 그대로 |
| 키 | 공급자별 환경 변수 | 키를 기록하지 않는 규칙 그대로 |
| 언어 | Jev는 영어 위주, Xevn은 한국어 위주 | 합격 뒤 모델 전용 Ko가 없으므로, 한국어 모델 시험은 재송신 도구의 S0 기록(ko 판)으로만 한다 |

- **[결정] 다른 모델 시험은 지금 재송신 도구에서 한다**(5.1 `backends/*.mjs`).

### 1.5 base-s3 변경 흡수
- **[결정] 흡수 장치**
  - 옛 string 필드를 그대로 두므로(P1), base-s3가 나중에 `desc = …`나 `Reason = …`를 새로 써도 컴파일되고 지금처럼 동작한다(F5 해소).
  - 그런 값은 `descEn`이 null이라 EN-UNTRANSLATED로 세어진다.
  - V2 조건(셈 0)과 gates.sh 고정 자료 검사가 놓친 것을 잡는다.
  - 새 판정을 한국어 문구로 짜면 gates.sh가 막는다(2.1).
- **[질문]** S5 동안 base-s3가 AIBrain.Candidates, AIBrain.Loop, AIBodySkills를 계속 고치면 충돌이 남는다(6-설계검수 5절). 그 기간의 작업 순서나 합치기 주기를 사용자와 정한다(Q6).

## 5. 합격 조건과 검증 순서

### 5.1 시험 도구: `Tools/decision-replay/` (P4 반영)
- **[결정] 입력: REQUEST 기록**
  - decisionlog.on일 때 decisions 로그에 다음 한 줄을 남긴다.

  - `build`는 커밋이고, `textLock`은 `text-lock.json` 해시다.
  - ko 판은 검증 기간에만 있다.
  - 키와 백엔드 JSON은 넣지 않는다.
- **[결정] 명령**

| 명령 | 하는 일 |
|---|---|
| `pick --logs <glob> --n N --strata cls,goal,nopts --split dev\|holdout --seed s` | 층별로 고르고 거의 같은 상태를 뺀다. 나누기는 5.2 |

- **[결정]** `import-legacy`는 첫판에서 뺀다(P4). 그 결과는 구현의 영어가 아니기 때문이다.

### 5.2 표본: 기준, 개발, 보류
- **[결정] 기준 KO는 S0 빌드(합친 직후)의 문장이다**(F13, P2).
  - 검증 기간의 빌드는 모델 전용 Ko를 얼린다. 해시 잠금으로 S0와 같은지 확인한다.
  - 이 빌드가 REQUEST에 ko 판으로 남긴다.
  - 한국어 화면 문장에 새 사실을 넣는 다듬기(Q3)를 하면 기준이 움직이므로, 검증 기간에는 하지 않는다.
- **[결정] 개발 세트와 보류 세트를 판 단위로 나눈다**(M1-b).
  - 판(게임 세션 하나, decisions 로그 하나) 단위로 나눠야, 거의 같은 상태가 두 세트에 함께 들어가지 않는다.
  - **개발 세트**: S5 진행 중에 기록한 판에서 약 300건. 신호 보존과 다듬기에 쓴다. 몇 번이고 다시 본다.
  - **보류 세트**: S5가 끝난 뒤 새로 기록한 판(다른 월드나 날짜)에서 약 450건. 비전투 150, 일반 전투 200, 근접전 100이다. V4에 한 번만 쓴다.
  - 보류 세트로 떨어져 다듬은 뒤 다시 판정할 때는 새 보류 세트를 기록한다. 같은 보류 세트로 두 번 합격을 주지 않는다.
  - 근거: 1차 판정에서 갈린 건수는 층당 15~36건이다. 1~2건으로 합격이 바뀌지 않으려면 층당 갈림 30건 이상이 필요하다. 갈림 비율은 16~24%다.

#### 5.3.1 V4 숫자 기준 (M1-c)
- **[결정] 층별(비전투, 일반 전투) 보류 세트 판정에서 다음 둘을 모두 만족하면 합격이다.**
  1. 셈 대상: KO와 EN이 갈렸고 판정이 X 또는 Y이며 확신도가 high나 mid인 경우.
     - 셈: 순손실 = (KO 승 − EN 승)
     - 기준: 순손실 ≤ max(2, ⌈0.02 × 층의 전체 표본 수⌉)
     - 보류 세트에서는 비전투 3건, 일반 전투 4건이 한도다.
  2. 부호 검정: KO 승이 EN 승보다 많다는 한쪽 부호 검정에서 p ≥ 0.10.
- **[결정] 같은 유형 반복 퇴보도 함께 본다.**
  - 유형 = (KO가 고른 kind → EN이 고른 kind, 층) 쌍이다(F12).
  - 같은 유형에서 KO 승이 3건 이상이고 EN 승이 0건이면 불합격이다. 그 유형은 V3d로 돌아간다.
- **[근거] 숫자를 이렇게 정한 이유**
  - 2%는 "판단 50번에 1번 꼴로 순손실"까지를 허용한다는 뜻이다.
  - 이미 있는 사례에 대보면(high/mid만 셈) 이 기준이 다음과 같이 가른다.
    - 1차 영어 비전투: 10 : 0. 순손실 10/95 = 10.5% → 불합격
    - 바꿔 쓰기 비전투: 10 : 3. 7/95 = 7.4% → 불합격
    - 1차 영어 일반 전투: 13 : 10. 3/135 = 2.2%, 한도 3 → 경계에서 통과(부호 검정 p ≈ 0.34)
    - 바꿔 쓰기 일반 전투: 7 : 9 → 통과
  - 따라서 판정에서 "확실히 진다"고 나온 비전투 손실은 걸러지고, 통계로 동률과 구별되지 않는 차이는 통과한다.
  - 부호 검정만 쓰면 갈림 15건 안팎에서 7 : 3도 통과한다(p ≈ 0.17). 그래서 순손실 한도를 함께 둔다.
- **[질문] 이 기준값(2%, p 0.10)은 사용자 확인 대상이다**(Q7). "원문보다 나빠지지 않을 것"을 숫자로 바꾼 것이다.

### 5.4 판정 절차 고정 (M1-d)
- **[결정]**
  1. **기준표 하나**: `Tools/decision-replay/rubric.md`. 7-대조판정의 판정.md와 3-판정의 기준을 합쳐 고정한다.
     - 위험한 적 앞의 근소한 이동 차이는 "둘 다 괜찮음"으로 본다.
     - 한쪽이 적 쪽으로 감, 한 번에 쓰러뜨리는 적 앞에서 자리를 지킴, 같은 위험에 목표 진행이 있음일 때만 한쪽을 낫다고 본다.
     - 자동 줍기, 출력 칸의 다 된 요리처럼 진행이 없는 행동도 기준표에 넣는다.
  2. **한 명이 전부 판정**: 한 번의 V4(층 전체)를 에이전트 하나가 처음부터 끝까지 판정한다. 나눠 맡기지 않는다. 1차는 셋이 나눠 했다.
  3. **확신도 기록**: high, mid, low와 근거 한 줄. low는 V4 셈에서 뺀다.
  4. **기준 사례 섞기**: 3-판정과 7-대조판정에서 high로 판정된 사례 12건을 무작위로 섞어 넣는다. 판정자에게는 알리지 않는다.
     - 판정자가 10건 이상 같은 판정을 내지 않으면, 기준표를 고치고 판정을 다시 한다.
     - 둘 다 괜찮음 비율도 따로 낸다(이번 50% 대 1차 22%의 차이를 감시).
  5. 금지 파일(key.json, 다른 판정, 문서)은 지금처럼 판정자에게 주지 않는다.

| F12 측정 불가 조건 | V4 유형 정의, V6 지표별 기준, V7은 같은 상태의 토큰 비율(V3c)로 바꿨다 |
| F13 기준 KO 이동 | 기준 KO는 S0 빌드로 고정. 검증 기간에는 화면 Ko에 새 사실을 넣지 않는다(Q3) |

### 9.2 제안

| 제안 | 결정 | 근거 |
|---|---|---|
| P1 곁 필드 | 채택 | 지시. F5, F6 위험이 줄고 base-s3 충돌이 준다 |

### 9.3 대조 판정(7-대조판정)과 사용자 결정에서 바뀐 것
- (a) S5에 신호 보존을 넣었다(4.2, V3d). 시작 사례는 두 판정 모두에서 원문이 이긴 비전투 6건(E095, E083, E070, E086, E016, E046)이다.
- (b) 개발 세트와 보류 세트를 판 단위로 나눴다(5.2).
- (c) V4 숫자 기준: 순손실 ≤ max(2, 2%), 부호 검정 p ≥ 0.10, 같은 유형 3 : 0 금지(5.3.1).
- (d) 판정 절차: 기준표, 한 명, 확신도, 기준 사례 12건(5.4).
- 근접전은 숫자 기준 없이 V4 결과로 사용자가 정한다(V5, Q1).
- 사용자 결정(P2): 모델 전용 문장은 합격 뒤 En 한 벌만 남긴다(S9). 기본 언어는 검증 전에는 ko이고 `decisionlang.en`으로 시험한다. 합격 뒤 스위치를 지운다. Ko 잠금은 합격 뒤 두 언어 문장으로 좁힌다.
- 처음 판의 Q4(한국어 되돌림 스위치를 계속 둘지)는 사용자 결정으로 닫혔다.
