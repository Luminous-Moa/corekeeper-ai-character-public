## 0. 결론

**추천: 안 C "계약을 타입으로 만들고, 변경이 몰리는 축을 따라 나누기".** 정적 클래스와 캐릭터별 Slots 구조는 유지한다. 대신 다음 네 가지를 한다.
(1) 문장으로 오가는 의미를 코드값으로 바꾼다.
(2) `AIBrain`을 목표 수명, 하위 판단 호출 수명, 후보 생성, 행동 종류 표, OpenAI 통신으로 나눈다.
(3) `AIPlanner`를 언제 물을지, 보고 만들기, 답 판독으로 나눈다.
(4) 비동기 입력은 캐릭터를 명시한 받은편지함으로 받는다.
브리지의 `plan()`은 단계별 모듈로 나눈다.

까닭은 다음과 같다. 예정 변경 1~4를 실제로 막는 것은 static이나 파일 길이가 아니다. 다음 세 가지가 막는다.

- **목표 칸이 하나뿐이다.** `AIGoal` 하나가 호스트 목표, LLM 목표, 자유 시간, 목표 없음(자기 방어)을 모두 나타낸다. 목표를 끝내는 코드는 일곱 곳에 복사되어 있다.
- **문장이 계약 노릇을 한다.** 실패 사유, 막힘 사유, 트리거, 거절 사유, 후보 설명, 로그 줄을 다른 코드가 다시 읽어 판단하는 곳이 20곳 넘는다.
- **위쪽 LLM 대화 계약이 흩어져 있다.** C# 손 파서, 브리지 키 순서, brief 문서, `shape()`가 같은 계약을 따로 들고 있다.

안 C는 이 세 곳을 정리하므로 1·3이 국소 변경이 되고 2·4도 수월해진다. 동작을 바꾸지 않는 단계로 나눌 수 있다.
전체를 인스턴스로 바꾸는 안 B는 비용과 위험에 비해 1~4에 주는 이득이 C보다 크지 않다. 이전 점검의 좁은 정리(안 A)만으로는 1번(목표 계층)과 3번(채팅 입력)의 비용이 크게 남는다.

**Cur/Slots 재평가:**

- 1번은 새 비동기 진입점이 없어 지금 구조로 충분하다.
- 3번은 채팅 훅이 캐릭터 범위 밖에서 돈다(Harmony prefix). 범위 밖에서 `AIAgent.Cur`는 Claude로 대체된다. 그래서 **캐릭터를 명시한 받은편지함은 3번 전에 꼭 필요하다.** 반면 전체를 인스턴스로 바꾸는 일은 여전히 필요하지 않다.
- 번호로 쓰는 Slots(0~14), 서로 다른 상태 패턴 세 가지, `AIBrain` 안 상태 밖 static 임시값은 타입 있는 접근자로 정리할 가치가 있다(작고 안전하다).

## 3. 문제 지점

### 3.1 책임이 뭉친 곳

1. **`AIBrain`(`S/AIDecisions.cs:122-2930`, 약 2,800줄, State 필드 100개 이상)에 서로 다른 이유로 바뀌는 책임이 다섯 개 있다.**
   - 목표 수명: SetGoal, ClearGoal, FreeTime, 완료·막힘 판정.
   - 하위 판단 호출 수명: 시점, 간격, 예산, 미리 묻기, 보류, 대기열, 낡은 답, 긴급, 반사.
   - 후보 생성: 준비 경로 포함 약 900줄.
   - 행동 종류 → 기술 변환.
   - OpenAI 통신·비용·키.

   변경 1은 첫째, 변경 2는 둘째~넷째에 닿는다. 서로 다른 변경이 같은 클래스의 공유 필드에서 만난다.
2. **`Send`가 요청 만들기와 목표 끝내기를 같이 한다**(`:1139-1225`). 요청을 보내려고 후보를 만들다가 "진행할 후보가 없다"는 사실로 목표를 끝낸다. 목표 수명의 판단이 호출 함수 안에 숨어 있다.
3. **`BuildCandidates`(`:1932-2658`) 한 함수가 생성, 세트 고르기, 제외, 메모, 재귀를 모두 한다.** 앞부분은 `WantedItems`가 `AIBase.ResetMissing/NoteMissing`으로 다른 모듈 상태를 채운 뒤 `AIBase.Candidates`가 그 상태를 읽는 순서 결합이다(`:1594`, `:1657`, `:1971`). 끝부분에서는 `_blockNote` 문장에 "도구 부족"이 처음 나오면 자기 자신을 한 번 더 부른다(`:2639-2644`). 이전 점검의 지적이 그대로 유효하다.
4. **`AIPlanner`가 시점 정책, 보고 만들기, HTTP, 판독, 검사, 적용을 한 클래스에서 한다.** 보고 맥락을 인자가 아니라 바뀌는 필드(`_lastGoalText` 등)로 넘긴다.
5. **브리지 `plan()`**: 2.4의 표 참고.

### 3.5 이미 잘 나뉜 곳(지킬 것)

- **몸의 단일 실행기:** `AISkill`(Start/Tick/Cleanup/Progress/EtaSeconds)과 `AIBody.Tick`이 실제 입력을 만드는 유일한 곳이다. 판단 모델의 답이 입력에 바로 닿지 않는다.

- **게임 연결부:** thin client, 패킷 펌프, 캐릭터 데이터 바꿔치기, 저장(`AIPlayerSpikeMod.cs`)은 검증된 경로이고 예정 변경 1~4와 거의 닿지 않는다. 길지만 지금 나눌 이유가 약하다. 바뀌는 곳은 3번의 채팅 훅뿐이다.

### 4.2 추천: 안 C

1. 비용 지도(2장)에서 반복해 나오는 막힘은 셋이다. 목표 칸 하나와 복사된 끝내기, 문장 계약, 위쪽 대화 계약. C는 셋을 모두 다루고, A는 셋째와 둘째 일부만 다룬다.
2. B가 더 해 주는 것은 static 제거로 캐릭터 소유를 강제하는 일이다. 그런데 그 이득이 실제로 필요한 곳은 비동기 입력이 들어오는 3번 하나다. 그것은 받은편지함 하나로 막을 수 있다. 1·2·4는 모두 캐릭터 범위 안에서 동기로 돈다.
3. 사용자 조건과 맞는다. "동작을 바꾸지 않는다"와 "상상한 미래가 아니라 예정된 변경이 쉬워지는 경계"를 모두 만족한다. C의 경계는 모두 2장의 실제 소비자에서 나왔다. 플러그인 체계, 이벤트 버스, 의존성 주입은 넣지 않는다.

## 5. 추천안(C) 단계 순서

원칙: 단계마다 동작을 바꾸지 않는다. 바꿔야 하는 곳은 사용자 결정으로 따로 뺀다. 각 단계는 따로 커밋하고 따로 확인한다. 로그 줄 형식(`DECISION #`, `SEND`, `SWITCH`, `SKILL`, `GOAL`, `PLANNER: report #n sent …`, `COMBAT`)과 기억 파일 형식은 그대로 둔다.

| 단계 | 내용 | 바뀌지 않아야 할 것 | 확인 방법 |
|---|---|---|---|
| **S0 기준선** | 기준 커밋 표시. Slots 번호 표를 문서로 남긴다. 기존 시험 실행(node 시험 3개, exp-sim). 기준 실게임 기록: decisionlog 켠 상태로 시험장(`/ai arena go/spawn`) 근접전 1회, 모으기(도구 부족 포함) 1회, 만들기 1회, 자유 시간·자기 방어 각 1회, 위쪽 LLM 켬 1회 | | node, dotnet, 실게임 1회(기준 기록용) |

순서의 까닭은 다음과 같다.
- S1·S2는 작고 경계가 선명하며 이후 단계의 안전망이 된다(문장이 아닌 코드로 비교할 수 있다).
- S3·S4가 끝나면 **변경 1·3을 시작할 수 있다.** 사용자가 정한 "리팩토링 다음 첫 작업"이 1번이다.
- S5·S6은 변경 2(전투) 전에 필요하다.
- S8은 변경 4 전에 필요하고 C# 쪽과 병렬로 해도 된다.
- 꼭 줄여야 하면 **S1~S4 + S8만 먼저** 하고 S5·S6은 전투 작업 직전에 해도 된다(미해결 질문 5).

### 하지 않을 것

- static 전체를 인스턴스로 바꾸기, AgentContext·의존성 주입, 이벤트 버스, 목표·행동 종류 플러그인 로더.
- 별도 asmdef나 어셈블리로 나누기(ModSDK 패키징 미확인).
- 게임 연결부(thin client, 패킷 펌프, 캐릭터 저장, Harmony 패치) 재구성. 3번 때 채팅 훅만 고친다.
- 후보 설명, 채팅 문장, 로그 줄 형식, 기억 파일 형식(events/goals/memory/known/exp_state) 바꾸기.
- 리팩토링 중 동작 변경: 후보 순서, 14개+wait, 근접전 세트, 실패 2회·30초 제외, 길 없음 90초·5칸, 동작 경계 2초, 전투 간격 0.25초·분당 240, 위쪽 재시도 규칙, 응답 계약.
- 두 LLM 통로 합치기(아래쪽 OpenAI 직접 호출과 위쪽 브리지 호출은 성격이 다르다).
- 파일 길이를 맞추려고 나누기(예: `AIBodySkills.cs`의 기술을 한 파일씩 쪼개기. 해도 되지만 우선순위 밖).
- 리팩토링과 기능(1~4) 동시 구현.

**C# 동작 보존 제안:**

1. **순수 핵심을 늘려 dotnet으로 시험한다(exp-sim 방식).** 시험 대상은 위쪽 판독(S1), 결과 코드 ↔ 문장 분류 일치(S2), 트리거·받은편지함 규칙(S4), 후보 조립기(S6)다. Unity·게임 형식(`Entity`, `int2`, `ObjectID`)을 쓰지 않는 입력으로 설계한다. Unity.Mathematics·Unity.Entities DLL을 dotnet에서 참조할 수 있는지는 **미확인**이라 기대지 않는다.
2. **기록 재생 대조.** 실게임에서 decisionlog로 조립기 입력과 출력을 남긴다. 리팩토링 뒤 같은 입력을 dotnet에서 새 조립기에 넣어 출력이 같은지 비교한다. 게임이 비결정적이어도 이 단계는 정확히 비교할 수 있다.
3. **같은 프레임 이중 계산.** 보고 JSON(S4)처럼 게임 상태를 읽는 함수는 전환 기간에 옛 함수와 새 함수를 둘 다 돌린다. 다르면 로그를 남긴다. 확인이 끝나면 옛 함수를 지운다.
4. **로그 비교.** GOAL/EXP/PLANNER/SKILL 줄 문장은 같아야 한다. DECISION 결과 종류는 분포가 비슷해야 한다. S0 기준 기록과 비교한다. 정확 일치가 아니라 유형 비교라는 한계가 있다.
5. **실게임이 꼭 필요한 곳:** 틱 순서(S3·S5), 기술 실행, 네 캐릭터 동시(S7), 채팅 출력. 시나리오는 S0과 같은 묶음을 쓴다.
6. **컴파일 확인:** 지금은 `BuildAndInstall`뿐이다. 설치 없이 컴파일만 하는 편집기 메서드를 시험 도구 쪽(`Assets/HeadlessTools`)에 더하는 것을 제안한다(제품 코드 아님. 가능 여부 **미확인**).

## 7. 미해결 질문

### 사용자가 정할 것

1. **위쪽 답 판독을 진짜 JSON 판독기로 바꾸면** 지금 손 파서가 잘못 읽던 입력(say 안 이스케이프 따옴표, 답 안 중첩 키)의 결과가 달라진다. 엄밀히는 동작 변경이다. 버그 수정으로 받아들일지 정해야 한다(권장: 받아들이고 차이 표를 남긴다).
2. **목표 끝 순서 통일:** 일곱 곳의 Stop/OnGoalEnded 순서가 다르다. 로그 순서 말고는 영향이 없어 보이지만 확인하지 못했다. 리팩토링에서는 그대로 지키고 통일은 따로 정할지.
3. **시스템 종료**(비용 상한·키 없음·판단 3회 연속 실패)에서 위쪽 LLM에 알리지 않는 지금 동작이 의도인지. 리팩토링에서는 유지한다.
4. (변경 1 설계 때) 호스트 지시 아래 LLM 하위 목표를 경험 기록에서 어떻게 셀지. 지금 구조로는 지시 시도가 "replaced"로 끝난다. 리팩토링은 이 결정을 미리 정하지 않는다. `AIGoals`의 목표 모델 모양에만 영향을 준다.
5. **리팩토링 범위:** C 전체(S0~S8)로 할지, 1·3 대비분(S1~S4 + S8)만 먼저 하고 S5·S6은 전투 직전에 할지.
6. **시험 도구 추가 허용:** dotnet 시험 프로젝트 확장(exp-sim을 넓히거나 새로 만들기), decisionlog에 조립기 입출력 기록(시험 스위치 안), 컴파일 전용 편집기 메서드.
7. (변경 3 설계 때) 멤버 이름이 든 일반 채팅을 다른 플레이어에게도 보낼지. 지금은 `/ai`만 삼킨다.

### 확인하지 못한 것

- 게임·Unity·node·dotnet을 하나도 실행하지 않았다. 시험 검사 수는 코드를 읽어 센 것이다.
- ModSDK가 `Scripts/` 아래 하위 폴더를 패키징하는지, 별도 asmdef를 다루는지, 모드 코드를 게임 쪽에서 컴파일하는지, 지원 C# 버전, `Newtonsoft.Json` 런타임 사용 가능 여부.
- 목표 끝 일곱 곳의 호출 순서 차이가 로그 말고 다른 결과를 바꾸는지.
- `AIBodySkills`·`AIExplore`·`AICraft`·`AIBase`·`AIFarm`·`AICook` 내부는 시그니처와 호출 지점 중심으로 읽었다. 기술 내부의 실패 문장 소비처를 전부 셌다고 보장하지 않는다(대표 `StartsWith`/`Contains` 검색으로 찾은 곳만 적었다).

- 전투 계획의 관측 가능성(적 공격 준비 상태)은 계획 문서의 미확인 그대로다. 이 점검은 그것을 받을 코드 자리만 짚었다.
