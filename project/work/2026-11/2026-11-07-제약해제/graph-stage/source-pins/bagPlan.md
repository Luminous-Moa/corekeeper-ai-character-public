# 가방·장비 선택지 개선 계획안

2026-11-07. 이 대화는 가방·장비 부분을 맡으며, 현재 요청은 최근 행동 결과 그래프를 참고한 계획 수립까지다. 제품 코드 변경·설치·게임 실행은 하지 않는다. 아래 순서와 세부 방식은 제안이며, 기존 합의와 구분한다.

## 문제·목표·유지 조건

- 문제: 자동 무기 준비와 재료 보관은 있으나, AI가 가진 방어구를 골라 교체하고 필요한 물건을 필요한 수량만 챙기는 생활 흐름이 끊겨 있다.
- 목표: 사용자 부탁 → 상위 계획 → 현재 가방·장비·허용 상자를 바탕으로 한 현장 선택 → 실제 조작 → 슬롯·수량 변화 확인 → 다음 판단을 연결한다.
- 조건: 위쪽 LLM은 목적·계획, Decisions는 구체적인 대상·행동 선택을 담당한다. 코드는 선택한 조작과 결과 관측을 맡는다. 장비 점수로 코드가 최적 조합을 자동 선정하는 기능은 이번 제안에 포함하지 않는다.
- 조건: 공통 실행 담당의 중단·전환·단계 완료 계약을 사용한다. 원래 부탁과 진행 상태를 유지한다. 기존 호스트 상자 접근 제한을 유지하며 자원 공유 정책을 이 작업에서 변경하지 않는다.

## 근거와 적용 경계

- [기존 누락 조사](2026-11-06-행동누락조사/01-inventory.md): 보관·조건부 꺼내기·자동 도구 준비는 재사용 대상이다. 장착·해제·교체, 장비 보관, 부분 보관, 일반 꺼내기 및 전달의 연결 공백을 구분했다.
- [장착 규칙 수용](2026-11-07-행동결과완결/judging/20-장비장착v2수용.md): 9개 유형·450개 원본의 조건부 장착, 양 슬롯 교체, 반지·파우치의 예외, 효과·세트 조건을 수용했다.
- [컨테이너 규칙 수용](2026-11-07-행동결과완결/judging/30-음식v4와컨테이너v2수용.md): 205개 원본의 이동과 180개 열기 주장을 수용했다. 실제 슬롯 종류·입출력 제한·남는 공간에 따라 이동량이 달라진다. 요청 처리와 실제 이동 성공을 구별한다.
- [장비 역할 역링크](2026-11-07-행동결과완결/judging/29-원거리9100과장비역링크수용.md): 장비 원본에서 장착·수리·업그레이드의 조건과 근거를 추적할 수 있다. 수리·강화 실행은 시설 담당과 연결할 후속 경계다.
- [그래프 사용법](../게임행동-그래프/README.md): 정본과 검수된 증분 기록을 구별한다. 최근 수용 기록이 모두 정본에 합쳐졌다고 가정하지 않고, 착수 시 검수본·해시·조회 근거를 고정한다. 개발용 규칙을 실제 월드 성공이나 현재 모드 능력으로 해석하지 않는다.
- [공통 실행 계약](2026-11-07-공통실행자료/contract.md): 기존 후보와 skill의 상태·이유·사실 연결을 사용하며 stop_action / finish_goal / request_plan을 중복 구현하지 않는다.
- [이번 사실 조사](2026-11-07-가방장비-조사.md): HEAD 11eb461의 현재 구현과 stage-04/semantic-04 증분 그래프를 실제 대조했다. 8549:0의 장착 목적 슬롯과 100:0의 상자 이동 조건을 target/show/source로 조회해 independent_pass 수용 관계와 원문까지 확인했다. 두 규칙 모두 runtimeTested=false이며 전체 그래프도 wholeScopeComplete=false다. 해제는 이번 장착 규칙의 별도 검수 행동으로 확인되지 않았으므로 일반 장비 슬롯→가방 슬롯 이동의 조건과 결과를 따로 검증한다.

## 착수 순서

| 순서 | 만드는 선택과 연결 | 단계별 확인 |
|---|---|---|
| 1. 가진 장비 착용·교체·해제 | 가방과 실제 착용 슬롯을 읽고, 정확한 물건·출발 슬롯·목적 슬롯을 지정한 후보를 만든다. 먼저 흉갑 교체의 한 흐름을 완결한 뒤 다른 장비 종류와 반지·파우치 예외를 같은 규칙으로 넓힌다. | 새 장비가 착용 슬롯에 들어가고, 교체된 물건이 실제로 어디에 있는지 확인한다. 해제 공간 부족은 결과와 이유로 보고한다. |
| 2. 손에 들 도구·무기 선택 | 곡괭이·근접무기의 기존 준비 경로를 재사용하면서 AI가 물건을 지정할 수 있게 한다. 채굴·공격 진입 때 코드가 다른 물건으로 덮어쓰는 경로를 정비한다. | AI가 고른 무기로 실제 공격하고, 다시 고른 도구로 실제 작업하는지 확인한다. 파손·소실·작업 부적합은 사실로 알려 새 선택으로 연결한다. |
| 3. 필요한 만큼 보관·꺼내기 | 기존 Store/Take를 확장해 장비도 대상으로 삼고, 품목·개수·남길 수량·허용 상자를 명확히 한다. 상자 종류에 맞는 실제 인벤토리와 슬롯 제한을 사용한다. | 예비 검 보관·다시 꺼내기, 나무 10개 남기고 나머지 보관, 지정 수량 보급을 각각 확인한다. 출발 감소량·도착 증가량·남은 요청량을 관측한다. |
| 4. 내려놓기·전달 | 특정 물건과 수량을 바닥에 내려놓는 동작, 수령 대상을 지정한 전달의 구현 가능성을 별도로 확인한다. 기존 줍기를 재사용할 수 있는지 대조한다. | 내려놓기는 바닥 물건 생성까지, 전달은 수령자 가방 증가까지 확인한다. 바닥 생성만으로 전달 완료로 처리하지 않는다. |

첫 단계는 이미 가진 방어구로 시작한다. 상자에서 꺼내기·제작·귀환까지 먼저 묶으면 착용의 공백을 고치기 전에 다른 담당의 동작까지 필요해지므로, 한 동작을 완결한 뒤 생활 흐름으로 연결하는 순서를 권한다. 전체 가방·장비 범위를 흉갑 하나로 축소하는 것은 아니다.

## 구현 방식

1. 가방 슬롯, 착용 슬롯, 손에 든 물건, 내구도·개수, 접근 가능한 상자의 관측을 먼저 대조한다. 같은 ObjectID라도 변형·개체 상태와 실제 슬롯을 구별하고, 공개 가능한 관측만 모델 입력에 쓴다. 비중첩 장비의 amount 필드를 일반 스택 개수로 읽지 않고 실제 물품 상태로 해석한다.
2. 각 후보는 실제 대상과 조작을 구체적으로 지정한다. 장착 가능한 슬롯, 교체되는 장비, 옮길 수량, 공간 등 판단을 바꿀 조건과 효과만 짧게 제시한다. 그래프 전체나 개발용 근거 ID를 실시간 프롬프트에 넣지 않는다. 관측 범위 밖의 장비 지식을 자동 공개하는 정책 변경도 포함하지 않는다.
3. 실행 직전 대상과 슬롯을 다시 확인하고 게임의 기존 이동·교체 요청을 사용한다. 오래된 판단 뒤 슬롯 내용이 바뀌면 다른 물건을 조작하지 않고 변경 사실을 보고한다. 내구도·능력치·수량을 코드에서 성공값으로 만들어 쓰지 않는다.
4. 조작 후 실제 양쪽 슬롯·손 선택·수량 변화를 읽고 성공, 일부 이동, 불가 이유를 남긴다. 개별 조작이 끝난 사실과 계획 단계 완료·사용자 부탁 완료를 구별하고 공통 실행의 다음 판단으로 넘긴다.
5. 구현 시 격리 Git worktree에서 단계별 변경을 만든다. 가방·장비 동작 및 필요한 후보 연결을 이 작업이 맡고, 공통 제어는 공통 실행 담당, 원거리 발사·조준은 전투 담당, 제작·수리·강화는 시설 담당과 접점을 맞춘다. 이번 계획 단계에서는 worktree를 만들거나 다른 작업 코드를 수정하지 않는다.

## 검증과 완료 의미

- 단계마다 대상 선택·슬롯 교체·부분 이동에서 물건이 소실되거나 중복되지 않는지, 가방 가득참·상자 가득참·낡은 슬롯 참조 등 그 흐름의 핵심 실패를 오프라인으로 확인한다. 기존 회귀는 영향을 받는 부분만 실행한다.
- 각 단계의 실제 변경과 검수된 게임 규칙을 독립 검수한다. 구현 완료 보고만으로 통과시키지 않는다.
- 첫 실게임 확인은 **가방에 있는 흉갑을 AI가 선택 → 기존 흉갑과 교체 → 전후 슬롯과 실제 착용 상태 관측 → 다음 행동 선택**으로 한다. 이어 해제·공간 부족을 확인한다.
- 다음 단계에서는 지정 무기 공격/지정 도구 작업, 장비 보관/회수, 일부 수량 이동을 각각 실게임으로 검증한다.
- 전체 대표 흐름은 **자기 상자에서 필요한 물건·장비를 정한 수량만 꺼냄 → 장비를 선택해 교체 → 선택한 무기로 행동 → 남은 물건·이전 장비를 보관 → 원래 부탁을 이어 감**으로 한다. 한 요청에서 모델 후보·선택·몸 실행·실제 가방/장비 변화를 연결해 확인한다.
- 설치·게임 조작은 구현 후 기존 승인·사용자 플레이 상태를 확인하고 진행한다. 이번 계획 수립에는 게임 실행·설치·새 LLM 호출이 없다.

## 별도 판단으로 남기는 것

호스트·다른 AI 상자의 공유 허용, 물건을 영구 삭제하는 trash, 자동 최적 장비 정책은 이 제안에서 확정하지 않는다. 바닥에 내려놓기는 삭제와 다르다. 직접 전달의 구체적인 몸 입력과 수령 방식은 실제 게임 경로를 확인해 제시하며, 확인 전 지원을 약속하지 않는다. 수리·강화·분해는 시설 동작과 역할을 맞춘 후 별도 범위를 정한다.
