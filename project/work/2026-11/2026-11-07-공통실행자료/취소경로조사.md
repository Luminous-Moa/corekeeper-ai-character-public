# AI 행동 취소·폐기·후보 차단 경로 독립 조사

조사 기준: `C:/Dev/CoreKeeperModSDK`, HEAD `11eb461ae122f404acec94563c086b09e002987c`.
대조 합의: `2026-11-07-공통실행-합의.md`. 조사 범위는 AIPlayerSpike C# 실행·계획·후보 경로와 ai-bridge의 해당 연결이다. 저장소와 게임을 수정하거나 실행하지 않았다. 아래는 기준 코드의 정적 조사이며 별도 common-execution 구현의 현재 상태 판정이 아니다.

## 핵심 결론

수량 완료 분기를 바꾸는 것만으로는 합의가 충족되지 않는다. `CheckAfterBuild`의 목표 폐기, `Send`의 only-wait 대체 및 5회 종료, 호출 실패 3회 종료, 응답 나이로 답/보류/다음 휘두르기/미리 받은 답 폐기, timeout 시 대기 선택 전체 삭제, 반복 실패·무피해·막힌 자리로 후보 차단까지 이어진다. 상위 계획은 관측상 완료를 받으면 호출 없이 다음 단계로 넘어가며, 같은 source에 실린 사용자 원래 부탁을 완료 처리할 수도 있다.

구분 기준은 다음과 같다.

- **AI가 결정할 정책**: 충분히 모았는지, 오래 했는지, 진척이 적어 포기할지, 반복 실패 대상을 다시 시도할지, 위협이 사라져 싸움을 끝낼지, 계획의 다음 단계로 갈지. 사실을 보고하고 명시 계속·중단·전환을 받는다.
- **실제 실행 불가/작업 결과**: 플레이어 다운, 대상 엔티티 소실, 벽이 이미 부서짐, 재료 없음, 놓을 공간이 실제 점유됨, 입력 버퍼나 필수 컴포넌트 없음, 예외. 그 실행 회차가 수행하지 못한 결과를 내고 새 상태를 판단하도록 한다. 원래 부탁·계획 전체를 자동 폐기할 근거는 아니다.
- **요청 수송·거래 경계**: 네트워크 timeout, 이동/제작 요청 ACK 미확인, 인벤토리 반영 지연. 요청을 종료하거나 같은 명령의 중복 전송을 막을 수 있다. 그것이 행동 의도 취소나 목표 완료를 뜻하지 않는다. 특히 인벤토리 timeout을 무기한 동일 주문 반복으로 바꾸면 중복 제작·이동 위험이 생긴다.
- **사용자 직접 stop / 새 AI 선택**: 사용자 `/ai stop`, 명시 목표 해제, 실제 퇴장, 최신 AI의 hold/set/다른 행동 선택은 유효한 취소·교체 입구다. 사용자 stop 뒤 도착한 답은 다시 실행시키면 안 된다.
- **AI가 처음부터 고른 유한 원자 동작**: 한 타, 정한 좌표까지 이동, 표시된 3초 거리 벌리기, 묶음 동작의 명시 단계는 그 원자 동작의 완료를 보고할 수 있다. 코드가 임의 예산을 뒤늦게 적용해 장기 의도까지 끝내는 것과 구분한다.

## 상위 계획·원래 부탁 경로

1. `AIPlanner.cs:317 OnGoalEnded`는 goal_done/explore_ended를 완료로 보고 현재 plan에 다음 단계가 있으면 `_planNext=true`; `Tick:461`→`StartNextStep:359`→`Plan.Advance()`로 **새 호출 없이** 다음 목표를 건다. 수량 관측을 기존 goal_done 이름으로 보내기만 해도 이 자동 전환이 재발할 수 있다. 단계 관측, AI가 승인한 advance, 최종 부탁 완료를 구분해야 한다.
2. 같은 함수 `:345`는 비완료 종료이면 Plan.Stop으로 나머지를 내리고, `:349`는 `S.Orders.GoalEnded(source, done, ...)`를 호출한다. `Core/AIHostOrders.cs:132`는 같은 source의 '따름' 원래 부탁을 모두 끝남/막힘으로 바꾼다. **'갑옷 부탁을 따른 구리 확보'의 수량 충족이 갑옷 부탁 끝남으로 번역될 수 있는 연결점**이다. 원래 부탁 완료는 AI의 명시 order done 판정이어야 한다.
3. `StartNextStep:364`는 `CheckGoal` 실패 시 Plan.Stop 후 plan_step_failed. 실제 수행 회차의 불가와 전체 계획 폐기는 분리해야 한다. 다음 단계가 아직 승인되지 않았다면 먼저 AI에게 현재 결과를 주고 선택을 받는다.
4. `CheckReason:743`→`StepForm:766`/`CheckGoal:791`→`PlanCut`→`Apply:664`는 알 수 없는 kind/item/형식 오류 외에도 Gather 허용 품목, Gather 30/Craft 10 상한, KnownRecipe, 가방에 보관할 것 없음, 이미 기지, CanFarm/CanCook 등의 현재 상태를 근거로 plan 뒷부분을 잘라낸다. JSON/kind/좌표 형식 검증은 필요하다. 수량 상한과 현 실행 능력 제한은 정책 또는 지원되지 않은 동작 사실이며, 원래 의도와 계획 꼬리를 조용히 잃지 않고 이유를 돌려준다.
5. `Apply:666`의 upperPlanMaxSteps 초과 tail 제거도 별도 정책 입구다. 프로그램이 처리할 수 있는 범위는 제한할 수 있으나 초과 의도를 보존하고 잘린 부분을 AI가 보도록 해야 한다.
6. `CheckReason:750–752`와 `Core/AIPlanRules.cs:34`는 revision/down/180초 age로 일반 상위 답을 drop; host 답은 ask once 후 TalkOnly라 set/hold는 적용하지 않는다. age 단독 폐기와 진짜 사용자 stop/다른 최신 AI 선택에 대한 과거 답 불일치를 분리해야 한다. report/goal_rev echo가 전혀 안 맞는 잘못된 응답은 여전히 수락하지 않는다.

8. AI가 명시한 `hold` (`:637`)와 `set` (`:662`)은 정상 중단·교체 경로. hold는 원래 부탁을 미룸으로 보존하고 추후 관찰하는 기존 처리를 유지할 근거가 있다. 사용자 `/ai stop`은 `AIBody.Commands.cs:73`와 planner Disable 경로까지 포함해 재실행 방지 확인이 필요하다.

## 비정상 성능·spin을 결과와 재판단으로 풀 조건

1. **같은 사실을 매 frame 보고하지 않기**: run id + 관측 종류 + 경계 횟수로 한 번 알리고 다음 중요한 변화에 다시 알린다. 완료 수량 도달 이후 매 tick 상위 호출을 재생성하면 기다리는 답이 계속 폐기될 수 있다. 이 관측 중복 억제는 AI 행동을 취소하는 정책이 아니다.
2. **진척 이력은 AI가 읽게**: 누적 시간, 최근 이동거리/피해/수량변화, 입력 횟수, 손 든 도구, 길찾기 시도/상한, 마지막 실패 위치·당시 문/적 상태, 최근 같은 선택과 결과를 보고한다. AI가 계속 눌러도 결과가 없는 것을 볼 수 있어야 한다.
3. **실행 유지와 input 재발행은 구분**: 유효한 이동·공격은 답 기다리며 계속할 수 있다. 한 번 보낸 제작·이동거래 명령은 ACK/수량 확인을 기다리는 상태로 유지하고 매 frame 주문을 재발행하지 않는다.
4. **AI 응답 인과관계**: goal revision만으로 모든 것 무효화하지 말고 사용자 stop, 선택 revision, 실행 run id, 대상 identity를 추적한다. 같은 key의 새 swing을 old continue가 지배하거나 늦은 old switch가 최신 AI 선택을 덮어쓰지 않게 한다. 이 경우 폐기 사유는 '오래됨'이 아니라 '다른 회차/뒤의 명시 결정으로 대체됨'이다.
5. **선택지가 없으면 사실을 물어보기**: only-wait 루프를 코드가5회 후 끝내는 대신 상위 AI가 지금 실행 능력·미발견·지원 제약을 보고 무엇을 할지 고를 수 있어야 한다. 수송 제한 때문에 동일 wait 하나로 Decisions 호출을 못 해도, 원래 부탁을 없애는 근거는 되지 않는다.
6. **계산 예산은 관측**: 길찾기40,000칸/후보14개 같은 계산·입력 예산을 무제한으로 늘리면 프레임 정지/비용 문제가 생긴다. 예산 내 미발견/목록 생략이라는 사실을 함께 보고하고, 현재 선택을 계속할지 다른 탐색을 할지 AI가 판단하게 한다. 예산 상한은 목표 불가능의 증명이 아니다.
7. **통신 장애**: 실패 원인별 재시도·월 비용 상한·1요청 in-flight를 지키되 원래 부탁/실행 의도를 저장한 채 유효 실행을 유지한다. 장애 복구 보고에는 장애 중 실제로 무엇이 진행됐는지 포함한다.

## 브리지 경계

`Tools/ai-bridge/plan.mjs` preflight(busy/login/subscription/quota), `recall-loop.mjs:87–99` deadline/abort, `protocol.mjs` shape 검증은 모델 호출을 완료하지 못한 **운영·형식 결과**를 만든다. `bridge.mjs:141`의 연결 종료→CLI 중단은 수송 작업 수명 제어다. 이 제한이 모델의 유효한 몸 행동을 끝내야 한다는 결론은 아니므로, C# 쪽에서 해당 오류를 받아 목표·실행 취소로 번역하지 않는 것이 핵심이다. recall 검색 예산·deadline 자체를 무제한으로 풀 필요는 없다.

## 공통 구현 인계 우선순위

1. 목표 관측과 실제 종료를 분리하고, 관측을 받은 상위 경로에서 auto plan advance/host order done이 재발하지 않게 한다.
2. timeout·호출실패·응답나이의 공통 소유권을 정리한다. 기다리는 동안 기존 실행·이미 받은 선택을 보존하고 사용자 stop/새 AI 선택만 정확히 우선한다.
3. 반복실패 메모리를 후보 금지에서 결과 설명으로 바꾸되, 생성 전 LeftOut/skipF/noPath까지 살핀다.
4. only-wait·self-defence·free-time·frontier-placeholder처럼 별도 임의 Stop/StartSkill 입구를 감사한다.
5. 기능 담당에 시간·진척·거래 결과 보고 API를 인계한다. 특히 ACK 지연은 중복 주문을 막는 요청 상태와 AI의 계속 의도를 분리해야 한다.

조사 산출물만 작성했다. 실제 게임 확인, 컴파일, 테스트 실행과 신규 구현 적합성 검수는 호출한 대화에서 별도로 확인해야 한다.
