# LLM 경험 기억 방향 독립 검토

2026-11-04. 검토 범위: 기존 기억 구조 조사와 현재 AI 모드·브리지의 사건→목표 결과→상위 판단 흐름. 구현·게임 실행·외부 모델 호출·설정 변경은 하지 않았다. 적용 지침은 C:/Dev/AGENTS.md이며, 과거 모델·추론 강도 지정은 적용하지 않았다.

## 결론

**방향은 타당하다. 다만 지금 확정할 것은 기억 파일의 층 수나 교훈 점수가 아니라, 무엇을 독립된 경험으로 세고 어느 조건에서 다시 적용할지다.** 사건 원본, 코드로 만든 목표 결과, 짧은 수정 가능한 해석, goal-key 조회부터 시작하는 구성이 현재 상위 CLI 목표 선택 구조에 맞는다. 임베딩·경험 그래프 DB를 먼저 넣을 이유는 확인되지 않았다.

목표는 실패·죽음을 줄이는 것 자체가 아니라 **상황에 맞지 않았던 판단을 조건 변화 없이 되풀이하는 일을 줄이는 것**이다. 따라서 “주석 실패 2회 → 주석 회피”보다 “이 장비·이 지역·이 진행 제약에서 주석 목표가 어떻게 되었고, 지금 달라진 조건이 무엇인가”가 핵심이다. 같은 목표를 다시 고른 횟수만으로 개선을 판정하면 정당한 재도전까지 나쁜 판단으로 취급한다.

현재성 보정: 상위 호출은 고정된 “몇 분 주기”가 아니다. 목표 완료·막힘·부활 계기에 호출하며(AIPlanner.cs:141–159), hold는 120초 후 재검토(244, 326행), LLM follow는 180초에 종료·재검토한다(AIDecisions.cs:619–627). 짧은 목표가 이어지면 호출도 짧게 이어진다. 메모 처리를 이유로 이 빈도를 줄이거나 대기시간을 늘려서는 안 된다.

## 유지할 설계

- 아래 Decisions의 world-state memory 유지. 현재도 세계/캐릭터 경로로 분리되어 있고 광석·제작대의 마지막 관찰 시각이 있다(AIExplore.cs:101–153).
- 경험 원본과 LLM 해석을 분리하고 해석에 근거를 연결. 목표 결과와 간단한 집계는 코드가 만든다. 보고 직전 조회 역시 코드가 수행한다.
- 기존 CLI 답에 작은 plan/lessons 갱신을 선택적으로 싣는다. 별도 반성 호출은 첫 단계에 넣지 않는다. relations와 월드 간 교훈 승격은 실제 필요한 사례가 생길 때 추가한다.
- 게임 지식 그래프와 경험 기억은 분리하고 게임 ID로 연결한다. 공유 게임 데이터 위의 캐릭터별 열림 조건은 유지한다. 경험용 역색인은 이 게임 지식 그래프를 대체하지 않는다.

## 중요한 보완 다섯 가지

### 1. goal_rev를 경험 식별자로 쓰면 안 된다

조사 149행은 “goal_id는 지금 목표 rev”라고 제안하지만, 현재 Revision은 응답의 유효성을 검사하는 번호다. SetGoal·ClearGoal뿐 아니라 자기방어 시작·끝에도 증가한다(AIDecisions.cs:367–373, 481–498, 994–1007). 한 목표가 여러 rev에 걸칠 수 있다. 완료 시 ClearGoal 다음에 OnGoalEnded가 호출되고 보고에는 현재 Revision이 들어간다(649–651, AIPlanner.cs:217). 따라서 보고 rev는 종료된 목표 식별자도 아니다.

Revision은 메모리 State의 int이며 영속 목표 식별자로 저장되지 않는다(AIDecisions.cs:117–120). 게임 프로세스를 다시 시작하면 같은 값이 재사용될 수 있다. 참고로 Reset() 자체는 Revision을 0으로 만들지는 않으므로 “재접속마다 0으로 초기화”라고 단정하면 안 된다.

**최소 수정안:** 실제 목표를 채택할 때 별도 goal_run_id를 한 번 발급하고 종료까지 유지한다. event_id와 goal_run_id는 world·character·실행 세션 범위가 충돌하지 않게 한다(UUID 또는 session+sequence면 충분). rev는 기존 응답 검사 용도로 남긴다. 여러 down을 같은 목표의 사건으로 기록하며 goals 집계는 goal_run_id당 종료 결과 한 번만 반영한다. 중복 기록을 다시 읽거나 goals를 재생성해도 횟수가 늘지 않아야 한다.

### 2. 사건·종료·실행 장애를 분리해야 한다

현재 back_up은 목표가 진행 중인 채로 재보고할 수 있다(AIPlanner.cs:148–159). 이를 goal_end=down으로 기록하면 하나의 목표가 여러 번 실패한 것처럼 보인다. follow의 done도 3분 재검토 지점이다(AIDecisions.cs:619–627). explore_ended는 현재 가능한 탐색 후보가 소진된 상태이며, 목표가 나쁜 선택이었다는 증거와 같지 않다(1063–1072). skill 실패·취소도 별도 개념이다(377–380).

현재 `events`는 영속 사건 로그가 아니다. Auto가 켜진 동안만 모으고 종류를 문자열로 합치며 6개만 유지하고 보고 전송 직후 비운다(AIPlanner.cs:97–115, 226). 브리지 plan 로그는 답을 기록하지만 목표가 실제 채택됐는지와 이후 결과를 보장하지 않는다(bridge.mjs:203–210; 실제 채택 검사는 AIPlanner.cs:311–334). 그러므로 이 둘을 그대로 L1 원본으로 삼을 수 없다.

**최소 수정안:** 사건은 발생 지점에서 기록하고, 목표 종료 때 `completed / blocked / cancelled / replaced / unknown` 같은 종료 의미와 구체 원인을 별도로 남긴다. 통신·파싱 실패, 오래된 답 폐기는 판단 요청의 결과로 기록한다. 사용자 취소·새 명령은 목표 난도의 실패 횟수에 넣지 않는다. 쓰러짐은 사건으로 남기고 목표가 실제 끝났을 때만 종료 결과를 붙인다. 세션 종료로 끝을 관찰하지 못한 목표는 실패로 추정하지 않는다. 종료 전 목표 스냅샷과 관찰된 진척을 보존하면 충분하다.

### 3. 교훈의 지지 횟수는 LLM의 재동의 횟수가 아니다

조사 135행의 `lesson_agree +1`, 목록이 차면 더 크게 감점하는 규칙을 그대로 쓰면 같은 사건을 여러 번 읽는 것만으로 신뢰가 높아진다. 점수는 실제 경험의 횟수라는 의미를 잃는다. 실재하는 evidence id를 붙였다고 교훈의 내용이 그 사건에서 따라 나온다는 보장도 없다.

**최소 수정안:** 첫 단계에는 인위적인 +2/+1 투표를 빼도 된다. 교훈에 근거 goal_run_id/event_id 집합, 적용 조건, 유효 상태를 보존한다. 같은 목표에서 나온 여러 로그를 독립 시도 여러 번으로 세지 않는다. 같은 근거 재제출은 점수를 올리지 않고, 새 목표 경험은 추가 근거가 된다. 새 관찰이 기존 해석과 다르면 근거는 남기고 조건을 좁히거나 해석을 교체한다. 근거 존재·접근 가능성 검사는 코드로 하고, 내용 해석은 가설로 표시한다. 카드 공간 부족은 검색·노출 문제이지 교훈이 거짓이라는 증거가 아니다.

### 4. goal-key는 조회 시작점이고, 적용 판단에는 최소 맥락이 필요하다

`gather:TinOre`는 좋은 첫 색인이다. 그러나 장소·장비가 달랐던 시도를 합친 실패율만 넣으면 영구 회피가 생긴다. 반대로 과도한 복합 키는 경험을 너무 잘게 나눈다.

**최소 수정안:** key는 그대로 두고 결과에 원인이 된 조건만 부가한다. 기본은 world/character 범위, 목표 수량·관찰된 진척, 시각, 관련 지역/대상이다. 장비 부족이면 당시 도구·장비, 길 막힘이면 경로/지역과 관찰 시각, 전투 개입이면 관찰된 적·당시 장비·동행 상황을 붙인다. 조건을 모르면 unknown으로 둔다. 매 사건에 거대한 전 상태를 복제할 필요는 없다. 조회에서는 현재 조건과 일치하는 사례와 조건이 달라진 반례를 함께 짧게 보여 준다. 실패 유형을 무조건 높은 중요도로 두는 조사 130행의 규칙은 성공·준비 완료·새 경로 같은 변화가 밀리지 않도록 바꾸는 편이 낫다.

현재 상위 goal은 do/item/count뿐이다(AIPlanner.cs:22). “서쪽은 피하겠다”는 say/why가 아래 경로 선택의 제약으로 전달되지는 않는다. 따라서 기억만으로 경로 반복이 해결된다고 약속할 수 없다. 첫 검증은 현재 표현 가능한 “장비 준비 목표 뒤 재도전” 등으로 잡고, 다른 지역/경로를 지정해야 하는 사례는 상·하위 계약 보완의 필요성을 별도로 판단한다. 같은 주석을 다시 골랐다는 사실만으로 실패 판정을 내리지 않는다.

### 5. 캐릭터 범위·관찰 시점·응답 적용 경계를 조회와 쓰기 양쪽에 둔다

현재 world-state는 캐릭터별이고 상위 보고의 동료도 자기 화면에서 본 대상이다(AIExplore.cs:104, AIPlanner.cs:203–205). 경험 조회 전에 world/character 범위를 제한하고, 공유 게임 지식은 그 캐릭터에게 열린 항목만 조회해야 한다. 같은 ObjectID가 있다고 다른 캐릭터의 관찰·교훈·숨은 레시피까지 가져오면 안 된다.

source=game/host/llm만으로 사실과 추론이 완전히 나뉘지도 않는다. 예를 들어 “갈 길 없음”은 현재 후보 생성기의 결과이고 세계에 영원히 길이 없다는 사실이 아니다. 사건 종류와 관찰 시각, 판정한 주체를 함께 보존한다. 게임 관찰로 확인되지 않은 LLM why는 해석으로 남긴다. 인용된 근거가 실제로 존재하며 이 캐릭터가 접근 가능한지 확인한다.

memo를 브리지의 응답 수신 순간에 확정하면 모드가 나중에 버리는 오래된 답도 기억에 남는다. 현재 모드는 rev·호스트 목표·시간으로 답을 검사한다(AIPlanner.cs:340–344). 첫 구현에서는 이 수용 경계 뒤에 memo도 반영하고 같은 응답 재처리는 멱등으로 만든다. 선택적 memo 형식 오류 때문에 정상 목표 선택을 버리거나 추가 LLM 재호출을 만들 필요는 없다. 메모 오류는 기록하고 해당 메모만 제외하는 단순한 정책이 판단 빈도 유지에 맞는다.

## 제안하는 최소 한 흐름과 검증

첫 구현은 `목표 채택 → 구조화 사건 → 실제 목표 종료 → 코드 요약 → 다음 보고에 관련 결과 포함 → 상위 답 검증·채택 → 다음 결과 연결` 한 줄을 완성한다. 새로운 DB, 전용 reflection 호출, relations, 복합 점수식은 이 흐름에 필요하지 않다. L1을 원본으로 삼고 L2는 다시 만들 수 있는 파생 결과로 두면 두 파일 쓰기 중 하나가 실패해도 복구할 수 있다. 실제 목표가 채택됐는지까지 기록해야 “LLM이 말했다”와 “실제로 했다”를 구분한다.

구현 후 오프라인 고정 입력으로 먼저 확인할 사례:

1. 한 주석 목표 중 자기방어 rev 변경 두 번과 down 두 번, 이어 완료: 목표 시도 1개·완료 1개·down 사건 2개로 집계된다.
2. 동일 사건/답 재처리·로그 재독·프로세스 재시작: 목표 횟수와 교훈 지지 근거가 증가하지 않고 ID가 충돌하지 않는다.
3. 같은 주석 목표, 동일 장비·지역에서 막힘 / 장비 준비 또는 새 접근 경로 관찰 뒤 재도전: 앞선 제한과 바뀐 조건이 함께 보고되고 목표를 영구 금지하지 않는다.
4. 사용자 교체·통신 실패·오래된 답·다른 캐릭터의 근거: 목표 난도의 실패 집계에 섞이지 않고 잘못된 memo가 저장되지 않는다.

이 검토에서는 모델·실게임 시험을 하지 않았다. 위 오프라인 검증은 데이터 계약만 확인한다. 실제 판단 개선은 후속 허용된 시험에서 “조건이 그대로인데 같은 부적합 판단을 반복하는 비율”, “조건 변화 뒤 적절한 재도전”, 진척, 판단 간격을 함께 봐야 한다. 추가 호출 0회와 추가 지연 0은 다르므로 기존 보고의 입력량·지연과 아래 Decisions 판단 간격도 함께 비교한다.

## 외부 원문 확인과 기존 조사 수정 제안

결론에 영향을 주는 세 원문만 확인했다. 모두 구조 아이디어의 근거이며, 이 프로젝트의 구체 설계가 효과적이라는 확정 근거는 아니다.

- [Voyager curriculum 코드](https://raw.githubusercontent.com/MineDojo/Voyager/main/voyager/agents/curriculum.py): completed/failed 목록을 유지하고 성공한 과제는 실패 목록에서 제거한다(310–345행). 실패를 영구 금지로 만들지 않는 참고 사례다. 해당 목록만으로 우리 목표 선택이 개선된다는 분리 실험 근거는 아니다.
- [Optimus-1 논문 §2.1.2 및 §F.1.2](https://arxiv.org/html/2408.03615v1): 제작·채굴 의존 지식을 그래프로 두고 목표 관련 부분과 경험 사례를 구분한다. 조사 5장의 HDKG 불확실성은 이 범위에서 해소 가능하다. 다만 이 논문은 우리 캐릭터별 공개 범위나 game-data-only 계약을 검증하지 않는다.
- [ExpeL update_rules 코드](https://raw.githubusercontent.com/LeapLabTHU/ExpeL/main/agent/expel.py): AGREE/EDIT 증가와 목록 크기에 따른 REMOVE 감점은 확인된다(658–703행). 이것은 규칙 편집 점수이며 독립 경험 수나 확률적 신뢰도라고 볼 근거는 없다. 따라서 점수식을 그대로 채택하기보다 근거 집합을 채택한다.

기존 조사에서 고칠 표현:
