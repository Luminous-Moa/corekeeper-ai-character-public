# 행동 수행 정체의 근본 원인

2026-11-08 최신 사용자 플레이의 종료 로그, 실제 선택·실행 기록, 현재 43c3817 코드와 변경 이력을 대조했다. 이번 작업은 분석 보고다.

## 핵심 판단

행동이 진전하지 않는 대기 상태인데도 `Running`과 `continue`가 유지되고, 그 선택 후 판단 요청이 다시 발생하지 않는 연결 결함이 있다. 여기에 실제 전달 결과를 놓치는 관측 결함과, 이전 목표의 성공 사실을 새 목표에 붙이는 문제가 겹친다.

최신 실행의 하위 요청 63개는 모두 파싱됐고 HTTP 오류는 0이었다. 준비 CPU 합계는 약 1.748초, 한 준비의 최대는 126.4ms였다. 반면 갑옷 전달 행동은 425.3초 동안 남았고, 마지막 통로 대기는 100초 동안 하위 요청이 없었다. 긴 정체를 설명하는 주요 구간은 준비 계산 이후의 행동과 재판단 흐름이다.

## 확인된 문제

### 1. 계속하기가 진전을 만들지 못하고 다음 판단도 잠든다

`AISkill.ObserveOnce`는 같은 키의 사실을 한 번만 알린다. 관측 수정번호는 요청을 보낼 때 소비된다. 비전투 `Running` 상태에서 새 판단 필요 표시가 없으면 `AIBrain`은 다시 요청하지 않는다. 최소 호출 간격 설정은 주기적인 재판단 예약 기능을 하지 않는다.

갑옷 수령 미확인을 한 번 보고한 뒤 `continue`가 선택되면, 새 사건이 생기기까지 같은 행동이 유지될 수 있다. 실제 하위 요청 사이에 132.7초와 285.9초의 공백이 있었다. 그동안 상위 Gemini의 `keep` 응답이 여러 번 와도 현장 판단은 다시 시작되지 않았다.

통로에서도 같은 문제가 발생했다. 방향 선택 대기는 입력을 멈춘 채 `Running`을 유지한다. `continue`는 필요한 새 방향을 채우지 않는다. t637.5에 `continue`를 선택한 뒤 t737.5까지 하위 요청과 좌표 변화가 없었다.

### 2. 실제 전달 결과를 놓쳐 끝나지 않는 실행이 남는다

갑옷 전달의 `DropTick`은 바닥 아이템 엔터티를 포착한 뒤에만 수령자 가방 증가를 확인한다. 출발 가방은 1개 줄었고 사용자는 방어구가 들어왔다고 말했지만, 바닥 엔터티는 `Null`로 기록됐다. 이 분기에서 수령 증가 0은 실제 측정값이 아닌 초기값이다.

완료 사실을 관측하지 못한 실행이 계속 남았다. 이후 상자 보관 목표로 바뀌어도 기존 전달 행동을 계속 선택했다. 바닥 엔터티를 놓친 정확한 순간과 원인은 현재 로그만으로 확정하지 못했다.

### 3. 이전 목표의 관측이 새 목표에 섞인다

`SetGoal`은 목표의 완료·막힘 상태를 지우지만, 실행 관측 문장과 수정번호의 소속을 함께 정리하지 않는다. 미소비 관측이 있으면 새 목표의 판단 계기를 이전 관측으로 덮을 수 있다.

실제 #56 요청의 목표는 구리 광석 5개였는데, 판단 계기에는 직전 나무 곡괭이 작업의 ‘수량 1/1 확보’가 붙었다. 곧 `finish_goal`이 선택돼 구리 0/5인 채 단계가 종료됐다. 코드 경계와 SEND 기록은 일치한다. 전체 입력 원문과 모델 내부 이유가 없어 그 문장이 선택의 유일한 원인이라고 단정하지는 않는다.

### 4. 판단 권한을 지탱할 사실 정보가 충분히 명확하지 않다

기존 공통 실행 계약은 현장 AI가 현재 계획 단계의 완료를 선택하고, 스크립트가 수량·도착·전달 등의 사실을 관측하도록 정했다. 원래 부탁 전체의 완료는 상위 Gemini가 판단한다.

따라서 `finish_goal` 선택권은 합의된 설계다. 이번 투구 단계에서는 전달 실행 없이 그 선택이 나왔고 보유 2개도 유지됐다. Give의 확인 수량과 실행 유무가 목표 옆에 항상 분명히 제시되지 않는 경계가 있다. AI가 현재 사실로 판단하려면 관측마다 목표·대상·실행 회차와 확인 상태가 명확해야 한다.

## 이전과 달라진 이유

공통 실행 685dde4에서 한 번뿐인 관측 알림과 실행 관측 수정번호가 도입됐다. 장비 변경 77484ec7에서는 Give의 6초 미확인 실패 종료가 ‘관측 알림 후 Running 유지’로 바뀌었다. AI가 다음 행동을 고르게 하려는 변경이었으나, 계속하기 이후 다시 판단하는 연결이 충분하지 않았다. 통로 구현 51e07a0에도 방향 대기를 한 번 알리고 입력을 멈춘 채 Running을 유지하는 흐름이 들어갔다.

이 정체 연결과 목표 관측 혼합은 최근 최적화 전 7af8f91에도 있었다. 43c3817 최적화에는 재준비로 약 9~18초 지연된 별도 실기 근거가 있지만, 이번 사용자 실행의 준비 취소는 0회였다. 현재 425초·100초 정체의 직접 원인을 그 재준비 지연으로 설명할 수는 없다.

이전 플레이와 현재 플레이는 월드·주변 적·명령 조건이 달라 체감 변화 전체의 정량 인과는 미확정이다. 다만 과거 자동 실패 종료를 없앤 뒤 필요한 재판단 연결이 빠진 변경은 코드 이력으로 확인됐다.

## 해결 우선순위

1. 실행 중, 다음 선택 대기, 결과 미확인, 완료 상태를 구별한다. 진척 없는 대기에서는 경과 시간과 변한 사실을 갱신해 다시 판단할 수 있게 하고, 계속하기가 무엇을 실행하는지 정확히 제시한다.
2. 관측을 목표·단계·실행 회차·대상에 묶는다. 새 목표에 이전 성공 사실이 붙지 않도록 하고 현재 단계의 실제 수량과 완료 관측을 분명히 제공한다.
3. 전달 결과 확인을 바닥 엔터티 포착에만 의존하지 않도록 고친다. 확인된 전달과 미확인 상태를 구별한다.
4. 새 상위 계획과 현재 몸 행동의 관계를 판단 입력에 표시해, 이전 동작 유지와 전환을 현재 사실에 근거해 고르게 한다.
5. 부탁 완료까지 검증한다. 장비 전달은 수령자 가방 증가와 다음 부위 진행, 통로 이동은 방향 대기 후 선택·전진, 목표 변경은 관측 소속과 새 행동 진입을 확인한다.

## 앞선 검증의 한계

최적화 실기는 API 오류 해소, 화면 응답, 일부 이동을 확인했다. 갑옷 부탁의 최종 수령과 연속 단계 수행, 조용한 상황에서 대기 후 재판단이 계속 발생하는지는 검증하지 못했다. 제가 그 결과로 사용자가 체감하는 수행 능력까지 충분히 확인하지 못한 점이 이번 조사에서 드러났다.

코드·게임·설정은 이번 분석에서 변경하지 않았다. 완료 판단권을 스크립트로 옮기는 정책 변경도 별도 사용자 결정이다.
