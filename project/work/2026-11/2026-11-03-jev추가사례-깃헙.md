# Jev 추가 GitHub 사례: 게임·NPC 원코드 조사

조사일: 2026-11-03. 독립 사실 조사. 기존 mrubens/jevcraft, sc2musa/Jev_Star, NevaMind-AI/JevTown 외에 부모 작업에서 지정한 4개 저장소를 확인했다. 설치·실행·API 유료 호출은 하지 않았다. 공개 README, 구현 파일, 검증 문서만 읽었다.

## 핵심 결과

네 사례 모두 TypeSafe Jev의 실제 호출 경로가 있다. Core Keeper 캐릭터의 판단 계층에 가장 가까운 것은 **HEIST//ONE의 경비 NPC**다. 다만 공개된 연결 코드의 존재, 작성자의 실험 결과 보고, 독립 재현은 서로 다른 증거 수준이다. 이번 조사에서는 원코드를 확인했고 작성자 보고를 대조했으며 독립 재현은 하지 않았다.

## 1. AbdelStark/heist-one — 경비 NPC의 국소 판단

- 저장소: https://github.com/AbdelStark/heist-one
- 확인 커밋: `632c9a55a1e5eb2cbf0b9f87db575f0b5eb36e8c` (2026-09-17).
- 성격: 독립 커뮤니티 프로젝트. README가 TypeSafe와의 제휴·공인을 명시적으로 부인한다. 6명 경비가 있는 박물관 잠입 게임의 MVP다.

**입력과 출력.** `compileJevRequest()`는 월드 tick/alert와 각 경비의 local context를 넣고 경비마다 네 질문을 만든다. 위협 존재는 Noul, 의심 정도는 5단계 rubric의 Score, 즉시 행동과 주의 대상은 Choice다. 행동 후보에는 순찰 유지, 관찰, 조사, 신원 확인, 추격, 유물 보호, 보고, 경보, 지원 요청이 있지만 매 호출에는 해당 경비의 `legalIntents`만 들어간다. 주의 대상도 `attentionOptions`로 제한한다. [질문 생성 코드](https://github.com/AbdelStark/heist-one/blob/632c9a55a1e5eb2cbf0b9f87db575f0b5eb36e8c/apps/server/src/jev.ts#L47)

**실제 호출.** 공식 `@typesafe-ai/sdk`의 `TypeSafeClient`를 생성하고 `decide()`에서 `client.systemOne({state, questions})`을 호출한다. 응답 타입을 검사하여 경비별 판단으로 복원한다. `session.ts`는 `mode === "jev"`이고 API key가 있을 때 실제 `JevDecisionEngine`을 선택한다. 키가 없는 일반 실행은 scripted mode일 수 있으므로 모든 시연을 Jev 실행으로 간주하면 안 된다. [호출](https://github.com/AbdelStark/heist-one/blob/632c9a55a1e5eb2cbf0b9f87db575f0b5eb36e8c/apps/server/src/jev.ts#L140), [세션 연결](https://github.com/AbdelStark/heist-one/blob/632c9a55a1e5eb2cbf0b9f87db575f0b5eb36e8c/apps/server/src/session.ts#L71)

**작성자가 공개한 결과.** 2026-09-17 TypeSafe sandbox에서 jacket → badge → vault → artifact → exit 경로를 browser-controlled 방식으로 완료(`won`)했다고 보고한다. 12 batch 요청, 288 typed judgments, 성공 응답 12, 오류·fallback·stale 모두 0; adapter latency 중앙값 259.9ms, p95 344.1ms다. 이는 **하나의 종단 간 실행**이다. 플레이어의 완주이지 Jev NPC의 전투력·적대적 지능 우위를 입증하는 결과는 아니다. [검증 문서](https://github.com/AbdelStark/heist-one/blob/632c9a55a1e5eb2cbf0b9f87db575f0b5eb36e8c/docs/LIVE-JEV-VERIFICATION.md)

**한계.** 검증 문서는 원본 JSONL이 `traces/`의 git-ignored 로컬 파일로 남아 있다고 명시한다. 세션 ID·checkpoint hash·영상 hash는 공개됐으나 원자료를 내려받아 수치를 다시 계산할 수는 없었다. 실제 공급자 비용은 응답에 없어 unknown이다. 30Hz는 서버 시뮬레이션 속도이며 Jev 요청 빈도가 아니다. 일반 scripted AI와의 사전 정의된 반복 비교는 향후 과제로 기재돼 있다. [README](https://github.com/AbdelStark/heist-one/blob/632c9a55a1e5eb2cbf0b9f87db575f0b5eb36e8c/README.md)

**응용 판단(조사자 해석).** Core Keeper 캐릭터에도 보이는 객체/위협/소지품/플레이어 요청을 근거로 합법 행동 후보를 만들고, Jev는 짧은 판단을 공급하며 실행기는 이를 검증하는 구조를 가져오기 좋다. 이 저장소는 자유로운 장기 계획이나 자연어 대화의 근거는 아니다.

## 2. AmoghCreator/doom-jev — ViZDoom 전투 에이전트

- 저장소: https://github.com/AmoghCreator/doom-jev
- 확인 커밋: `b27663fc0fa386f9d15ad6ea3c8f15374b855479` (2026-09-17).

**실제 호출과 판단.** `agent/jev_client.py`는 `https://api.typesafe.ai/v1/systemone`에 Bearer 인증으로 POST하고 모델 `jev-latest`를 지정한다. `macro_goal`(engage/collect_weapon/explore/flee), `target`, `movement`, `rotation`은 Choice, `jump`와 `firing`은 Noul이다. 입력은 화면 픽셀 대신 ViZDoom 상태를 직렬화한 YAML이고 보이는 적 후보가 동적으로 주어진다. [요청 코드](https://github.com/AmoghCreator/doom-jev/blob/b27663fc0fa386f9d15ad6ea3c8f15374b855479/agent/jev_client.py#L107)

**게임 연결과 보정.** `main.py`는 비동기로 `get_decision()`을 요청하고 결과를 `resolve_dag()`로 보내 ViZDoom 버튼 배열로 바꾼다. 응답 사이에는 마지막 행동을 유지한다. `composition_dag.py`에서는 보이는 적이 있으면 기하학적 조준이 Jev의 회전 제안을 덮어쓴다. 선택된 적을 못 찾으면 가장 가까운 가시 적을 찾는 fallback도 있고, 조준각 조건이 맞으면 Jev의 낮은 firing 판단에도 코드가 자동 사격할 수 있다. 따라서 ‘Jev 혼자 조준·사격을 완전히 결정’한 사례로 쓰면 부정확하다. [메인 루프](https://github.com/AmoghCreator/doom-jev/blob/b27663fc0fa386f9d15ad6ea3c8f15374b855479/main.py), [기하/사격 보정](https://github.com/AmoghCreator/doom-jev/blob/b27663fc0fa386f9d15ad6ea3c8f15374b855479/agent/composition_dag.py#L88)

**성과와 한계.** README는 비동기 실시간 플레이와 약 10Hz inference를 설명하지만 공개 점수·승률·반복 seed·측정 로그는 확인하지 못했다. 코드의 실제 상수는 `GAME_TICRATE=35`, `TICKS_PER_DECISION=4`이므로 요청 기회는 약 8.75Hz이고, `api_task is None`일 때만 새 호출하므로 실제 호출률은 네트워크 지연에도 제한된다. README의 ‘0 dropped frames’도 이번 조사에서 검증된 결과가 아니다. 파일 머리의 오래된 60fps 설명보다 현재 실행 상수를 기준으로 해석해야 한다. [README](https://github.com/AmoghCreator/doom-jev/blob/b27663fc0fa386f9d15ad6ea3c8f15374b855479/README.md), [실제 상수/루프](https://github.com/AmoghCreator/doom-jev/blob/b27663fc0fa386f9d15ad6ea3c8f15374b855479/main.py#L28)

## 3. mizuamedesu/SuperTuxKart-Jev — 실제 레이싱 엔진 제어

- 저장소: https://github.com/mizuamedesu/SuperTuxKart-Jev
- 확인 커밋: `49b94197c8723a97da3ab2ce2703430e1175aa09` (2026-09-17).

**실제 호출과 판단.** C++ 엔진 컨트롤러가 레이스/차량/물리/경로 데이터를 로컬 UDP로 보내고 Node bridge가 Vercel AI Gateway의 `gateway.evaluationModel("typesafe-ai/jev")`를 `experimental_evaluate()`로 호출한다. 조향 7개 Choice, 스로틀 4개 Choice, drift/nitro/use_item/rescue boolean 질문을 함께 보낸다. 화면 인식 에이전트가 아니라 엔진 telemetry를 읽는 통합이다. [설명](https://github.com/mizuamedesu/SuperTuxKart-Jev/blob/49b94197c8723a97da3ab2ce2703430e1175aa09/JEV_DEMO.md), [모델 호출](https://github.com/mizuamedesu/SuperTuxKart-Jev/blob/49b94197c8723a97da3ab2ce2703430e1175aa09/tools/jev-controller/bridge.mjs#L253)

**코드의 몫.** `decision.mjs`는 곡률별 추천 속도, predicted heading/offset, yaw damping, 조향 요구각, throttle guidance까지 미리 계산한다. Jev의 조향 프롬프트에는 요구각 부호를 뒤집지 말라는 제한도 있다. 응답을 수치 제어로 매핑하고 정지 상태의 brake를 전진 복구로 바꾸는 보정이 있다. bridge도 추가 runtime guard를 적용한다. [사전 계산/응답 매핑](https://github.com/mizuamedesu/SuperTuxKart-Jev/blob/49b94197c8723a97da3ab2ce2703430e1175aa09/tools/jev-controller/decision.mjs), [추가 보정](https://github.com/mizuamedesu/SuperTuxKart-Jev/blob/49b94197c8723a97da3ab2ce2703430e1175aa09/tools/jev-controller/bridge.mjs#L494)

**엔진 실행 확인.** `JevController::pollCommands()`가 UDP 명령을 받고 범위를 제한하며 `applyCommand()`가 실제 kart steer/accel/brake/nitro/drift/rescue/fire를 설정한다. 중복·순서 뒤집힘을 거르고 제어가 끊기면 watchdog이 보정한다. [C++ 적용](https://github.com/mizuamedesu/SuperTuxKart-Jev/blob/49b94197c8723a97da3ab2ce2703430e1175aa09/src/karts/controller/jev_controller.cpp#L401)

**성과와 한계.** 실행 문서와 구현은 있지만 공개 완주 시간·순위·승률·반복 실험 결과표는 확인하지 못했다. 기본 100ms/10Hz는 요청 dispatch 설정이며, 최대 in-flight 12와 비동기 overlap을 둔다. 실제 request/result/applied rate는 별도다. 프로토콜 문서의 `RESULT 9.8 Hz`, `APPLY 8.1 Hz`, `410 ms`는 예제 JSON에 들어간 값이므로 실험 결과로 인용하지 않는다. mock은 deterministic transport test이며 Jev 성능이 아니다. [프로토콜](https://github.com/mizuamedesu/SuperTuxKart-Jev/blob/49b94197c8723a97da3ab2ce2703430e1175aa09/doc/jev-controller-protocol.md)

## 4. leftspace89/JevBird — 파이프 단위 경로 선택

- 저장소: https://github.com/leftspace89/JevBird
- 확인 커밋: `e5ace2cd9dbf73ae08d2943475a4c97eb67deb16` (2026-10-04).

**실제 호출과 판단.** `JevPilot`은 기본 경로에서 Python `typesafe_sdk.TypeSafeClient`를 생성하고 `_ask()`에서 `system_one(state, questions)`을 호출한다. `path` Choice로 비행 경로를 고르고 `danger` Noul로 파이프 난도를 판단한다. danger는 HUD용이며 행동을 바꾸지 않는다. [SDK 생성/호출](https://github.com/leftspace89/JevBird/blob/e5ace2cd9dbf73ae08d2943475a4c97eb67deb16/jev_pilot.py#L310), [질문/후보](https://github.com/leftspace89/JevBird/blob/e5ace2cd9dbf73ae08d2943475a4c97eb67deb16/jev_pilot.py#L216)

**핵심 설계.** 코드가 55개의 단순 flap 정책을 시뮬레이션하고 중복 경로를 줄인다. 충돌하지 않는 후보가 2개 이상이면 충돌 후보를 빼고, 중앙선에서의 최대 이탈로 정렬한 상위 10개를 보낸다. Jev는 새 경로를 생성하지 않는다. 다음 파이프의 간격도 미리 알고 시뮬레이션한다. 답변 지연을 예측해 미래 상태에서 경로를 만들며, 35px 이상 경로 이탈이면 재요청하고 0.3초 안의 충돌이 예상되면 emergency flap이 Jev 계획을 덮어쓴다. [구조 설명](https://github.com/leftspace89/JevBird/blob/e5ace2cd9dbf73ae08d2943475a4c97eb67deb16/HOW_JEV_PLAYS.md)

**작성자 보고.** README는 150초씩의 headless runs에서 약 0.55 calls/s(파이프당 약 1회), 일반 round-trip 0.30초, 관측 최악 1.2초, 녹화 점수 47 pipes라고 적는다. 2분 35초 MP4와 GIF 파일을 공개한다. 이는 작성자 측 측정·녹화이며 이번 조사에서 영상을 재분석하거나 실험을 재현하지 않았다. [결과/미디어 링크](https://github.com/leftspace89/JevBird/blob/e5ace2cd9dbf73ae08d2943475a4c97eb67deb16/README.md)

**한계.** README의 입력 토큰 범위는 1,800–2,800, 상세 문서는 1,800–2,500으로 다르므로 고정 성능치로 사용하지 않는다. 단순히 시뮬레이터 1위 후보를 고르는 정책과의 대조 실험은 확인하지 못했다. Jev의 추가 이득과 코드의 forward simulation 기여를 분리할 수 없다. 또 `JEV_BASE_URL`을 설정하면 Jev 대신 Laya 같은 자체 호스팅 호환 서버로 보내므로 그 모드의 결과를 Jev 결과로 계산하면 안 된다. [구현](https://github.com/leftspace89/JevBird/blob/e5ace2cd9dbf73ae08d2943475a4c97eb67deb16/jev_pilot.py#L310)

## 적용 시사점 — 사실에서 도출한 해석

반복되는 패턴은 ‘게임 상태를 구조화 → 코드가 후보/실행 가능성을 계산 → Jev가 짧은 typed judgment → 코드가 신선도와 합법성을 검증 → 게임 엔진이 실행’이다. 캐릭터의 반사적 판단을 붙이는 근거는 있지만, 무제한 자율 행동·긴 목표 계획·대화 능력이 자동으로 생긴다는 근거는 없다. FPS·레이싱·Flappy Bird 사례는 특히 코드의 인지/예측/자동 보정 기여가 커서, Jev 자체의 우월함보다는 **혼합 제어 구조가 구현 가능함**을 보여준다.
