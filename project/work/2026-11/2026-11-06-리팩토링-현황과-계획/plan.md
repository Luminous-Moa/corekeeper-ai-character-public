# 코어키퍼 봇 구조 개선 계획

## 목적과 판단 기준

비효율적으로 흩어진 공통 규칙을 모으고, 한곳에 섞인 서로 다른 책임을 나누어 이후 개발과 유지보수를 쉽게 만든다. 다음 기지 기능만을 위한 최소 정리로 한정하지 않는다.

주 흐름은 호스트의 말·명령 → 위쪽 모델의 목표 → 게임 관측과 행동 후보 → 현장 모델의 선택 → 몸의 실행 → 결과·기억·다음 판단이다. 이 흐름의 각 단계가 무엇을 입력받고, 무엇을 결정하며, 어떤 상태를 바꾸는지 읽을 수 있게 하는 것이 목표다.

좋아졌다는 기준:
- 같은 규칙을 바꿀 때 여러 기능의 복사본을 찾아다니지 않는다.
- 새 목표 종류의 공통 선언과 기능별 행동 구현을 어디에 넣는지 명확하다.
- 문자열 표현을 바꾸어도 행동 분류가 달라지지 않는다.
- 상태를 바꾸는 곳과 읽는 곳이 명확하며, 숨은 선행 호출에 기대지 않는다.
- 이미 확인된 동작·저장·보고 계약과 판단 준비 비용을 보존한다.

파일 수나 줄 수 감소, 모든 중복 제거, 새로운 범용 프레임워크 구축은 완료 기준으로 삼지 않는다.

## 단계별 추천안

### 0. 기준과 경계 확정

a07166f에서 별도 작업 브랜치·worktree를 만들고 현행 오프라인 관문을 기준으로 기록한다. 기존 SDK 로컬 설정은 필요한 것만 복사한다. 모델·프롬프트·후보 순서와 상한·종료 순서·저장 포맷·보고 문자열을 보존 계약으로 잡는다.

최근 실게임 로그를 변경 전 증거로 먼저 사용한다. 이번 수정 경로의 정상·막힘·취소를 비교할 근거가 없을 때만 변경 전 재현을 추가한다. 이미 존재하는 replay·logshape·movecheck·core-tests·가짜 브리지를 재사용한다.

완료: 현재 동작, 변경할 책임, 의도적으로 남길 차이, 비교 시나리오가 한 문서로 정해진다.

각 구현 묶음 착수 전에 변경 책임 → 관측 가능한 기존 동작 → 확인 방법을 연결한다. 기준 근거가 없으면 먼저 확보하며, 확보할 수 없는 책임의 분리는 보류한다. 예를 들어 명령/채팅은 대상 캐릭터와 전달 순서, 저장은 기존 저장 읽기와 재접속 복원, 입력 hook은 주입·정지·해제, 탐험/파들어가기는 후보·경로·취소를 대조한다. 각 묶음의 완료 시 미검증 변경 책임이 없어야 하며 게임에서만 볼 수 있는 동작은 필요한 실게임 확인까지 표시한다. 모든 기능을 매번 전수 시험하는 요구는 아니다.

### 1. 목표의 공통 선언과 기능별 책임 정리

대상은 목표 낱말·종류·입력 범위·보고 가능 목록·경험 키와, 목표 시작/완료/막힘에서 반복되는 종류별 분기다.

- 공통 메타데이터는 하나의 C# 정의에서 읽게 한다.
- 제작·요리·농사·놓기 등의 실제 후보·완료·막힘 판단은 해당 기능이 소유한다. 큰 중앙 표에 모든 실행 로직을 옮기지 않는다.
- 판단 루프는 처리 순서를 조율하고, 목표별 규칙은 명확한 기능 진입점을 통해 호출한다.
- C# 정의와 브리지의 허용 목표·모델 설명은 같은 계약 사례로 대조한다. 언어를 넘는 런타임 플러그인 체계나 코드 생성기를 새로 만들 필요는 없다.

완료: 새 목표 추가 시 공통 선언과 해당 기능 구현, 외부 계약 대조 위치가 명확하다. 현행 목표 종류별로 입력 형식·허용 범위·실행 담당·끝/막힘·보고/경험 키를 연결한 계약 목록을 만들고, 누락 또는 C#과 브리지의 허용 종류/범위 불일치가 자동 검사에서 드러나게 한다. 현재 목표의 시작·완료·막힘·취소 결과와 호출 순서는 같다.

### 2. 후보의 의미와 표시 문장 분리

둘레 보수·문 놓기·일반 놓기 등의 분류를 설명 문장 앞부분으로 판단하는 경로, 부서짐 계기의 문장 판정, 여러 뜻으로 쓰이는 후보 필드를 정리한다.

- 분류에 필요한 의미는 코드값으로 전달하고, 문장은 마지막 출력 단계에서 만든다.
- 후보의 공통 정보와 행동별 인자를 구분한다. 모든 행동을 한꺼번에 거대한 타입 계층으로 바꾸지 않고 실제 오용이 있는 필드부터 한다.
- 후보 조립기는 순서·상한·묶음 규칙을 담당한다. 분야별 후보 생성과 섞지 않는다.
- 과거 기록을 읽기 위한 문장 판독과 현재 실행을 위한 판정은 구별한다. 아직 실제로 보지 못한 기존 막힘 갈래를 추정만으로 제거하지 않는다.

완료: 설명 문장 수정이 후보 종류나 배정 몫을 바꾸지 않는다. 같은 입력의 후보 ID·순서·상한·핵심 사실이 기존과 같다.

### 3. 공간 사실과 이동 후보의 중복 정리

칸·문·물체를 읽는 공통 사실과, 목적별로 그 사실을 해석하는 규칙을 나눈다.

- 이미 모인 DoorCell, OwnDoorStands, MyDoorLook, PassSide, StandTile, PlanFrom, AISettle, AIPressQueue를 재사용한다.
- 둘레용·도달용·놓기용 격자에는 목적 차이가 있다. 공통 판독을 재사용하되 서로 다른 차단 의미를 유지한다.
- 설 칸 → 경로 계산 → 이동/파기 후보 조립 중 실제로 같은 부분을 공유한다. 최대 검사 수, 후보 키, 경로 캐시, 우회 검사 허용 여부, 둘레 개방 허용 여부, 설명은 명시적으로 보존한다.
- AIPlaceGoal.Go를 다른 기능에 그대로 적용하지 않는다. 이 경로는 우회 비교·둘레 경로 후보·문 통과 사실을 추가하는 동작까지 갖고 있다.
- '기지 안'은 생활 범위, 둘레 안쪽, 도착 판정처럼 용도를 드러내는 이름으로 구분한다. 하나의 boolean으로 강제 통일하지 않는다.
- 물체 종류와 장소 ID는 공통 판독 경로를 검토하되, 분류 결과나 ID가 달라지는 수정은 동작 변경으로 별도 판정한다.

완료: 같은 사실 판독의 복사본이 줄고, 목적별 차이가 함수 계약에 드러난다. 기존의 문·물·다리·미지 칸·기지 안팎 사례와 경로 계산 비용을 보존한다.

### 4. 큰 파일의 혼합 책임과 상태 소유 정리

위 단계에서 드러난 경계를 따라 파일과 상태를 함께 정리한다.

- AICraft에 섞인 놓기 자리 판정·놓기 실행을 제작 책임과 구분한다.
- AIBodySkills는 몸의 단일 실행 책임을 유지하면서, 명령 처리·게임 관측/시야·이동 계산·개별 기술을 기존 형식 경계에 따라 나눈다. 단순 partial 이동으로 충분한 곳과 상태 접근을 좁혀야 하는 곳을 구별한다.
- AIExplore에 함께 있는 탐험·기억 저장·드롭 지식·물체 조회·파들어가기, AIPlayerSpikeMod에 섞인 초기화·채팅·입력 패치·캐릭터 저장은 독립적으로 이해하고 수정할 수 있는 경계부터 분리한다. 실행 순서와 게임 hook은 보존한다.
- AIEdge의 계획·기억과 문 관측·위협/도달 계산의 경계를 드러낸다. 순수 계산 Core와 게임 데이터 판독의 구분을 유지한다.
- AIBrain.Candidates의 분야별 후보 생성과 최종 조립을 구별한다. AIBrain.Loop에는 판단 준비·호출·적용의 주 순서가 보이게 한다.
- 적 위협 정보를 조회하면서 다른 조회가 읽을 캐시를 갱신하는 순서 의존을 줄인다. 먼저 같은 판단 구간에서 필요한 정보를 만들고 소비자가 읽게 하되, 거리·기억·자기 방어처럼 목적이 다른 적 목록을 무조건 통합하지 않는다.
- 판단 준비 임시값과 지속 상태를 구별한다. 비동기 후보 계산·미리 묻기·늦은 모델 응답·목표 교체에서 어떤 시점의 관측과 목표 번호를 읽는지 확인하고, 임시값을 옮길 때 캐릭터/판단 사이에 섞이지 않도록 수명을 검증한다.
- 기억 조회에는 Ensure를 통해 월드 전환·저장에 닿는 경로가 있다. 조회라는 이름만으로 순수 함수로 간주하지 않고 실제 읽기·갱신·저장 시점을 구분한다.
- 파일만 옮기는 변경과 상태 수명/갱신 시점이 달라지는 변경을 별도 커밋·검증 단위로 둔다. 후자는 현행 순서와의 차이가 있으면 사용자 판단 항목으로 되돌린다.

완료: 해당 책임을 고칠 위치와 상태를 만들고 갱신하고 버릴 주체가 명확하다. 파일 분할 후에도 같은 정적 상태를 여러 파일이 임의로 바꾸는 구조를 개선으로 치지 않는다.

### 5. 통합 확인과 다음 개발 인계

각 묶음은 컴파일과 관련 시험·독립 검수 뒤 합칠 수 있는 단위로 끝낸다. 최종 묶음에서는 다음 대표 실제 경로를 확인한다.

호스트가 제작/놓기 목표를 말함 → 상위 목표 수용 → 현재 관측으로 후보 생성 → 현장 모델 선택 → 자기 문을 지나 재료/목적지로 이동 → 놓기·제작 수행 → 완료/막힘을 보고하고 기억에 반영.

추가 회귀는 변경 경계에 맞춘다: 문 시야 밖 기억과 사라짐, 둘레 안팎과 두 문 통로, 경로 재계산 시 둘레 개방 중단, 목표 취소·교체, 캐릭터 간 상태 격리. 전투 상태를 옮겼다면 위협 있음/없음·자기 방어 진입/이탈도 확인한다.

게임 시험은 사용 일정·설치본·월드 보존을 확인한 뒤 수행한다. 시험 월드는 복원 전에 게임 안에서 지워 Steam Cloud에 남지 않게 한다. Unity 배치와 게임을 동시에 실행하지 않는다. 현재 요청에서는 이 실행을 하지 않는다.

함수·파일 이동 후 개발 그래프의 앵커와 제품 그래프 스냅샷을 갱신한다. 과거 실측을 새 코드의 실측으로 승격하지 않는다. 최종 변경은 검증 근거와 남은 차이를 제시한 뒤 기존 승인 조건에 따라 병합한다.

| 생활 기지 범위를 반경에서 둘레 기준으로 변경 | 시설 선택·home·농사 범위가 바뀜 |
| BaseStand·StandTilesFor 등에 더 엄격한 설 칸 조건 적용 | 지금 허용하는 접근 경로가 막힐 수 있음 |
| 농사 경로를 무조건 PlanC 캐시로 전환 | 탐색 시점·비용·갱신 의미가 달라짐 |
| 모든 이동에 우회 비교 적용 | 과거 검사 범위를 줄인 비용 결정과 충돌 |
| 물체 분류를 이름에서 컴포넌트로 일괄 변경 | 보고 종류·장소 식별자·후보가 달라질 수 있음 |
| 둘레 뿌리 채굴 금지, 기지 일을 코드가 자동 선택 | 모델의 선택 정책을 바꾸는 제품 변경 |
| 놓은 물건 기억 저장소 통합 | 저장 형식·기존 기억 이전 문제 발생 |

이 항목들은 현재 구조를 명확히 정리한 뒤 필요성이 입증되는 것을 별도 기능 수정으로 제안한다. 새 저장소, 전면적인 격자 통합, 모든 캐릭터 상태의 객체화, 모델 교체는 이번 권고 범위에 넣지 않는다.

## 실행 단위와 우선순위

전체 방향은 1~4를 단계적으로 수행하는 것이다. 첫 구현 묶음은 0~2로 권고한다. 목표 추가 비용과 문장 계약 문제를 먼저 줄이고, 3의 공간·이동 정리, 4의 책임·상태 정리를 이어간다. 4의 단순 파일 이동은 해당 책임을 다루는 앞 단계와 함께 할 수 있다. 기지 단계 4 기능 개발은 합의한 구조 정리 묶음이 검증된 뒤 재개한다.

각 단계의 상세 설계에서 실제 공통분모가 작으면 작은 함수로 끝낸다. 동작 불변을 지키려면 많은 스위치와 예외가 필요한 공통화는 그 경계를 다시 나눈다. 처음부터 큰 추상화를 정답으로 고정하지 않는다.

## 계획 검토

[독립 검토](review.md)에서 목적 부합, 중앙 표 비대화 방지, 목표 누락 검사, 판단 상태 수명을 확인했다. 남은 권고인 '넓어진 책임 분리 범위와 검증의 대응'은 위 단계 0의 묶음별 착수·완료 조건에 반영했다. 이 문서는 구현 명세나 사용자 실행 승인으로 대신 쓰지 않는다.
