# 게임 지식그래프 2단계: 설계

작업 브랜치: 게임-지식그래프 (2026-11-04). 설계만 했다. 코드·게임·Unity·브리지는 건드리지 않았다.
근거: [1-데이터-뽑기-확인.md](1-데이터-뽑기-확인.md). Conf 실제 구조, 디컴파일 참고본(`C:\Dev\_ref\corekeeper-decomp`), 지금 모드 코드(main 2678a64), 생활 worktree(`ai-life` 509ebd5)의 바뀐 파일 목록을 직접 확인했다.

## 0. 합의된 것 (다시 정하지 않음)

- 출처는 게임 데이터만 쓴다.
- 전체 그래프는 하나이고 모든 캐릭터가 공유한다.
- 캐릭터에게는 열린 부분만 보인다.
  - 본 적 있거나 가진 적 있는 아이템·물체가 열린다.
  - 본 적 있는 제작대는 그 레시피 목록이 열린다.
  - 열린 것끼리의 관계만 보인다.
  - 캐릭터마다 따로 열린다.
- 사람(개발자)은 전체를 본다.
- 본 데이터는 모드의 시험 스위치 뒤 "지식 뽑기" 명령으로 뽑는다. 실행은 게임 실기 시험이 끝난 뒤다.
- 그 전에는 Conf로 뼈대·형식·열림 규칙·조회를 만든다.

## 1. 전체 모양

```
[게임 설치본 Conf JSON] ─┐
                          ├─ build.mjs ─→ graph.json (게임 빌드별, 전체)
[모드 뽑기 명령 dump.json]┘                     │
                                                ├─ kg.mjs (개발자 조회: 전체)
[모드: 캐릭터별 known.json] ───────────────────┤
                                                └─ 브리지: 보고에 "knowledge" 칸 (열린 부분, 목표·가방 관련만)
```

- **모드(C#)는 두 가지만 한다:** 뽑기 명령, 캐릭터별 "봤다·가졌다" 기록.
  - 둘 다 새 파일 `AIKnowledge.cs` 하나에 둔다.
  - 기존 파일에는 부르는 줄만 넣는다(아래 2·3장).
- **그래프 만들기와 조회는 Node 쪽**이다. 새 폴더 `Tools/knowledge/`에 둔다.
  - 이유 1: 게임을 다시 빌드하지 않고 고칠 수 있다.
  - 이유 2: 소비자인 위쪽 LLM의 보고를 브리지가 이미 받고 있다.
  - 이유 3: 개발자 조회 도구와 같은 코드를 쓴다.

## 2. 그래프 형식

### 노드 (키 = ObjectID 숫자, 드롭 표·바이옴·조건은 앞에 접두어)

| 종류 | 키 | 무엇 | 출처 |
|---|---|---|---|
| object | `o:<ObjectID>` | 아이템·설치물·벽 물체·광석·적 등 게임 물체 전부 | 이름·번호: Conf `ID/ObjectID.json` · 종류·수치: 뽑기 |
| loot | `l:<LootTableID>` | 드롭 표 | Conf `Loot/*.json`, 이름: `ID/LootTableID.json` |
| biome | `b:<Biome>` | 바이옴 | Conf `ID/Biome.json` |
| cond | `c:<ConditionID>` | 효과(체력 회복, 채굴 피해 + 등) | 이름: Conf `ID/ConditionID.json` · 값: 뽑기 |
| tile | `t:<tileset>:<tileType>` | 타일(벽·바닥) | 이름: Conf `ID/PugTilemap.*` · 물체 연결: 뽑기 |

object 노드의 속성(뽑기 뒤 채워짐):
- `kind`: ObjectType 원값에 `role` 태그를 더한다. role은 `tool`·`weapon`·`food`·`placeable`·`station`·`material`·`creature`·`wall`·`ore` 중 여럿.
  - role은 ObjectType과 컴포넌트 유무로 build가 정한다. 예: CanCraftObjectsBuffer가 있는 설치물이면 station.
- 그 밖: `name_ko`, `name_en`, `rarity`, `stackable`, `craftingTime`, `health`, `damageReduction`, `weaponDamage`, `durability`, `sellValue`.

### 관계

| 관계 | 방향 | 속성 | 출처 |
|---|---|---|---|
| `ingredient` | 재료 o → 결과 o | 개수 | 뽑기: `EntityObjectInfo.requiredObjectsToCraft` |
| `crafted_at` | 결과 o → 제작대 o | 만들어지는 개수 | 뽑기: 제작대 프리팹의 `CanCraftObjectsBuffer` |
| `hand_craft` | 결과 o → (손) | 개수 | 뽑기: 플레이어 프리팹의 `CanCraftObjectsBuffer` |
| `uses_loot` | o → l | | 뽑기: `EntityObjectInfo.lootTableID`(디컴파일에서 뱅크 항목에 직접 있음 확인), 적은 `DropsLootFromLootTableCD`로 보충 |
| `loot_item` | l → o | 가중치, 개수 min/max, 보장 여부, 바이옴 한정 | Conf `Loot/*.json` |
| `spawns_in` | o → b | initial/respawn, tileset, 확률 | Conf `Spawn/Initial/<바이옴>/*.json`, `Spawn/Respawn/*.json` |
| `tile_is` | t → o | | 뽑기: `PugDatabase.GetObjectID(tileset, tileType)` |
| `gives` | o → c | 값, 시간, 먹을 때/장착할 때 | 뽑기: `GivesConditionsWhenConsumedBuffer` / `…WhenEquippedBuffer` |
| `mineable_by` | 벽·광석 o → 도구 o | 예상 타격 수 | **계산**(아래) |
| `requires` | 결과 o → 조건 | 보스 처치 등 | 뽑기: `CraftingPrerequisites`(**위치 미확인**, 아래 6장) |

- **계산 관계는 표시를 붙인다.** `mineable_by`에는 `derived: "hp/(damage-reduction)"`를 단다. 벽 `health`·`damageReduction`과 도구 채굴 피해(장착 효과 `gives`)로 build가 만든다.
  - 모드의 굴 계획(AITunnel)과 같은 식을 쓴다.
  - 게임이 직접 준 사실과 구분하기 위해서다(지식그래프 이론 01: 관찰·투영 구분).
- **뽑지 못한 것도 기록한다.** 예: 어떤 물체의 프리팹을 못 찾음, 이름 번역이 없음. 이런 것은 `unresolved` 목록에 남긴다. 조회는 "모름"으로 답하고, 없는 사실처럼 비워 두지 않는다(이론 06).

### 파일과 위치

- 코드: `Tools/knowledge/` — `build.mjs`(그래프 만들기), `kg.mjs`(조회 라이브러리 + 개발자 명령줄), `README.md`.
- 데이터: `Tools/knowledge/data/<steam buildid>/`
  - `conf/`: Conf에서 필요한 파일 사본
  - `dump.json`: 뽑기 결과 사본
  - `graph.json`: 만든 그래프
  - `data/current.txt`: 지금 쓰는 buildid
- **게임 데이터는 git에 넣지 않는다**(`.gitignore`). "GitHub에는 모드 파일만"이라는 기존 결정과 맞고, 게임 데이터를 공개 저장소에 올리지 않기 위해서다. 코드만 올린다.
- graph.json 머리:
  ```json
  {"version":1,"game":{"steamBuildId":26332184,"appVersion":"<dump의 Application.version>"},
   "built":"<시각>","sources":{"conf":"<경로, 파일 수>","dump":"<시각, 모드 커밋>"},
   "nodes":{...},"edges":[["ingredient","o:3","o:27",{"n":2}],...],"unresolved":[...]}
  ```
  - 관계는 배열 한 줄로 둔다(작고, 거꾸로 찾기 색인은 kg.mjs가 읽을 때 만든다).
  - 크기 추정: 물체 약 2400개, 관계 수천 개로 1~3MB. 브리지가 시작할 때 한 번 읽으면 된다.

### 다시 뽑을 때 (게임 버전 표시)

- 게임 빌드는 Steam `appmanifest_1621690.acf`의 `buildid`로 판단한다(확인 시점 26332184). 뽑기 결과에는 게임의 `Application.version`도 담는다.
- `build.mjs`는 시작할 때 설치본의 buildid를 읽는다.
  - `current.txt`와 다르면 새 폴더를 만들고 Conf를 다시 복사한다.
  - dump.json의 빌드가 다르면 "뽑기를 다시 하라"고 알리고, Conf 부분만으로 만든다(낡은 dump를 새 빌드에 섞지 않는다).
  - 옛 빌드 폴더는 남겨 둔다(바뀐 점 비교용).
- 브리지와 kg.mjs는 graph.json의 buildid가 설치본과 다르면 경고만 하고 계속 쓴다.

## 3. 뽑기 명령 명세 (모드)

- 위치: 새 파일 `Assets/AIPlayerSpike/Scripts/AIKnowledge.cs`의 `AIKnowledge.Dump(World server)`.
- 부르는 법: 시험 명령 `/ai kgdump`. 기존 시험 명령과 같이 `testcmds.on` 스위치 뒤에 둔다.
  - 기존 파일 변경은 두 군데뿐이다.
    - `AIBody.TestCommands` 배열(AIBodySkills.cs:658)에 이름 하나 추가
    - 명령 분기(AIPlayerSpikeMod.cs)에 `case "kgdump"` 한 줄
- 하는 일: 서버 월드에서 `DatabaseBankCD` 싱글턴의 `objectInfos` 전체(BlobArray<EntityObjectInfo>)를 돈다. 모드가 이미 같은 방법으로 은행을 얻는다(AIBodySkills.cs:1009). 항목마다 다음을 쓴다.
  - `EntityObjectInfo`: objectID, variation, objectType, rarity, sellValue, lootTableID, craftingTime, isStackable, prefabTileSize, tileset, tileType, requiredObjectsToCraft[]
  - 프리팹 엔티티(`GetPrimaryPrefabEntity(id, bank, variation)`)에 있는 컴포넌트:
    - `CanCraftObjectsBuffer`[] (objectID, amount, craftingTimeOverride)
    - `HealthCD`(max)
    - `DamageReductionCD`
    - `WeaponDamageCD`
    - `DurabilityCD`
    - `DropsLootFromLootTableCD`
    - `GivesConditionsWhenConsumedBuffer`[]
    - `GivesConditionsWhenEquippedBuffer`[]
    - `TileDamageTagCD`
    - `FactionCD`(있으면)
    - 그 밖에 `CraftingPrerequisites`를 담은 컴포넌트를 찾으면 그 값
  - 표시 이름 한국어·영어: 게임 로컬라이즈 API(I2 `LocalizationManager.GetTranslation` 계열로 추정, 구현 때 확인). 실패하면 비우고 unresolved에 남긴다.
  - 타일 → 물체: Conf `PugTilemap.Tileset × TileType` 조합 가운데 `GetObjectID`가 None이 아닌 것만.
  - 플레이어 프리팹의 손 제작 목록(`CanCraftObjectsBuffer`): 모드의 `AICraft.HandRecipes`와 같은 출처.
- 출력: `<persistentDataPath>/AIPlayers/knowledge-dump.json`. JSON은 손으로 쓴다(StringBuilder). 모드는 JsonUtility가 중첩 클래스를 떨군 적이 있어 쓰지 않는다(AIExplore.cs 주석).
  ```json
  {"dump":1,"appVersion":"…","time":"…","modCommit":"…",
   "objects":[{"id":3,"var":0,"type":"Tool","rarity":1,"loot":0,"craftTime":1.0,"stack":false,
     "req":[[48,4],[…]],"canCraft":[[…,1]],"hp":null,"red":null,"wdmg":[min,max],"dur":200,
     "dropLoot":null,"eat":[[cond,value,dur]],"equip":[[cond,value]],"ko":"구리 곡괭이","en":"Copper Pickaxe"}],
   "tiles":[[tileset,tileType,objectId]],"hand":[[id,amount]],"errors":[…]}
  ```
- 실행 비용: 한 번에 약 2400항목이라 한 프레임에 다 해도 되지만, 안전하게 프레임당 200항목씩 나눠 쓴다. 끝나면 채팅으로 "kgdump 완료: 항목 N, 오류 M"을 보낸다.
- 시점: 게임 실기 시험이 모두 끝난 뒤 한 번 돌린다. 합친 최종 모드에서 돌리며, 새 빌드는 필요 없다(이 명령이 들어간 빌드면 된다). 결과 파일을 `build.mjs`가 복사해 간다.

## 4. 열림 규칙

### 무엇이 열리나 (캐릭터·월드별)

| 열림 | 언제 | 얻는 곳 |
|---|---|---|
| object 본 적 있음 `seen` | 화면 안 물체·적·땅에 떨어진 아이템·광석 벽·제작대 | `AIObservation`: `objects`, `enemies`, `items`, `wallTiles`(tileset·ore) |
| object 가진 적 있음 `held` | 가방에 들어온 적 있음 | `AIBody.InventoryCounts` |
| 제작대의 레시피 목록 | 그 제작대 object가 `seen` | 그래프의 `crafted_at`(뽑기) |
| 손 제작 목록 | 처음부터 | 그래프의 `hand_craft` |
| 드롭 표 | 그 표를 쓰는 object가 열림 + 그 표에서 나온 아이템을 실제로 얻은 적 있음 → 그 줄만 | 아래 "드롭" |
| 바이옴 | 그 바이옴에 서 본 적 있음 | **지금은 기록 없음**. v1에서는 열지 않는다(스폰 관계는 개발자 조회 전용) |

- **보이는 관계:** 양쪽 끝이 열린 관계만 보인다. 예외는 하나다.
  - 레시피를 볼 때 열리지 않은 재료는 이름 없이 `모르는 재료 1종`처럼 개수만 보인다. 이건 기본값이고 사용자 확인이 필요하다(6장 선택 1).
  - 열린 결과물이라도 재료를 다 모르면 "다 안다"고 오해하지 않게 하기 위해서다.
- **드롭:** 표 전체(확률 포함)는 사람이 위키를 보는 지식에 가깝다. 그래서 캐릭터에게는 **겪은 드롭만** 보인다.
  - 모드에는 이미 "부수면 나온 것" 기억(AIDrops)이 있으니 그걸 열림으로 쓴다.
  - 그래프의 드롭 표는 개발자 조회와 "그 물체는 뭔가를 떨군다(N종, 모름)" 표시에만 쓴다.
- **게임의 제작 열림 조건**(`CraftingPrerequisites`: 보스 처치·콘텐츠 번들)은 게임 화면처럼 처리한다. 조건을 채우지 못한 레시피는 그 월드에서 제작대 목록에 안 보이는 것으로 둔다.
  - 판정은 뽑기 때 값이 있으면 그래프 `requires`로, 월드 상태(보스 처치 여부)는 모드가 known.json에 함께 적는다.
  - **값의 위치가 미확인**이라(6장) 못 찾으면 v1은 조건 없이 다 보이게 둔다.

### 어디에 기록하나

- **새로 기록해야 한다.** 지금 memory.json으로 얻을 수 있는 건 일부뿐이다.
  - 있는 것: 광석 위치·종류, 제작대, 겪은 드롭, 안 부서진 물체.
  - 없는 것: 본 적·가진 적 있는 물체 전부에 대한 기록.
- 파일: `<persistentDataPath>/AIPlayers/<world>/<member>/known.json`. memory.json 옆에 별도 파일로 둔다.
  - memory.json의 `Data` 클래스(AIExplore.cs)는 생활 worktree도 고치고 있다(ai-life에서 AIExplore.cs +17줄). 그래서 형식을 섞지 않는다.
  ```json
  {"version":1,"seen":{"<id>":<unix 처음>},"held":{"<id>":<unix 처음>},
   "tiles":{"<tileset>:<tileType>":<unix>},"bosses":["Bird",...],"updated":<unix>}
  ```
  - 벽·광석은 뽑기 전에는 물체 ID를 모를 수 있다. 그래서 타일 키(tileset:tileType)로 적고, 그래프의 `tile_is`로 풀어 쓴다.
  - 뽑기 전에 쌓은 기록도 뽑기 뒤에 그대로 쓸 수 있다.
- 기록 시점: `AIKnowledge.Note(server, player, o)`를 `AIMemory.Observe`(AIExplore.cs:200, 1초 간격)에서 한 줄로 부른다.
  - 가방 읽기는 그 안에서 2초 간격으로 한다.
  - 새 항목이 생길 때만 더럽힘 표시하고, 저장은 memory.json과 같은 때(AIMemory.Save) 같이 한다. 이것도 한 줄이다.
- 처음 시작: 이미 있는 캐릭터는 memory.json에서 미리 연다. 광석 ID, 제작대 ID, AIDrops에서 얻은 아이템을 `seen`/`held`로 넣는다. 지금까지 플레이한 캐릭터가 빈 상태로 시작하지 않게 하기 위해서다.
- 개발자 조회는 known.json을 무시하고 전체를 본다. 옵션으로 캐릭터 시점 `--as claude --world <id>`도 둔다(열림 시험용).

## 5. 조회

### 위쪽 LLM 보고에 넣기 (브리지)

- 브리지가 graph.json을 시작할 때 읽는다. 보고를 받으면 그 캐릭터의 known.json을 읽는다.
  - 경로: 모드 보고 본문의 `world` + 멤버 id. persistentDataPath는 브리지 config에 둔다.
  - 그리고 보고 JSON에 `knowledge` 칸을 덧붙여 턴을 만든다.
- 모드의 보고 만들기(AIPlanner.cs)는 고치지 않는다. AIPlanner는 생활 worktree도 고친다(+19줄).
- 무엇을 넣나. 초점 대상은 보고에서 뽑는다.
  - 대상: 현재·직전 목표의 item, `craft_needed`에 나온 것, `can_do.craft`의 결과물, 가방 상위 10개, `stations_in_view`·`known_stations`.
  - 초점 대상마다 열린 것만, 아래 순서로 넣는다.
    1. **얻는 법**: 만드는 곳과 재료(모르는 재료는 개수만), 캐는 데 필요한 도구(`mineable_by`, 가진 도구 기준 예상 타격 수), 겪은 드롭
    2. **어디에 쓰나**: 이걸 재료로 하는 열린 레시피 최대 5개(결과물 이름, 만드는 곳)
    3. **효과**: 먹을 때·장착할 때(`gives`)
  - 크기 상한: 초점 대상 최대 8개, 줄 최대 25줄, 약 2000자. 넘치면 목표 item → craft_needed → 가방 순으로 자른다.
  - 형식: 한국어 짧은 줄. 예: `"구리 곡괭이: 작업대에서 구리 주괴 ×?·나무 ×? / 캐는 것: 주석 광석 벽(약 6타) / 쓰임: 모르는 레시피 없음"`
- brief.md에 `knowledge` 칸 설명 한 줄을 넣는다. brief.md도 생활 worktree가 고치므로(+5줄) 합칠 때 함께 맞춘다.
- **순서상 주의:** 이건 "LLM 층" 작업이다. 사용자 순서는 인게임 기술을 다듬은 다음이 LLM 층이다. 그래서 보고에 넣는 단계는 6장 선택 2로 따로 묻는다.

### 개발자 조회 (kg.mjs 명령줄)

- `node Tools/knowledge/kg.mjs uses <이름|ID>`: 어디에 쓰나(재료인 레시피, 장착·먹기 효과)
- `node Tools/knowledge/kg.mjs how <이름|ID>`: 얻는 법(레시피·제작대, 캐는 도구, 떨구는 것·드롭 표, 나오는 바이옴)
- `node Tools/knowledge/kg.mjs station <제작대>`: 레시피 목록
- `node Tools/knowledge/kg.mjs find <글자>`: 이름 찾기(한국어·영어·ID 이름)
- 옵션: `--as <멤버> --world <id>`는 그 캐릭터에게 보이는 것만, `--json`은 기계용 출력
- 같은 조회 함수를 브리지가 import한다(조회 코드는 한 곳).

### 조회 코드 위치 선택지

| 위치 | 장점 | 단점 |
|---|---|---|
| **Node 라이브러리 + 브리지·명령줄 공용 (추천)** | 게임 재빌드 없이 고침, 소비자(LLM 보고)가 브리지에 있음, 개발자 도구와 같은 코드 | 모드 쪽 즉시 판단(Decisions)이 쓰려면 따로 넘겨야 함 |
| 모드 C# | 행동 판단도 바로 씀 | 고칠 때마다 빌드·게임 재시작, AIPlanner를 생활 쪽과 같이 고침 |
| 별도 도구만 | 가장 단순 | LLM 보고에 못 넣음 |

- 빠른 판단층(Decisions)이 그래프를 쓰는 일은 이번 범위가 아니다. 지금 모드는 레시피·수치를 실행 중에 직접 읽고 있어서 급하지 않다.

## 6. 사용자 선택이 필요한 것

1. **모르는 재료 표시.** 레시피 결과물은 열렸는데 재료 일부가 안 열렸을 때 어떻게 보일까.
   - (추천) `모르는 재료 1종`처럼 개수만 보인다. "다 안다"는 착각을 막는다.
   - 아예 안 보인다. 합의 때 든 예("주석 쪽은 안 보입니다")에 더 가깝다.
   - 참고: 실제 게임에서는 제작대를 열면 재료 아이콘이 모두 보인다.
2. **보고에 넣는 시점.**
   - (추천) 그래프·열림 기록·개발자 조회는 지금 만들고, 위쪽 LLM 보고에 넣는 것은 뽑기 뒤 LLM 층 차례에 한다. 사용자 순서(인게임 기술 → LLM 층)와 맞고, 뽑기 전 Conf만으로는 드롭·스폰뿐이라 보고에 넣을 가치가 작다.
   - 뽑기 직후 바로 넣는다.
3. **드롭을 캐릭터에게 어디까지 보일까.**
   - (추천) 겪은 드롭만 보인다. 표 전체(확률)는 개발자 조회 전용이다.
   - 떨구는 물체를 봤으면 표 전체가 보인다.

사소한 것은 아래처럼 정해 둔다.
- 게임 데이터는 git에서 뺀다.
- 기존 캐릭터는 memory.json에서 미리 연다.
- 바이옴은 v1에서 열지 않는다.
- 크기 상한은 25줄 / 2000자다.
- 명령 이름은 `kgdump`다.

## 8. 불확실한 점

- **`CraftingPrerequisites`가 어느 컴포넌트·필드에 담기는지 모른다.** 디컴파일 참고본에는 구조체 정의만 있고 쓰는 곳이 안 보인다. 뽑기 구현 때 찾고, 못 찾으면 v1은 조건 없이 둔다.
- **한국어 이름을 실행 중에 얻는 API를 확인하지 못했다.** I2 Localization 추정. 실패하면 ID 이름(영어 식별자)을 쓴다.
- **도구 채굴 피해의 정확한 출처를 확인해야 한다.** 장착 효과의 어느 ConditionID인지, 모드가 memory.json `toolBonus`로 읽는 값과 같은지. `mineable_by` 계산이 여기에 달려 있다.
- **variation이 있는 물체**(같은 ID, 다른 변형)는 v1에서 variation 0만 노드로 하고 나머지는 속성으로 둔다. 변형이 레시피에 쓰이는 경우가 있는지 모른다.
- **Conf 형식은 게임 README에 "바뀔 수 있음"이라고 적혀 있다.** `ID/*.json`은 쉼표가 없는 유사 JSON이라(확인함) 줄 단위로 파싱해야 한다.
- **합칠 때 손댈 곳:** 기존 파일에 들어가는 한 줄들이 생활 worktree와 같은 파일에 들어간다(AIExplore.cs, AIBodySkills.cs, AIPlayerSpikeMod.cs, 그리고 넣는다면 brief.md·bridge.mjs). 충돌은 작지만, 생활을 먼저 합친 뒤 그 위에 얹는다.
