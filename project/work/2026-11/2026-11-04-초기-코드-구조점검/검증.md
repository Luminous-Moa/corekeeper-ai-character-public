# 초기 코드 구조점검 — 독립 검증

검증일: 2026-11-04. HEAD가 제시한 다섯 후보를 직접 소스로 확인했다. 코드·게임·브리지·설정 변경, 빌드, 라이브 실행, LLM 호출은 하지 않았다. 기존 합의 범위와 HEAD Core start-job 스킬을 읽었으며 세션 기록 도구와 하위 에이전트를 사용하지 않았다. 다른 조사자의 상세진단을 읽지 않고 검증했다.

## 결론

전체 재작성은 근거가 부족하다. 우선 다룰 만한 경계는 ① 후보 생성과 후보 조합, ② 기계가 읽는 실패 원인과 사람이 읽는 설명, ③ 브리지 응답 판독이다. 이는 파일을 짧게 만드는 과제가 아니라 각각 후보 정책 변경 시의 검토 범위, 문구 수정의 행동 영향, 자유로운 텍스트의 손실을 줄이는 과제다. 캐릭터 상태의 Cur/Slots는 향후 비동기 경계에서 조심할 설계지만 현재 혼선 버그로 확정할 수 없다. CLI 취소 범위는 recall 작업에 이미 수정되어 있으므로 별도 미해결 리팩토링 과제로 중복 제안하지 않는다.

## 조사 기준과 동시 변경

- 요청 기준 main은 a03192d였지만 검증 시작 시 C:/Dev/CoreKeeperModSDK HEAD는 039d8b5437c1d435a1729c85c3ce12280f6822f9였다. unstick도 같은 커밋이다. 따라서 a03192d는 git show로 고정해서 읽고 현재 039d8b5를 대조했다. 초기 범위 문서의 SHA를 현 상태로 오인하지 않는다.
- recall은 2f7f92d54257b4b5846bf299735ce1e05b051d2d, kg는 1d0cb171124a89e7c9e576efc8597174012fc5ca였다. 이번 다섯 후보는 main과 recall 코드가 직접 근거이며 kg의 전체 구현을 검수한 것은 아니다.
- main/unstick 작업 트리에는 Unity 자산·패키지·프로젝트 설정 등의 기존 변경이 있었다. 아래 핵심 조사 파일은 git hash-object와 HEAD blob ID가 같아 추적 소스 수정이 없는 것을 확인했다.
- 아래에서 a03192d 줄 번호와 현재 039d8b5 줄 번호를 구분한다. 이번 변화로 후보 생성 위치가 이동했으며 최신 변경을 예전 줄 번호로 지목하면 안 된다.

## 1. BuildCandidates: 책임 집중 확정, 전체 brain 분리 의무는 아님

a03192d AIDecisions.cs 1857–2471, 현재 039d8b5 1932–2658 부근을 확인했다. 단일 메서드가 관찰·이동 가능 영역·제작 준비에서 시작해 전투, 채굴, 기억한 자원, 탐험, 동료, 후보 조합, 실패 제외, 문구, 식별자까지 연결한다. 같은 AIBrain 안에 요청 수명·prefetch·응답 유효성·목표 변경도 있다. 현재 1136에서 후보를 만들고 1228에서 요청 JSON을 만들며 1275–1281에서 전송한다.

길다는 사실 외에 다음 결합이 실제 근거다.

- a03192d 1872의 WantedItems가 이전 _blockNote를 읽는 준비 경로에 의존하고, 2445–2456에서 새 도구 부족 결과가 처음 생기면 전체 후보 생성을 한 번 다시 실행한다. 현재도 1614와 2632–2643에 같은 연결이 남아 있다. 후보 생성은 순수한 목록 반환 함수가 아니다.
- 후보 생성 중 전투 로그 상태를 쓰고(a03192d 1942–1945), prefetch일 때 관찰의 enemies 목록을 제거한다(1903). _weaponBroken, _curMoveTo, _blockNote, _skippedNote 등 후속 설명·판단용 결과도 갱신한다. 단순 함수 이동만으로 경계가 생기지 않는다.
- 2360–2424의 안정 순서·계속하기·근접 전투 묶음과 2426–2469의 실패 제외·14개 제한·wait·choice 이름 결정은 다른 후보 생성 부분과 함께 검토해야 한다. 후보 추가가 목록 뒤쪽 후보를 밀어낼 수 있다.

최소 분리는 한 번의 후보 생성에 필요한 입력/임시 사실과 반환할 사실을 명시하고, 전투·탐험 등의 후보를 만드는 부분과 최종 조합/제외/식별자 부여 부분을 구분하는 정도가 적절하다. 이미 AIBase/AIFarm/AICook.Candidates로 분리된 경계(a03192d 1874–1878)를 활용할 수 있다. 모든 행동에 새 플러그인 프레임워크를 도입하거나 AIBrain을 한 번에 전면 교체할 근거는 없다.

보존 조건: 후보 내용·설명·순서·안정 choice·14개 제한·wait 위치·실패 기억·근접 전투 정책·prefetch 관찰 처리·도구 준비 재생성 1회를 유지한다. 재귀를 없애면서 준비 시점이나 후보 선택 전략을 바꾸는 것은 별도 제품 변경이다. 현재 039d8b5의 자유 시간·손 칸·탐험 점진 처리도 이미 추가된 동작이며 되돌리는 정리는 권하지 않는다.

## 2. Reason/blocked 문구: 실제 변경 결합 확정

- a03192d AIDecisions.cs 396–404: GotoSkill 실패의 Reason이 '길 없음', '막힘', '시간 초과'로 시작하는지에 따라 주변 탐험 후보를 한동안 제외한다. 410–414는 'AI가 쓰러짐'을 제외하고 실패 누적을 늘린다. 417은 '처치'라는 단어로 처치 수를 센다. 현재 대응 위치는 452–473이며 같은 의존이 남아 있다.
- a03192d 2452, 현재 2639: _blockNote의 '도구 부족' 포함 여부가 후보 재생성을 결정한다. 현재 1614에서도 이 문구가 더 좋은 곡괭이 준비를 켠다. 단순 로그 문구가 제어 신호로 사용된다.
- AIExpCore.cs 217–237의 ExpRun.Classify는 ClearGoal 원인에서 outcome과 cls를 만든다. 'stalled:' 이후 '기지로 갈 방법이 없음'/'넣을 방법이 없음'/'기다리기뿐'/'만들 방법이 없음'/'도구 부족'에 따라 no_place/only_wait/cannot_craft/tool_weak/no_source를 고른다. 757에서 실제 종료 기록에 사용된다.

따라서 설명을 더 자연스럽게 고치거나 새 실패 설명을 추가할 때 행동 재시도·경험 분류까지 확인해야 하는 결합은 확정이다. 다만 현재 모든 분류가 잘못된다는 뜻은 아니다. SkillStatus, outcome, cls 같은 구분은 이미 일부 있으므로 'typed outcome이 전혀 없다'는 표현은 부정확하다.

권할 최소 경계는 Skill의 실패 원인 코드와 표시 Reason, 후보 생성의 도구 부족 사실과 설명, 목표 종료 원인 코드와 경험 표시문구를 각각 분리하는 것이다. 저장된 경험 전체를 다시 쓰거나 모든 Reason을 한 번에 거대한 enum으로 바꿀 필요는 없다. 기존 no-path 제외 범위·실패 횟수·다운 예외·분류 우선순위는 보존해야 한다.

## 3. AIAgent.Cur와 object[15]: 현재 버그 주장은 축소

AIAgents.cs 24의 object[15], 45의 범위 밖 Claude 기본값, 48–59의 Scope/Enter는 호출 경계가 생략돼도 컴파일 단계에서 막아주지 않는다. 슬롯 인덱스를 서로 다른 State 타입에 중복 할당하면 런타임 문제가 생기고, Enter 범위를 벗어난 비동기 콜백이 static 접근자를 쓰면 잘못된 캐릭터를 참조할 가능성이 있다.

그러나 현재 코드에서 다음 반증이 있다.

- AIPlayerSpikeMod.cs 229–248은 각 캐릭터를 Enter로 감싸 순서대로 Tick한다. 459–467의 명령도 대상별 Enter로 처리하고, 캐릭터 생성 패치는 1449–1461에서 guid로 대상자를 찾은 뒤 Enter한다.
- AIPlanner.cs 339–348은 요청 완료를 해당 캐릭터 Tick 안에서 폴링하고 그 범위에서 응답을 읽는다. 현재 조사 C#에 async/await 기반 연속 실행이나 완료 콜백으로 캐릭터 상태를 바꾸는 경로는 확인되지 않았다.
- StateOf 할당을 대조한 결과 슬롯 0–14의 사용은 중복 없이 15개다. 현재 슬롯 충돌을 발견하지 않았다.

따라서 지금 여러 캐릭터 상태가 섞인다는 결론이나 전 클래스 인스턴스화의 긴급 권고는 기각한다. 향후 채팅·외부 콜백 경계를 추가할 때 owner를 명시하고, 잘못된 무범위 접근을 검출하거나 슬롯 이름/타입 접근을 제한하는 좁은 개선은 가치가 있다. 비동기 추가 전에 경계 점검 항목으로 남길 정도다. 이번 읽기만으로 모든 Harmony/게임 실행 스레드 조건이 안전하다고 증명한 것은 아니다.

## 4. 수동 JSON 판독: 결함은 확정, recallSummary 주석의 인과는 축소

a03192d AIPlanner.cs 446–454(현재 492–500)의 Field는 문자열 전체에서 정확히 '"key":'를 처음 찾은 뒤, 값이 따옴표로 시작하면 다음 따옴표에서 끊는다. JSON 문자열 escape를 해석하지 않고 현재 객체 깊이도 확인하지 않는다. a03192d 344–358(현재 390–403)의 answer/for/goal 탐색도 첫 일치와 뒤의 첫 여는 중괄호에 의존한다. 반면 ObjectAt 자체(a03192d 458–469)는 문자열 및 escape를 고려하므로 '중괄호 탐색이 전부 깨진다'는 표현도 과장이다.

이 알고리즘을 그대로 옮긴 격리 JS 문자열 실험 결과(게임·브리지 실행 및 C# 빌드 아님):

| 입력 | Field 결과 | 의미 |
|---|---|---|
| say 값이 `그는 "동굴"이라고 말했다`인 JSON.stringify 결과 | `그는 ` 뒤 역슬래시에서 잘림 | escaped quote를 값 끝으로 오인 |
| say 값에 실제 줄바꿈이 든 JSON.stringify 결과 | 줄바꿈 대신 `\\n` 문자열 | escape 미복원 |
| `{"answer":{"decision":"hold","error":"memo"},"error":null}` | error = memo | 중첩 속성을 envelope 속성으로 오인 |
| `{"say" : "안녕"}` | null | 키/콜론 사이의 합법적 공백 미지원 |

현재 bridge는 JSON.stringify로 응답하므로 키 앞뒤 공백 사례는 당장의 생성 경로가 만드는 오류는 아니다. 중첩 error 사례는 파서의 구조적 제약 재현이며 실제 운영 로그에서 발생했다고 주장하지 않는다. 자유 텍스트의 인용부호·줄바꿈 손실은 현재 say/why/detail에도 해당하는 제약이다.

recall-loop.mjs 123–127은 이 판독기를 이유로 요약에서 따옴표·역슬래시와 error/answer 단어를 지운다. 이는 소비자 제약을 공급자가 의식한 실제 증거지만, 단어 제거까지 반드시 필요하다는 주석 설명은 그대로 믿으면 안 된다. 정상 JSON.stringify 문자열 내부의 escaped `\"error\":`는 원래 탐색 패턴과 같지 않다. recall bridge.mjs 259의 최상위 answer/error가 요약보다 앞에 있고, 요약은 264에서 마지막에 온다. 요약에 단어 및 인용부호 포함 키 문구를 그대로 넣은 격리 입력에서도 최상위 error = null을 제대로 찾았다. 따라서 'error/answer라는 일반 단어가 요약에 있으면 응답이 깨진다'는 주장은 기각한다. 인용부호를 지우는 처리는 Field의 문자열 잘림 회피와 관련 있지만 단어 자체 삭제의 필요성은 입증되지 않는다.

최소 개선은 브리지 응답을 한 번 구조적으로 파싱하여 envelope와 answer의 정확한 경계에서 필드를 읽고 문자열 escape를 복원하는 것이다. 채팅·정보 정정처럼 인용문과 자유 텍스트를 늘리기 전에 할 가치가 있다. mod-compiled 코드의 JsonUtility 중첩 클래스 문제 때문에 수동 판독을 쓴 주석이 있으므로 단순 JsonUtility 회귀만 권하지 않는다. 기존 ExpJson 같은 파서의 적용 가능성은 별도 검증할 수 있으나 이번 조사에서 그 적합성까지 확정하지 않는다.

## 5. bridge 취소: main의 사실은 확정, 신규 미해결 권고는 기각

현재 main 039d8b5의 Tools/ai-bridge/bridge.mjs 227은 응답 연결이 끝나기 전에 닫히면 running 전체를 killTree한다. 다른 멤버의 동시 CLI도 포함될 수 있는 코드는 실제다.

그러나 recall 2f7f92d bridge.mjs 291–295는 gone을 설정하고 요청 member의 실행 파일에 대응하는 childrenOf만 종료한다. recall-loop.mjs 131–133에 members/CLIs 1:1 전제와 필터가 있다. 따라서 '미해결 구조 문제이니 새 취소 관리자부터 구현'은 중복 제안이다. HEAD는 recall의 기존 수정이 main에 통합되는지를 추적하면 된다. 멤버-CLI 1:1 전제가 바뀌는 미래까지 현재 구현이 일반적 요청별 취소를 보장한다고 확장해서 말하지 않는다.
