# 초기 코드 구조 진단 — 읽기 전용

작성: 2026-11-04. 범위는 같은 폴더 `범위.md`. 제품 코드·설정·설치본을 고치지 않았고 게임 실행, 모델 호출, 빌드, 운영 프로세스 조작, 그래프 재생성을 하지 않았다. 아래는 소스 구조 진단이며 실행 성능·게임 행동의 재검증 보고서가 아니다.

## 판단

**몇 곳은 실제로 뭉쳐 있다. 가장 큰 것은 `AIBrain`의 후보 생성과 준비 경로이고, 그다음은 사람이 읽는 문자열과 프로그램 계약이 붙어 있는 경계다. 전체 1만 5천 줄을 하나의 덩어리로 보거나 전면 재작성을 시작할 상태는 아니다.** 이미 목표 계획 → 행동 선택 → 단일 몸 실행 → 경험 저장의 구분과 기능별 기술 클래스가 있다. 이 분리를 보존하면서 다음 확장 전에 세 경계를 작게 정리하는 편이 타당하다.

1. 후보 생성·준비 경로를 요청 수명 및 실행 전환과 분리한다.
2. 실패·막힘의 코드와 설명 문장을 분리한다.
3. 브리지 응답의 읽기·검증 계약을 한 경계로 모은다.

멀티 캐릭터의 암묵적 현재 캐릭터는 네 번째 구조 위험이다. 현재 동기 실행이 잘못되었다고 단정할 근거는 없고, 채팅·비동기 입력을 붙이는 시점에 소유자를 명시하는 작은 경계가 필요하다. 파일 길이 때문에 기존 기술·저장·게임 연결을 전부 잘게 나누는 일은 후순위다.

## 발견 1 — 후보 생성과 준비 경로가 판단 조정자에 집중됨

**분류: 확인한 구조 집중. 우선순위 높음. 즉시 오류라고 판정한 것은 아님.**

`AIDecisions.cs`는 파일 하나에 여러 클래스가 있는 정도를 넘어, `AIBrain` 한 클래스가 다음 변경 이유를 함께 가진다.

- 목표 명령 해석·시도 시작/종료(`431`, `501`, `378`).
- 판단 호출·timeout·반사·예산·사용량 기록(`563`, `1061`, `1230`, `2643` 이후).
- 미리 묻기/보류/동작 경계에서 전환(`913`~`1019`).
- 제작 재료·제작대·도구 준비(`WantedItems:1527`~`1661`).
- 탐험/전투/생활 후보 생성, 경로 검사, 모델 문장, 정렬, 실패 제외(`BuildCandidates:1857`~`2471`).

후보가 단순 반환값도 아니다. `WantedItems:1532`는 `AIBase.ResetMissing`, 이후 `NoteMissing`으로 다른 기능 상태를 채운다. `BuildCandidates:1872`에서 이를 먼저 부른 뒤 `1874`에서 `AIBase.Candidates`가 그 상태를 사용한다. 끝에서는 `_blockNote`, `_toolShortRed`, `_skippedNote` 등 다음 호출에 영향을 주는 상태를 바꾼다. `2452`에서는 처음 도구 부족을 발견하면 같은 BuildCandidates를 한 번 재귀 호출해 준비 후보를 다시 만든다. 이 순서를 모르고 함수를 나누면 기존 행동이 바뀐다.

후보 자료형도 사용법이 암묵적이다(`AICandidate:87`). `eatVariation`은 먹기 variation, 제작/상자 꺼내기 수량, cookwait 초 수에 재사용된다(`Apply:1490`~`1501`; `AICook.cs:430`). `digWhat`도 굴 설명뿐 아니라 농사 동작과 요리 put/take/fill을 담는다. 새 기술을 붙일 때 생성부와 공통 switch 양쪽의 필드 관례를 알아야 한다.

**구체적 변경 부담:** “새 도구가 필요한 채집 행동”을 추가하면 도구 준비, 후보 생성, 실패 이유, 설명문, 실행 변환, 목표 정체 판정까지 이 클래스 안팎을 함께 읽어야 한다. “후보 문장을 자연어 지시와 맞춘다”는 변화도 정렬/진행 가능 표시/가까운 전투 후보 축소와 섞여 있어 문장만의 수정인지 확인하기 어렵다.

**최소 정리 경계:** 먼저 준비 계산을 입력(목표·가방·보이는/기억한 제작대·도구 제약) → 결과(필요 재료·준비 후보·설명·막힘 코드)로 꺼낸다. 이어 후보 생성기를 탐험/전투/기능별 생성과 최종 모으기·제한으로 나눈다. 기존 `AIBase.Candidates`, `AIFarm.Candidates`, `AICook.Candidates`의 형태가 이미 출발점이다. `AIBrain`에는 언제 물을지, 어떤 요청이 현재 유효한지, 언제 기술을 바꿀지를 남긴다. 단순 `partial` 파일 분할만으로는 상태 의존이 사라지지 않는다.

**보존할 동작:** 후보 key/선택값 안정성, 14개 후보+wait 상한, 근접 전투의 목표 쪽 후보 제한, `progress` 의미, 미리 물을 때 continue 제외, 재시도 제외 기간, 도구 부족 발견 당회에 준비 후보가 생기는 동작, 준비 계산 후 상자 재료 후보를 만드는 순서. 미리 묻기·보류 전환까지 한 번에 재설계하지 않는다.

현재 `039d8b5`에서도 `WantedItems:1589`, `BuildCandidates:1932`, 재귀 재생성 `2639`로 같은 구조가 이어진다. 자유 시간 추가는 기능상 의미가 있지만 이를 분리해 준 변경은 아니다.

## 발견 2 — 설명 문구를 고치면 행동·기억 의미까지 달라질 수 있음

**분류: 확인한 계약 결합. 우선순위 높음. 현재 문구가 틀려 이미 오분류됐다는 실행 증거는 없음.**

첫 흐름은 기술 실패다. `AIBody.EndSkill:249`가 기술 객체를 `AIBrain.OnSkillEnded`로 보내면, `AIDecisions:397`~`407`은 `Reason.StartsWith("길 없음"/"막힘"/"시간 초과")`를 보고 주변 5칸을 90초 제외한다. `410`의 `Reason.StartsWith("AI가 쓰러짐")` 여부는 일반 실패 누적에서 죽음을 제외하고, `417`의 `Reason.Contains("처치")`는 처치 통계에 쓰인다. 이미 `SkillStatus`는 열거형인데 원인과 세부 결과는 문장에 의존한다.

둘째 흐름은 목표 결과다. `Send:1090` 이후에서 막힘 문구를 만들고 `ClearGoal("stalled: " + why)`를 부른다. `ClearGoal:382` → `AIExperience.GoalEnding:213` → `ExpRecorder.GoalEnd:757` → `ExpRun.Classify:217`로 이어져 `"만들 방법이 없음"`, `"도구 부족"`, `"기다리기뿐"`, `"기지로 갈 방법이 없음"` 등의 포함 여부를 원인 코드로 바꾼다. `ExpResolve.Measured:279`는 그 코드에 따라 도구 레벨·광석 기억·재료/제작대 등 서로 다른 변화를 비교한다.

예를 들어 같은 실패를 사용자에게 더 자연스럽게 보이도록 `"만들 방법이 없음"`에서 `"제작할 수 없음"`으로만 바꿔도 `cannot_craft` 판별을 벗어난다. 이후 재료가 생겼을 때 재시도할 만한 변화로 보는 의미가 달라질 수 있다. 반대로 `WantedItems:1552`와 `BuildCandidates:2452`는 `"도구 부족"`을 직접 읽어 상위 곡괭이 준비를 넣는다. 이는 단순 로그 검색 용도가 아니다.

**최소 정리 경계:** 기술 결과에는 status + reasonCode + 대상/측정 사실 + displayText를, 목표 종료에는 outcome + blockedCause + displayText를 전달한다. 모든 문장을 한 번에 바꾸지 말고 길 없음·쓰러짐·도구 부족·제작 불가부터 코드로 옮긴다. 기존 이벤트 로그는 버전 호환 판독 단계에서 현재 Classify 규칙으로 받아들이고 새 사건은 코드와 문장을 함께 남긴다.

**보존할 동작:** 죽음을 일반 실패 누적으로 세지 않기, 목표 시도 중복 종료 방지, 기존 events/goals 파일 읽기, 원인별 재시도 조건과 대기 정책. 로그 문구는 첫 변경에서 그대로 유지해 기존 관측 도구도 깨지지 않게 한다. 사람의 정보 정정이나 자동 플레이 로그를 붙일 때 사람이 고친 문장이 프로그램 원인 코드를 조용히 바꾸지 않는 것이 이 경계의 가치다.

## 발견 3 — JSON 읽기 제약이 브리지·기억 검색까지 전파됨

**분류: 확인한 구조 결합이며, escape 포함 문자열의 판독 결함도 소스에서 확인 가능. 우선순위 높음.**

`AIPlanner.Apply:341`은 응답 전체에서 `"answer":`를 찾고 `ObjectAt`으로 부분 객체를 자른다. 이어 `Field:446`는 깊이를 구분하지 않는 문자열 검색으로 첫 `"key":`를 찾고, 문자열이면 다음 큰따옴표에서 끝낸다. `ObjectAt`은 escape를 고려하지만 Field는 고려하지 않는다. 따라서 올바른 JSON의 `say`가 `그는 \"이동\"이라고 말했다`라면 첫 escape 큰따옴표에서 값이 잘린다. 줄바꿈·역슬래시 등의 JSON escape도 문자열 의미로 복원되지 않는다. 코드가 표현할 수 있는 입력에 대한 판독 결함이며, 이번에 실게임에서 발생했다고 주장하지 않는다.

제약을 의식한 코드가 다른 모듈에도 있다. recall 브랜치 `Tools/ai-bridge/recall-loop.mjs:123`~`129`의 `recallSummary` 주석은 모드의 첫 error/answer 키 검색을 언급하고, 검색 요약에서 큰따옴표·역슬래시와 error/answer 단어를 제거한다. **이 제거가 현재 JSON.stringify envelope에서 실제로 필수라는 주장은 하지 않는다.** escaped quote는 원래 검색 패턴과 다르고 summary 위치도 뒤여서, 이는 판독 제약을 우려한 방어 코드가 새 기능에 전파된 사례로 한정한다. 실제 판독 결함의 근거는 앞의 Field 알고리즘이다. `AIPlanner.Check:393`의 게임 사실 검증 자체는 필요한 역할이며 없앨 대상이 아니다.

**구체적 변경 부담:** 자연어 지시·정보 정정·긴 발화·검색 출처를 담은 필드를 하나 더 넣을 때마다 값 안의 인용문, 중첩 구조, 같은 키, 새 필드 순서를 수동 파서와 함께 검토해야 한다. 목표 종류 추가 역시 모드 enum/명령/Check/Apply, 브리지 shape, brief에 퍼진다. 서로 다른 언어 사이에 양쪽 검증이 있는 것은 정상이나 계약과 fixture가 없이 개별 switch와 문구로만 맞추는 부담은 줄일 수 있다.

**최소 정리 경계:** Unity 모드에서 실제 사용할 수 있는 JSON 판독/escape 복원 경로 하나로 브리지 envelope와 goal DTO를 읽는다. 지원 라이브러리 검증은 구현 작업 때 할 일이다. 과거 JsonUtility의 중첩 클래스 문제가 주석에 명시되어 있으므로 그냥 그 코드로 되돌리라고 권하지 않는다. set/hold/ask, for, 오류 envelope와 확장 필드를 대표 fixture로 고정하고 모드의 사실 검증은 유지한다. 상위 목표 HTTP와 하위 Decisions의 서로 다른 응답은 한 기능으로 합치지 않고 공통 JSON 판독만 공유할 수 있다.

**보존할 동작:** report/goal_rev 일치, 호스트 목표 우선, 답 나이 제한, 대상 현재 유효성 검사, 미지 필드 허용과 미지 decision 거부, recall 검색은 브리지 내부에서 끝내기. 옛 이벤트·요약의 판독 호환도 보존한다.

현재 메인 `039d8b5`에는 `AIPlanner.Apply:387`, `Field:492`로 같은 방식이 남고, recall `2f7f92d`도 이를 대체하지 않았다.

## 발견 4 — 캐릭터 상태 소유자와 틱 순서가 암묵적

**분류: 확장 시 구조 위험. 현재 캐릭터 간 상태 오염을 발견했다고 말할 근거 없음. 우선순위는 새 입력/비동기 경계 추가 시.**

`AIAgents.cs:24`의 `object[15] Slots`를 각 기능이 번호로 사용한다. `AIBody.StateOf:82`, `AIBrain.StateOf:211`, `AIPlanner.StateOf:58` 등은 static 함수인데 `AIAgent.Cur`의 State를 읽고 쓴다. 범위 밖이면 Cur는 첫 멤버 Claude다(`AIAgents:45`). 경험(`AIExperience:47`)과 게임 지식(`AIKnowledge:54`)은 별도 Dictionary로 같은 현재 캐릭터를 따른다.

현재 `AIPlayerSpikeMod.Update:223`은 멤버마다 `using (AIAgent.Enter(a))` 안에서 동기 틱하고, 명령·패치도 대상 범위로 들어간다. UnityWebRequest 응답 적용도 해당 멤버 Tick에서 처리한다. 이 때문에 지금 구조를 곧바로 멀티스레드 버그로 부를 수 없다.

하지만 향후 새 채팅 callback이 `SetGoal`이나 기억 저장을 범위 밖에서 부르면 조용히 Claude에 적용될 수 있고, Enter를 await 너머로 유지하면 전역 현재값이 다른 일에 영향을 준다. 이것은 새 비동기 진입을 만들 때 검토해야 하는 구체적 제약이다. 슬롯 번호 충돌·누락은 타입 검사로 잡히지 않는다는 부담도 있다.

또한 상위 계획/경험 수집은 몸 Tick 안에 숨겨져 있다(`AIBodySkills:153`~`155`, `AIPlanner:283`). 몸 실행 책임을 정리하면서 이 호출을 무심코 빼면 기억 수집과 다음 목표 진행을 잃는다.

**최소 정리 경계:** 새 외부 입력은 member/world/request 식별자가 있는 명령으로 받아 해당 캐릭터 큐에서 처리한다. 필요한 State부터 명시적 소유자·타입 있는 저장소로 옮기고 전체 static 변환을 동시에 하지 않는다. 틱 조정자는 현재 Brain→Body→관측/생명→Planner→Experience 순서를 드러내되 먼저 순서 자체는 바꾸지 않는다. 기존 동작 경계·캐릭터별 저장 경로·월드 교체/reset을 보존한다.

## 추가로 확인한 실제 결함과 진행 중 수정

시작 메인 `a03192d` 및 `039d8b5`의 `Tools/ai-bridge/bridge.mjs:227`은 한 HTTP 응답 연결이 닫히면 전역 `running` 집합의 **모든** 자식 프로세스에 killTree를 호출한다. 서로 다른 멤버는 동시에 요청 가능하므로 한 멤버의 취소가 다른 멤버의 CLI 실행까지 종료할 수 있는 코드 경로다. 이번 조사에서 프로세스를 종료하거나 재현하지 않았다.

**이것을 새 미해결 구현 과제로 중복 권하지 않는다.** recall `2f7f92d`의 `bridge.mjs:291`~`295`는 중단 표식을 세우고 `childrenOf(running, bin)`만 종료하도록 바꾸었다. `recall-loop.mjs:131`~`133`에 현재 멤버와 CLI가 1:1이라는 전제가 명시되어 있다. 통합 검수에서는 이 수정 보존을 확인하면 된다. 향후 같은 CLI를 쓰는 멤버를 여럿 만들 때는 bin별이 아니라 요청별 프로세스 소유권이 필요하다.

## 이미 잘 나뉜 곳과 지금 나누지 않을 곳

- **몸의 단일 실행자:** `AISkill`의 Start/Tick/Cleanup와 `AIBody.Current`가 하나의 실제 입력을 만든다. 여러 기능이 모델 응답을 직접 게임 입력에 쓰는 형태가 아니다. 기술별 결과를 확인하고 Cleanup하는 경계를 유지한다.
- **기능별 기술:** Base/Farm/Cook는 자기 후보·가능 여부·완료 판정·실행 기술을 묶고 있다. 기능 안에서 함께 바뀌는 코드이므로 파일 길이만으로 모든 클래스를 한 파일씩 쪼갤 이유가 없다. 공통 후보 자료형과 조정자 경계부터 고치는 편이 효과가 크다.
- **게임 연결부:** `AIPlayerSpikeMod.cs`에는 `AIPlayerSpikeMod`, 네트워크 드라이버, Harmony 패치, 세계 설정, 캐릭터 저장 클래스가 각각 있다(`51`, `1361`, `1396`, `1490`, `1561`). 길지만 이미 타입 경계가 있어 모두 한 객체에 뭉친 것은 아니다. 이 파일을 탐색 편의로 나눌 수는 있으나 우선적인 구조 위험 해소와 동일시하지 않는다. 검증된 thin-client 입력·캐릭터 저장 루트를 이번 구조 작업 때문에 바꿀 필요가 없다.
- **몸 파일의 여러 책임:** `AIBodySkills.cs`에는 시야 `897`, 타일 읽기 `956`, 관측 `1145`, 길찾기 `1258`, 개별 기술이 별도 타입으로 있다. 소스 탐색상 나누면 편하지만 `BuildCandidates`처럼 한 함수 안의 순서·공유 상태 결합과 심각도가 같지 않다.
- **경험 저장 경계:** 게임 적응부 `AIExperience`와 순수 저장/분류/판정 `AIExpCore`는 분리되어 있고, `Tools/exp-sim/Program.cs`라는 오프라인 검증 진입도 있다. Classify의 문자열 입력 계약을 바꾸면 되지 경험 시스템을 새로 만들 이유는 없다.
- **기억과 게임 지식:** `AIKnowledge`는 관측/소지 사실의 known.json, `Tools/knowledge/build.mjs`는 게임 자료 추출, `kg.mjs`는 질의 및 캐릭터 공개 범위를 맡는다. recall의 memgraph는 원본 이벤트를 고치지 않고 인덱스를 만들고, recall-loop는 chat/runQueries/clock을 주입받는다. 검색 루프를 모드의 프레임 상태와 분리한 것은 적절하다. 다만 개발용 전체 지식과 캐릭터가 아는 범위를 계속 구분해야 한다.

## 구현을 시작한다면 순서와 확인할 행동

1. 진행 중 기능 브랜치의 검수·통합을 기준점으로 확정한 뒤, 실패 코드와 JSON 계약처럼 작고 범위가 선명한 경계를 먼저 정리한다. 이것은 후보 생성 분리 중 의미를 잃지 않게 하는 기반이 된다.
2. 준비 계산 → 후보 생성 순으로 책임을 빼고, 중앙 Brain에는 요청·유효성·전환 정책을 남긴다. 처음부터 목표 종류별 플러그인 체계나 일반화된 이벤트 버스를 만들 필요는 없다.
3. 채팅 등 새 진입 경계를 만들 때 멤버/월드 명시와 명령 큐를 도입한다. 기존 static 전체 교체는 필요성이 입증될 때 넓힌다.

향후 변경 검증은 파일 줄 수 감소가 아니라 다음 행동 보존으로 판단한다: 같은 후보 key가 같은 뜻을 유지하는가, 준비 후보가 이전과 같은 순서/조건으로 생기는가, 기술 정상 종료 때만 미리 받은 답을 쓰는가, 목표 변경/쓰러짐/오래된 답이 폐기되는가, 한 캐릭터 취소가 다른 캐릭터를 건드리지 않는가, 실패 설명을 바꿔도 코드·재시도 판정은 그대로인가, 기존 기억 파일이 계속 읽히는가. 이번 읽기 전용 진단에서는 이 실행 검증을 수행하지 않았다.

현재 보고서의 세 핵심 권고는 채팅·자연어 지시·정보 정정·플레이 로그를 이번에 구현하자는 제안이 아니다. 그 기능을 붙일 때 기존 코드 전체를 다시 읽어야 하는 부담을 줄일 가장 작은 경계를 지목한 것이다.
