# 길 계산 반복 구조 — 독립 교차검토

2026-11-08. 최신 소스 읽기와 순수 캐시 모의계산만 수행했다. 코드·설정·서비스·게임 변경 및 새 로그 수집은 하지 않았다.

## 결론

많은 행동 선택지를 남긴 결정과, 선택지마다 같은 지도 탐색을 처음부터 반복하는 구현은 별개다. 현재 구현은 작은 후보 규모에 쓰던 캐시·동기 계산 구조를 수천 대상까지 그대로 확대했다. **주요 결함은 반복 최소비용 탐색, 같은 build 안에서 사라지는 계획 결과, 후보 생성 전체의 프레임 예산 부재다.**

[제약 해제 합의](../2026-11-07-제약해제/00-agreement.md)는 목표/허기 기반 후보 숨김과 옛 탐험 대표지점 압축 제거를 명시한다. give여도 탐험을 남기는 동작, 2,179개 탐험 target을 보존한 사실 자체를 버그라고 판정하지 않는다. 임의 후보 축소·압축 복구는 이번 해법 결정이 아니다.

## 숫자 검증: 707과 2179는 서로 다른 단위

이 분해는 실제 후보 설명·기억 수·실패1개와 코드가 일치하고, 관측된 `n707 cached0 tunnel707 2pass0`를 정확히 설명한다. 사이트별 런타임 카운터를 새로 얻은 것은 아니다. n은 PlanC 캐시 미스 계산 수, cached는 적중 수, tunnel은 AITunnel.Plan 전체 호출 차이, 2pass는 그중 두 번 검색한 Plan 호출 수다(Loop:682~687/1124). 707을 서로 다른 목적지707개로 읽으면 안 된다.

첫 SEND 때 frontier found0은 아직 진행 중인 작업의 부분 결과가 아니다. 다음9프레임에서 탐색을 완료해3462타일을 확장하고2179target을 얻는다. 다음 재시도에서 처음 포함된 `found2179/offered2179`는 frontier2179개 전부에 1차 PlanC가 성공해 목록에 추가됐다는 뜻이다(Candidates:689~701). **707→2179는 같은 카운터의 증가가 아니다.** 다음 build 전체 호출 수·최종 선택지 수·후처리 재탐색 완료 수는 SEND 전에 멈춰 미측정이다.

## 경로 하나마다 무엇을 다시 하는가

1. [AITunnel.Plan](C:/Dev/CoreKeeperModSDK/Assets/AIPlayerSpike/Scripts/AITunnel.cs:243)은 호출마다 도구 피해 추정, 화면 물체 차단 집합, tileCost/wallInfo 사전을 새로 만든다. 같은 출발점·지도에서 인접 목적지 수백~수천 개를 비교해도 이 자료를 공유하지 않는다.
2. [AITunnelSearch.Find](C:/Dev/CoreKeeperModSDK/Assets/AIPlayerSpike/Scripts/Core/AITunnelSearch.cs:26)는 g/came/heap을 매번 새로 만들며 출발점부터 검색한다. heap 우선순위는 누적비용 g뿐이므로 **휴리스틱 A*가 아닌 Dijkstra식 탐색**이다. 여러 목적지가 공유하는 앞부분을 반복 확장한다.
3. target에 따라 보호 경계 벽을 끝점에서 허용하는 예외가 있고, 경계 폐쇄/개방 및 detour 비교는 의도된 의미다(FindWithDetour:102~118). 한 Plan은 최대2회의 Find를 할 수 있다. 오늘 첫707은2pass0이므로 그 첫 지연을 경계2차탐색 탓으로 돌릴 수 없다.
4. FrontierJob은 다중 목적지를 한 번의 분산 탐색으로 찾지만 부모 포인터/완성 TunnelPlan을 넘기지 않는다. 비용도 Plan과 완전히 같지 않다(문 비용/보호 경계 정책). 기존 FrontierJob의 cost만 그대로 경로로 대체하면 결과 의미가 바뀔 수 있다.
5. 후보 작성 때 얻은 TunnelPlan을 해당 build 결과로 보존해 후처리에 전달하지 않고, target을 통해 PlanC에 다시 요청한다. 위험 설명을 만드는1162행은 단순 문자열 조립이 아니라 캐시 미스 시 또 전체 경로 탐색이다. 기지 경계 설명1151행도 같은 구조다.

## 캐시가 중복 계산을 막지 못하는 이유

[Loop:1092~1126](C:/Dev/CoreKeeperModSDK/Assets/AIPlayerSpike/Scripts/AIBrain.Loop.cs:1092)의 키는 대상 좌표이며, 출발점 허용 이동·성공TTL평시5초/전투2초·실패10초·detour 검사 수준을 확인한다. 서로 다른 목적지 사이의 탐색 공유는 없다.

미스 때 `if (plans.Count > 64) plans.Clear()`라 실제65개까지 있다가 다음 새 항목에서 **기존 전체를 삭제**한다. 순차적으로 많은 target을 방문하면 바로 앞 build의 결과도 남기기 어렵다. 동일2179키를 같은 순서로 두 번 방문하는 순수 모의계산에서, TTL·이동·지도 변화 없이도 첫2179미스/두 번째2179미스·두 번째적중0이었다. 이는 정책만 검증한 것이며 실제 최종 hang 후처리 횟수 측정은 아니다.

캐시를2179개 이상으로 늘려도 처음 계산12초는 그대로다. 전체 경로 목록을 모두 보관하면 메모리는 경로 길이 합만큼 늘며, TTL·이동·도구·지도 변경에 대한 유효성도 남는다. TTL시각은 Plan 시작 전에 기록하므로 긴 계산 묶음에서는 같은 build 중 먼저 만든 결과의 수명도 소모될 수 있다. `64만 키우면 해결`은 불충분하다.

## 결함 우선순위와 선택권을 유지하는 개선 방향

- **최우선: 후보 생성·경로/후처리 전체에 프레임 예산을 둔다.** 현재120,000 step guard는 개별 Find당 상한이고 수천 번 합산 작업의 상한이 아니다. FrontierJob만 분산해도 다음 PlanC 루프는 한 프레임에 돈다. 계산 중이라는 상태와 완료 결과를 구별하고, 부분 목록을 완성된 선택지처럼 보내지 않는 방식이 필요하다.
- **같은 build의 경로 결과를 직접 재사용한다.** 후보별 경로 핸들/불변 BuildContext를 유지해 위험/경계 설명이 앞서 구한 동일 계획을 사용하게 한다. 전역 TTL 캐시와 분리하면 캐시 용량 때문에 같은 프레임에서 결과를 잃는 문제를 막을 수 있다. 위험 설명 자체를 누락하는 변경과 구별한다.
- **동일 출발·정책의 다중 target 검색을 공유한다.** 버전이 고정된 지도·차단 물체·도구·출발점에 대해 거리/부모 트리를 만들고 목적지별 경로를 복원하는 설계를 검토할 수 있다. 경계 개방/폐쇄·target벽 예외·문 비용·실패/상한 진단·동률 선택을 보존해야 한다. 기존 FrontierJob을 이름만 바꿔 재사용하는 수준이 아니다.
- **계산을 늦출 때 선택에 필요한 사실은 유지한다.** 공통 비용/위험 자료와 경로 요약을 재사용하고 자세한 경로 복원을 필요 시 수행할 수 있지만, 모델이 선택하기 전 알아야 할 위험을 선택 후에만 계산하면 계약이 바뀐다. 모든 target에 접근할 수 있는지, 추정치와 확정치가 구분되는지 검증해야 한다.
- **캐시를 보조 장치로 정리한다.** 전체 Clear 대신 세대/의존성 기반 유효성과 제한된 축출을 검토하되, 메인 해법을 큰 캐시에만 의존하지 않는다. Unity World를 그대로 워커 스레드에 넘기는 제안도 하지 않는다.

오늘12초 뒤 정확한 마지막 호출 스택은 없으므로 위험 주석 재검색을 최종 hang 위치로 확정하지 않는다. 다만 첫707의 중복350회와 frontier2179회의 동기1차계산은 코드·로그에서 설명되며, 순수 캐시 모의계산도 반복 미스를 확인한다. 다음 구현 검증은 선택지/위험 사실 동등성, tile 확장·PlanC 사이트별 호출·적중·프레임 최대시간·할당량을 함께 비교해야 한다. 제품 계약 변경과 구현 작업은 이번 분석에 포함하지 않았다.
