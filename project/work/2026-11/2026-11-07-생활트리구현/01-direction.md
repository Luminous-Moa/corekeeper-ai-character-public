# 기지 생활 트리 개발 방향

이 문서는 [구현 합의](00-agreement.md)를 개발 구조와 순서로 옮긴 제안이다. 제품 코드·공식 그래프·게임 상태를 변경하지 않았다. HEAD가 이 방향을 판단한 뒤 별도 컨텍스트에서 파일·함수·분기 수준 명세를 작성한다.

## 큰 그림

기존 **상위 목적·계획 → 현장 Decisions → AICandidate → AIActions/AISkill → 실제 결과 보고** 사이에 읽기 전용인 생활 선택 탐색을 넣는다. 탐색은 새 몸 행동이나 새 목표가 아니다. 현장 AI가 필요한 대상·재료·시설의 정보를 좁혀 보고, 완전히 지정된 실행을 골랐을 때만 기존 실행 경로를 사용한다.

수량과 타일 조합을 전부 후보로 만드는 방법은 쓰지 않는다. 상위 계획이 정한 현재 작업 수량·범위는 매개값으로 전달하고, 현장 트리는 종류와 구체 대상을 단계별로 고른다. 현재 Decisions의 질문/답변은 choice 하나이므로 현장 모델이 자유 정수를 생성할 수 있다고 가정하지 않는다. 수량을 바꾸려면 기존 request_plan으로 현재 사실과 변경 이유를 상위에 전달한다. 원래 부탁의 최종 수량, 이번 작업의 요청 수량, 이번 몸 실행에서 실제 시도/확인한 수량은 각각 표시한다.

예: 원래 부탁은 음식 6개 준비, 현재 작업은 씨앗 A를 밭 구역에 8개 심기일 수 있다. 8칸·8개를 요구했어도 현재 실행 가능한 칸/재료가 5개면 실행 후보는 실제 5개와 미충족 3개를 명시한다. 부족분에 대해 다른 밭을 고르거나 준비/재계획할지는 AI가 정한다. 5개를 심었다고 음식 6개 부탁을 완료하지 않는다.

## 탐색의 입력·출력과 책임

### 생활 탐색

입력은 현재 목표와 그 수정번호, 캐릭터에게 열린 지식, 자기 가방·사용 가능한 자기 시설·밭의 현재 관측, 기억한 대상의 마지막 관측, 현재 탐색 경로다. 출력은 현재 경로의 설명, 다음으로 좁힐 선택, 실행 가능한 구체 행동, 부족한 사실이다. 개발용 행동 그래프 전체나 다른 캐릭터의 비공개 상태를 모델에 넣지 않는다.

트리 노드의 선택은 캐릭터·목표 수정·탐색 수정에 바인딩한다. 오래된 노드 응답이 새 경로나 목표를 덮어쓰지 않게 하고, 불일치는 실행 실패가 아닌 다시 볼 사실로 처리한다. 목록은 현재 수준의 항목만 생성하고, 많은 품목은 페이지로 이어 본다. 같은 레시피·대상을 서로 다른 탐색 경로에서 찾더라도 최종 실행 대상 신원은 같다.

뒤로·루트·탐색 닫기와 다른 생활 갈래로 이동을 제공한다. 탐색을 닫아도 현재 몸 행동과 원래 부탁은 유지한다. 생활 트리를 살펴보는 도중에도 현재 행동 계속·명시 중단·계획 요청, 현재 위험에 필요한 행동은 선택 가능해야 한다. 전투 상황에서는 기존 전투 판단 경로를 유지하고 생활 커서는 일시 보관하되, 이후 실행 때 현재 사실을 다시 본다.

탐색만 했을 때는 StartSkill/Stop/CancelPendingChoices, 목표 완료, 상위 부탁 종료, 성공 receipt를 호출하지 않는다. prefetch로 보낸 질문에서 탐색 응답이 와도 스킬 종료를 기다리는 실행 queue로 넣지 않는다. 기존 호출/비용 한도는 그대로 지킨다.

### 직접 실행

대상·재료·시설·수량을 상위 계획에서 이미 지정했거나 현재 경로에 완전한 선택이 있으면 루트부터 다시 탐색할 필요 없이 해당 실행 후보를 바로 제공한다. 별도 명령 실행 엔진을 만들지 않고 트리 말단과 직접 후보가 같은 후보 생성/재검증 입구를 사용한다.

말단 후보에는 무엇을 얼마나 어디에 실행하는지와 현재 부족 조건이 표시된다. 실행 직전 시설 존재/소유, 재료·슬롯/variation, 대상 칸의 현재 적합성을 다시 읽는다. 선택 뒤 바뀐 대상에는 임의 대체 실행을 하지 않고 차이를 보고한다. 구역 안에서 명시한 작업을 수행할 적합한 칸을 짧은 순서로 묶는 것은 기존 몸 실행을 재사용하되, 구역 밖 확대·다른 씨앗·다른 작업 선택은 AI에게 남긴다.

### 결과

탐색 결과, 실행 요청 접수, 투입, 생산/성장, 가방 수령 또는 장비 실제 변화는 서로 다른 사실이다. 기존 실행 관측과 보고 경로를 사용한다. 수량 충족은 관측이며 finish_goal은 현장 AI, 원래 부탁 완료는 상위 order=done에 맡긴다.

요리/제작의 커서·시설에 남은 출력이나 농사 수확 후 바닥에 남은 물건을 가방 확보로 처리하지 않는다. 회수되지 않은 결과는 다음 후보와 관측에 남긴다. 선택 수량에 비해 일부만 실행되면 실제 확인량과 잔량을 전달하며 같은 요청을 무조건 다시 보내지 않는다.

## 생활별 연결과 착수 순서

### 첫 일관된 구현 단위: 공통 탐색 + 기존 실행의 실제 선택 확대

기존 제작·요리·농사·보관/꺼내기의 선택을 트리와 직접 실행 양쪽으로 연결한다. 결과가 있는 기존 실행이어서 공통 탐색이 실제 몸 입력과 다음 판단까지 도달하는지를 확인할 수 있다. 이는 전체 시설 생활 기능 완료가 아니라 첫 통합 단위다.

| 갈래 | 탐색과 실행 연결 |
|---|---|
| 요리 | 자기 솥/작업 → 첫 재료 → 상대 재료 → 지정 작업량으로 투입 또는 수령. 재료 조합은 필요한 가지에서만 계산하고 BestPair는 예측·추천 정보로 재사용한다. 가장 배고픔 이득이 큰 한 짝만 허용하지 않는다. 입력 순서/variation/출력 적합성은 게임 규칙으로 검증한다 |
| 농사 | 작업(일구기/심기/물주기/물채우기/수확) → 관련 씨앗/작물 → 자기 밭 구역 또는 특정 칸. 작업 수량은 상위 단계의 지정값이다. s.seeds[0] 고정 선택을 없애고 지정 종자와 구역을 몸 실행까지 전달한다. 식용 외 종자는 게임 규칙·알려진 사용처를 확인해 실제 가능한 범위를 노출한다 |
| 제작 | 알려진 품목/레시피 → 사용 가능한 제작대 또는 손 제작 → 단계 수량. 현재 Prep의 첫 제작대 선택과 `craft:<item>` 신원을 대상별로 확장한다. prerequisite·생산 단위·출력 공간과 실제 가방 수령을 연결한다 |
| 보관/꺼내기 | 작업 → 자기 상자 → 물품/정확한 슬롯 → 단계 수량/남길 수량. 가방장비 구현의 정확한 대상·정상 MoveAmount·실제 수량 receipt를 소비한다. 동일 상자·품목의 수량별 조합은 열거하지 않는다 |

선택한 작업이 현재 목표와 다른 준비/생활 행동일 수 있으므로, 실제 실행의 진척을 무조건 현재 목표 진척으로 더하지 않는다. 현재 부탁을 보존한 채 다른 일을 할 수 있고 중요한 계획 변경은 상위로 요청한다. 새 목표를 임의로 덮어써 트리 갈래를 옮기지 않는다.

### 이어서 수행할 전체 단위

1. **자동 가공/제련과 수리:** 일반 Craft와 자동 생산 소비자가 다른 점을 반영해 시설 투입·완성·수령을 연결한다. 수리는 정확한 장비·비용·요청·내구도/재료 전후의 실행을 추가한다. 선택지가 적으면 직접 후보를 유지하고 필요할 때 세부 정보를 펼친다.
2. **장비 강화:** 수리대의 내구 강화와 대장간의 레벨 업그레이드를 구별한다. 장비 선택→가능한 방식/단계→효과/비용으로 탐색한 뒤 정상 게임 요청과 실제 상태 변화를 확인한다. 1의 장비 신원·상태 관측에 의존한다.
3. **거래 및 낚시:** 거래는 상인→구매/판매→상품과 가격/재고→수량을 연결하고 실제 소비/획득을 확인한다. 낚시는 도구/미끼/물 대상 선택은 탐색으로, 입질·당기기 같은 시점 판단은 직접 제시한다. 시작/상점 열기만 지원하는 단계에서 실행 완료 능력으로 노출하지 않는다.

위 후속 단위는 승인된 전체 계획의 남은 구현이다. 첫 단위를 끝냈다는 이유로 이들을 완료/폐기하지 않는다. 단계마다 명세·검수·관측을 붙여 이어 간다. 새 몸 실행이 아직 없는 갈래는 모델에 실행 가능한 말단으로 제공하지 않고 지원 능력 메타데이터와 보고를 실제 구현에 맞춘다.

## 가방장비 담당과 통합

가방장비의 최신 결과 문서가 고정한 통합 후보는 `C:/Dev/CoreKeeperModSDK-bag-common`의 `77484ec7f563f4169600a5b01aa66487cfbbb493`이다. 원래 독립 worktree HEAD `3095226`보다 공통실행을 함께 수용한 후보가 연결 기준에 맞다. 이 후보에는 item/count/where/keep/slot, AIInventory, 정상 Swap/MoveAmount/Drop과 실제 수량 receipt, 손 장비 선택 보존이 있다. Unity 결과 `final-unity-exit.json`은 exitCode 0이다. validation.md의 표에는 아직 실행중 문장이 남아 있으므로 최종 독립 판정과 본 반영 상태는 HEAD가 다시 확인한다.

가방·장비 생산 소스는 이 생활 작업에서 별도로 다시 작성하지 않는다. HEAD가 수용한 가방장비 통합 커밋이 본에 들어오면 그것을 기반으로 격리 생활 worktree를 만들거나, 생활 후보와 그 후보를 별도 통합 worktree에서 합친 뒤 검증한다. 타담당 worktree나 공식 미커밋 파일을 수정하지 않는다. 첫 단위에서 보관/꺼내기 트리를 정상 수량 receipt에 연결하려면 이 의존을 실제로 통합해 검증해야 한다. 단순히 향후 지원이라고 적고 첫 단위 완료로 세지 않는다.

시설 담당은 작업/재료/시설/구역 선택과 생산·수령 결과를 소유한다. AIInventory는 정확한 물품 이동·장착·전달을 소유한다. 공통실행은 stop_action/finish_goal/request_plan과 원래 부탁 상태를 소유한다. 같은 선택·재검증·결과 수량 규칙을 두 모듈에 복제하지 않는다.

## 검증과 전달

### 대표 오프라인 실제 파이프라인

상위의 농사 단계(seed A, 범위 R, 작업량 6)를 실제 PlanProtocol/PlanStep/Goal에 전달한다. 현장 후보 생성으로 농사→심기→seed A→R를 선택하고 실행 전 실제 후보 payload와 수량을 확인한다. 이 과정에서 기존 probe 몸 행동과 held/queued 선택이 유지됐는지 확인한다. 말단을 골라 실제 Apply→AIActions.Make→FarmSkill의 실행 입구와 작업 결과 관측까지 연결한다. 실제 월드·버퍼·입력 경계는 최소 어댑터를 쓰되 정책·상태·실행 선택 로직을 별도 복사하지 않는다. 4칸만 유효한 장면에서는 4개 실행/2개 미충족 보고와 다음 판단을 확인한다.

이어 실제 요리 소스를 링크한 표본에서 기본 BestPair와 다른 유효 재료·둘째 자기 솥을 고르고, 투입/생산/가방 수령 사실을 구별하는 경로를 확인한다. 트리를 거치지 않은 동일 지정 실행이 같은 후보·재검증 입구를 쓰는지도 확인한다. 이 검증은 모델/API·실제 게임 소비자의 실행 성공을 뜻하지 않는다.

### 필요한 회귀

- 트리 탐색의 어느 깊이에서도 back/root/닫기 및 직접 실행 접근이 유지되고 후보 상한/페이지에서 사라지지 않음.
- 탐색·오류·호출 실패가 실제 행동·목표·원래 부탁을 취소하지 않음. prefetch/held/queued 경계에서 조회가 몸 동작으로 처리되지 않음.
- 다른 캐릭터/목표/탐색 수정의 응답과 교체된 시설/재료/슬롯이 잘못 적용되지 않음.
- 품목·시설·재료 순서·범위가 다른 후보의 identity가 충돌하지 않음. 수량별 모든 후보/전체 조합을 만들지 않음.
- 화면 밖 시설은 마지막 관측으로 표시하고 현재 실행 가능 상태를 몰래 조회해 전지적 후보로 만들지 않음.
- 일부 실행/가방 가득 참/결과 시설 잔류를 실제 가방 확보로 표시하지 않음. 원래 부탁과 중간 단계 수량·완료가 구분됨.
- 변경한 PlanProtocol/bridge 공유계약과 Core 회귀, 공통실행 실제 입구 회귀, 재사용 AIInventory 어댑터 회귀가 유지됨.

빠른 컴파일은 `dotnet build Tools/compile-check -c Release`, Core는 `dotnet run --project Tools/core-tests -c Release`, 상위 protocol은 기존 `Tools/ai-bridge` 테스트, 공통실행은 `Tools/execution-tests/run.ps1`을 사용한다. 새 실제 생활 모듈을 실행하는 어댑터 검증은 명세에서 해당 소스를 직접 링크하거나 생산 입구를 추출하는 방식으로 정한다.

그 뒤 격리 Unity 6000.0.59f2에서 `-batchmode -quit -projectPath <격리 경로> -executeMethod HeadlessSdk.CompileCheck -logFile <결과 폴더 로그>`만 실행한다. 게임 SDK assembly 사본과 USE_PUG_OTHER가 필요한 기존 환경 조건을 재사용하고 다른 Unity 배치와 겹치지 않게 조정한다. `BuildAndInstall`, 설치 파일 변경, 게임 실행/자동조작은 기존 보류를 유지한다.

최종 독립 검수는 합의·명세와 실제 변경/검증 결과를 대조한다. 프로젝트 그래프는 승인된 기획·구현 커밋·정적 검증·실게임 미확인을 구별해 원본에서 갱신하고, 게임 행동 그래프를 제품 지원 능력으로 바꿔 쓰지 않는다. 실게임 보류가 해제된 뒤에는 실제 모델의 탐색→선택→게임 입력/소비→가방 결과→다음 판단 대표 흐름을 별도로 확인한다.

## 명세에서 정할 것과 HEAD 판단점

일반 구현 선택인 노드/페이지 신원, 상태 필드, 상위 selector 전달, 후보 조립 자리, nav 응답 분기 위치, 각 실행의 재검증·부분 결과 처리는 다음 명세에서 정확히 정한다. 개발 방향은 위 책임 분리와 기존 계약 재사용으로 충분하며 외부 API·새 요금/모델·새 영구 저장 스키마를 결정할 필요가 없다.

HEAD가 먼저 판단할 점은 첫 통합 단위에 실제 가방장비 후보를 수용할 기반과 후속 단위 진행 순서다. 수량은 상위 count를 쓰는 방향을 HEAD가 승인했다. 공유 자원·희귀 재료 일괄 소비·새 생활 모드 정책은 추가하지 않는다. 새 구매/내구강화의 구체 게임 요청과 비용은 후속 단위에서 검수 수용 원본과 실제 소비자를 더 확인해야 한다.
