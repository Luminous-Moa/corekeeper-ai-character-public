# 코어키퍼 오브젝트별 상호작용 수집 지침

## 목적과 범위

게임 자체의 대상 × 행위 목록을 만드는 첫 수집이다. 현재 모드가 구현한 행동 목록으로 게임의 가능성을 제한하지 않는다. AI가 사용하는 모드의 기능은 나중에 이 목록과 대응한다. 이번 결과는 최종 기능 설계나 완성된 계획 그래프가 아니라, 근거가 달린 오브젝트 상호작용 자료다.

전체 모집단은 Steam build 26332184의 ObjectID 등록 목록과 기존 실행 덤프의 합집합이다. dump의 (id, var) 3,020건과 덤프에 없는 등록 ID 11건, 합계 3,031건이다. variation을 합쳐 버리지 않는다. 좌표·액체·추상 상태 등 ObjectID 밖의 대상까지 모두 수집했다는 뜻은 아니다.

게임 실행과 설치 변경은 하지 않는다. 게임 원본 자료를 읽고 지정된 작업 폴더에만 결과를 쓴다. 기존 그래프·모드·세션 context·저장 기록은 변경하지 않는다.

## 사용 원본

- 고정 입력: 이 폴더의 inputs/dump.json, inputs/ObjectID.json, inputs/appmanifest_1621690.acf. 원본 경로와 SHA-256은 sources.json.
- dump는 게임 데이터베이스를 기존 kgdump 도구로 추출한 자료다. 이번에는 게임을 재실행하지 않고 이 자료를 재사용한다.
- 게임 코드 보충: C:/Dev/_ref/corekeeper-decomp/ 아래 디컴파일. 모드 코드는 게임 행동의 증거로 쓰지 않는다. 덤프 형식의 의미를 확인할 때만 C:/Dev/CoreKeeperModSDK/Assets/AIPlayerSpike/Scripts/AIKnowledge.cs의 writer를 참조할 수 있다.
- 디컴파일과 설치 빌드가 일치하는지 이번에 증명하지 않았다. 디컴파일에서 확인한 추가 행동은 code_candidate로 기록한다. 실제 프리팹 연결이나 버전 대응이 없으면 특정 ObjectID에 확정 행동으로 붙이지 않는다.

## 먼저 재현할 1건

이 폴더에서 `node collect.mjs`를 실행한다. 처음에는 원본 3개를 inputs에 복사하고 이후에는 그 스냅샷을 재사용한다. 게임·운영 그래프에는 쓰지 않는다.

pilot-iron-sword.json을 확인한다. id=8901,var=0인 철검의 req는 철 주괴(id 1002) 8개와 황금 주괴(id 1003) 1개다. canCraft에 8901이 있는 제작 장소는 4014, 4021, 4024, 4034, 4047의 5개다. 덤프에서 해당 인덱스와 배열 값을 직접 읽어 일치 여부를 확인한다. 이 결과는 실제 철검 제작 성공 증거가 아니다.

핵심 방법은 이름으로 가능성을 추측하는 것이 아니라, ID로 직접 연결된 게임 데이터 또는 해당 타입을 실제 처리하는 게임 코드를 근거로 삼는 것이다.

## 각 오브젝트를 수집하는 순서

1. input-<group>.json의 모든 key를 읽는다. key는 id:variation이다. 0이 아닌 변형, noPrefab, 이름 없는 항목, 덤프가 없는 항목도 남긴다.
2. raw를 읽고 이미 추출된 interactions의 JSON pointer 근거를 확인한다. canCraft→출력 ID는 제작하기, req→재료 ID는 제작 재료로 사용하기, 제작 장소의 canCraft는 제작 장소로 사용하기의 데이터 근거다. 출력/재료 관계의 subject.variation=null과 variationApplicability=unknown은 특정 행의 variation을 제작하거나 재료로 쓸 수 있다는 주장이 아님을 뜻한다. recipeObservation은 해당 덤프 행의 req 관측이며 실제 출력 변형과의 연결은 미확정이다. 이를 실행 조건으로 승격하지 않는다.
3. eat/equip/tt/hp/dur/type 등 남은 필드를 단서로 게임 디컴파일에서 실제 처리 조건과 경로를 찾는다. `rg`로 좁히고 필요한 파일·함수만 읽는다. 같은 타입에 공통인 처리는 한 번 분석해 명시적 규칙으로 적용한다. 덤프의 효과값만으로 식용·장착 슬롯·파괴 가능 여부를 전부 확정하지 않는다.
4. 근거가 있는 상호작용을 추가한다. 대상 자체에 하는 일과 도구로 사용하는 일을 구별해 objectRole에 target/tool/station/ingredient/output을 적는다. 제작되는 품목은 output이다. 새로운 고정 행동 설계를 결정하지 말고 게임에서 확인한 의미를 기록한다.
5. 코드에 메서드가 있다고 해당 프리팹에 연결된 것은 아니다. 이름 유사성이나 상속만으로 모든 변종에 적용하지 않는다. 연결이 부족하면 규칙 후보와 unresolved에 남긴다.
6. 각 항목을 결과에 남긴다. 미확인은 불가능과 다르다. 모든 항목을 처리했다는 것과 모든 상호작용을 알아냈다는 것을 구분한다.

## 역할 분할

- equipment: 장비·무기·도구 621건.
- world: PlaceablePrefab 1,209건.
- creatures: Creature/Critter/Pet/TrainingDummy/PlayerType 198건.
- items: 나머지 및 ID 전용 항목 1,003건.

담당 그룹의 출력만 쓴다. 입력, collect.mjs, 다른 그룹 파일을 수정하지 않는다.

## 출력 계약

각 담당자는 `workers/<group>/`에 다음을 쓴다.

- collect.mjs: 고정 입력에서 아래 결과를 재생성하는 스크립트. 외부 패키지 설치 없이 Node 내장 모듈 사용. 파일 경로는 import.meta.url 기준으로 계산한다.
- results.json: `{group, records:[{key, interactions:[...기존+추가], unresolved:[...], reviewMethod}], rules:[...], coverage:{inputCount,outputCount,unresolvedCount}}`.
- report.md: 확인한 것, 미확인/경계, 재현 명령, 대표 원문 대조 2~3건. 수치만으로 성공을 주장하지 않는다.

추가 interaction 형식:

```
{verb:"안정적인 영문 키", label:"한국어 행위", objectRole:"target|tool|station|ingredient|output",
 evidenceLevel:"code_candidate", applicability:"적용 근거·범위",
 conditions:{...확인한 것만}, result:{...확인한 것만}, ruleId:"group-...",
 sources:[{file:"게임 소스 절대 경로", line:시작줄, endLine:끝줄, sha256:"전체 파일 해시", excerpt:"핵심 조건/처리 짧은 원문"}]}
```

data 수준은 고정 덤프가 직접 말하는 관계에만 사용한다. 관측 효과값과 추정 행동을 섞지 않는다. code_candidate는 실행 미확인·버전 대응 미확인이라는 뜻이며 불확실성을 유지한다. 보충 code rule에는 적용한 ObjectType/ID 조건과 제외 조건을 명시하고, 입력에 존재하는 key에만 적용한다. 추가 근거가 없으면 기존 상호작용과 미확인 이유만 반환해도 된다.

## 스스로 확인할 것

- 입력 key 집합과 출력 key 집합이 정확히 같다. 중복이나 빠짐이 없다.
- 기존 interactions를 보존한다. 추가 행동의 근거 파일과 줄·해시가 실제로 맞는다.
- 대표가 서로 다른 오브젝트 2~3개에서 결과→원본을 따라가 직접 대조한다.
- 스크립트를 다시 실행해 results.json의 SHA-256이 같은지 확인한다.
- 특정 상태·도구·재료·권한 조건을 제거해 무조건 가능한 행동으로 바꾸지 않는다.
- 타입별 공통 규칙으로 덮이지 않는 특수 행동은 미확인으로 드러낸다. 전체 상호작용 완성이라고 보고하지 않는다.

HEAD는 네 그룹을 통합해 전 모집단 처리 여부와 근거를 검사하고, 별도 검수자가 표본과 과장된 적용을 확인한다. 게임에서 실제 실행하는 검증은 후속 시험 환경 작업의 범위다.
