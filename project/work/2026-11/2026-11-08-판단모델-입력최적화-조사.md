# 판단모델(celeris-1.1-decision) 입력·선택지 설계 조사

- 날짜: 2026-11-08
- 범위: GitHub(공식 저장소, SDK, 예제, 이슈, PR, 연구 저장소)를 먼저 보고, Celeris와 TypeSafe 공개 문서, arXiv 초록으로 보충했다.
- 표기
  - **[검증]**: 출처 원문에서 직접 확인한 내용이다. 문서 페이지는 원문 마크다운(curl)이나 GitHub 원문으로 읽었다. 일부(OpenAI Decisions 가이드, arXiv HTML)는 요약 도구를 거쳐 읽었고, 그런 경우 따로 적었다.

- 출처 대부분은 Jev(TypeSafe, System One API의 원조), 다른 판단모델, 일반 LLM을 다룬다. **Celeris 1.1에서 직접 측정된 근거는 거의 없다.** 그래서 아래 권고는 모두 우리 오프라인 재생으로 확인해야 하는 가설이다.

## 1. Celeris 자체 자료 (최우선)

### 1-1. GitHub에는 선택지·입력 작성 지침이 없다 [검증]
- 공식 조직은 `ai-celeris`이다(https://github.com/ai-celeris). 저장소는 `celeris-cli`, `celeris-cookbook`, `homebrew-tools` 세 개다.
- `celeris-cookbook`(https://github.com/ai-celeris/celeris-cookbook)의 예제는 모두 chat 모델 celeris-1용이다(분류, 추출, 가드레일 등). decision 모델 예제나 Choice 작성 지침은 없다. 저장소 전체에서 "decision"이 나오는 곳은 README의 일반 문장뿐이다.
- 제3자 SDK인 tryAGI/OpenAI 가이드(https://github.com/tryAGI/OpenAI/blob/main/docs/guides/decisions.md)는 제한 사항만 정리한다. `x_celeris`, 질문 512개, 이미지 8장, user 역할만 허용 등이다.
- 우리 적용: 선택지 문구, 순서, 개수, 언어에 대한 Celeris 공식 권고는 GitHub에 없다.

### 1-2. 공개 문서 docs.celeris.ai/decisions [검증]
출처: https://docs.celeris.ai/decisions (원문 .md), https://docs.celeris.ai/models
- 모델 이름은 `celeris-1.1-decision`이다. 컨텍스트는 131,072 토큰이고, 답을 위해 일부가 예약되어 입력 한도는 그보다 조금 작다.
- 한도: choice 질문 하나에 선택지 512개, 요청 하나에 질문 512개(explain을 켜면 64개).
- `input`에는 문자열이나 user 메시지 목록을 넣는다. "The model reads all text parts in order, joined with blank lines."
- `confidence`는 1위 확률을 0(균등 분포)~1(확신) 범위로 다시 맞춘 값이다. probabilities는 소수 둘째 자리에서 반올림된다.
- **`x_celeris.explain: true`를 주면 질문마다 "왜 그 답을 골랐는지" 한 문장을 돌려준다.** 대신 요청이 느려진다.
- 문서에 없는 것: 선택지 순서의 영향, 권장 개수, 설명 길이, 언어별 성능, value 문자열을 모델이 읽는지 여부.
- 우리 적용: 오프라인 재생에서 explain을 켜면 "계속하기"나 "단계 마치기"를 고른 이유 문장을 모을 수 있다. 원인 진단에 바로 쓸 수 있다.

### 1-3. docs.celeris.ai/prompting (chat 모델용이지만 관련 있는 부분) [검증]
출처: https://docs.celeris.ai/prompting
- "When the output is a label, list the valid labels and close the set." 그리고 fallback(`none`/`unknown`/`other`)을 넣으라고 한다. 이유는 "Otherwise, it may choose the closest label."이다.
- "Keep variable prompt content concise." "Put reusable instructions first"(캐시 단가 때문).
- 우리 적용 [추론]: 고정 지시를 앞에 두고 변하는 관찰을 짧게 줄이라는 일반 원칙만 확인된다. decision 모델에 대한 실측 근거는 아니다.

### 1-4. Celeris는 System One API 호환을 표방한다. 가장 가까운 상세 지침은 Jev 문서다 [검증 + 추론]
- Celeris 문서: "It implements TypeSafe's System One API, so code written for Jev ... runs against it". 제3자 소개(https://infrabase.ai/inference-apis/celeris-1-decision)에 따르면 diffusion LM 기반이다.
- 런칭 페이지(https://celeris.ai/celeris-1-decision)에도 순서 편향, 언어, 질문 작성법은 나오지 않는다. 이 페이지는 요약 도구로 읽었다.
- [추론] API 모양이 같다고 내부 동작까지 같다는 보장은 없다. 그래도 아래 2장 이후의 Jev 지침이 우리가 쓸 수 있는 가장 가까운 지침이다.

### 1-5. Celeris 공개 측정치 (참고) [검증]
- decision-bench PR(https://github.com/atlanai/decision-bench/pull/39): celeris-1.1-decision이 1,071행 중 93.84%를 맞혔다. **Celeris가 직접 제출한 결과**이고, GPT-6 Luna와의 차이는 +0.2pp [−2.2, +2.6]로 사실상 같다.
- system-one-bench Round 11(https://github.com/alilibx/system-one-bench): 측정 대상은 celeris-1-decision(1.0)이다. 지수 83.6으로 37개 중 4위, 영어 83.2(2위), 아랍어 83.1(9위), 보정 오차 2.6%(9위)였다. 이미지는 base64를 텍스트로 읽어서 우연 수준이었다.
- typed-decisions 보정 표(https://github.com/wideraHannes/diffusion-language-models-blog/blob/main/benchmark/results/report.md): 측정 대상은 celeris-1-decision(1.0)이다. 정확도 0.739, ECE 0.072였고, 2,000건 모두에서 1위 확률이 0.5 이상이었다.
- 한국어, 선택지 수십 개, 긴 설명, 행동 선택 같은 우리 조건과 비슷한 측정은 없다.

## 2. 선택지 이름(라벨) 편향: 실패 1 "계속하기"와 관련

| # | 발견 | 출처 | 구분 | 우리 설정에 적용 |
|---|---|---|---|---|
| 2-1 | "The option names and their descriptions are both sent to the model." 모델은 이름과 설명을 모두 읽는다. 질문 id는 보지 않는다. | https://docs.typesafe.ai/primitives/choice | 검증(Jev) | value가 `c1..cN`이면 모델에게 의미 없는 번호다. 그 경우 설명 첫머리의 라벨이 사실상 이름 역할을 한다. Celeris가 value 문자열을 읽는지는 문서에 없다. [추론] |
| 2-2 | Literal reading: "Write the exact condition, criteria for each available option". 틀린 답을 보고 "사실 이런 뜻이었다"고 설명하게 되면 "that explanation is the missing half of the instruction". | https://docs.typesafe.ai/model-jaggedness | 검증(Jev) | 실패 1, 2를 문구 수정으로 고친 것과 같은 원리다. "계속하기"를 "제자리에 서 있기(이동·전투 없음)"로 바꾼 것처럼, **라벨은 선택했을 때 실제로 생기는 일을 적어야 한다.** |
| 2-3 | Label-word reliance: 모델이 증거 대신 라벨 단어에 반응한다. 해결책은 라벨마다 관찰 가능한 조건을 적는 것이다. | https://github.com/vicfei/awesome-jev-prompts/blob/main/categories/anti-patterns.md (#11) | 검증(커뮤니티 정리, Jev) | "계속하기", "단계 마치기(완료 확인)"처럼 좋은 결과를 암시하는 동사 라벨은 피한다. 효과를 서술하는 라벨로 바꾼다. |
| 2-4 | LLM 객관식의 selection bias는 위치보다 **선택지 ID 토큰에 대한 사전 선호(token bias)** 에서 주로 생긴다. 선택지 내용을 바꿔 가며 사전 선호를 추정해 빼는 PriDe를 제안한다. | https://arxiv.org/abs/2309.03882 , https://github.com/chujiezheng/LLM-MCQ-Bias (ICLR 2024) | 검증(일반 LLM) | `c1`, `c2` 같은 ID에도 사전 선호가 있을 수 있다. [추론] 순서를 섞은 재생으로 확인할 수 있다(5장). |
| 2-5 | 글자 라벨(A–F)을 쓰면 순열을 바꿔도 결과가 평평해지고 `attack`만 반복했다. 행동 단어를 라벨로 쓰고 유효한 행동만 내놓자(`--legal-only`) 완주율이 0%에서 40%로 올랐다. | https://github.com/lovelacemadeline/systemone-gridworld/blob/main/docs/stories/4-5-legal-actions-and-labels.md | 검증(로컬 Gemma 분류기, Celeris 아님) | 라벨 형식과 무효 행동 제거가 함께 크게 작용한 사례다. 판독 방식이 Celeris와 다르므로 방향만 참고한다. |

## 4. 피난처·기본값 선택지(계속, 대기, 완료 확인)와 반복

## 13. 오프라인 재생으로 시험할 변경 (우선순위 순)

1. **무효 선택지 마스킹과 문구 수정 비교.** 코드가 미완료를 아는 상태(구리 0/8)에서는 "단계 마치기"를 목록에서 뺀다. 실행 중인 행동이 의미 없을 때는 "계속하기/서 있기"를 뺀다. 문구 수정판과 마스킹판을 같은 로그로 재생해 다음 행동 분포와 목표 관련 선택률을 비교한다. (4-5, 4-6, 10-3)
2. **순서 민감도 측정.** 같은 요청에서 선택지 순서를 뒤집거나 섞고 `c` 번호를 다시 매겨 재생한다. 1위가 바뀌는 비율을 잰다. 민감하면 두 가지를 시험한다. (a) 같은 choice 질문을 순서만 바꿔 한 요청에 두 번 넣고 확률을 평균한다(PriDe 방식). (b) 피난처 선택지를 항상 맨 끝에 고정한다. (3-1, 3-2, 2-4)
3. **설득·기본값 문장 제거.** 남은 비용·권유 문장을 사실형으로 바꾸고, 모든 선택지에 같은 형식으로 붙인다. 일반 지시 "현재 행동 유지" 줄을 빼거나 조건형으로 바꿔 재생한다. 조건형 예: "계속하기는 진행 중인 행동이 목표 아이템에 가까워지고 있을 때만". (4-1, 4-4, 5-1, 5-2)
4. **설명 정형화.** "[선택 시 일어나는 일] / [목표와의 관계 꼬리표: 목표 아이템 있음·목표에 가까워짐·변화 없음] / [필요한 사실]" 순서로 통일한다. 거리와 비용 비교는 코드가 "가장 가까움" 같은 말로 바꿔 넣는다. (5-4, 5-5, 5-6, 6-1)
5. **숨은 하위 목록을 병렬 질문으로 대체.** 최상위 choice와 각 하위 목록 choice를 한 요청에 함께 보내고 확률 곱으로 합친다. usage로 비용이 얼마나 늘어나는지도 확인한다. 대안은 목표 관련 하위 항목을 최상위로 꺼내는 것이다. (8-1, 8-3, 8-4)
6. **반복 태그.** 직전 N회에 골랐는데 상태 변화가 없던 선택지에 "최근 N회 선택, 변화 없음"을 붙인다. 같은 실패가 반복되면 코드가 대체 선택지를 샘플링한다. (4-6)
7. **입력 축소.** 결정과 무관한 기억이나 관찰을 잘라 낸 판과 원본을 비교한다. 목표 줄과 단계 판정은 맨 앞에 둔다. (7-1, 7-3)
8. **진단용 `x_celeris.explain: true`.** 실패 사례(계속하기, 단계 마치기)의 이유 문장을 수집한다. 64개 질문 제한과 지연 증가는 재생에서는 문제없다. (1-2)
9. **확률 기준 재조정.** Celeris 확률 분포로 "근소 차이면 재질문" 같은 기준을 새로 맞춘다. gpt-6-luna 기준을 그대로 쓰지 않는다. (9-1, 9-2)

## 14. 확인하지 못한 것
