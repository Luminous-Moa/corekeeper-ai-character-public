# 행동 판단 그래프를 프로젝트 지식그래프에서 조회할 필요성

개발자가 구현·검수 중 게임 행동의 조건과 실패 원인을 확인하는 데 기능별 연결이 필요하다. 권장 범위는 프로젝트의 기획·기능에서 해당 게임 규칙의 현재 게시본과 검토 당시 근거를 함께 조회하는 것이다. AI 캐릭터에게 무엇을 공개하고 실행시킬지는 별도의 제품 결정이다.

## 확인한 경로

- [프로젝트 기획 편집 원본](2026-11-07-기획연결/source.mjs)은 `P.expedition`에서 당시 행동 판단 그래프 자료를, `R.expedition-implementation`에서 `R.expedition-game-evidence`를 참조한다. 후자는 [채굴·문·다리 조회 기록](../채집이동귀환-구현자료/graph/final-source-pins/expeditionHandoff.md)의 28~36행을 돌려준다. `R.extraction`도 이전 정적 추출 결과를 가리킨다.
- 대표 확인은 프로젝트 CLI의 `source R.expedition-game-evidence`에서 곡괭이 조건 ID를 읽고 [현재 행동 그래프 CLI](../게임행동-그래프/README.md)의 `source completion:B:melee-pick-2-0:cost-followup-v1/condition/conditions`로 원문을 열었다. `/cases/75/conditions`의 정규화 SHA-256 `c16abe006ebab5b88f8045039bab89e3a09c334fabd345a746e2aa15a4348943`이 기록과 일치했다. 장착·입력·쿨다운 조건과 실행 중 결정되는 적중·파괴가 구별되어 있었다. 현재 이 단계는 수동이다.
- 생활 기획 `P.life-tree-first-scope`에 포함된 요리도 행동 그래프 `cooking 1645 1646`에서 `cooking:1`로 좁혀 `source cooking:1`로 원문을 확인할 수 있었다. 두 재료의 정확한 sourceKey·순서, 출력 ObjectID 9504와 variation 107873901, 슬롯·수량·타이머 등의 조건이 있다. 이는 신규 연결 후보이다.

## 연결 방식과 한계

프로젝트의 관련 노드마다 판단에 실제로 쓰는 행동 노드 ID를 참고 관계로 등록하고, 프로젝트 조회에서 해당 노드의 조건·결과·실패 및 원문으로 이동하게 하는 방식을 권한다. 검토한 게시본 식별값과 원문 해시를 함께 보관하고, 새 게시본에서 ID 누락이나 원문 변경을 구분한다. 이름이나 ObjectID만으로 variation과 prefab을 합치지 않는다. 먼저 기존 채굴·문·다리에 적용할 수 있다.

현재 [행동 게시본](../게임행동-그래프/published/manifest.json)의 manifest SHA-256은 `98377f972972c5f3dbcd555ae0c9e42ed5421eb559992d6fd4d45db3d5bf3870`이다. 256수용묶음·2,539사례이며 정적 규칙과 실제 게임 성공은 서로 다른 증거다. 기존 `R.expedition-behavior-graph`의 제목은 당시 126판을 가리키고 연결된 README 사본은 133판을 설명하므로, 현재·당시 판을 식별할 때 제목만 사용하면 안 된다. 프로젝트 `product.mjs check`는 구조 오류가 없고 코드 기준이 `20b1aced`로 일치하지만 `todo.md` 입력 해시가 달라 전체 결과는 `ok:false`였다. 이번 작업은 조사로 끝냈다.
