## 1. 선택과 설명의 의미

- 대상 key/좌표/행동 종류·가용성·진행 표시·선택 가능한 모든 target을 유지한다. 계산 중 일부 목록을 완성된 목록으로 제출하지 않는다. 단순히 count가 같다는 검사보다 key 집합과 필요한 설명의 동등성을 확인한다.
- 알려진 위험, 기지 경계 개방, 문 우회·경계 파괴 대안, 도구 부족·모르는 타일·막힘의 구별을 모델이 **고르기 전** 제공한다. 자세한 경로를 늦춰 복원하더라도 선택에 필요한 위험을 선택 뒤로 미루지 않는다.
- 경로 비용은 기존 보행1·채굴타격 비용·문 비용2, 화면 물체 차단과 기억/현재 관측, 도구 피해·감소의 실제 의미를 유지한다. 화면 밖 기억을 현재 사실로 승격하지 않는다.
- 보호 경계 폐쇄 우선, 끝점 자체가 보호 벽인 target 예외, 개방 fallback, detour 검사 요청 수준·조건·시간 추정과 대안 표시를 각각 검증한다. closed/open 공통 트리를 쓰면 target 예외와 문 정책을 따로 입증해야 한다.
- 도달 불가, 탐색 상한 도달, 아직 계산 중을 구별한다. null·빈 경로·start==target·정수 경계·불연결 지도·도구 부족·닫힌 문·target 벽에 별도 기대값을 둔다. 미완료를 no-way로 캐시하지 않는다.
- 모델 선택을 프로그램이 임의 행동으로 대체하거나, 위험을 이유로 후보를 자동 삭제하지 않는다. 기존 실행 시 재검증/정상 입력 경로는 유지한다.

## 2. 재사용과 무효화

- 같은 build에서 얻은 계획/요약을 후처리에 넘겨 중복 탐색을 막았는지 실제 호출 경로로 확인한다. 큰 전역 캐시만 추가해 첫 build의 수천 회 탐색을 그대로 두면 원인 해결로 인정하지 않는다.
- context에 AI·world·출발점·관측/지도 상태·차단 물체·도구/채굴 피해·경계/문 정책·detour 검사 수준 중 무엇을 고정하는지 명시한다. 공유 가능한 조건이 다른 결과를 섞지 않는다.
- 이동·도구 변경/파손·벽 파괴/설치·문/물체 변화·알려진 타일 변화·사망/재접속·월드 종료에서 결과를 폐기/재검증하는 경계를 확인한다. 기존 의도된 TTL/이동 허용을 이유 없이 변경하지 않는다.
- 검사가 더 약한 계획으로 detour 사실을 보장하지 않는다. 실패 결과의 진단도 다른 tool/world에 누출하지 않는다. 캐시 삭제가 현재 build의 살아 있는 계획 핸들을 무효 참조로 만들지 않는다.
- 여러 AI가 같은 target을 물어도 캐시·계수·상태가 섞이지 않는다. 원래 per-agent 스코프와 `_building` 계측 소유가 yield/재진입 후에도 맞는지 확인한다.

## 3. 프레임 분산·중단·Unity 접근

- 한 프레임의 작업 예산이 내부 정책으로 존재하고, 모든 target을 결국 계산한다. 개별 Find의120000 step guard만으로 총 예산을 대신하지 않는다. target 사이에서만 yield하면 단일 긴 경로가 막을 수 있으므로 내부 확장도 예산을 따른다.
- 스냅샷 수집/지도 열거, 공통 탐색, target별 경로 복원, 벽·위험 요약, 후보 설명·조합·JSON/거대 로그까지 새로 이동한 병목이 없는지 확인한다. expansion 카운터만 줄어도 전체 frame 비용이 남을 수 있다.
- Unity World/EntityManager·AITileReader·정적 AIAgent.Cur 등 라이브 게임 접근을 임의 작업 스레드에서 하지 않는다. worker를 쓴다면 메인 스레드에서 만든 순수 불변 입력만 넘기고 결과 적용도 수명 검사를 거친다.
- 새 명령/goal revision·stop·off·world unload·AI entity 소멸·사망/respawn·상위 답변 적용·긴급 전투 상황이 오래된 build를 취소/대체하는 경로를 확인한다. 취소 뒤 오래된 요청 전송·목표 변경·body 입력·메모리/경험 기록이 발생하면 반려한다.
- 계산이 여러 프레임에 걸쳐도 오래된 request context나 잘못된 character scope가 되살아나지 않아야 한다. 취소한 상태의 사전/버퍼·Native 자원이 정리되고 pending 상태가 영원히 남지 않아야 한다.
- 계속 변하는 세계에서 무한 재시작/계산 기아가 생기지 않는지, 여러 AI의 예산이 한 프레임에 누적돼 큰 정지를 만들지 않는지 확인한다. 기존 진행 행동/최소 reflex 의미를 임의 변경하지 않는다.

## 4. 테스트와 실제 검증 경로

- `dotnet run -c Release --project Tools/core-tests`: 실제 `Scripts/Core/**/*.cs`와 AIExpCore를 직접 컴파일하는 C#8/net10 경로다. 순수 탐색·경계·문·기존 선택지 회귀를 실행한다.
- `dotnet build Tools/compile-check -c Release -nologo`: 실제 모드 전체를 설치 게임 DLL 읽기 참조로 C#8/netstandard2.1 컴파일한다. 새 Core가 Unity 타입에 의존하면 core-tests에서도 드러나야 한다. fast compile을 게임 로드 성공으로 부르지 않는다.
- `Tools/restriction-tests`는 실제 AITunnelSearch/AICandidateAssembler 등을 링크하지만 이것만으로 Unity 후보 생성·중단 통합을 검증했다고 하지 않는다. 변경된 생산 경로를 링크/호출하는 오프라인 통합 대역이 필요한 범위는 owner가 제시한다.
- Unity batchmode CompileCheck는 게임/Unity가 실행 중이면 기존 gate가 거부한다. 게임·서비스·설치 조작 금지 조건에서 검수자가 임의 실행/종료하지 않는다. 승인 범위에 없는 실제 LLM 요청이나 실게임 성공을 만들어 내지 않는다.
- 오라클은 작은 수제 지도에 기대 비용/도달성/벽·위험을 직접 적거나, 다른 알고리즘의 완전탐색/독립 참조로 계산한다. 새 구현을 그대로 옮긴 테스트 도우미와 self-equality만으로 동등성을 주장하지 않는다.
- 과거 알고리즘과 differential 비교는 회귀 보조이며 단독 정답으로 쓰지 않는다. tie 경로를 보존해야 하는지 먼저 명시하고, 다르면 비용만 같다는 이유로 경계·위험·후보 설명 차이를 무시하지 않는다.
- 707 원인 구성과2179target 이상 표본을 별도로 검증한다. key 전체 보존, 위험 사실, 사이트별 실제 계산/적중/확장 수, 중간 yield와 완료·취소를 측정한다. 두 번째 sweep 적중0이 사라졌다는 것만으로 첫 계산/프레임 비용 통과를 대신하지 않는다.
- 성능은 같은 입력·빌드 조건에서 전체 준비/가장 긴 작업 조각·할당/유지 메모리와 계산 총량을 함께 기록한다. 순수 C# 마이크로초를 실제 Unity 최대 프레임 시간으로 표시하지 않는다. 실게임을 하지 않았다면 전체 정지 해소는 아직 미확인이라고 남긴다.

## 수용과 반려

선택권/필수 위험 정보/실행 조건 보존, 원인 경로의 실제 중복 계산 감소, 프레임 분산과 취소 통합, 관련 회귀·전체 소스 컴파일 증거가 함께 필요하다. 미충족은 구체 경로와 재현 입력으로 owner에게 반려한다. 범위 밖 문제·기존 실패는 새 회귀와 구별하며, 설치/실게임/외부 모델 성공 여부를 별도 표기한다. 구현자 검증이 끝난 확정 diff를 받아 독립 검수를 이어간다.
