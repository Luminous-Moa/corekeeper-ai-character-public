# 동일 출발 공유 검색 후속 검수

2026-11-08. `2a0112d` 실기 실패 뒤 후속 변경을 검수했다. 생산 코드 수정은 구현자가 담당했다. 현재 문서는 검색 코드·시험 checkpoint이며 전체 작업의 최종 실기 수용은 대기한다.

## 출발 증거

ai2의 기억 탐험 끝은 30,492개 타일에서 7,526개 목적지를 만들었다. 목적지별 검색을 프레임에 나눈 2a0112d는 147.9초 동안 SEND를 만들지 못하고 54,636.3ms의 준비 작업 뒤 위협 변화로 취소됐다. 이 실기 결과는 이전 코드 단계 검증의 한계를 드러냈다. 화면 안 `lExplore`는 BFS 거리 `_reachDist`를 재사용한다. 긴 작업의 대상은 기억 탐험 끝 `fr → PreparePlan → PlanC → lDigExplore`, `kind=dig`다.

## 구현 확인

- `SharedSearchJob`은 같은 출발·피해 조건의 열린 그래프와 보호 경계를 닫은 그래프를 공유한다. `SharedQueryJob`은 완료된 거리·부모 정보를 사용해 경로를 복원한다.
- 보호 경계 자체가 목적지이면 그 목적지를 마지막 한 칸으로만 붙인다. 확정된 인접 칸의 최저 거리와 목적지 비용으로 도달을 판정한다. 보호 경계 목적지를 통과해 다른 목적지로 진행하는 경로는 닫힌 트리에 생성되지 않는다. 이 경우 목적지별 Dijkstra fallback은 없다.
- 검색 상한 뒤에는 확정된 일반 목적지만 반환한다. 경계 목적지는 확정 인접 거리와 frontier 하한으로 최적성이 입증돼야 반환한다. 미확정과 도달 불가를 구별한다.
- 누적 비용은 long이며 좌표 이웃도 overflow를 검사한다. 0 비용 경로의 부모 순환과 긴 복원 중 yield를 검사했다.
- 같은 최소 비용에서 경로 타일 순서는 이전 목적지별 heap 검색과 달라질 수 있다. 타격·벽·위험은 실제 반환 경로에서 계산한다. `EdgeClosed`와 tool-short 수치는 공유 그래프에서 관측한 범위로 넓어지며 생산 설명에 공유 검색임을 표시한다.

## 직접 실행

`dotnet run -c Release --project Tools/core-tests -- TUNNEL-SHARED`는 18개 상위 검사를 통과했다. 내부에서 frozen 이전 구현과 8,640개의 목적지 조합을 비교하고 도달성·최저 비용·경로 유효성·타격·작업 예산을 검사한다. 수제 경계 목적지, 문 비용을 보존하는 통합 경로, 우회와 목적지 타격 제외, 상한, 0 비용과 극단 좌표 사례를 읽었다.

7,526개 보호 경계 목적지와 알려진 타일 30,492개의 Core 합성 지도에서는 두 트리만 사용했다. 검수자 실행은 heap pop 53,458회, 비용 callback 61,152회, 261ms였다. 15,052개 경로 query 중 heap pop과 비용 callback이 추가되지 않았다. 보호 경계 목적지가 대부분인 조건에서도 per-target 검색으로 돌아가지 않았다.

생산 AITunnel의 Plan부터 PlanBatch/SharedTrees/SharedPlanSearch/PlanJob까지 추출한 `tunnel-shared-harness`는 71,637개 검사를 통과했다. 추출 구간을 당시 생산 소스와 문자열 비교해 일치함을 확인했다. .NET8 런타임이 없어 설치된 .NET10에서 `DOTNET_ROLL_FORWARD=Major`로 실행했다.

통합 대역의 7,526개 보호 경계 목적지·30,492개 알려진 타일은 모든 목적지를 완료했다. SearchCount=2, ExpandedTotal=30,666, CapturedTileCount=31,191, 경로 타일 합계=1,291,721이었다. 예열·query·최종 검증을 포함한 검수자 실행은 372.6ms였다. 예열 후 각 목적지 query 동안 ExpandedTotal이 증가하지 않았다. 매 목적지의 실제 경로 끝점·hits·폭발 위험 설명을 확인하고 긴 안전 우회와 위험한 경계 대안의 분리도 검사한다.

`dotnet run -c Release --project Tools/core-tests` 전체 1,571개 통과도 직접 확인했다.

## 후속 발견과 처리

1. 초기 통합에서는 `StepCapture → CandBuild.Prep/Enemies → PlanC miss → RunUntilDone`으로 첫 공유 트리 전체를 동기 생성할 수 있었다. 이를 구현자에게 전달했다. `PlanBatch.StepSearches(workBudget)`가 추가됐고 통합 대역에서는 예열 뒤 모든 query에서 검색 확장이 0임을 확인했다. 이후 생산 PreparationSteps에서 후보 생성 전에 `StepSearches(32)` 완료까지 yield하는 연결을 직접 읽었고, 실제 Preparation.cs 링크 시험 25개와 전체 소스 컴파일 경고 0개·오류 0개를 재확인했다.
2. 닫힌 그래프가 완전 소진됐지만 열린 그래프가 상한에 걸린 실패에서 `FirstCapped && second.Capped`가 false가 되어 길 없음으로 단정했다. 공유 경로의 최종 불확정 판정을 열린 query의 Capped로 수정했다. closed 50개 완전 소진, open 120,000개 상한 사례가 상한·미확정 설명을 반환하는 회귀 시험을 직접 통과했다.

## 수용 범위

위 수치는 알려진 타일 수와 목적지 수를 맞춘 합성 입력이다. 실기 ai2 타일 지도·위험·문·도구를 그대로 재생한 fixture가 아니다. Unity entity query, 실제 프레임, 전체 후보 문자열·JSON·HTTP 요청 시간도 포함하지 않는다. 최종 수용에는 실제 ai2의 후보 준비 완료·취소·SEND 확인이 남아 있다. 전체 그래프 예열이 경로가 필요 없는 메뉴·소규모 판단에도 비용을 추가하는지 실측해야 함을 구현자에게 전달했다. 255개 choices 초과 문제는 기존 선택 트리 연결 감사와 함께 별도로 수정·검증해야 한다. ## 선택 트리 연결 이후 checkpoint

후속 변경은 단순 메뉴·소수 경로에서 전체 그래프를 예열하지 않도록 바뀌었다. `BeginSinglePlan`이 배치 사실과 마지막 검증을 공유하며 먼저 실행된다. 현재 build의 완료 계획 수 또는 선택된 경로 수 hint가 8 이상일 때 `PreparePlan`이 `StepSearches(32)`로 예열하고 이후 목적지는 공유 트리를 사용한다. 8은 실행할 대상의 누락 상한이 아니라 검색 방식 전환 조건이다. 동기 PlanC miss는 예열 전에는 단일 검색, 예열 뒤에는 공유 트리 query를 사용하므로 첫 소비자가 새 전체 트리를 동기 구축하던 발견은 닫혔다.

생활·가방과 기존 채집이동 트리의 코드 연결을 다시 읽었다. 큰 광석·기억 탐험 끝은 싼 key/좌표/설명 목록을 먼저 만들고, 현재 트리 노드에서 표시할 leaf에 대해서만 `PreparePlan`과 기존 실행 후보 생산자를 호출한다. 최종 경계·위험 설명은 해당 실행 후보가 만들어진 뒤, 모델이 실행 후보를 고르기 전에 붙는다. 화면 안 `lExplore`의 BFS 거리 재사용 흐름과 이 deferred dig 흐름을 구별했다.

직접 `Tools/execution-tests/run.ps1`을 실행해 118/118 통과를 확인했다. 실제 258개 요청의 kind/key fixture를 읽고 그중 208개 mine/dig leaf와 합성 452/7,526개 leaf를 기존 Compose·Navigate 응답·BuildJson으로 전수 방문했다. 각 노드의 전체 전송 배열은 제어와 직접 후보를 포함해 255 이하였다. 루트·닫힘에서 미선택 경로 준비 0, 선택 leaf만 준비, 현재 몸 행동과 원래 목표 유지, 뒤로·루트와 오래된 토큰 취소를 검사했다. 후보 생산자 전체는 이 시험의 대역이며 실제 생산자 연결은 코드와 최종 실기에서 확인한다.

같은 dig key가 관측 목록과 긴급 entity 경로·life-bound 실행·명시 Home/Goto 목적지에 겹치면 직접 후보가 접힐 수 있음을 전달했다. 생산 등록의 DirectRoute 검사와 Compose의 entity/life/명시 목적지 보존 조건을 추가하고 같은 key 충돌 회귀를 통과했다. 미준비 채집 대상도 기존 기회 보고와 이탈 전 미검토 ledger에 관측 사실로 남도록 수정됐다. deferred 탐험 leaf를 만든 뒤 `_exploreOptions`를 다시 계산하도록 수정한 점도 확인했다.

HEAD는 직접 대응 후보만으로 255를 넘는 추가 범위를 이번 새 트리 설계로 확대하지 않기로 결정했다. 해당 경우 최종 전송 전 개수 검사, 명시 진단과 HTTP 400 재시도 방지를 적용하고 한계를 공개한다. 현재 코드는 후보를 잘라 보내지 않으며 과대 요청을 보내지 않는다. 이 경계는 이번 실제 258·452 world leaf와 7,526개 목적지의 연결 검수와 구별해 기록한다.

## 2차 통합 코드 검수 판정

구현자가 지정한 2차 통합 checkpoint에서 보고한 차단 결함은 수정·재검수됐다. 현재 코드와 오프라인 증거는 후속 실기에 넘길 수 있다. 최종 실기 완료 판정은 유지해서 대기한다.

- 직접 재실행한 결과는 Core 1,571개, 스케줄러 25개, 실행·탐색 연결 118개, restriction 47개 통과이며 전체 소스 dotnet 컴파일 경고 0개·오류 0개다.
- `unity-compile-shared.log` 1794행의 `[HeadlessSdk] CompileCheck: ok`를 직접 확인했다. 생산 소스와 Tools의 `git diff --check`도 종료 0이다.
- 최신 생산 코드는 닫힌 원정 트리에서 기억 frontier 검색 job을 새로 시작하지 않는다. travel 갈래를 펼쳤을 때 기존 background frontier job이 목록을 만들고, 현재 leaf에 해당하는 목적지만 상세 경로 준비를 한다. 목록 안의 목표 key를 임의 삭제하는 처리는 없다.
- 전수 leaf 탐색 시험의 Compose/Nav/JSON은 생산 코드를 사용하지만 전체 CandBuild·Unity 세계는 대역이다. restriction은 실제 RememberedOres 생산자를 추출해 두 알려진 광석 종류의 등록과 준비 경로를 확인한다. 실제 ai2의 상위 응답→첫 SEND→트리 탐색→실행 선택·행동과 7,526개 목록의 응답성은 실기로 확인해야 한다.
- 같은 비용의 경로 순서 변화, 공유 그래프 관측 진단의 범위, 원자 epoch 미보장, 직접 대응만으로 API 상한을 넘을 때의 전송 중단은 최종 보고에 공개할 한계다. Unity가 생성한 환경 파일은 구현자가 제품 변경과 구별해 정리한다.
