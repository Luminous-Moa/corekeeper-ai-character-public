# 600경로 최종 독립 검수

2026-11-07. 판정: **세 합성 장면의 반복 실행 결과로 수용**. 600개가 실제로 종료되었다는 기록, 동결 조건, 원문 응답, 집계의 일치를 확인했다. 제품 전반의 검색 정확도·목적 달성·속도 우열을 보증하는 시험은 아니다. 아래의 고갈 장면 99개는 원래 자동 false와 역할 경계 미정을 유지해야 한다.

## 범위와 방법

## 실행과 동결의 일치

- queue는 600개 고유 ID이며 실제 trial 디렉터리도 같은 600개다. 각 조건 100개, 각 scene의 A 선행/B 선행 각 50쌍이다. seed로 큐를 별도 재생성해 일치했고, 모든 쌍의 두 경로가 순차 실행되었음을 시각으로 확인했다.
- 시도 디렉터리는 정확히 600개이며 모두 `attempt-001`이다. 추가·누락·교체 시도, failed/blocked, transport retry, 429는 0이다. 완료 600은 실행 절차 종료이고 자동 수락 600이라는 뜻은 아니다. 각 append events 로그와 result.events가 일치했다.
- 시작/종료 구간을 별도로 합산한 최대 동시 trial은 4이며 status의 maxActive와 같다. 세션은 하나이고 정상 종료 후 trackedChildren=0이다.
- 상위 실제 로그 1,002개는 모두 `gpt-6.1-sol`/`low`, Decisions 요청·응답 1,215개는 모두 `gpt-6-luna`이다. `models.json` 및 setup과 일치한다. 이는 이번 실행의 기록 확인이며 향후 모델 강도 지정은 아니다.
- core SHA-256은 `0d7860c1c6d76edb2f5fe970bd089b8ef0c4817d56b5c6d15acd67132d931971`, batch는 `1e5f50819e791ca8244e37f5fb709007da47ec6bf6479d7e833c62ce133bda45`로 저장된 session sources와 같다. pilot 원본/복사본 해시도 contract와 같다. fixture/조회, 상위 기본 지시, 경로 지시식, 선택지, 원래 accept의 5개 원문 구간을 별도 추출해 core 포함 여부와 contract 구간 해시를 모두 확인했다.
- 각 scene의 초기 관찰과 같은 조회 결과는 모든 반복·경로에서 동일했다. 모든 모델 입력의 retrieved/current_plan은 해당 시점까지 실제로 공개된 상태와 같았다. 기대 행동·숨은 requirement/past/expected가 별도 입력 필드로 들어간 흔적은 없었다. 선택지와 시험 프롬프트가 행동 공간을 제한하는 것은 동결된 시험 설계의 일부다.

Decisions 응답에는 model/answers/usage만 있고 개별 요청 ID는 없다. 따라서 공급자 요청 ID에 의한 독립 중복 감사까지 한 것은 아니다. 600개 원본 시도, transport 이벤트, 시각, usage의 일치에 근거한 실행 감사다.

미공개 target/evidence ID, 최종 계획 대상과 선택의 불일치, 고갈 광맥 이동, 준비 부족 상태의 채굴 이동은 발견하지 않았다. 인용 ID의 공개 여부는 근거 내용 전체의 논리적 사용을 보증하지 않는다. Decisions는 선택값·확률만 반환하므로 모델이 특정 근거 문장을 실제로 사용한 내부 과정을 증명할 수 없다.

- **s1-B 조회 생략은 오류가 아니다.** sites만 조회한 73개도 near 결과의 e:3에 같은 도구 등급으로 4개를 얻은 기록이 있다. 26개는 sites→history, `s1-009-B`는 history→sites다. 해당 희귀 순서의 원문도 확인했다.
- **s2-B는 순수 Decisions 전용 검색 경로가 아니다.** 96개는 Decisions의 재상신 후 prepare_tool로 변경했다. 이 중 `s2-048-B`는 history만 조회한 뒤 재상신했으며, 필요한 등급 2와 현재 등급 1의 대조 근거가 충분했다. 나머지 4개(`s2-061-B`, `070-B`, `081-B`, `092-B`)는 상위가 처음부터 history를 조회했다. `070-B`는 상위가 sites도 추가 조회해 상위 호출이 3회였다. 네 개 모두 원문을 확인했으며 재상신 실패나 중복 실행으로 볼 수 없다.
- **s3-B의 99개 false는 삭제하거나 오답으로 확정하면 안 된다.** 모두 두 조회 뒤 gather 계획 아래 frontier1 탐색을 선택했다. 최신 고갈 관측과 사용자 목표에는 적절하지만 하네스의 plan.task=explore 조건은 충족하지 않았다. 동결 지시는 작업 내 탐색을 반드시 상위 변경으로 봐야 한다고 명확하게 정하지 않았으므로 역할 경계 미정이다.
- **`s3-039-B` 한 개는 실제 수락이다.** sites→history→escalate→상위 explore/frontier1→explore로 진행했다. 원본 valid=true이며 totalMs=19,148.710이다. 다른 99개와 섞어 100개 모두 확정 계약 수락이라고 부르지 않는다.

## 통계와 시간 해석

전체 원본에서 분위수와 paired B−A 차이를 별도 재계산해 summary의 값과 일치를 확인했다. 분위수는 정렬 후 ceil(p×n)번째인 nearest-rank다. 각 조건의 수락/경계 구분, 모델·검색·API 대기·quota 대기도 확인했다.

| 조건 | 첫 선택까지 p50 / p90 / p95 (초) |
|---|---|
| s1-A | 16.576 / 20.494 / 21.446 |
| s1-B | 9.887 / 17.535 / 22.051 |
| s2-A | 17.086 / 21.559 / 23.406 |
| s2-B | 23.315 / 31.379 / 33.236 |
| s3-A | 17.099 / 21.117 / 21.515 |
| s3-B | 10.122 / 18.103 / 24.296 |

s1의 B는 짝 비교 85/100에서 짧고 중앙값도 짧지만 p95와 최대값은 A보다 길다. 모든 지연 구간이 개선되었다고 주장할 수 없다. s2의 B는 89/100에서 더 길다. s3의 표는 목표에 맞는 탐색 선택까지이며, B의 99개는 확정 계약 수락까지의 시간이 아니다. 양쪽 자동 수락인 s3 쌍은 한 개뿐이어서 일반 속도 비교 근거가 되지 않는다.

`totalMs`는 trial별 adapter 생성 뒤 시작한다. fixture/기억 초기 구축, 해당 trial 시작 전 큐 대기, 공통 최초 인증·preflight(14,330.485ms)는 제외된다. 반면 trial 도중 상위 호출 전의 quota refresh 대기와 공유 API slot 대기·재시도 대기는 포함된다(이번 retry는 0). quotaWait의 합은 약 302.811초, API wait 합은 약 1,326.961초이며 병렬 경로별 대기를 더한 값이므로 벽시계 시간과 더해서는 안 된다. 모델 호출 자체의 시간에도 CLI·서비스 지연이 섞인다.

배치 status의 elapsedMs=2,599,225.518, 약 43.320분은 공통 최초 preflight를 포함하는 배치 벽시계다. fixture/프로세스 시작 전체 시간이나 사용자 요청 600개를 동시에 제출했을 때 각 요청의 전체 대기 시간과 같지 않다. queueWaitMs는 배치 타이머부터 각 trial 시작까지의 경과이며 초기 preflight와 선행 경로 실행도 섞인다.

원본 합계는 상위 입력 11,963,362(캐시 9,116,928)·출력 93,614, Decisions 입력 1,294,347이고 usageAllAttempts와 같다. 상위 1,002/Decisions 1,215개 모두 usage가 보고되었다. 로컬 조회는 sites 596회+history 527회=1,123회다. 토큰과 호출 수는 비용 실측이나 실제 광석 확보 건수가 아니다.

## 수용 범위

동결된 실험용 짧은 프롬프트, 세 합성 장면, 장면마다 동일 기록 3개, 고정된 소수 대상과 선택지를 100회씩 반복했다. 600개의 서로 다른 실제 세계나 다양한 사용자 과제를 시험한 것이 아니다. 좌표와 관측 cause를 보충하는 시험용 공통 조회 어댑터를 썼으므로 현행 제품의 검색 API가 이미 이 기능을 제공한다는 증거도 아니다.

실제 게임 이동·경로 도달·제작·채굴·광석 4개 확보, 장시간 기억 검색, 세계 변화에 따른 응답 노후화는 시험하지 않았다. 병렬 배치의 30회/분 공유 API 제한·구독 점검·서버/CLI 상태가 시간에 섞이므로 초기 단일 실행이나 제품 전체 프롬프트 지연과 직접 등치하지 않는다.

검수 중 최종 보고서와 summary notes가 fixture 색인도 배치 벽시계에 포함한다고 설명한 오류 1건을 지적했다. 작업자가 집계 코드의 보고 문구를 고쳐 재생성했으며, 보고서·summary.md/json에서 fixture는 trial/batch 모두 제외, 최초 preflight는 trial 제외/batch 포함으로 정정된 것을 확인했다. 원본 시간값이나 실행 결과 변경은 없었다.

검수 시점의 원본·집계에서 실행 재현성이나 통계를 뒤집는 결함은 발견하지 않았다. 최종 보고서는 99개 경계, B 상위 선검색 4개, 지연 포함/제외 범위와 합성 반복 한계를 보존하고 있다. 위 범위에서 최종 보고를 수용한다.
