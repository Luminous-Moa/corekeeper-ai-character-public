# 검색 경로 시뮬레이션 결과

2026-11-07. 게임 없이 실제 위쪽 LLM과 Decisions를 호출했다. 정상적인 위치 확인은 Decisions에 검색을 맡기는 경로가 한 번의 위쪽 호출을 줄였고, 준비 계획을 바꿔야 하는 장면은 상위 재판단이 필요해 오히려 더 오래 걸렸다. 낡은 위치 장면은 두 경로 모두 고갈된 광맥을 피했지만, Decisions가 탐색을 직접 시작해도 되는지의 역할 경계가 드러났다.

## 무엇을 실제로 실행했나

- 위쪽: 현행 기본 구성 `gpt-6.1-sol`, effort `low`, 기존 구독 CLI 어댑터. 로그인·구독·사용량 검사 통과(최대 사용률 45%, 후속 46%).
- 행동 판단: 운영 설정과 같은 `gpt-6-luna`, 실제 Decisions API. 키는 기존 환경변수 경로에서 읽었으며 로그·파일에 저장하지 않았다.
- 기억: 기존 `memgraph.mjs`의 `context/runQueries`와 합성 기록. `resource_sites`는 위치 좌표·관측 시각, `resource_history`는 같은 원본 사건의 상세 관측 cause를 보충하는 시험용 공통 API다.
- 실행: 모델의 첫 이동 선택을 합성 장면의 대상·준비 조건·상위 작업과 대조하여 수락 여부를 검사했다. 실제 캐릭터 이동이나 길 찾기는 실행하지 않았다.
- 3장면 × A/B 각 1회. 위쪽 LLM **10회**, Decisions **12회**, 로컬 검색 **11회**. 추가 모델 호출 없이 결과 감사만 했다.

## 비교 결과

시간은 공통 초기 설정·인증 확인 이후 새 부탁을 위쪽 LLM에 전달한 순간부터 첫 행동 선택과 모의 수락 검사까지다. 각 경로는 동일한 부탁·관찰·기억에서 출발한다.

| 장면 | A: 위쪽이 검색·계획 | B: 작업 후 Decisions 검색 | 첫 선택과 판단 |
|---|---:|---:|---|
| 정상 광맥 위치·조건 확인 | **18.848초** / 위쪽 2회·Decisions 1회 | **9.301초** / 위쪽 1회·Decisions 2회 | 둘 다 기억한 광맥으로 이동. 동일한 준비 조건과 목적지에 부합하여 수락 |
| 현재 도구로 채굴 불가 | **17.016초** / 위쪽 2회·Decisions 1회 | **20.060초** / 위쪽 2회·Decisions 4회 | 둘 다 먼저 도구를 준비할 제작대로 이동. B는 실제로 위쪽에 재판단 요청 후 수락 |
| 옛 위치가 최근 고갈됨 | **15.679초** / 위쪽 2회·Decisions 1회 | **9.884초** / 위쪽 1회·Decisions 3회 | 둘 다 새 구역 탐색 선택. A 수락. B는 목표에는 적절하지만 상위 작업 범위 경계가 미정이라 아래처럼 구분 |

첫 행의 B는 A보다 9.547초 짧았다. 둘째 행의 B는 A보다 3.045초 길었다. 셋째 행은 같은 탐색 이동을 선택했지만 상위 재계획 절차가 달라 **동일 계약의 성공 지연으로 단정해 비교하지 않는다**. 전체 평균이나 일반적 정확도 비율로 확대하지 않는다.

## 실제로 선택한 흐름

### 정상 위치 확인

- A: 위쪽이 위치·경험 두 조회를 한 번에 요청 → 검색 결과를 읽고 `gather / ore1` 계획 → Decisions `move_resource`.
- B: 위쪽은 `gather / 대상 미지정`으로 전달 → Decisions `resource_sites` 조회 → `move_resource`.
- B의 위치 조회에는 기존 `near` 결과로 같은 도구 등급에서 확보한 성공 경험도 함께 들어왔다. 따라서 별도 경험 조회를 생략해도 이 장면에서는 준비 근거가 있었다. 특정 조회 함수를 반드시 호출해야 성공으로 셈하지 않았다.

### 도구 준비 필요

- A: 위쪽이 위치·경험 조회 → 필요한 도구 등급 2와 현재 등급 1을 비교 → `prepare_tool / bench1` 계획 → Decisions `move_bench`.
- B: 위쪽 `gather` → Decisions 위치 조회 → 경험 조회 → `escalate` → 위쪽 `prepare_tool / bench1`로 변경 → Decisions `move_bench`.
- B의 재상신 뒤에는 위쪽도 필요하면 추가 검색할 수 있게 설계했다. 따라서 B는 **현장 검색 중심 + 상위 재계획을 허용하는 혼합 경로**다. 실제 이번 재상신에서는 위쪽의 추가 조회 없이 전달받은 사실로 계획을 바꿨다.

### 낡은 기억

- A: 위쪽이 위치·경험 조회 → 최신 고갈 관측을 보고 `explore / frontier1` 계획 → Decisions `explore`.
- B: 위쪽 `gather` → Decisions 위치·경험 조회 → 상위 재상신 없이 `explore`.
- B가 고갈된 광맥으로 이동한 것은 아니다. 새 탐색이라는 선택은 사용자 목표와 숨은 장면 사실에 부합한다.
- 원래 자동 판정기는 `plan.task === explore`를 요구하여 B를 `valid:false`로 남겼다. 그러나 프롬프트는 **gather 작업 중 광맥 탐색이 반드시 상위 계획 변경에 해당한다**고 명시하지 않았다. 최근 합의에서도 작업 내 이동·대상 변경은 Decisions가 맡으므로 이 조건은 아직 명확하지 않다.
- 원본 `valid:false`를 유지하고, 사후 감사에서 **목표 적합: 예 / 상위 enum 일치: 아니오 / 역할 계약 판정: 미정**으로 분리했다. 이를 모델 검색 정확도 실패나 완전 통과로 셈하지 않는다. B의 9.884초는 첫 적절한 탐색 선택까지이며 확정 계약에 따른 실행 수락까지의 시간은 아니다.

## 속도와 정확도 해석

| 장면/경로 | 위쪽 호출 합 | Decisions 호출 합 | 로컬 검색 합 |
|---|---:|---:|---:|
| 정상 A | 16.894초 | 1.952초 | 1.195ms |
| 정상 B | 8.754초 | 0.547초 | 0.157ms |
| 도구 A | 16.762초 | 0.253초 | 0.334ms |
| 도구 B | 18.711초 | 1.347초 | 1.515ms |
| 고갈 A | 15.422초 | 0.256초 | 0.351ms |
| 고갈 B | 9.205초 | 0.678초 | 0.394ms |

- 이 작은 fixture에서는 로컬 검색이 아닌 위쪽 모델 호출 횟수가 지연 차이를 지배했다. 첫 Decisions 호출은 1.952초이고 후속 호출들은 더 짧아 연결·서버 상태·실행 순서의 영향도 섞여 있다. 한 장면 한 번으로 안정적인 배율을 추정하지 않는다.
- Decisions는 필요한 조회를 스스로 선택했고, 준비 부족에는 재상신했으며, 고갈 관측을 무시하고 옛 광맥으로 이동하지 않았다. 이 표본에서는 검색을 맡기는 것이 곧 정확도 저하로 이어지지는 않았다.
- 원래 자동 판정은 조회 존재와 작업 종류 위주였다. 추가 [감사 결과](audit.json)는 각 상위 계획이 지정한 대상이 당시 공개된 ID인지, 인용한 기억 ID가 실제로 주어진 것인지, 최종 대상과 첫 행동이 맞는지를 재검사했다. 미공개 대상·근거 ID의 사용은 없었다. 대상 미지정은 B에서 Decisions에 맡긴 경우로 구분했다.
- Decisions 응답은 선택값뿐이다. 근거가 입력됐고 결과가 그 사실에 맞았다는 관측이며, 모델 내부에서 그 근거를 실제로 사용한 과정을 입증하지는 않는다.

## 한계와 실행 경계

- 세 장면은 합성 기록이며 실제 게임 기록을 잘라 재생한 것이 아니다. 광맥 수량·도구 등급·제작 비용은 시험 전제다. 각 기억은 사건 3개라 실제 장시간 기억 검색 성능을 대표하지 않는다.
- 초기 관찰과 검색 도구는 양쪽 동일하지만, 역할별 프롬프트는 다르다. 기존 전체 제품 brief 대신 실험용 짧은 역할·형식 프롬프트를 사용했다. 따라서 수치는 **제안한 연결 구조의 이번 시험 지연**이며 현재 게임 전체 프롬프트의 실측값이 아니다.
- 초기 기억 색인 구축과 로그인·사용량 확인은 표 시간에서 제외했다. 공통 preflight는 첫 묶음 6.581초, 후속 묶음 7.519초였으며 경로별로 반복하지 않았다. 새 프로세스의 첫 사용자 경험에는 이 비용이 더해질 수 있다.
- 두 경로 모두 새 시험 조회 API의 좌표·상세 관측 보충을 사용했다. 현행 제품이 이 조회 계약을 이미 제공하거나 Decisions 검색을 이미 구현했다는 뜻이 아니다.
- 첫 이동 선택까지만 봤다. 광석 4개 확보 완료, 경로 도달, 실제 제작·채굴, 움직이는 세계에서 응답이 낡는 문제는 검증하지 않았다.
- 운영 코드·설정·게임 저장·context.md는 수정하지 않았다. 게임과 운영 브리지를 시작하지 않았다. 기존 기지 4a 작업을 재개하지 않았다.
- 초기 첫 묶음에서 설정 JSON의 BOM을 읽지 못해 Decisions 기본값 `gpt-6-luna`가 사용되었다. 저장된 실제 요청 모델은 운영 설정과 동일하다. 후속 묶음 전에 BOM 처리를 보완하고 설정 읽기 실패 시 중단하도록 고쳤다. 모델 응답 비교를 위해 첫 묶음을 다시 호출하지 않았다.

이 폴더에서 다음 명령은 모델 호출 없이 fixture와 저장 결과를 확인한다.

```powershell
node .\run.mjs --mode fixture
node .\audit.mjs
```

다음 명령은 **실제 모델을 새로 호출**한다. 이번 작업에서는 이미 완료했으므로 결과 확인을 위해 반복할 필요가 없다. 새 label을 사용해 원본을 보존한다.

```powershell
node .\run.mjs --mode run --label new-run --scenes s1,s2,s3 --routes A,B
```

이번 호출 사용량은 위쪽 입력 128,857토큰(캐시 포함 92,928), 출력 973토큰, Decisions 입력 12,740토큰이다. 위쪽은 구독 CLI이며 실제 청구 비용을 측정하지 않았다. 운영 Decisions 사용량 파일은 수정하지 않고 시험 결과에 별도로 남겼다.
