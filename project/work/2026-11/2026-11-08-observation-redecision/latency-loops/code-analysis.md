# 이동 반복과 대기 재관측 코드 대조

분석 대상은 실제 설치된 09e418a와 evidence/20261108-114512-Player.log, 같은 시각 decisions.log 및 plan.jsonl이다. 분석 구간은 t531~746.1이다. 제품 코드와 게임 상태를 변경하지 않았다. t556 이후 호스트 이동이 포함된 관측이다.

## 새 5초 재판단과의 관계

52개 하위 SEND의 trigger와 구간 전체 로그에서 `대기 조건 재관측` 문구는 0회다. 해당 문구는 AISkill.RefreshPendingObservation이 5초 갱신을 발급할 때 항상 붙는다. 따라서 이번 왕복을 5초 갱신이 계속 깨워 만든 현상으로 설명할 직접 근거가 없다.

현재 AISkill은 AIBody.Tick 시작마다 BeginObservationTick으로 표식을 비우고, 실제 ObserveOnce가 호출된 Tick만 다음 Brain에서 갱신 대상으로 삼는다. 실제 정상 이동 Tick에 대기 조건이 다시 발생하지 않으면 옛 대기 문구는 주기 재발행되지 않는다. 준비 중·응답 대기 중·기존 미소비 관측이 있을 때도 같은 조건의 주기 발급을 보류한다.

이 구간의 하위 호출은 새 갈림길 대기, 통로 끝, 새로 보인 물체, 새 목표로 발생했다. 새 목표 trigger는 11회다. 문구 변경이 모델의 방향 선호에 미친 영향은 이전 버전과 같은 입력의 대조 실행이 없어 확정할 수 없다.

## 방문 결과가 다음 선택에 연결되지 않는 경계

AITravel.State.Map과 travel-memory.json은 관측된 타일의 통행 가능 여부를 저장한다. 어떤 가지를 실제 걸었고 어디서 끝났으며 언제 되돌아왔는지의 실행 이력은 저장하지 않는다.

TravelSkill._walkedEdges는 개별 실행 객체의 필드다. 같은 실행에서 동일 방향 간선을 반복하면 멈추지만, 막다른 곳에서 모델이 restart를 고르면 AITravel.Make가 새 TravelSkill을 만들고 집합이 새로 시작한다. 따라서 앞 실행에서 확인한 막다른 가지를 새 실행이 다시 선택할 수 있다.

AddChoices의 분기 설명은 방향과 선택 시점의 통로 조건을 제공한다. 앞 실행에서 그 방향을 갔다 돌아온 결과와 방문 횟수는 붙지 않는다. `너머 자원·위험·연결은 미확인` 문구도 일률적으로 사용한다. 관측된 지형 메모리가 있어도 이 선택 설명에서 이전 가지의 실제 끝·방문 결과를 활용하지 못하는 연결 공백이다. 해당 구조와 AITravelRules 알고리즘은 43c 이전부터 존재했다.

## 상위 재계획이 반복되는 별도 경로

상위 보고 #14~27은 모두 action_replan으로 전송됐다. 실제 report.events에는 `현장 이탈 선택 전에 미검토 자원 기회`가 반복해 들어 있다. AIExpedition.Choosing은 travel_turn과 continue를 현재 실행 후보 s.Current로 바꾼다. 그 후보가 explore이면 leaving이 항상 참이어서 가까운 갈림길 선택도 현장 이탈로 평가한다.

미검토 자원 집합을 문자열로 묶어 ShouldReport에 넣으므로 시야 이동에 따라 흙벽 채집 묶음의 구성이나 물체 집합이 달라지면 새 보고가 된다. 상위는 그 보고에 13회 explore 재설정으로 답했다. SetGoal은 목표 세대를 바꾸고 다시 하위 판단을 요청한다. 현재 몸 동작을 그 자체로 자동 중단하지는 않는다.

이 Choosing 연결은 7af8f91에도 있었다. 43c는 경로 계산을 미룬 query 대상까지 자원 사실에 추가했다. 그 변경이 현재 보고량을 얼마나 늘렸는지는 같은 월드의 전후 대조가 없어 확정할 수 없다. 현재 반복 보고가 해당 미검토 자원 사건에서 나왔다는 사실은 요청 본문으로 확인했다.

## 준비 지연

구간의 준비 취소 114회 중 장애물 범위 18회, 장애물 위치 64회, 타일 변경 1회, 위험 변경 2회, 새 적 1회, 새 목표 6회, world/goal/execution 변경 22회다. 하위 SEND 간격 중앙값은 3.4초, 최대 13.2초다. 전송까지 완료된 후보 준비 CPU 합계는 11.7초이며, 취소된 114회 준비가 사용한 CPU는 별도로 20.38초다.

이 재시작 비용은 판단이 나오기까지의 지연을 더한다. 반복 방문 경로 자체는 위에 적은 분기 선택과 restart로 만들어졌다. 새 5초 재관측은 이 구간에서 발급되지 않았다.

## 전달 지연과 구분할 사실

투구·갑옷·바지의 실제 전달 실행은 약 0.7~1.0초에 수령 확인을 얻었다. 바지 단계는 53.7초가 걸렸고 실제 전달은 그중 1.0초였다. 도구 메뉴 진입 뒤 미확인 finish_goal을 6회 선택했으며 재판단 간격은 약 5.3초였다. 메뉴 취소 후에는 준비가 28회 취소됐고 CPU 6.277초, 경과 시간 약 16.9초가 더 들었다. 이때 완료 검사는 부족 사실을 유지했고 재판단이 계속됐다. 전체 수행 지연의 큰 부분은 실제 아이템 이동 전에 선택을 반복하는 구간이었다.

수정 범위를 정할 때는 실제 방문·막다른 길 결과를 다음 후보 사실로 전달하는 경계, 가까운 분기를 현장 이탈로 반복 보고하는 경계, 준비 무효화 범위를 각각 확인해야 한다. 자동 방향 선택이나 후보 삭제는 이번 분석에서 결정하지 않았다.

## 바지 메뉴 선택의 원문 대조

live1-decisions-113324.log의 #92 INPUT은 c3을 `분류 도구`, c7을 `분류 착용 장비`로 전송했다. t378.02의 #92 ANSWER는 c3을 선택했고 같은 key `category:도구`가 기록됐다. 확률은 c3 0.550, c7 0.300이다. 실제 메뉴도 도구로 열렸다.

AIInventoryMenu의 categories 생성은 group.Key를 다음 frame.category에 넣으며 ApplyNavigation은 그 선택 토큰을 적용한다. AIBrain.HandleResponse는 전송한 _reqCands에서 value가 응답 choice와 같은 후보를 찾는다. 이번 기록에서 c3이 다른 메뉴로 잘못 연결된 증거는 없다. 이후 #93과 #94는 c1 finish_goal을 반복 선택했고 현재 수령 0/1 검사가 이를 보류했다. 이 선택을 한 모델 내부 이유는 알 수 없다.

같은 (28,8)에서 북쪽 (28,9)으로 가는 #116·#121·#128·#133의 선택 설명에는 모두 `너머 자원·위험·연결은 미확인`이 들어 있다. 이전 방문에서 확인한 막다른 가지라는 사실이 해당 분기 설명에 축적되지 않는 사례다.
