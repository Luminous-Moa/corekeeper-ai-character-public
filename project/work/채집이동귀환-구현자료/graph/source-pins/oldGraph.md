# 코어키퍼-AI-캐릭터 개발 지식그래프

## 작업을 시작할 때

이 폴더에서 `node tools/product.mjs intent`로 제작자가 정한 최종 목표인 Core Keeper 모드 제작·배포와 그 모드가 제공할 플레이 경험을 읽는다. 작업 주제는 `find`로 찾고, `intent <기획 ID>`로 그 주제가 플레이 경험에서 어떻게 이어지는지 본다. 판단 근거는 `source <기획 ID>`가 보여 주는 합의 원문에서 확인한다.

예를 들어 갑옷 제작을 맡기는 작업은 `intent P.original-request`에서 시작한다. 중간 수량 충족과 부탁 완료를 구분한 합의에서 기존 제작 활동과 당시 실게임 기록을 각각 조회할 수 있다. 기획 항목에는 합의·제안·미정·설명용 사례가 표시되며, 참고 항목에는 근거의 종류가 표시된다.

게임 자체의 대상·행위·조건·결과와 정적 근거·미결은 [게임 행동 그래프](../게임행동-그래프/README.md)에서 조회한다. 검수된 원본 추출의 파생 그래프이며, 이 문서의 모드 개발 그래프 및 게임 내 LLM의 현재 조회 경로와 구별한다.

### 기능의 선

기능은 코드를 소유하지 않는다. 기능은 `코드 앵커`에서 시작하는 선이다. 도구가 앵커에서 모드 안 직접 호출(`부름`)을 따라가 닿는 함수를 모두 `지남`으로 잇는다. `Log`처럼 여러 선에 함께 있는 함수도 있다.

게임이 직접 부르는 함수(Harmony 패치 함수, IMod 수명 함수, 게임 인터페이스 구현)는 호출로 닿지 않는다. 그래서 기능.md에 앵커로 적거나 "선 밖 코드 분류"에 적어야 한다. 어디에도 없으면 도구가 미결(`선 밖 코드`)로 낸다.

### 실행 모델(이 모드가 쓰는 호출 꼴)

`graph/요약.md` 맨 아래에 꼴마다 개수가 나온다.

| 꼴 | 처리 |
|---|---|
| 직접 호출(같은 형식, 형식 이름 붙임) | 따라간다(`부름`) |
| Harmony 패치(`TryPatch(AccessTools.Method(typeof(G),"m"), prefix/postfix: …)`) | 처리 함수 → 게임 함수 `패치(prefix/postfix)`. 등록 함수 → 처리 함수 `패치 등록`(따라가지 않음). 처리 함수는 게임이 부르는 진입점. 게임 안에서 그 게임 함수를 부르는 곳도 적는다 |
| Harmony 패치인데 대상이 실행 중 계산되는 꼴(`TryPatch(변수, prefix: …)`, 예: 리플렉션으로 찾은 스폰 람다) | 처리 함수는 진입점으로 표시. 대상은 모른다 → 미결 `처리 안 한 꼴`. 사람이 대상을 읽어 기능의 `게임 지점`으로 적는다 |
| 게임 인터페이스 구현(IMod, INetworkStreamDriverConstructor) | 진입점(게임이 부름) |
| `new 모드형식()` | `만듦`만 잇고 따라가지 않음 |
| 리플렉션 필드(`AccessTools.Field`) | 게임 비공개 필드로 `리플렉션 필드` |
| 리플렉션 문자열(`FindType("…")`, 빌드 도구) | 색인 밖으로 기록 |
| 람다 | 감싼 함수의 일로 본다(근사). 미결 `처리 안 한 꼴`로 개수를 낸다 |
| 게임 정적 멤버 사슬(`Manager.saves.X`) | 선언 형식을 따라 멤버마다 `사용`. 못 찾으면 미결 |
| 게임 형식 이름(형식 위치의 대문자 이름) | `참조`. using으로 보이는 네임스페이스의 형식만. 둘 이상이면 미결 `게임 이름 모호` |

```
node tools/query.mjs unresolved 미정           # 종류로 거르기
node tools/query.mjs find "STEP 3 OK"          # 로그 글·이름·규칙에서 찾기
node tools/query.mjs list 정책                 # 타입별 목록
node tools/query.mjs show pol.reflex-while-late
node tools/query.mjs check                     # 그래프가 원본과 맞나, 인용이 아직 원문에 있나
```

- 묻기마다 원본 해시를 다시 잰다. 원본이 바뀌었으면 맨 위에 "주의: 그래프가 원본보다 낡았다"가 나온다. 그때는 다시 만든다.
- 빈 결과는 "없다"가 아니다. 그래프가 그 해상도로 담지 않았을 수 있다. 원본을 직접 본다.
- 그래프는 위치를 알려 준다. 동작이 맞는지는 코드를 읽어 판단한다.

## 작업하면서 고치는 법

작업 하나를 마칠 때마다 아래 중 해당하는 것만 한다. 그다음 `node tools/build.mjs --strict`와 `node tools/query.mjs check`를 돌린다.

1. **모드 코드를 고쳤다**
   - 다시 만든다. 코드 층·선·게임 지점은 저절로 따라온다.
   - 경고가 나오면 고친다.
     - `앵커 없음`: 함수 이름이 바뀌었다 → 기능.md의 앵커를 고친다.
     - `선 밖 코드`: 새 함수가 어떤 선에도 없다 → 기능의 앵커로 잇거나 분류표에 적는다. 새 Harmony 패치 함수나 인터페이스 구현이면 거의 늘 앵커로 적어야 한다.
     - `인용 깨짐`: 미결이 코드 주석·상수를 인용하는데 그 글이 바뀌었다 → 미결이 닫혔는지 보고 고치거나 지운다.
   - 새 능력이 생겼으면 기능.md에 기능을 더한다(상태, 한 줄, 관측 지점, 정책, 앵커, 근거).
2. **실게임 시험을 했다**
   - 시험 전에 `node tools/build.mjs`로 다시 만들고, `node tools/query.mjs code F.x`로 그 기능의 지금 선 서명을 본다.
   - 먼저 세션 기록에 결과를 남긴다. 기록에 선 서명(또는 graph/요약.md의 모드 sha256 앞 12자)을 함께 적는다.
   - 기능.md의 `상태`를 바꾸고(`구현 중` → `실게임 확인` 등) `근거`에 그 기록 줄을 인용하고, `확인한 선:`에 서명을 적는다. 그 뒤 선 위 코드가 바뀌면 도구가 "확인 뒤 코드 바뀜"을 낸다.
   - 그 시험으로 닫힌 미결(예: U.ai-char-live)은 미결.md에서 지운다. 새로 본 문제는 더한다.
3. **사용자가 결정했다**
   - 먼저 세션 기록에 사용자 결정을 그 자리에서 남긴다(이론 03: 결정은 내려지는 순간에 기록).
   - 정책.md에 항목을 더하고 그 기록 줄을 `근거`로 인용한다. 후보가 확정됐으면 후보를 정책으로 옮긴다.
   - 그 결정으로 닫힌 미결을 지운다. 바뀐 결정이 기존 기능과 어긋나면 미결(`사용자 확인 필요`)로 남긴다. 그래프에서 어느 한쪽을 조용히 덮지 않는다.
4. **설계를 바꿨다**: 설계만 있는 기능의 한 줄·정책·근거를 고친다. 설계 제안은 후보로 둔다.
5. **새 파일을 더했다**: `tools/config.json`의 `codeFiles`에 넣는다. `codeDirs`(모드 Scripts 폴더, 하위 폴더 포함) 아래 .cs가 `codeFiles`에 없으면 다시 만들 때 `원본 빠짐`으로 알리고 `--strict`가 실패한다.
6. **게임이 업데이트됐다**: 디컴파일을 다시 한 뒤 다시 만든다. `게임 지점 낡음`이 나오면 기능.md의 게임 지점 줄 번호를 고친다.

ID는 한 번 붙이면 바꾸지 않고 다른 것에 다시 쓰지 않는다. 기능을 없애면 상태를 고치거나 항목을 지우고, 그 ID를 새 기능에 쓰지 않는다.

## 해상도와 한계

- 코드 신원은 함수 단위다(`형식.함수`). 줄 번호는 위치일 뿐이다. 한 함수가 두 일을 하면(예: `Step2_NameAndPrepareInput`은 이름 짓기와 입력 준비) 두 기능 선에 다 들어간다. 함수 안 어느 부분인지는 그래프가 말하지 못한다.
- 게임 쪽은 형식 단위 참조, 정적 멤버 사슬, 패치 대상, 리플렉션 필드까지다. 변수에 담긴 게임 객체의 인스턴스 멤버(예: `cd.inventory`)는 따로 잇지 않는다. 그 형식(`CharacterData`)까지만 잇는다.
- Unity.Entities·Unity.Transforms·Harmony·System 등은 디컴파일이 없다. 그 이름은 게임 지점으로 잇지 않고 미결 `색인 밖 이름`에 모아 둔다.
- C# 읽기는 정규식과 괄호 짝 맞추기다. 완전한 파서가 아니다. 속성 본문(get/set)과 람다 안 호출은 따로 보지 않는다(개수는 미결로 나온다).
- 정책이 기능에 지켜지는지(일치·어긋남)는 자동 판정하지 않는다. 도구는 "지는 기능이 없다", "기능에 정책이 없다"만 계산한다. 맞는지는 사람이 코드를 읽어 판단하고 미결로 남긴다.
- 실행 증거(실게임 시험)는 세션 기록 인용으로만 들어온다. Player.log를 자동으로 읽어 선과 맞추지는 않는다(이론 09의 5단계는 아직 아님).
- 이론 09 기준으로 1~2단계 그래프다(코드가 이름에 붙고 구조 관계가 기록됨). 함수 단위 신원은 있지만 이름 변경을 넘어 신원을 잇지는 않는다.
