# 화면·활동·기능의 연결 근거

## 실제 출력과 코드 입구

| A 화면 / 상태 | 실제 요청 | B 입구 | 판정 |
|---|---|---|---|
| BRG-02 / HTTP 200, ok:false | GET /v1/health | ai-bridge:GET /v1/health | method/path 일치. preflight 상태 결과 출력. 현재 게임 캐릭터 상태 아님 |
| BRG-04 / HTTP 400 unknown member | POST /v1/plan | ai-bridge:POST /v1/plan | 요청 입구 일치. plan의 early reject만 관측. CLI 호출/기억 검색 실행 관측 아님 |
| BRG-05 / HTTP 500 bridge/parse detail | POST /v1/plan | ai-bridge:POST /v1/plan | route JSON 파싱의 catch 응답. plan 처리 전체 실행의 근거 아님 |
| BRG-03 / HTTP 404 | GET / | 독립 등록 API 없음 | bridge.mjs fallback. 새 GET / 기능을 만들지 않음 |
| BRG-01 / 경고·listening | 프로세스 시작 | ai-bridge:startup:bridge.mjs.module | 시작 stdout. 화면 조작 이벤트가 아님 |

출력 요소는 결과를 받는 것이므로 간선 방향은 **기능→화면요소**다. D가 A requestMappings와 B 입구로 생성한다. C는 같은 간선을 중복 생성하지 않는다. 유저 활동에서 결과 요소를 거쳐 기능을 찾는 조회는 이 마지막 간선을 역방향으로 탐색한다. 출력 자체가 요청을 일으킨다는 화면요소→기능 간선은 만들지 않는다.

A의 관측 화면 5개·요소 89개는 A 문서를 정본으로 사용한다. C는 이를 복제하지 않는다. OUT-01~06/GAME-01은 C-1 예약 수집 문서이며 표준 노드에 적재하지 않는다. 게임 활동 UA-01~08의 단계에서 실제 요소를 알 수 없는 부분은 사용자 유예/미관측으로 남긴다.

## HEAD 질문의 원문 길

1. **캐릭터 상태**: UA-01 → F.ai-toggle 대응 → `slash:ai` → `AIPlayerSpikeMod.TryHandleChatCommand` → `Dispatch` → `StatusText` → `AIWorldSettings.Members` → 파일 읽기. B/question-coverage.json에 기계 코드 ID와 read 간선이 있다. 읽는 경로 변수 p의 실제 설정 위치는 AIWorldSettings.PathFor(원문 AIPlayerSpikeMod.cs:1549 부근)에서 확인한다. 게임 화면 요소는 이번에 없으므로 첫 단계의 시각적 연결은 끊어진 채 명시한다.
2. **호스트/자율 목표**: UA-02/UA-04와 F.goal-cmd/F.llm-goal 대응. AIGoals.cs:144·168의 host 설정과 AIPlanner.cs:353의 llm 출처 설정은 같은 AIGoals.SetGoal 경로를 사용한다. AIGoals.cs:196은 host 때 OnHostGoal을 부르며 AIPlanner.cs:194 이후에는 호스트 목표를 쓰러짐 뒤 자율 재판단으로 바꾸지 않는 경계가 있다. 구독 CLI 원칙은 pol.llm-subscription, 현장 행동 선택 담당은 pol.selector-openai다. 목표 종류·허용 항목 전부를 정책으로 새로 확정하지 않는다.
3. **기억 검색 결과**: UA-06 → F.memory-recall 대응 → `ai-bridge:POST /v1/plan` → plan의 recallLoop와 runQueries 전달 → memgraph.mjs:587 runQueries → runQuery → Q registry의 질의별 처리. 결과 text/log가 고리에 되돌아가 composeTurn에서 다음 모델 입력에 붙는다. HTTP 오류 응답 2개로 이 성공 경로가 실행되었다고 하지 않는다. B registry 간선은 가능한 callback이고 그 요청이 일곱 질의를 모두 실행했다는 뜻이 아니다.

## 정책 연결의 의미

C graph의 정책→기능 4개는 사용자 규칙을 담당하는 처리 위치를 나타낸다. 규칙 전체 충족을 입증한 실게임 간선이 아니다. 기본 검색 budget=2와 설정값, memoryIndex 플래그/유효 world 조건, 외부 CLI adapter 경계는 각 edge의 coverage/evidence에 남겼다. 후보와 역사 규칙은 표준 활성 정책으로 승격하지 않았다.
