## 2. 가까운 싸움 묶음 스위치

- 파일 `AIPlayers\closefight.off`가 있으면(그리고 `testcmds.on`이 있을 때만) 가까운 싸움이어도 예전처럼 모든 후보를 낸다. 없으면 가까운 싸움 묶음(기본 켬). 1초마다 한 번 파일을 본다(`AITestSwitches.Refresh`, `AIBrain.Tick`에서). 바뀌면 로그 `TEST-ONLY close-fight candidate set: OFF (closefight.off)` / `ON`.
- SEND 줄: 묶음을 쓰면 `set=close-fight`, 가까운 싸움 조건이었지만 꺼서 모든 후보를 냈으면 `set=all(close-fight off)`. 그래서 끔 판에서도 "가까운 싸움이었던 요청"을 셀 수 있다.
- 왜 파일: 같은 빌드에서 판마다 바꿀 수 있고, 앞서 쓰던 `movetrace.on`과 같은 방식. `testcmds.on`이 없으면 무시하므로 잊고 남겨도 평소 놀이에는 영향 없음.

## 3. 지난 "계속하기" 답의 실행 불일치

- 문제(검토 analysis.md 1장, swarm4 #827): 거리 벌리기가 돌 때 보낸 요청의 답 "거리 벌리기 계속"이, 그 사이 기다리던 공격 바꾸기가 경계에서 시작된 뒤 도착했다. `StaleReason`의 continue는 "지금 도는 기술이 있나"만 봤고 `Apply`의 continue는 아무것도 하지 않아, 새 공격이 그대로 이어졌다.
- 고침(`AIBrain.StaleReason`, continue): 답의 키(요청 때 돌던 행동의 키)와 지금 도는 기술의 키가 다르면 `계속하라던 행동이 이미 바뀜(<그때 키>→<지금 키>)`으로 버리고 바로 다시 묻는다(기존 DISCARD 길: `_needCall`, trigger `이전 답 버림(…)`).
- 왜 "그 키로 바꾸기"가 아니라 "버리고 다시 묻기":
  1. 답의 전제가 거짓이 됐다. 모델은 "지금 행동을 이어 갈지"를 골랐는데 지금 행동이 바뀌었다. 전제가 바뀐 답은 버리고 다시 묻는 것이 이미 있는 규칙(목표 수정 번호·대상 사라짐·너무 늦음과 같은 길)이다. 새 장치를 더하지 않는다.
  2. 그 키로 되돌리면 방금 경계에서 시작한 행동을 0.2초 만에 끊는 되돌림(REVERSAL)이 된다. 경계에서 기다렸다 바꾼 뜻이 없어지고, 다시 묻는 데는 약 0.22초면 된다(그동안 지금 행동은 그대로 돈다 — 원래 그랬던 것과 같음).
  3. continue 후보에는 그 행동을 다시 만들 정보(대상 칸·경로 등)가 없다. 되살리려면 후보 설계를 바꿔야 한다.
  4. 모델 판단을 붙잡거나 덮는 장치가 아니다. 다음 답은 새 상태(지금 행동이 계속하기, 예전 행동은 새 후보)를 보고 모델이 고른다.
- 실게임 증거(빌드 polish1):
  - 월드에 들어가자마자 자기 방어 중: `DECISION #9 RESULT choice=away_near (계속하기 — 방금(0.9초 전) 시작한 '거리 벌리기'(away:near) 이어 하기 …) top=[away_near=0.66, retreat_0_-1=0.22, attack_68573=0.06] … DISCARD: 계속하라던 행동이 이미 바뀜(away:near→attack:70291)` → `DECISION #10 SEND rev=1 trigger='이전 답 버림(계속하라던 행동이 이미 바뀜(away:near→attack:70291))'` → #10 `choice=attack_70291 (계속하기 — 방금(0.2초 전) 시작한 '공격'…) APPLY`. 그 사이: #8 공격 HOLD → 거리 벌리기가 저절로 끝남 → `DECISION #8 held switch APPLY (idle)` → 공격 START → #9 도착. swarm4 #827과 같은 꼴(예전 코드면 공격이 그냥 이어졌다).
  - 켬 판: #39 `attack_89540` HOLD → `SWITCH 공격(attack:98284, ran 0.29s) -> attack(attack:89540) at boundary` → `DECISION #40 RESULT choice=attack_98284 … top=[attack_98284=0.72, attack_89540=0.25, attack_92197=0.01] DISCARD: 계속하라던 행동이 이미 바뀜(attack:98284→attack:89540)` → #41 `choice=attack_89540 top=[attack_89540=0.96, …] APPLY`(다시 물으니 새 상태를 받아들임, 되돌림 없음).
  - 끔 판: 0번.

## 4. 판단 입력·답 전문 기록

- 파일 `AIPlayers\decisionlog.on`이 있으면(그리고 `testcmds.on`이 있을 때만) `AIPlayers\decisions-<HHmmss>.log`를 열고 다음을 쓴다:
  - `DECISION #n INPUT … trigger=… set=… running=<그때 키> motion=… input=[입력 전문, 줄바꿈은 ⏎] options(N): || <값> [<종류> <키>] <설명 전문> …`
  - `DECISION #n ANSWER choice=… [<종류> <키>] probs=[모든 후보 확률] confidence=… latency=… running=<도착 때 키>`
  - Player.log의 `DECISION #`·`SWITCH `·`SKILL ` 줄 사본(그 답이 APPLY/HOLD/DISCARD/QUEUED 됐는지, 무엇이 실행됐는지). 줄마다 `t=… @이름`.
- 프레임: Player.log(Debug.Log, 줄마다 스택 추적)로 보내지 않고 64KB 버퍼 파일에 쓰고 1초마다 한 번 비운다. API 키·요청 JSON은 쓰지 않는다. PERF 30초 묶음: 켜기 전(t=154, 자기 방어 싸움 포함) 모드 AI당 평균 0.35ms·최대 102.7ms, 켠 뒤 싸움 묶음 0.18~0.28ms·최대 34.7~51.8ms, 프레임 p99 8.34~8.58ms(120fps) 그대로. 켜기 전과 비교한 정밀 측정은 아님(묶음마다 싸움 양이 다름) — 눈에 띄게 느려지지 않았다는 정도. t=274의 프레임 최대 350ms는 모드 쪽 최대 34.7ms라 모드 밖(순간이동·적 생성 때). 두 판 81요청에 약 790KB(요청당 약 9.7KB).
- 끄는 법: 파일을 지우면 1초 안에 닫힌다(`TEST-ONLY decisionlog: OFF`). 단, `Refresh`는 AI가 월드에 있을 때만 돈다. AI를 먼저 끄면 다음에 AI가 들어올 때까지 파일이 열려 있다 → 파일을 지운 뒤 AI를 끈다.
- 실게임: 켬 판 SEND 45 = INPUT 45, 두 판 합 INPUT 81·ANSWER 79(답이 안 온 2개는 판 끝 `/ai all stop`에서 끊긴 것). 사본: 대화 scratchpad `cs\logs\decisions-114306.log`.
